Monet 整体架构总览

Monet 是网易互娱 AI 美术平台的 本地 Agent 服务——跟 Monet 桌面客户端打包在一起，为用户提供画布式 AI 创作能力。这一节的目标是：看完能画出它的架构图，并能用自己的话说明各模块的职责和协作关系。

Monet 的独特定位：不是云端 SaaS，而是运行在用户客户端上的 Agent 服务，跟一个画布客户端（dm-tapnow）打包为桌面软件。这个定位决定了 Monet 的几个关键设计：本地 shell 能力、画布节点感知、SSE 流式响应、Human-in-the-Loop 审批。
🎨 品牌级概念：Harness Artist
官方技术方案对 DM Agent 的品牌定位是 "Harness Artist"——对标软件工程界的 "Harness Engineer"：美术师从"亲手画画"转变为"驾驭 AI Agent 完成创作"，通过定义约束、能力、验证标准和流程来驾驭 Agent。这个词可以帮助你理解 Monet 的产品定位，而不只停留在代码层面。
——出处：POPO 团队空间 · DreamMaker Agent 技术方案

一、一句话架构

Monet = FastAPI 服务 + DeepAgent 框架 + 画布工具集 + SSE 流式协议。

它在客户端本机启动一个 HTTP 服务（默认端口在 settings.port），前端画布通过 HTTP + SSE 跟它交互。Agent 内部由 LangGraph 驱动状态机，调用 tools 操作画布节点、生成图像/视频/3D 内容。

四、关键设计点（阅读重点）

4.1 基于 DeepAgent + LangGraph 的 Agent 内核

Monet 没有自研 Agent Loop，而是用 DeepAgent 框架的 create_deep_agent()。看 agent/factory.py：

agent = create_deep_agent(
    model=model,                    # 请求级 model（携带鉴权）
    system_prompt=SYSTEM_PROMPT,
    checkpointer=checkpointer,      # 共享 checkpointer（LangGraph 状态持久化）
    tools=[
        query_models,               # 查询可用模型
        generate_and_create_node,   # 生成 + 创建画布节点
        create_canvas_node,         # 创建画布节点
        fit_size_and_create_node,   # 裁剪 + 创建节点
        canvas_create_input_node,   # 创建输入节点
        canvas_node_detail,         # 查询节点详情
        canvas_subgraph,            # 查询画布子图
    ],
    backend=LocalShellBackend(...), # 本地 shell 执行能力
    skills=[builtin_path, global_path],  # 技能路径
    interrupt_on=INTERRUPT_ON_TOOLS,     # HITL 审批
)

🛡️ 思考：为什么用 DeepAgent 而不是自研？

  1. DeepAgent 底层是 LangGraph，提供了状态机 + checkpointer 免费的能力（对话续跑、异常恢复）
  2. Agent Loop、Tool Calling、Human-in-the-Loop 这些都是行业成熟模式，自研收益低
  3. DeepAgent 提供的 InterruptOnConfig 直接支持"某些工具执行前需人工审批"的能力，正好匹配 Monet 的 shell/文件写入场景

4.2 请求级 Model + 进程级 Checkpointer

细读 factory.py 的注释："使用共享的 checkpointer 和请求级别的 model（携带当前请求的认证信息）"。

这个设计的动机：Monet 是本地客户端服务，只服务本机用户（host=127.0.0.1）；但同一用户会在同一进程内发起多次请求，每次请求携带的 AIGW token 可能已刷新、前端指定的模型名（GPT-4o / Claude / Gemini …）也可能变化，所以 model 必须请求级重建。而 checkpointer 是纯粹的存储组件（AsyncSqliteSaver），全局单例避免重复建 SQLite 连接的开销。

常见误区（我自己也犯过）：不要以为"共享 checkpointer"意味着"不同 session 能看到彼此的记忆"。共享的是存储组件本身，记忆内容按 session_id（LangGraph 里叫 thread_id）严格隔离，删除 session 时也只删对应 thread：await checkpointer.adelete_thread(session_id)。也不要以为"多个用户共享 Agent 进程"——Monet 只监听 127.0.0.1，本来就是单机单用户场景。

4.3 SSE 流式响应 + 会话取消

看 agent/runner.py：进程级 _running_chats: dict[str, asyncio.Task]，以 session_id 为 key。作用：

  • 同 session 新 chat 自动 cancel 旧 task（避免多次点击生成同一个）
  • /sessions/{id}/cancel 接口停止流式响应
  • 应用关停时优雅清理

4.4 Human-in-the-Loop 审批

INTERRUPT_ON_TOOLS 定义了哪些工具需要人工审批：

INTERRUPT_ON_TOOLS = {
    "execute": True,    # 本地 shell 命令执行
    "write_file": True, # 写文件
    "edit_file": True,  # 编辑文件
}

因为 Monet 有 LocalShellBackend，能在用户本机执行命令和读写文件——安全性风险大，必须让用户审批。

4.5 Skills 系统：三级路径

技能 = 预定义的能力描述（比如"生成图片时的提示词优化"）。Monet 从三个位置加载：

  • resolve_builtin_path() — 内置技能（打包在应用里）
  • resolve_global_path() — 用户全局技能（用户目录）
  • resolve_workspace_path() — 当前工作区技能

🔑 从时序图能读出的三个关键设计：
  1. 两条独立的 upstream：ChatAIGW → AIGW（蓝色框，低延迟高频）和 Tool → DM Scheduler（橙色框，异步耗时）。绕开了让所有请求都走 Scheduler 的性能陷阱。
  2. Agent Loop 是多轮 LLM 调用：至少 两次 LLM 请求——第一次决定用哪个工具，第二次拿到工具结果后组织自然语言回复。真实任务里可能十几轮。
  3. SSE 全程流式：thinking / tool_use / tool_result / text 都以 block.delta 事件流式推给前端，用户不用等整轮完成。

九、检索练习

Q1. Monet 为什么用"请求级 model"而不是"进程级 model"？

  • A. AIGW token 可能已刷新、前端指定模型也可能变化
  • B. 不同用户共享同一 Agent 进程需要隔离
  • C. 请求级 model 更省内存
  • D. LangGraph 强制要求
A。Monet 只监听 127.0.0.1，是单机单用户场景，B 不成立。请求级 model 的真正原因是：每次请求都要用最新的 AIGW token + 前端指定的 model_name（用户随时可能在 UI 切换 GPT-4o / Claude / Gemini），所以 model 必须请求级重建；而 checkpointer 是纯存储组件，全局单例避免重复建 SQLite 连接的开销。

Q2. INTERRUPT_ON_TOOLS 里为什么只有 execute / write_file / edit_file 需要审批？

  • A. 这三个 tool 最耗时
  • B. 这三个 tool 会影响用户本机文件系统或执行命令，风险最大
  • C. 这三个 tool 是 LocalShellBackend 提供的
  • D. B 和 C 都对
D。这三个能力都由 LocalShellBackend 提供（这是让 Monet 能读写用户文件、执行命令的原因），也正因如此风险最大——如果 Agent 决策失误，可能删掉用户重要文件或执行恶意命令。HITL 是唯一安全保障。

Q3. 一个用户在同一 session 里连续点击两次"生成图像"，会发生什么？

  • A. 两个任务并行执行，返回两张图
  • B. 第二次点击被拒绝，前端报错
  • C. 第一次任务被 cancel，第二次接管
  • D. 排队执行，先生成第一张再生成第二张
C。_running_chats 以 session_id 为 key，新 chat 会自动 cancel 旧 task。这个设计避免用户重复操作导致资源浪费。
