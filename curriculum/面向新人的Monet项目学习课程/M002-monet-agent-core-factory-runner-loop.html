Monet Agent 核心：工厂、Runner 与 Agent Loop

上一节你看到了 Monet 的整体架构。这一节深入 Agent 核心——一次用户对话从收到请求到流式返回结果，代码到底怎么跑的。学完你能画出 Agent Loop 的完整数据流，并向学习官讲清每个环节的设计决策。

一、四个文件，四个职责

src/monet/agent/ 下只有四个文件，分工清晰：

文件职责一句话
factory.pyAgent 工厂每次请求创建一个编译后的 Agent 实例
runner.pyIn-flight 注册表进程级 dict，管理正在运行的 chat 协程
prompts.pySystem PromptAgent 的行为定义——"你是谁、能做什么、怎么做"
state_reader.py只读状态图从 DeltaChannel checkpoint 重建完整消息历史

关键洞察：Monet 的 Agent Loop 不在 Monet 代码里——它在 create_deep_agent() 返回的 CompiledStateGraph 内部。Monet 代码做的是编排：创建 Agent、喂入消息、消费事件流、翻译为 SSE。这个分工决定了 Monet 对 DeepAgent 框架的依赖深度。

三、factory.py — Agent 工厂详解

这是 Monet Agent 的"出生地"。每次 /chat 请求都会调用 create_agent_for_request(model)：

def create_agent_for_request(model: BaseChatModel) -> CompiledStateGraph:
    checkpointer = get_checkpointer()          # 进程级单例
    workspace_path = resolve_workspace_path()
    backend = LocalShellBackend(root_dir=str(workspace_path), virtual_mode=False)

    agent = create_deep_agent(
        model=model,                           # 请求级（携带当前请求的认证信息）
        system_prompt=SYSTEM_PROMPT,           # Agent 行为定义
        checkpointer=checkpointer,             # 状态持久化（对话续跑）
        tools=[...],                           # 7 个工具
        backend=backend,                       # 本地 shell 执行能力
        skills=[builtin_path, global_path],    # 技能路径
        interrupt_on=INTERRUPT_ON_TOOLS,       # HITL 审批
    )
    return agent

3.1 七个注册工具

工具名功能来源文件
query_models查询可用的 AI 模型及其参数定义tools/query_models.py
generate_and_create_node生成内容 + 创建画布节点（一步完成）tools/generate_node.py
create_canvas_node仅创建画布节点（需要先有 ticket）tools/canvas.py
fit_size_and_create_node裁剪 + 创建节点tools/crop_node.py

canvas_node_detail查询单个节点的完整信息tools/canvas_query.py
canvas_subgraph查询一组节点及其连线tools/canvas_query.py

🛡️ 思考：为什么 tools 只有 7 个？不是应该更多吗？

Monet 的设计哲学是 "一个 tool 做一件事，Agent 组合它们"。比如 generate_and_create_node 内部已经封装了"提交生成任务 → 轮询结果 → 创建画布节点"三步，Agent 不需要分别调用。工具数量少但每个工具的抽象层次高，减少了 Agent 的决策负担（tool 越多，LLM 选错的概率越大）。

3.2 HITL 审批工具集

INTERRUPT_ON_TOOLS = {
    "execute": True,      # 本地 shell 命令
    "write_file": True,   # 写文件
    "edit_file": True,    # 编辑文件
}

这三个工具 不属于上面注册的 7 个——它们来自 LocalShellBackend（DeepAgent 框架内置）。Agent 除了有 7 个画布工具，还有 3 个本地 shell 工具（execute / write_file / edit_file），这 3 个全部需要人工审批。

所以 Monet Agent 实际可用的工具是 10 个（7 + 3），其中 3 个走 HITL 审批。

四、Agent Loop 的内部机制

CompiledStateGraph.astream_events() 是 LangGraph 的核心 API。Monet 不需要自己写 Agent Loop——框架内部的状态机自动驱动：

flowchart LR
    A["用户消息 + 历史"] --> B["LLM 推理"]
    B --> C{"输出是文本
还是 tool_call?"}
    C -->|文本| D["直接返回
（流式输出给用户）"]
    C -->|tool_call| E["执行 Tool"]
    E --> F["Tool Result
追加到消息历史"]
    F --> B
    D --> G["Agent 完成
（LLM 不再请求 tool）"]

这个循环在 LangGraph 内部运行，Monet 只通过 astream_events(version="v2") 消费产出的事件流。每轮循环可能产出：

事件流的本质：AsyncGenerator

astream_events() 返回的不是一个列表，而是一个 Python 异步生成器（AsyncGenerator）——一个数据管道，上游产一个事件、下游就读一个、处理一个、推一个，中间不存储。像自来水管：水厂产水 → 水管传输 → 水龙头出水，不是先存到水池再一次性倒出来。

# deepagent.py 里的代码
async for event in self._agent.astream_events(agent_input, config=config, version="v2"):
    # 每产出一个事件，这个循环就跑一次
    # event 是一个 dict，比如：
    # {"event": "on_chat_model_stream", "data": {"chunk": AIMessageChunk("我来")}}
    # {"event": "on_chat_model_stream", "data": {"chunk": AIMessageChunk("帮你生成")}}
    # {"event": "on_tool_start", "data": {"input": {...}}}
    # {"event": "on_tool_end", "data": {"output": "..."}}
    ...

三层管道：从 LangGraph 事件到前端 SSE

"消费"事件流就是读取 → 翻译 → 转发，像流水线一样。整个链路是三层嵌套的异步生成器：

LangGraph 产出事件              Adapter "消费"事件                    推给 Frontend
─────────────────              ──────────────────                    ──────────────
astream_events()                _generate_frames()                    SSE 流
    │                                │                                  │
    │ yield event                    │ 翻译为 SSEFrame                   │ 序列化为文本
    ├─→ "on_chat_model_stream"  ──→  ├─→ block.delta {content:"我来"}  ──→ "data: {...}\n\n"
    │                                │                                  │
    │ yield event                    │ 翻译为 SSEFrame                   │ 序列化为文本
    ├─→ "on_tool_start"         ──→  ├─→ block.updated {status:"running"} ──→ "data: {...}\n\n"
    │                                │                                  │
    │ yield event                    │ 翻译为 SSEFrame                   │ 序列化为文本
    ├─→ "on_tool_end"           ──→  ├─→ block.updated {status:"completed"} ──→ "data: {...}\n\n"
事件类型含义Monet 怎么处理
on_chat_model_streamLLM 正在流式输出文本→ block.created / block.delta（text 类型）
on_chat_model_stream（tool_call_chunks）LLM 正在流式输出 tool call→ block.created / block.delta（tool_use 类型）
on_tool_start开始执行一个 tool→ block.updated（status: running）
on_tool_endtool 执行完毕→ block.updated（status: completed + result）
on_custom_event自定义事件（如画布节点变更）→ 透传为同名 SSE 事件
🔄 Agent 什么时候停止？ 当 LLM 的下一轮推理不再请求任何 tool call，只输出文本时，LangGraph 的状态机判定"Agent 已完成思考"，循环结束。这就是为什么 System Prompt 里写了"连续 2 次失败要停下来"——防止无限循环。

五、DeepAgentStreamAdapter — 事件翻译器

这是 Monet 最有工程含量的文件之一（sse/deepagent.py，~780 行）。它的职责是把 LangGraph 的内部事件翻译成前端能理解的 SSE 协议帧。

5.1 适配器模式

class AgentStreamAdapter(ABC):           # 抽象基类
    async def _generate_frames(...)      # 子类实现：框架事件 → SSEFrame
    async def stream(...)                # 基类提供：心跳 + 格式化 + 错误处理

class DeepAgentStreamAdapter(AgentStreamAdapter):  # 具体实现
    async def _generate_frames(...)      # 消费 astream_events v2 事件

为什么用适配器？换 Agent 框架时前端零改动。如果未来从 DeepAgent 换成别的框架，只需新写一个 XxxStreamAdapter 子类，前端 SSE 协议不变。

5.2 SSE 协议三层内容模型：conversation → message → block

Adapter 把 LangGraph 事件翻译成的 SSE 协议，是一个三层嵌套结构。类比微信聊天：

层级类比Monet 里指什么
conversation（会话）你跟某个人的聊天窗口一个 session（session_id 对应）
message（消息）窗口里的一条消息气泡Agent 某一轮的完整回复
block（内容块）气泡里的具体内容一段文字 / 一次工具调用 / 一张图片

一次 /chat 请求的实际结构：

conversation（session_id 对应的那个会话）
  └── message（Agent 这一轮的回复）
        ├── block: text       "我来帮你生成一张赛博朋克风格的猫"
        ├── block: tool_use   generate_and_create_node({...})
        └── block: text       "已为你生成并添加到画布"

事件动作：created / delta / updated

动作含义什么时候用
created"这个东西刚出现"首次创建
delta"内容追加了一小段"流式输出时，每次来几个字就发一个 delta
updated"这个东西的状态/属性变了"状态变化（generating → running → completed）

完整事件序列示例

把三层结构和动作拼在一起，一次完整的对话请求，前端收到的 SSE 事件流是这样的：

message.created        → "Agent 开始回复了，这是消息 ID"
  block.created        → "出现了一个 text 块"
  block.delta          → "追加几个字：'我来'"
  block.delta          → "追加几个字：'帮你生成'"
  block.delta          → "追加几个字：'一张猫'"
  block.updated        → "text 块完成（status: completed）"

  block.created        → "出现了一个 tool_use 块（generate_and_create_node）"
  block.delta          → "tool 参数流式输出：{model_id: ...}"
  block.updated        → "tool 开始执行（status: running）"
  block.updated        → "tool 执行完了（status: completed，带 result）"

  block.created        → "又出现一个 text 块"
  block.delta          → "追加：'已为你生成'"
  block.updated        → "text 块完成"

message.updated        → "整条消息完成（status: completed）"

前端收到这些事件后，逐步渲染出完整的聊天气泡——先显示文字，然后显示工具执行进度，最后显示结果文字。

为什么这样设计？跟 LangGraph 事件解耦。LangGraph 内部的事件（on_chat_model_stream、on_tool_start）是框架细节，直接暴露给前端的话，换框架前端全部要改。Monet 的 message → block 协议是稳定的对外契约，Adapter 层负责翻译，换框架只需新写一个 Adapter 子类。这个设计的价值在于："AgentStreamAdapter 抽象基类（模板方法模式），换 Agent 框架前端零改动"。

5.3 状态管理

每个请求创建一个 DeepAgentStreamAdapter 实例，内部维护：

状态用途
message_id当前消息的唯一 ID
block_indexblock 序号（递增）
current_text_block_id当前正在输出的 text block
pending_tool_callstool_call_chunks 流式追踪（index → block_id）
tool_block_ids工具 block 映射（run_id → block_id）
url_cleaner流式清理 AI 文本中的图片 URL

这 6 个状态变量全部是 Monet 自定义的，在 _generate_frames() 里作为局部变量定义。LangGraph 框架不管这些——它只负责 yield 原始事件，怎么追踪 block 状态、怎么关联 run_id 到 block_id，都是 Monet 的 Adapter 层自己实现的。

逐个详解

1. message_id — 消息唯一标识

message_id = str(uuid.uuid4())

每次 /chat 请求生成一个新的 UUID，作为这次 Agent 回复的 ID。所有产出的 block 都挂在这个 message_id 下面。

2. block_index — block 序号计数器

block_index = 0

每创建一个新 block（不管是 text 还是 tool_use），block_index += 1。前端用它来决定 block 的显示顺序。

3. current_text_block_id — 当前 text block 追踪

这是最巧妙的一个。LLM 流式输出时，token 是一个字一个字来的：

chunk 1: "我"       → current_text_block_id is None → 创建 block.created，赋值 block_id
chunk 2: "来"       → current_text_block_id 有值   → 发 block.delta
chunk 3: "帮你"     → current_text_block_id 有值   → 发 block.delta
...
遇到 tool_call     → _close_text_block()          → 发 block.updated，清空为 None

核心逻辑：None 表示"当前没有打开的 text block"。第一个 token 来了就创建，后续 token 追加，直到要切换到 tool_use 时关闭。

4. pending_tool_calls — tool call 流式追踪

pending_tool_calls: dict[int, str] = {}   # tool_call index → block_id

LLM 的 tool call 参数也是流式输出的（tool_call_chunks）。比如调用 generate_and_create_node，参数 JSON 可能分多个 chunk 到达：

chunk 1: {index: 0, name: "generate_and_create_node", args: "{\"model_id"}
chunk 2: {index: 0, name: "",                          args: ": \"seedream"}
chunk 3: {index: 0, name: "",                          args: "-4.5\"}"}

用 index 做 key，把同一个 tool call 的多个 chunk 关联到同一个 block_id。

5. tool_block_ids + tool_names — 工具执行追踪

tool_block_ids: dict[str, str] = {}   # run_id → block_id
tool_names:    dict[str, str] = {}   # run_id → tool_name

LangGraph 的事件里，on_tool_start 和 on_tool_end 通过 run_id 关联。但前端 SSE 协议用的是 block_id。这两个 dict 做 ID 映射：

on_tool_start(run_id="abc")  → 找到 block_id → 发 block.updated(status: running)
on_tool_end(run_id="abc")    → 找到 block_id → 发 block.updated(status: completed)

tool_names 额外记录工具名，用于 on_tool_end 时判断是否需要埋点（只有 TRACKED_TOOLS 里的工具才上报）。

6. url_cleaner — 流式 URL 清理器

url_cleaner = StreamingUrlCleaner()

它要解决什么问题？LLM 有时候会在回复里输出 Markdown 图片语法：

![猫](https://dreammaker.netease.com/static/image/cat.png)

但前端只需要路径部分（/static/image/cat.png），域名由前端自己拼。需要把 https://dreammaker.netease.com 剥掉。

难点在哪？LLM 是逐 chunk 流式输出的，Markdown 图片语法可能被 chunk 切断：

chunk 1: "![猫](https://dreammaker.n"
chunk 2: "etease.com/static/image/cat.png) 请查看"

chunk 1 里的 URL 不完整，直接做字符串替换匹配不上。

核心思路：不是检测"URL 是否完整"，而是检测 Markdown 图片语法 ![](...) 是否闭合。用 ]( 和 ) 作为明确的开始/结束标记。

def _drain(self):
    while self._buffer:
        trigger_pos = self._buffer.find("](")     # 找触发器

        if trigger_pos == -1:
            return safe_output                    # 没找到，输出安全部分

        # buffer 以 "](" 开头
        if after_trigger.startswith("https://dreammaker.netease.com"):
            close_paren = after_trigger.find(")")
            if close_paren == -1:
                break                             # ⏳ 还没闭合，等更多 chunk
            # ✅ 找到了！替换 URL 并输出
            output += f"]({stripped_url})"

        elif domain.startswith(after_trigger):
            break                                 # ⏳ 可能是域名开头，太短不确定

        else:
            output += "]("                        # ❌ 不是 DM 域名，原样输出

用例子演示：

场景 1：完整 URL 在一个 chunk 里
  chunk: "![猫](https://dreammaker.netease.com/static/cat.png) 请查看"
  → 找到 "](" → 后面是完整域名 → 找到 ")" → 替换
  → 输出: "![猫](/static/cat.png) 请查看"

场景 2：URL 被 chunk 切断
  chunk 1: "![猫](https://dreammaker.n"
    → 找到 "](" → 后面太短，可能是域名开头 → break，不输出
  chunk 2: "etease.com/static/cat.png) 请查看"
    → buffer 拼完整了 → 找到完整域名 → 找到 ")" → 替换
    → 输出: "![猫](/static/cat.png) 请查看"

场景 3：不是 DM 的图片
  chunk: "![图](https://google.com/logo.png)"
  → 找到 "](" → 域名不匹配 → 原样输出 "]("，继续处理后面

feed() 和 flush() 的配合：feed(chunk) 每次吃一个 chunk，把 chunk 拼到 buffer 里然后尝试 drain（提取已确认安全的输出）；flush() 在 text block 关闭时把 buffer 里所有剩余内容全部强制输出。

状态协作流程

LLM 输出 "我来帮你"
  ├─ current_text_block_id=None → 创建 text block，赋值
  └─ 后续 token → block.delta

LLM 输出 tool_call
  ├─ _close_text_block()  → 关闭 text block，current_text_block_id=None
  ├─ pending_tool_calls   → 追踪 tool_call_chunks，创建 tool_use block
  └─ on_tool_start        → tool_block_ids 记录映射，status → running

Tool 执行完毕
  ├─ on_tool_end          → 通过 tool_block_ids 找到 block_id
  ├─ tool_names           → 判断是否埋点
  └─ status → completed

LLM 继续输出文字
  └─ current_text_block_id=None → 创建新的 text block，循环继续

六、Interrupt / Resume 机制（HITL 实现）

当 Agent 调用 execute / write_file / edit_file 时，LangGraph 会 暂停 graph 执行（interrupt），等待用户审批。Adapter 里有一段关键代码处理这个：

# 循环检测 interrupt：每次 resume 后可能又触发新的 interrupt
# 直到 graph 完成（无 pending interrupt）为止
while True:
    state_snapshot = await self._agent.aget_state(config)
    if not (state_snapshot.next and state_snapshot.interrupts):
        break  # 无 interrupt，graph 正常完成

    # 发出交互请求帧给前端
    for interrupt in state_snapshot.interrupts:
        yield self._build_interaction_frame(interrupt)
    # → SSE: interaction.request {id, type: "confirmation", options: ["approve", "reject"]}

    # 挂起等待用户决定（300 秒超时）
    wait_event = register_interrupt(thread_id)
    await asyncio.wait_for(wait_event.wait(), timeout=300)

    # 用户通过 /chat/{session_id}/resume 提交决定
    decision = pop_decision(thread_id)
    resume_input = Command(resume=matched_decision)

    # 用 Command(resume=...) 恢复 graph，继续处理事件流
    async for event in self._agent.astream_events(resume_input, config=config, ...):
        ...
    # resume 流结束后，loop 回去检查是否有新的 interrupt

🛡️ 思考：Interrupt 为什么用 while 循环而不是 if？

因为 resume 之后可能又触发新的 interrupt。比如 Agent 先 write_file（interrupt 1），用户 approve 后 Agent 继续推理，又决定 execute（interrupt 2）。所以必须循环检测直到 graph 真正完成（无 pending interrupt）。

七、System Prompt 设计要点

prompts.py 定义了 Agent 的完整行为指令。阅读时重点关注 prompt 里包含哪些关键约束：

Prompt 章节内容设计意图
节点引用规则只接受 node ID，不接受 URL；URL 必须走导入流程防止 Agent 把 URL 直接当参数传给生成工具
主体（Subject）引用{{node_id}} 占位符 + reference_nodes角色/素材复用机制
推荐模型seedream-4.5 / tripo-P1 / kling-video-o3 / claude-sonnet-4-6减少 Agent 每次 query_models 的开销
画布感知每轮自动注入画布概览，优先用概览信息减少不必要的 tool 调用
失败处理规范不盲目重试、不用相同参数重试、连续 2 次失败停下防止 Agent 陷入死循环烧 token
System Prompt 是 Agent 行为的"宪法"：它定义了 Agent 能做什么、不能做什么、遇到异常怎么办。代码（factory.py）定义 Agent 的能力，Prompt 定义 Agent 的行为准则。如果想理解 Agent 如何控制行为，System Prompt 是最直接的入口。

八、runner.py — In-flight 注册表

只有 22 行代码，但支撑了三个关键能力：

🛡️ 思考：为什么 cancel 要 await？不能直接 cancel 吗？

task.cancel() 只是发出取消信号，task 可能正在执行 tool（比如 HTTP 请求），需要等它处理完 CancelledError 才能安全清理。代码里是 task.cancel(); await task，确保旧 task 彻底结束后新 task 才开始，避免两个 task 同时操作同一个 session 的状态。

九、state_reader.py — Checkpointer 与对话续跑

Agent 需要记住"之前聊过什么"，这样才能在多轮对话中保持上下文。Monet 用 LangGraph 的 Checkpointer 机制实现对话持久化。

9.1 Checkpointer：对话状态的"存档点"

每次 Agent 完成一轮对话（LLM 推理 + 可能的工具调用），LangGraph 会把当前的消息历史存档到 checkpointer。下次用户继续对话时，Agent 可以从存档点恢复，继续工作。

# factory.py 里的配置
checkpointer = get_checkpointer()  # 进程级单例

agent = create_deep_agent(
    model=model,
    system_prompt=SYSTEM_PROMPT,
    checkpointer=checkpointer,  # ← 注入 checkpointer
    tools=[...],
    ...
)

进程级单例：整个 Monet Agent 进程只有一个 checkpointer 实例，所有对话共享。它负责把对话状态持久化到 SQLite 数据库。

9.2 DeltaChannel：增量存储，不是完整快照

DeepAgent 0.6+ 将 messages channel 改为 DeltaChannel——checkpoint 存的是增量（每次只存新增的消息），不是完整快照。

为什么用增量而不是完整快照？节省存储空间。如果每轮都存完整消息（可能包含大量工具调用结果），几轮对话后 checkpoint 就会变得很大。增量存储只存新增部分，体积增长慢得多。

9.3 问题：怎么从增量重建完整消息？

直接读 checkpoint blob 只能看到最后一次的增量片段，不是完整消息列表。LangGraph 提供了 aget_state() API，内部会自动把所有增量合并成完整消息——但前提是必须通过一个 StateGraph 调用。

state_reader.py 构建了一个最小的只读 StateGraph，专门用来调用 aget_state() 重建消息历史：

# src/monet/agent/state_reader.py

def build_state_reader(checkpointer: Checkpointer) -> CompiledStateGraph:
    """构建只读状态图，用于通过 aget_state 重建 DeltaChannel 消息。"""
    graph = StateGraph(state_schema=_ReaderState)  # 定义 messages channel

    # 只有一个 noop 节点，什么都不做
    graph.add_node("_noop", lambda state: state)
    graph.add_edge(START, "_noop")
    graph.add_edge("_noop", END)

    # 编译时注入 checkpointer
    return graph.compile(checkpointer=checkpointer)

关键点：

  • _ReaderState：定义了 messages 字段，使用 DeltaChannel 和相同的 reducer（合并逻辑）
  • _noop 节点：什么都不做，只是为了满足 StateGraph 的结构要求（至少一个节点）
  • checkpointer：注入同一个 checkpointer 实例，确保读到相同的 checkpoint 数据

9.4 对话续跑的完整流程

用户重新打开对话（比如关闭 Monet 后重新打开，或者第二天继续昨天的对话）：

sequenceDiagram
    autonumber
    participant U as 用户
    participant F as Frontend
    participant R as routes.py
    participant SR as state_reader.py
    participant CP as Checkpointer
(SQLite)
    participant AG as Agent

    U->>F: 打开之前的对话
    F->>R: POST /chat {session_id, message}

    R->>SR: build_state_reader(checkpointer)
    SR->>CP: aget_state(thread_id=session_id)
    CP-->>SR: 所有 checkpoint 的增量数据
    SR->>SR: DeltaChannel reducer 合并增量
    SR-->>R: 完整消息历史

    R->>AG: create_agent(checkpointer=...)
    AG->>CP: 读取 checkpoint（继续存档）
    AG->>AG: 基于完整历史继续推理
    AG-->>R: 流式返回回复
    R-->>F: SSE 流
    F-->>U: 显示回复
  1. build_state_reader：构建只读 StateGraph，注入 checkpointer
  2. aget_state(thread_id)：通过 StateGraph 调用 LangGraph API，读取所有 checkpoint 的增量数据
  3. DeltaChannel reducer 合并：把所有增量合并成完整消息列表（[消息 1, 消息 2, ..., 消息 N]）
  4. 创建 Agent：注入同一个 checkpointer，确保后续对话继续存档到相同的 checkpoint
  5. 继续推理：Agent 基于完整历史继续工作，用户感觉"对话没断过"

🛡️ 思考：为什么不直接用 LangGraph 的 API 读 checkpoint？

因为 DeltaChannel 的 checkpoint 存的是增量（每次只存新增的消息），不是完整快照。LangGraph 的 aget_state() 内部会自动把所有增量合并成完整消息列表。自己直接读 blob 就只能看到最后一次的增量片段。

而且 aget_state() 要求通过 StateGraph 调用——即使你只是想"读"状态，也必须构建一个 StateGraph。这就是 state_reader.py 存在的原因：构建一个最小的只读 StateGraph（只有一个 noop 节点），专门用来调用 aget_state()。

🛡️ 思考：为什么 checkpointer 是进程级单例？

因为 checkpointer 本质是数据库连接池。如果每个请求都创建新的 checkpointer，会导致：

  • 数据库连接数爆炸（每个请求一个连接）
  • SQLite 文件锁冲突（SQLite 不支持高并发写）
  • 内存浪费（每个 checkpointer 实例都有缓存）
进程级单例确保所有对话共享同一个数据库连接，复用连接池和缓存。

9.5 Prompt Caching 降本

多轮对话场景下，System Prompt + Tools 定义在每一轮都会重复发送。以 Monet 为例：System Prompt 约 2000 token，7 个工具的 JSON Schema 约 3000 token，每轮对话都要重新计算这些"固定内容"，浪费且昂贵。

Claude 提供了 Prompt Caching 机制：在请求的特定位置标记 cache_control，AIGW/Anthropic 会缓存从开头到标记处的内容。后续请求如果前缀相同，直接复用缓存，input token 价格降低约 90%。

三个缓存断点

cache_control.py 在请求 payload 里注入最多 3 个断点（Claude 限制 4 个，保留 1 个余量）：

#3最后一条 user 消息之前的消息对话历史（不含最新 user 消息）同一轮 tool loop 中多次 API 调用时，"最后一条 user 消息"不变，后续调用全部命中缓存

代码实现

# src/monet/model/cache_control.py

def inject_cache_control(payload: dict[str, Any]) -> None:
    """为 Claude 模型请求注入 prompt caching 标记。"""
    if not _should_enable(payload):  # 只对 claude-* 模型启用
        return

    messages = payload.get("messages", [])
    tools = payload.get("tools", [])

    _mark_system_message(messages)    # 断点 1：System Prompt
    _mark_tools(tools)                # 断点 2：Tools 定义
    _mark_conversation_prefix(messages)  # 断点 3：对话历史

注入时机：在 ChatAIGW._get_request_payload 构建完请求 payload 后、发送前调用：

# src/monet/model/aigw.py
def _get_request_payload(self, input_, stop=None, **kwargs):
    payload = super()._get_request_payload(input_, stop=stop, **kwargs)
    inject_cache_control(payload)  # ← 注入缓存标记
    return payload

缓存命中效果

示例：10 轮对话的成本对比
  • 无缓存：每轮都重新计算 System + Tools + 全部历史 → 10 轮 × 5000 token = 50,000 token
  • 有缓存：System + Tools 只算 1 次，历史消息每轮只算新增部分 → 5000 + 10 × 200 = 7,000 token
  • 节省：约 85% 的 input token 成本

🛡️ 思考：为什么只在 claude-* 模型上启用？

cache_control 是 Claude API 特有的显式缓存标记方式。其他模型也有 Prompt Caching（如 OpenAI 自动缓存相同前缀、Gemini 有 Context Caching API），但它们不需要也不识别 cache_control 字段。代码里通过 model_name.startswith("claude-") 判断，只对 Claude 模型注入标记，避免其他模型因不识别该字段而报错。

🛡️ 思考：为什么保留 1 个断点余量（只用 3 个，不用满 4 个）？

Claude 最多支持 4 个缓存断点，但代码只用 3 个。这是为了应对未来可能的变化：如果新增一个"永不变"的内容块（比如画布概览注入），可以加第 4 个断点而不需要重构。这是防御性设计——留一个余量，避免后续改动时超出限制。

🛡️ 思考：断点 3 为什么标记"最后一条 user 消息之前"而不是"最后一条 assistant 消息"？

因为用户可能连续发多条消息（比如先说"帮我画猫"，还没等回复又追加"要赛博朋克风格"）。如果标记在最后一条 assistant 消息上，assistant 之后的所有连续 user 消息都不在缓存前缀里，白白多算 token。标记在"最后一条 user 消息之前"，能最大化缓存前缀长度——无论末尾有多少连续 user 消息，都只有最后一条不进缓存，其余全部命中缓存。

十一、检索练习

Q1. Agent Loop（"LLM 推理 → 判断 tool → 执行 → 再推理"）在哪里运行？

  • A. factory.py 的 create_agent_for_request 里
  • B. DeepAgentStreamAdapter._generate_frames 里
  • C. CompiledStateGraph 内部（LangGraph 状态机）
  • D. routes.py 的 chat 函数里
C。Agent Loop 在 CompiledStateGraph（LangGraph 状态机）内部运行。Monet 代码只负责编排：factory.py 创建 Agent，routes.py 启动流，Adapter 消费事件流。真正的"思考→调用工具→再思考"循环是 LangGraph 框架的核心能力，Monet 通过 astream_events() 消费其产出。

Q2. 一次 /chat 请求中，Agent 实际可用的工具有几个？

  • A. 7 个（factory.py 注册的 tools 列表）
  • B. 3 个（INTERRUPT_ON_TOOLS 里的 execute/write_file/edit_file）
  • C. 10 个（7 画布工具 + 3 shell 工具）
  • D. 不确定，取决于 skills 加载了多少
C。factory.py 注册了 7 个画布工具（query_models / generate_and_create_node / create_canvas_node / fit_size_and_create_node / canvas_create_input_node / canvas_node_detail / canvas_subgraph），加上 LocalShellBackend 提供的 3 个 shell 工具（execute / write_file / edit_file），共 10 个。Skills 不增加 tool 数量，它们是能力描述文件。

Q3. DeepAgentStreamAdapter 处理 interrupt 时为什么用 while 循环？

  • A. 防止用户审批超时后没有重试机会
  • B. resume 后可能又触发新的 interrupt，需要循环检测直到 graph 完成
  • C. 一次请求可能有多个 session 同时 interrupt
  • D. LangGraph 要求必须用 while 循环消费 astream_events
B。Agent 恢复执行后，下一轮推理可能又决定调用 write_file 或 execute，触发新的 interrupt。所以必须 while True 循环检测 aget_state() 是否还有 pending interrupt，直到 graph 真正完成（无 state_snapshot.next）才 break。
