Monet Tool Use 系统

M002 讲清了 Agent Loop 和 SSE 流式协议。这一节聚焦 Agent 的"手脚"——10 个工具（7 画布 + 3 shell）。学完你能讲清每个工具的职责、Agent 怎么组合它们完成任务、以及 Tool Calling 的工程实现细节。

核心概念：Tool 就是 Agent 可调用的函数。LangGraph 的 Tool Calling 机制让 LLM 决定"我要调哪个函数、传什么参数"，框架执行函数并把返回值喂回 LLM。Monet 的工作是定义这些函数——函数签名（输入参数）+ 函数体（业务逻辑）。

设计哲学：高抽象、少数量。Monet 的 7 个画布工具每个都封装了多步操作（比如 generate_and_create_node 内部 = 提交生成 → 轮询结果 → 创建节点 → 建立连线）。工具少（7 个）但每个抽象层次高，减少 LLM 的决策负担——tool 越多，LLM 选错的概率越大。

二、工具分类：做什么 vs 查什么

按功能分两大类：

类别工具特点
创建类（写操作） generate_and_create_node、create_canvas_node、fit_size_and_create_node、canvas_create_input_node 会在画布上创建新节点，成功后发 canvas.render 自定义事件通知前端刷新
查询类（读操作） query_models、canvas_node_detail、canvas_subgraph 只读不写，返回文本（markdown 格式）给 Agent

三、核心工具详解

3.1 query_models — "查字典"

Agent 在生成之前，需要知道"有什么模型可用、每个模型需要什么参数"。query_models 就是这本字典。

class QueryModelsInput(BaseModel):
    category: str | None    # 按类型过滤：image / video / model_3d / text
    node_type: str | None   # 按节点类型过滤：gen-image / gen-video ...
    model_id: str | None    # 精确查询单个模型的参数定义

典型用法：

用户："帮我生成一张猫的图片"
  │
  ▼
Agent 第一步：调 query_models(category="image")
  → 返回："可用模型：seedream-4.5（参数：prompt, aspect_ratio, image_size）
           nano-banana-pro（参数：prompt, width, height）..."
  │
  ▼
Agent 第二步：根据用户需求和返回结果，选模型、填参数
  → 调 generate_and_create_node(
      node_type="gen-image",
      model_id="seedream-4.5",
      model_params={"prompt": "一只可爱的猫", "aspect_ratio": "1:1"},
      label="可爱猫咪"
    )

🛡️ 思考：System Prompt 里不是已经推荐了模型吗？为什么还要 query_models？

System Prompt 里的推荐模型是"常用的几个"（seedream-4.5 / tripo-P1 / kling-video-o3），但可用的模型远不止这些。query_models 的另一个关键作用是查参数定义——每个模型需要什么参数、类型是什么、有没有默认值，这些不能硬编码在 prompt 里（模型列表会频繁更新）。Agent 调 query_models(model_id="seedream-4.5") 可以精确获取该模型的完整参数 schema。

3.2 generate_and_create_node — "一键生成"

这是 Agent 最常用的工具，一步完成"生成内容 + 创建画布节点"：

class GenerateAndCreateNodeInput(BaseModel):
    node_type: str              # 能力类型：gen-image / gen-video / gen-3d / gen-text
    model_id: str               # 模型 ID：seedream-4.5 / kling-video-o3 ...
    model_params: dict          # 模型参数：{prompt, aspect_ratio, ...}
    label: str                  # 节点标签：8-16 字中文短语
    reference_nodes: list[str]  # 参考图节点 ID（自动解析为 URL 注入参数）

注意：这个 tool 本身只有 120 行。真正的业务逻辑委托给了 AgentGenerationService：

service = get_agent_generation_service()
result = await service.generate_and_create(
    AgentGenerateRequest(...)
)

工具文件只做框架适配：从 LangGraph config 取 canvas_id / auth_headers / thread_id，构造请求，调用 service，返回结果文本。

3.3 create_canvas_node — "先检后放"的备用路径

跟 generate_and_create_node 的区别：这个工具是两步走——先让 Agent 看到生成结果（通过 ticket），再决定是否放到画布上。

class CreateCanvasNodeInput(BaseModel):
    ticket: str         # 生成工具返回的 ticket ID
    label: str          # 节点标签
    pick: list[int]     # 可选：只创建指定的 outputs

流程：

generate_and_create_node 的特殊模式（返回 ticket 而非直接创建）
  → Agent 拿到 ticket，可以"看看"生成结果
  → 满意 → create_canvas_node(ticket="gen-001", label="...")
  → 不满意 → 不调 create_canvas_node，重新生成

System Prompt 里写了："仅在需要先检视生成结果再决定是否落盘的特殊场景使用"。常规场景直接用 generate_and_create_node 一步完成。

3.4 canvas_create_input_node — "导入外部资源"

当用户发了一个 URL（图片/视频/3D 模型），需要把它导入画布。这个工具做的事情比看上去多得多：

flowchart LR
    A["用户发的 URL"] --> B["下载资源"]
    B --> C["检测类型
image/video/audio/3d"]
    C --> D["计算 MD5"]
    D --> E{"画布上已有
相同 MD5 的节点?"}
    E -->|是| F["返回已有节点
（去重复用）"]
    E -->|否| G["上传到 Storage"]
    G --> H["创建 input-* 节点"]

关键设计：MD5 去重。下载资源后计算文件 MD5，遍历画布上所有节点的主图 MD5，如果已有相同的就跳过上传，直接返回已有节点。避免用户反复发同一个 URL 导致画布上出现一堆重复节点。

🛡️ 思考：为什么不能根据节点 label 判断重复？

因为 label 只是人写的描述文字，两个不同的图片可能有相同的 label（比如都叫"赛博朋克猫咪"），同一个图片也可能有不同的 label。只有文件内容的 MD5 才能确定两张图是不是同一个文件。System Prompt 里也明确说了："label 仅为显示用途，不能反映实际资源内容"。

3.5 fit_size_and_create_node — "裁剪/缩放"

从源节点取图，用 本地 PIL 适配到目标尺寸，上传后创建新节点。

流程：
1. canvas_client.get_node_detail(source_node_id)  → 拿到源节点的输出图片 URL
2. httpx.get(source_url)                           → 下载图片
3. PIL.Image.open() + crop_or_resize()             → 本地裁剪/缩放
4. storage_client.upload_from_bytes()              → 上传处理后的图片
5. canvas_service.create_plain_image_node()        → 创建新节点

这是唯一一个在 本地做图像处理的工具（用 PIL），其他工具都是调远程服务。

3.6 canvas_node_detail / canvas_subgraph — "查画布"

两个查询工具，解决"Agent 需要看画布"的问题：

工具输入返回什么时候用
canvas_node_detail 一个 node_id 节点的完整信息（type / label / 位置 / params / outputs） 画布概览不够，需要看某个节点的具体参数或输出
canvas_subgraph 一组 node_ids 这些节点 + 它们之间的连线 理解画布上的局部拓扑关系

两个工具都优先复用 /chat 入口缓存的画布详情（contextvar），缺失时才回退现拉一次。返回 markdown 格式的文本给 Agent 阅读。

四、工具间的组合模式

Agent 不是孤立调用某个工具，而是组合多个工具完成复杂任务。几个典型场景：

场景 1："帮我生成一张赛博朋克风格的猫"

1. query_models(category="image")          → 查可用模型
2. generate_and_create_node(                → 生成 + 创建节点
     node_type="gen-image",
     model_id="seedream-4.5",
     model_params={prompt: "..."},
     label="赛博朋克猫咪"
   )

场景 2："参考画布上已有的那张风格，生成一张类似的"

1. canvas_subgraph(node_ids=[...])          → 查画布上的参考节点
2. query_models(model_id="seedream-4.5")    → 查参数定义
3. generate_and_create_node(                → 生成（带参考图）
     node_type="gen-image",
     model_id="seedream-4.5",
     model_params={prompt: "..."},
     reference_nodes=["node-xxx"],          ← 参考图自动解析为 URL
     label="类似风格的猫咪"
   )

场景 3：用户发了一个 URL 说"把这个放到画布上"

1. canvas_create_input_node(                → 下载 + 去重 + 上传 + 创建节点
     url="https://example.com/cat.png",
     label="外部猫咪图片"
   )

场景 4："生成的图片尺寸不对，帮我裁一下"

1. fit_size_and_create_node(                → 本地裁剪 + 上传 + 创建新节点
     source_node_id="node-xxx",
     target_width=512,
     target_height=512,
     label="裁剪后的猫咪"
   )
关键点：Agent 的工具组合不是预先编排好的，而是 LLM 根据用户意图和当前画布状态实时决策的。这正是用 Agent 而不是工作流的原因——工具组合空间太大，无法枚举。

五、Tool 的代码结构（统一模式）

所有 Monet 自定义工具遵循相同的代码结构：

# 1. 定义输入参数（Pydantic BaseModel）
class XxxInput(BaseModel):
    param_a: str = Field(description="...")
    param_b: int = Field(description="...")

# 2. 用 @tool 装饰器注册
@tool(args_schema=XxxInput)
async def my_tool(param_a: str, param_b: int) -> str:
    """工具的文档字符串（LLM 据此理解工具用途）"""

    # 3. 从 LangGraph config 取上下文
    config = get_config()
    canvas_id = config.get("configurable", {}).get("canvas_id")
    auth_headers = config.get("configurable", {}).get("auth_headers")

    # 4. 参数校验
    if not canvas_id:
        return "错误：无法获取画布 ID"

    # 5. 调用 service 执行业务逻辑
    result = await some_service.do_something(...)

    # 6. 发 canvas.render 通知前端刷新（仅创建类工具）
    await adispatch_custom_event(name="canvas.render", data={})

    # 7. 返回文本结果给 Agent
    return "已完成：..."

几个关键设计点：

设计点说明
返回 str，不抛异常 工具失败时返回错误文本（"错误：xxx"），而不是抛 Python 异常。LLM 能读懂错误信息并决定下一步；抛异常会导致 Agent 无法处理
Pydantic BaseModel 做参数校验 LLM 生成的参数经过 Pydantic 自动校验，类型不对或必填项缺失会在框架层拦截，不会进入业务逻辑
LangGraph config 传上下文 canvas_id、auth_headers、thread_id 都通过 LangGraph 的 configurable 传递，不需要全局变量
业务逻辑委托给 Service 工具文件只做框架适配（取上下文 + 构造请求 + 格式化返回），真正的业务逻辑在 services/ 层

六、canvas.render 自定义事件

前几节讲了工具怎么创建节点。现在的问题是：前端画布怎么知道要刷新？

三种方案对比

方案做法问题
A. 工具返回完整画布数据工具执行后，把完整画布状态塞进 tool result数据量大；工具不该负责序列化画布
B. 后端推送完整画布快照后端主动在 SSE 里推完整画布状态数据量大，后端要负责序列化全量数据
C. 通知 + 前端自拉后端只发一个轻量通知，前端自己调接口拉最新数据✅ 职责分离、数据量小

Monet 选了方案 C。实现分三层：

第一层：工具 dispatch 自定义事件

所有创建类工具（generate_and_create_node、canvas_create_input_node、fit_size_and_create_node 等）在成功创建节点后，都会调 LangGraph 提供的 adispatch_custom_event：

# 代码来源：src/monet/tools/generate_node.py
for _ in result.node_ids:
    await adispatch_custom_event(name="canvas.render", data={})

这个调用告诉 LangGraph："我产出了一个自定义事件，名字是 canvas.render，payload 是空 dict。"

第二层：Adapter 透传

LangGraph 在 astream_events() 循环里把这个事件 yield 出来，event kind 是 on_custom_event。Adapter 检测到这个 kind 后直接透传为 SSEFrame——不加业务逻辑，只做格式转换：

# 代码来源：src/monet/sse/deepagent.py
elif event_kind == "on_custom_event":
    event_name = event.get("name", "")          # → "canvas.render"
    event_payload = event_data.get("data", {})  # → {}
    yield SSEFrame(
        event=event_name,
        data={"message_id": message_id, **event_payload},
    )

注意 Adapter 的角色：纯翻译器，不加业务逻辑。事件名 canvas.render 原样保留，payload 原样透传（额外附加 message_id 供前端关联消息）。这跟 Adapter 处理 on_tool_start / on_tool_end 的原则一致——框架事件翻译为 SSE 协议，不掺杂业务判断。

第三层：SSE 文本序列化

SSEFrame 被 base.py 的 _format_sse 序列化为标准 SSE 文本帧：

id: 7
event: canvas.render
data: {"message_id": "abc-123"}

前端 EventSource 收到这个帧后，主动调 HTTP 接口拉取最新画布数据来刷新渲染。

完整数据流

关键设计：职责分离。后端（工具）只负责"通知"——我改了一个节点，你来看看。前端负责"拉取 + 渲染"——前端自己知道怎么调接口、怎么局部更新。这样 SSE 管道里只流过一条几十字节的通知，而不是几 KB 的完整画布状态。

🛡️ 思考：为什么不在 tool 的返回值里带完整画布数据？

两个原因。第一，职责分离——工具的返回值是给 LLM 读的文本（如 "已生成并创建 1 个画布节点: node-xxx"），画布状态管理不是工具的 Responsibility。第二，画布后端有自己的 API，前端调用画布接口能拿到结构化的完整数据，比从 SSE 里解析 tool result 可靠得多。前端收到 canvas.render 通知后，用已有的画布 API 拉数据、做局部更新——这是前端最熟悉的流程，不需要改任何逻辑。

🛡️ 思考：payload 为什么是空的 {}？前端怎么知道变了什么？

前端不需要从 payload 里知道变了什么。它收到通知后自己调接口拉最新画布数据，对比前后差异做局部更新。这跟 Git 的 webhook 通知类似——payload 只告诉你"有 push 了"，具体变了哪些文件你要自己去 git fetch。如果 payload 里塞完整画布状态，每次创建节点都要推几 KB 数据，而前端反正要拉一次完整数据来保证一致性——那 payload 里的数据就是浪费。

七、reference_nodes 机制

generate_and_create_node 有一个巧妙的设计：reference_nodes 参数。

reference_nodes: list[str]  # 参考图节点 ID 列表（如 ['node-xxx']）

Agent 只需要传节点 ID，工具内部会自动：

1. 根据 node_id 查 Canvas Backend → 拿到节点的输出图片 URL
2. 把 URL 注入到 model_params 的对应字段（如 reference_images）
3. 创建节点时建立 UPSERT_EDGE 连线（表示"新节点参考了旧节点"）

为什么不让 Agent 自己传 URL？

  • Agent 看不到完整的 URL（画布概览里只有 node_id 和 type）
  • 减少 token 消耗（node_id 很短，URL 很长）
  • 保证 URL 的准确性（工具内部查，避免 Agent 幻觉）
  • 自动建立连线关系（Agent 不需要额外操作）

八、设计要点

📝 设计要点

  • Tool Use 系统设计：7 个画布工具 + 3 个 shell 工具，高抽象少数量，减少 LLM 决策负担
  • reference_nodes 机制：Agent 只传 node_id，工具内部解析 URL + 注入参数 + 建立连线
  • MD5 去重：canvas_create_input_node 通过文件 MD5 实现画布资源去重
  • 错误返回文本不抛异常：让 LLM 能读懂错误信息并自主决策下一步
  • canvas.render 自定义事件：工具创建节点后通知前端刷新，比推送完整状态轻量

九、检索练习

Q1. 用户说"参考画布上已有的那张风格，帮我画一张类似的"，Agent 最少需要调用几个工具？

  • A. 1 个（只调 generate_and_create_node）
  • B. 2 个（canvas_subgraph + generate_and_create_node）
  • C. 3 个（canvas_node_detail + query_models + generate_and_create_node）
  • D. 取决于画布概览里是否已有足够信息
D。如果画布概览（每轮对话自动注入）里已经包含了参考节点的 node_id 和 type，Agent 可以直接调 generate_and_create_node（传 reference_nodes），只需 1 个工具。如果概览不够（比如需要看节点的具体参数），就需要先调 canvas_node_detail 或 canvas_subgraph。如果 Agent 不确定用什么模型，可能还需要 query_models。

Q2. 工具失败时为什么返回错误文本而不是抛 Python 异常？

  • A. 抛异常会导致 LangGraph 状态机崩溃
  • B. LLM 能读懂错误文本并决定下一步（重试/换参数/告知用户）
  • C. Python 异常不能被序列化为 SSE 事件
  • D. A 和 B 都对
B。抛异常不一定会导致崩溃（LangGraph 有异常处理机制），但异常信息是给程序员看的，不是给 LLM 看的。返回结构化的错误文本（"错误：节点 node-xxx 不存在"），LLM 能理解含义并做出决策——比如换参数重试、或者告诉用户"这个节点不存在"。这也是 System Prompt 里"失败要思考根因，不要盲目重试"的前提：Agent 必须先能读到错误信息。

Q3. canvas_create_input_node 用什么机制判断资源是否重复？

  • A. 比较 URL 是否相同
  • B. 比较节点 label 是否相似
  • C. 比较文件内容的 MD5 是否一致
  • D. 比较文件大小和类型
C。下载资源后计算文件 MD5，遍历画布上所有节点的主图 metadata 里的 md5 字段。MD5 相同 = 同一个文件，跳过上传直接复用。URL 不靠谱（同一个文件可能有不同的 URL），label 不靠谱（不同文件可能有相同 label），只有文件内容的 MD5 才是确定性判据。
