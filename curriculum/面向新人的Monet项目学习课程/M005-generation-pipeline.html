Monet 生成链路（Generation Pipeline）

M003 讲了工具的定义和组合，但工具内部是怎么真正调用 AI 模型的？这一节深入生成链路的核心——从 Agent 决定生成到画布上出现节点的完整过程。学完你能讲清楚：

  • 生成链路的四层架构（编排 → 执行 → 服务 → 后端）
  • 模型注册表如何用 (capability, model_id) 复合键路由
  • submit → poll → fetch 三阶段协议
  • 重试策略和错误处理的设计权衡

一、问题引入

用户说"帮我生成一张赛博朋克风格的猫"。Agent 决定调用 generate_and_create_node 工具。但工具内部做了什么？

核心问题：

  • 怎么根据模型名找到对应的 AI 供应商？
  • 怎么把 Agent 的参数转成供应商要求的格式？
  • AI 生图需要几十秒，怎么异步等待结果？
  • 网络抖动、服务超时怎么办？

Monet 的答案是四层架构：

四层架构：
  1. AgentGenerationService：编排层，负责完整的业务编排（引用解析 → 参数构建 → 生成执行 → 节点创建）
  2. GenerationRunner：执行原语，提供 submit → poll → fetch → mirror 的可复用原子操作
  3. GenerationService：服务层，负责模型路由、参数转换、后端分发
  4. GenerationBackend：传输层，负责实际的网络通信（调用 DM API / AIGW / Ailab）

三、模型注册表（Registry）

生成链路的第一步是路由：根据 (node_type, model_id) 找到对应的模型定义。

3.1 复合键设计

注册表用 (capability, model_id) 复合键，而不是单纯的 model_id：

# src/monet/generation/registry.py

MODEL_REGISTRY: dict[str, dict[str, ModelDefinition]] = {}
#                 ↑ capability     ↑ model_id

def get_definition(capability: str, model_id: str) -> ModelDefinition:
    """通过 (capability, model_id) 查找 ModelDefinition。"""
    bucket = MODEL_REGISTRY.get(capability)
    if bucket is None:
        raise ModelNotFoundError(capability, model_id)
    definition = bucket.get(model_id)
    if definition is None:
        raise ModelNotFoundError(capability, model_id)
    return definition
为什么不直接用 model_id？

同一个 model_id 在不同 capability 下可能是不同的模型。比如 "jimeng" 在 gen-image 下是图片生成，在 gen-video 下是视频生成，对应不同的 sub_app 和参数 schema。复合键避免了歧义。

3.2 ModelDefinition

每个模型对应一个 ModelDefinition，包含路由和执行所需的全部信息：

@dataclass(frozen=True)
class ModelDefinition:
    """单个模型的路由定义。"""

    app: str                          # DM 平台 app 名称（如 "seedream"）
    sub_app: SubAppResolver           # sub_app 名称或动态解析函数
    params_schema: type[BaseGenerationParams]  # 参数 schema 类
    poll_interval: float              # 轮询间隔（秒）
    backend_type: Literal["api", "aigw", "ailab"] = "api"  # 后端类型
    output_parser: OutputParser | None = None  # 输出解析器
    max_references: int | None = None  # 最大参考图数量
    outputs_per_request: int = 1      # fanout：每次请求产出数
    agent_catalog: AgentCatalogMetadata | None = None  # Agent 目录展示信息

🛡️ 思考：sub_app 为什么是 SubAppResolver 而不是 str？

有些模型的 sub_app 是固定的（如 "seedream-4.5"），有些是动态的（取决于参数）。比如 Kling 视频生成，sub_app 要根据分辨率动态选择。所以 sub_app 可以是字符串，也可以是 Callable[[BaseGenerationParams], str]，在运行时根据参数决定。

四、GenerationBackend（传输层）

传输层负责实际的网络通信。Monet 有三种 Backend 实现，按执行模式分两类：

Backend用途执行模式说明
DmApiBackendDM 平台 HTTP API
（图片 / 视频 / 3D）		标准三阶段submit 返回 task_id → poll 查状态 → fetch 取产物
AigwBackendAIGW 网关
（LLM 文本生成）		同步阻塞submit 阶段直接调用 LLM，poll/fetch 从内存取缓存
AilabBackendAilab 平台
（动作生成 / 格式转换）		混合text-to-motion / pose-cap 走标准三阶段；
fbx-to-bip 同步阻塞
三种后端，两种模式：
  • 标准三阶段（异步）：DmApiBackend、AilabBackend 的 text-to-motion / pose-cap。AI 生图/视频/3D 需要几十秒甚至几分钟，必须异步轮询
  • 同步阻塞：AigwBackend、AilabBackend 的 fbx-to-bip。LLM 文本生成通常几秒，格式转换也很快，同步等待更简单

4.1 GenerationBackend 协议

"统一接口"统一的是什么？统一的是方法签名（都有 submit、poll、fetch_result 三个方法），而不是行为模式。上层代码（GenerationRunner、GenerationService）不需要关心后端是异步还是同步，都按三阶段调用。同步后端的 poll 直接返回 success，fetch_result 从内存取，对上层透明。这是策略模式——统一接口封装不同行为。

所有 Backend 实现统一的接口：

# src/monet/generation/protocol/backend.py

class GenerationBackend(Protocol):
    """生成后端的统一接口。"""

    async def submit(
        self,
        params: dict[str, Any],
        app: str,
        sub_app: str,
        num: int = 1,
        auth_headers: dict[str, str] | None = None,
    ) -> list[str]: ...

    async def poll(
        self,
        app: str,
        sub_app: str,
        task_id: str,
        auth_headers: dict[str, str] | None = None,
    ) -> DmTaskStatus: ...

    async def fetch_result(
        self,
        app: str,
        sub_app: str,
        task_id: str,
        auth_headers: dict[str, str] | None = None,
    ) -> dict[str, Any]: ...

4.2 DmApiBackend 实现

最常用的 Backend，调用 DM 平台的 HTTP API：

# src/monet/generation/dm_api_backend.py

class DmApiBackend:
    """dm HTTP API 封装。"""

    async def submit(self, params, app, sub_app, num=1, auth_headers=None):
        """提交生成任务。"""
        url = f"{self._api_base_url}/api/v1/apps/{app}/run"
        query_params = {"sub_app_name": sub_app}
        payload = {"params": params, "disable_record": True}

        data = await self._request("POST", url, params=query_params,
                                    json_body=payload, auth_headers=auth_headers)
        return [str(data["task_id"])]

    async def poll(self, app, sub_app, task_id, auth_headers=None):
        """查询任务状态，立即返回。"""
        url = f"{self._api_base_url}/api/v1/apps/{app}/status"
        query_params = {"task_id": task_id, "sub_app_name": sub_app}

        data = await self._request("GET", url, params=query_params,
                                    auth_headers=auth_headers)
        return DmTaskStatus(
            task_id=task_id,
            status=data.get("status", "unknown"),
            progress=data.get("progress", 0),
        )

    async def fetch_result(self, app, sub_app, task_id, auth_headers=None):
        """获取已完成任务的结果。"""
        # 与 poll 相同的 URL，但返回完整的 response.data
        ...

4.3 AigwBackend 的特殊处理

AIGW 后端用于文本生成（如 Claude），它的特点：submit 阶段直接完成生成，poll 直接返回 success：

# src/monet/generation/aigw_backend.py

class AigwBackend:
    """阻塞式文本生成后端。"""

    def __init__(self, aigw_base_url, default_model):
        self._results: dict[str, str] = {}  # 内存缓存结果

    async def submit(self, params, app, sub_app, num=1, auth_headers=None):
        """submit 阶段直接调用 LLM，结果存入内存。"""
        prompt = params.get("prompt", "")
        model = self._create_model(model_name, temperature, max_tokens, auth_headers)

        for _ in range(num):
            task_id = str(uuid.uuid4())
            response = await model.ainvoke([system_message, message])
            self._results[task_id] = str(response.content)
            task_ids.append(task_id)

        return task_ids

    async def poll(self, app, sub_app, task_id, auth_headers=None):
        """submit 已完成，直接返回 success。"""
        return DmTaskStatus(task_id=task_id, status="success", progress=100)

    async def fetch_result(self, app, sub_app, task_id, auth_headers=None):
        """从内存取结果。"""
        text = self._results.pop(task_id)
        return {"task_id": task_id, "text": text}
设计权衡：AIGW 后端用内存缓存结果，是因为文本生成通常很快（几秒），不需要持久化。但如果 Agent 重启，缓存会丢失。这是有意的设计——文本生成任务通常不需要断点续跑。

AIGW 网关的双重角色

Agent 的"大脑"（推理 + 工具选择）也走 AIGW 网关——factory.py 创建 ChatAIGW 实例传给 Agent Loop。所以 AIGW 网关承担两个角色：

角色调用方用途调用方式
Agent 推理 Agent Loop（LangGraph） 理解用户意图、决定调用哪个工具、生成回复 流式 _astream，带 tools 定义（Tool Calling 模式）
文本生成 AigwBackend 直接产出文本内容（gen-text 能力） 非流式 ainvoke，不带 tools（纯对话模式）

两者底层走的是同一个 AIGW 网关，只是调用方式不同：Agent 推理传 tools 定义走 Tool Calling 模式（流式），文本生成走纯对话模式（非流式）。

五、GenerationService（服务层）

GenerationService 是生成链路的核心调度者。它不直接调网络，而是做三件事：路由、参数转换、后端分发。

用一个具体例子走完这三步：

例子：Agent 调用 generate_and_create_node，想生成一张赛博朋克风格的猫。 
node_type = "gen-image"
model_id  = "seedream-4.5"
params    = {"prompt": "一只赛博朋克风格的猫", "aspect_ratio": "1:1"}
num       = 1  # 用户要 1 张图

5.1 路由：找到模型的"地址簿"

第一步：根据 (gen-image, seedream-4.5) 查注册表，拿到 ModelDefinition：

definition = get_definition("gen-image", "seedream-4.5")
# 返回：
#   app         = "seedream"          ← DM 平台上的 app 名
#   sub_app     = "seedream-4.5"      ← 具体模型版本
#   params_schema = Seedream45Params  ← 参数 schema 类
#   poll_interval = 5.0               ← 轮询间隔 5 秒
#   backend_type  = "api"             ← 走 DM API 后端
#   fanout        = 1                 ← 每次请求产出 1 张图

这一步回答了"去哪调？用什么后端？轮询间隔多少？"所有问题。

5.2 参数转换：从强类型到原始 API 格式

第二步：把 Agent 传入的 dict 转成后端 API 需要的原始格式。

这里涉及两次转换：

  1. 校验：用 params_schema.model_validate(params) 校验参数（Pydantic 检查类型、必填项）。Agent 传 {"prompt": 123} 会被拦截
  2. 格式化：调用 params.to_backend_params() 把强类型对象转成原始 API dict。比如：
# 输入（强类型，Pydantic 校验通过）
Seedream45Params(prompt="一只赛博朋克风格的猫", aspect_ratio="1:1")

# to_backend_params() 输出（原始 API 格式）
{"text": "一只赛博朋克风格的猫", "ratio": "1:1"}
#                              ↑ 字段名变了！

为什么字段名会变？因为 Agent 用的是统一的参数命名（prompt），但不同供应商的 API 字段名不同——DM 平台可能叫 text，其他平台可能叫 input_text。to_backend_params() 就是做这个适配。

5.3 fanout 换算：用户要 N 张，实际发几次请求？

有些模型一次请求产出多张图（fanout > 1），比如 Midjourney 一次产出 4 张。Agent 说"我要 4 张图"，但 Midjourney 的 fanout = 4，所以只需要发 1 次请求：

request_count = num // fanout
# = 4 // 4 = 1 次请求

而 seedream-4.5 的 fanout = 1（一次请求 1 张），Agent 要 4 张就要发 4 次请求：

request_count = 4 // 1 = 4 次请求

5.4 后端分发：选后端、调 submit

第三步：根据 backend_type 选后端，调用 submit：

backend = self._get_backend(definition.backend_type)
# definition.backend_type = "api" → 取出 DmApiBackend

task_ids = await backend.submit(
    params=payload,          # ← 转换后的原始 API 参数
    app=definition.app,      # "seedream"
    sub_app=sub_app,         # "seedream-4.5"
    num=request_count,       # 请求次数
)

_get_backend 的逻辑很简单——从初始化时注入的 dict 里按 key 取值：

# 初始化时
backends = {
    "api":   DmApiBackend(...),
    "aigw":  AigwBackend(...),
    "ailab": AilabBackend(...),
}

# 运行时
backend = backends["api"]    # → DmApiBackend
backend = backends["aigw"]   # → AigwBackend
backend = backends["ailab"]  # → AilabBackend
为什么叫"策略模式"？三个 Backend 都实现同一个 GenerationBackend 接口（submit / poll / fetch_result），Service 只需要 backend.submit(...)，不需要关心后端是 DM API 还是 AIGW 还是 Ailab。新增一个后端只需：实现接口 + 注册到 dict，Service 一行代码都不用改。

5.5 poll 和 fetch_result 也是同样逻辑

提交后，poll 和 fetch_result 也走同样的"选后端 → 调用"流程：

# poll：查任务状态
backend = self._get_backend(backend_type)  # 按 backend_type 选
return await backend.poll(app, sub_app, task_id, auth_headers)

# fetch_result：取产物 + 解析
backend = self._get_backend(backend_type)
raw = await backend.fetch_result(app, sub_app, task_id, auth_headers)
# raw 是原始 dict，需要解析成统一格式

if output_type == "text":
    # AIGW 后端：直接取 text 字段
    return GenerationResult(outputs=[GenerationOutput(url=raw["text"])])
else:
    # DM API 后端：用 output_parser 解析
    parser = definition.output_parser or default_dm_output_parser
    dm_result = parser(raw)
    return parse_generation_output(urls=dm_result.urls, ...)

不同后端返回的数据格式不同，GenerationService 根据 capability 推断 output_type，选择对应的解析方式。调用方拿到的是统一的 GenerationResult，不需要关心底层是哪个后端。

六、GenerationRunner（执行原语）

上一节 GenerationService 只负责"选后端、调 submit"，但 submit 之后的事它不管。GenerationRunner 接管后续的轮询、取结果、转存，把三阶段串成一个完整的生命周期。

继续用刚才的例子：seedream-4.5 生成一张赛博朋克猫咪，submit 已经发出了，拿到了一个 task_id。接下来 Runner 做什么？

6.1 三步走完生命周期

async def run_single_generation(spec, generation_service, output_mirror, ...):

    # 第 1 步：submit（委托 Service，上一节已讲）
    submitted = await submit_generation(spec, generation_service)
    # 返回 SubmittedGeneration，里面包着 task_id 和路由信息

    # 第 2 步：poll + fetch（轮询直到完成）
    outcome = await poll_and_fetch_one(submitted, dm_task_id, generation_service, timeout=600)
    # outcome 有三种可能：Succeeded / Failed / Aborted

    # 第 3 步：mirror（把产物转存到 DM 存储）
    if isinstance(outcome, Succeeded):
        return await mirror_result(outcome.result, output_mirror, ...)
    else:
        raise GenerationFailedError(reason=outcome.reason)

一句话概括：submit 拿到句柄，poll 等到完成，fetch 取出产物，mirror 转存归档。

为什么拆出独立的 Runner 模块？run_single_generation 不只是 Agent 在用——TaskManager（管理多任务批量生成）也复用同样的逻辑。把"三阶段协议"抽成可复用原语，避免 Agent 和 TaskManager 各写一套轮询代码。

6.2 poll_and_fetch_one：轮询的完整逻辑

这是 Runner 的核心函数。它做的事情可以用一个循环概括：

flowchart TD
    Start([开始轮询]) --> CheckAbort{should_abort?}
    CheckAbort -->|是| ReturnAborted([返回 Aborted])

    CheckAbort -->|否| Poll[调用 poll 查状态]
    Poll -->|成功| CheckStatus{状态是什么？}
    Poll -->|网络错误| Retryable{可重试？}

    Retryable -->|是，重试次数 < 8| Sleep1[sleep 后继续]
    Retryable -->|否| ReturnFailed1([返回 Failed])
    Sleep1 --> CheckAbort

    CheckStatus -->|running| Sleep2[sleep 后继续]
    CheckStatus -->|failed| ReturnFailed2([返回 Failed])
    CheckStatus -->|success| Fetch[调用 fetch_result 取产物]

    Fetch -->|成功| Mirror([返回 Succeeded])
    Fetch -->|网络错误| Retryable2{可重试？}
    Retryable2 -->|是，重试次数 < 8| Sleep3[sleep 后继续]
    Retryable2 -->|否| ReturnFailed3([返回 Failed])
    Sleep2 --> CheckAbort
    Sleep3 --> CheckAbort

用具体例子走一遍：seedream-4.5 生成一张图，poll_interval = 5 秒，timeout = 600 秒。

时刻poll 返回Runner 做什么
T+0srunning（生成中）sleep 5 秒，继续轮询
T+5srunningsleep 5 秒
T+10srunningsleep 5 秒
T+15ssuccess调 fetch_result 取产物
T+15sfetch 返回图片 URL调 mirror_result 转存

6.3 重试策略：区分"网络没问到"和"后端确认失败"

上面表格里假设每次 poll 都成功返回。但现实中可能遇到网络抖动。Runner 的重试策略：

错误类型示例含义处理
可重试网络超时、500/502/503、429"网络没问到"——后端可能没问题，只是网络抖了一下sleep 后重试，最多连续 8 次
不可重试400、404、参数错误"后端确认失败"——请求本身有问题，重试也没用立即返回 Failed
 
_RETRYABLE_STATUS = frozenset({429, *range(500, 600)})

def _is_retryable(exc):
    if isinstance(exc, httpx.TransportError):     # 网络层错误
        return True
    if isinstance(exc, DmApiError) and exc.status_code in _RETRYABLE_STATUS:
        return True
    return False

关键变量 consecutive：连续失败计数器。每次 poll 成功就清零；连续失败 8 次才放弃。

🛡️ 思考：为什么连续 8 次才放弃，而不是 3 次？

AI 生图通常需要 30-120 秒，poll_interval = 5 秒，总共可能轮询 6-24 次。如果连续 3 次失败就放弃（只给了 15 秒的容错窗口），遇到短暂网络波动就会误判失败。8 次 = 40 秒的容错窗口，能覆盖大部分网络抖动场景。这是经验值——太少容易误判，太多浪费等待时间。

6.4 mirror：转存到 DM 存储

拿到生成结果后，还需要把产物 URL 转存到 DM 自己的存储（OutputMirror）。为什么多此一举？

因为 AI 供应商返回的 URL 是临时的——可能几小时后就过期了。转存到 DM 存储后，URL 变成持久的，画布节点引用的图片不会因为供应商清理而消失。

# OutputMirror.mirror() 的逻辑
async def mirror(result, canvas_id, task_id, auth_headers):
    for output in result.outputs:
        # 下载供应商的图片 → 上传到 DM 存储 → 替换 URL
        new_url = await storage.upload(output.url, auth_headers)
        output.url = new_url
    return result

转存完成后，Runner 把最终的 GenerationResult（含 DM 存储的持久 URL）返回给编排层。

七、AgentGenerationService（编排层）

前几节讲了 Runner/Service/Backend 三层——它们只负责"把图生成出来"。但 Agent 调工具时还涉及一堆业务逻辑：参考图怎么处理？参数怎么校验？生成完了怎么创建画布节点？

编排层负责把这一切串起来。它站在最上面，调用下面三层，同时处理业务编排。

继续用具体例子。这次复杂一点——用户说"参考画布上那张赛博朋克猫咪的风格，帮我生成一张类似的"：

例子：Agent 决定调用 generate_and_create_node 
node_type     = "gen-image"
model_id      = "seedream-4.5"
label         = "类似风格的猫咪"
model_params  = {"prompt": "参考 {{node-abc}} 的风格，画一只类似的猫"}
reference_nodes = ["node-abc", "node-def"]
# node-abc 是之前生成的赛博朋克猫咪（subject 类型）
# node-def 是用户上传的参考图（普通类型）

7.1 第一步：校验 + 找模型定义

capability = validate_node_type("gen-image")  # → "gen-image"
model_def  = get_definition("gen-image", "seedream-4.5")
# 拿到 ModelDefinition：app、sub_app、params_schema、fanout 等

如果 node_type 或 model_id 不对，直接返回错误字符串给 LLM。

7.2 第二步：解析 reference_nodes（最复杂的一步）

Agent 只传了 ["node-abc", "node-def"] 两个节点 ID，但生成时需要的是 URL。编排层要做的：

flowchart TD

node-abc, node-def"] --> Split{分离节点类型}

分两种情况处理：

节点类型示例处理方式
Subject 类型（可复用角色/素材） node-abc：之前生成的"赛博朋克猫咪"主体 1. 把 prompt 里的 {{node-abc}} 替换成描述文字
2. 构造 character_reference（角色参考数据，告诉模型"保持这个角色的外观"）
普通类型（参考图） node-def：用户上传的图片 1. 根据 node_id 查画布后端，拿到输出图片 URL
2. 把 URL 注入到 params 的对应字段（如 reference_images）

处理完后，model_params 变成：

{
    "prompt": "参考风格，画一只类似的猫",     ← 占位符被替换了
    "character_reference": {...},            ← 角色参考数据
    "reference_images": ["https://..."]      ← 普通参考图 URL
}

7.3 第三步：Pydantic 参数校验

把处理好的 params 交给 params_schema 校验：

params = model_def.params_schema.model_validate(mp)
# Seedream45Params(prompt="...", character_reference=..., reference_images=[...])

如果参数不对（比如必填的 prompt 缺失，或者 aspect_ratio 传了非法值），返回格式化的错误信息给 LLM：

# 返回给 LLM 的错误文本：
"参数校验失败（模型 seedream-4.5），请修正后重试:
  - aspect_ratio: 值 '3:7' 不在允许的范围内
提示: 可通过 query_models 查看该模型的完整参数定义。"

7.4 第四步：调 Runner 执行生成

校验通过后，构造 GenerationRunSpec 调 Runner，进入前面讲的 submit → poll → fetch → mirror 流程：

run_spec = GenerationRunSpec(
    capability="gen-image",
    model_id="seedream-4.5",
    params=params,
    num=1,
)
result = await run_single_generation(run_spec, ...)
# 返回：GenerationResult(outputs=[GenerationOutput(url="https://dm-storage/xxx.png")])

如果生成失败（网络超时、后端报错等），返回错误字符串给 LLM。

7.5 第五步：前端参数转换 + 创建画布节点

生成完成后，需要创建画布节点。但前端展示用的参数格式和后端 API 不同：

# 后端 API 格式（to_backend_params 输出的）
{"text": "参考风格，画一只类似的猫", "ratio": "1:1"}

# 前端展示格式（to_frontend_model_params 输出的）
{"prompt": "参考风格，画一只类似的猫", "aspect_ratio": "1:1"}
#   ↑ 字段名改回用户熟悉的名称

然后调 CanvasService.create_nodes_from_generation，这一步会：

  1. 把生成结果的 URL 上传到 DM 存储
  2. 创建画布节点（ADD_NODE）
  3. 为每个 reference_node 建立连线（UPSERT_EDGE）
  4. 计算新节点的位置（放在参考节点旁边）

最终返回 [node_ids]，编排层包装成 AgentGenerateResult 返回给工具。

️ 思考：为什么错误都返回字符串而不是抛异常？

Agent 的工具返回值是给 LLM 看的。如果抛异常，LangGraph 会中断 Agent Loop，用户看到的是一个错误页面。如果返回错误字符串，LLM 能读懂错误信息，决定下一步——比如告诉用户"参数不对"，或者换个模型重试。这是 Agent 系统的常见模式：错误是数据，不是控制流。

八、Capability → Output Type 蕴含

不同 capability 的产物类型是固定的：

# src/monet/generation/service.py

CAPABILITY_TO_OUTPUT_TYPE: dict[str, str] = {
    "gen-image": "image",
    "gen-3d": "model_3d",
    "gen-video": "video",
    "gen-text": "text",
    "gen-motion": "motion",
    "post-3d-retopo": "model_3d",
    "post-3d-uv": "model_3d",
    "post-3d-texture": "model_3d",
}

这意味着 gen-image 的产物一定是图片，gen-video 的产物一定是视频。GenerationService 根据这个蕴含关系选择解析方式，调用方不需要传 output_type。

九、总结

生成链路的核心设计：

  1. 四层架构：编排 → 执行 → 服务 → 后端，职责分离，易于测试和扩展
  2. 复合键路由：(capability, model_id) 避免歧义，支持同名模型在不同能力下有不同的实现
  3. 协议抽象：Backend 协议统一三种后端（DM API / AIGW / Ailab），新增后端只需实现接口
  4. 重试策略：区分可重试（网络错误）和不可重试（业务错误），避免无意义重试
  5. 错误即数据：工具返回错误字符串而不是抛异常，让 LLM 能读懂并决策
设计要点：
  • 设计并实现了 Monet 的四层生成架构（编排 → 执行 → 服务 → 后端），支持 DM API / AIGW / Ailab 三种后端，新增 AI 供应商只需实现 Backend 协议
  • 实现了 submit → poll → fetch 三阶段异步协议，包含智能重试策略（区分可重试/不可重试错误），支持最大 600 秒超时
  • 设计了 (capability, model_id) 复合键路由机制，支持同名模型在不同能力下的差异化实现
