S001 · DreamMaker Scheduler 整体架构总览

课程: DreamMaker Scheduler 时长: ~35 分钟 难度: ★★★☆☆ 前置: 了解 Go 基础、HTTP 微服务基本概念

一、一句话架构

Scheduler = Go 微服务集群 + Redis 任务队列 + MongoDB 记录中心 + etcd Worker 注册中心 + K8s 服务发现 + dmfr 内部框架。

没有单一入口 —— 每个服务各有自己的 app/<service>/main.go。外部流量经 tmax istioingress（网易内部 K8s 平台的 Istio Ingress Gateway）进入。服务间内部通信使用 dmfr.HTTPClient()。任务状态分布在 Redis / Mongo / etcd 三套存储中。

二、基础设施说明

2.1 tmax / Istio / Envoy 是什么

概念解释
tmax网易内部 K8s 容器平台（类似阿里 ACK / 腾讯 TKE）
Istio开源 Service Mesh，提供流量路由、负载均衡、认证鉴权、可观测性
Envoy高性能 C++ 代理；是 Istio 的数据面。每个 Pod 内有一个 Envoy Sidecar
EnvoyFilterIstio 配置资源，用于注入自定义过滤逻辑（如在网关层做 JWT 鉴权）

tmax istioingress 做三件事：

  1. 路径路由：URL path → 内部服务（如 /api-outer/... → api-outer）
  2. 统一鉴权：通过 EnvoyFilter 在网关层做 JWT 校验，各服务无需重复实现
  3. 统一入口：前端、Monet、内部工具统一走这层

四、五层架构的职责边界

层级核心组件职责不能做的事
1. 外部请求层 前端 / Monet / 内部工具 组装 HTTP 请求，携带鉴权 Header 不能直接提交 Worker 任务
2. 业务服务层 api-outer / app-gateway / 2d / story-board 参数校验、鉴权、参数映射、持久化、入队、状态查询 不能直连 Worker，不能做 GPU 调度
3. 基础设施服务层 worker-scheduler 拉队列、分配任务、回写结果、Autoscaler 不关心具体推理逻辑
4. Worker 执行层 worker-sidecar + 各类 Worker 接收任务、适配后端、执行推理、上报进度/结果 不能反向依赖 app-gateway
5. 外部供应商层 ComfyUI / SD-WebUI / 火山 / 混元 / ... 实际 AI 推理 —

五、三大核心组件

5.1 app-gateway — 任务入口

四项职责：

  1. 权限校验：CheckAppAccess —— 用户是否有权使用该 app/sub_app
  2. 组件解析：解析 app component、group、cluster、taskMode、priority
  3. 持久化：向 Mongo 写入 AddAppRecord(status=queued)，向 Redis 队列写入 pending task
  4. 返回 task_id：立即返回，不等待 Worker 执行
为什么不能绕过 app-gateway？
  • 安全：api-outer + app-gateway 是唯一的鉴权和限流入口
  • 可观测：所有任务必须创建 AppRecord，用于计费、审计、错误分析
  • 一致性：任务状态机（queued → running → success/failed）依赖 action.Add 建立初始状态
  • 可扩展：预处理 / 参数映射 / 优先级都在这层

5.2 worker-scheduler — 分布式调度核心

关键行为：

  • 多副本并行：多个 Pod 各自独立工作（无 Leader 选举）；通过 Redis 分布式锁协调关键操作（如 Autoscaler）
  • 拉队列：从 Redis 拉取 pending tasks
  • 加载消息：从 Mongo 加载 AppTaskMsg（Redis 中只存 task_id，完整参数在 Mongo）
  • 注册运行态：将任务写入 etcd running 注册表，作为"当前执行中任务"的 source of truth
  • 下发给 Worker（Pull 模型）：Worker 主动上报"我空闲了"（report consume），scheduler 再下发 —— 是 Worker "拉"，不是 scheduler "推"
  • 结果回写：Worker 上报结果 → scheduler 调用 action.AfterCall / MapCallResponse → 写 Mongo → 删 etcd 注册
为什么要三套存储（Redis + Mongo + etcd）？
  • Redis：短生命周期"待消费"队列。使用 ZSet（score = 入队时间戳，FIFO）；不同优先级放在不同 Redis key。还存任务状态缓存供前端 /status 轮询（亚秒响应，避免打 Mongo）。
  • Mongo：长生命周期"任务记录中心"。所有任务参数、状态、结果存在这里，用于查询、审计、计费。
  • etcd："运行态"强一致注册中心。支持 Lease + Watch：Worker 挂掉 → Lease 过期 → 自动清理。Mongo 做不到"心跳自动清理"。

核心原则：不同语义用不同存储，不要强求一套存储搞定所有事 —— 这是经典的分布式系统取舍。

5.3 worker-sidecar — 异构后端适配器

worker-scheduler 只知道"把这个任务发给某个 Worker"，但实际的协议、参数、结果解析因后端而异（ComfyUI / SD-WebUI / Training / 外部供应商各不相同）。

这就是生产级别的 Adapter Pattern：sidecar 将 scheduler 的派发逻辑与具体推理后端解耦。

新增一个 AI 能力时：scheduler 派发代码不需要改。只需要：

  1. 在 sidecar 中新增 worker 实现（实现 pkg.Worker 接口）
  2. 在 app-gateway 的 action 层处理参数映射和结果处理
关于 sidecar 命名：
  • 本地后端（ComfyUI / SD-WebUI / GPT-SoVITS）：sidecar 部署在同一个 Pod，通过 localhost:8188 / localhost:7861 通信 —— 经典 Sidecar 模式
  • 外部供应商（火山 / Kling / Runway / Sora）：没有推理容器在旁边；sidecar 是独立进程调用外部 HTTP API —— 更像"Worker Adapter"

统一叫 sidecar 是历史原因：项目最早只有本地推理后端，后来加了很多外部供应商，代码复用同一套上报/调度机制，名字就保留了。

六、关键数据流：一个任务的完整生命周期

sequenceDiagram
    autonumber
    participant C as Client / Monet
    participant O as api-outer
    participant A as app-gateway
    participant M as MongoDB
    participant R as Redis Queue
    participant WS as worker-scheduler
    participant E as etcd
    participant W as worker-sidecar

    C->>O: POST /apps/{app}/run
    O->>O: JWT 认证 + API 模块权限校验
    O->>A: RunApp(...)
    A->>A: CheckAppAccess（App 访问权限）+ 参数映射
    A->>M: AddAppRecord(status=queued)
    A->>R: Produce pending task
    A-->>O: task_id
    O-->>C: task_id

    Note over W,WS: 异步阶段 — Worker 主动拉取
    W->>WS: report consume（我空闲）
    WS->>R: 拉 pending task
    WS->>M: 加载 AppTaskMsg
    WS->>E: 注册 running task
    WS-->>W: JobReportData

    W->>W: 执行推理
    W->>WS: report progress
    W->>WS: report result

    WS->>A: AfterCall / MapCallResponse
    A->>M: 写入 Success / Failed
    WS->>E: 删除 running task

    C->>O: GET /apps/{app}/status?task_id=xxx
    O->>A: GetAppTaskStatus
    A->>M: 读取 record
    A-->>C: status / output
设计要点：
  • 提交和执行完全异步 —— 提交后立即返回 task_id，客户端通过 /status 轮询
  • Worker "Pull" 模型 —— Worker 主动上报空闲，天然背压；Worker 不会被打爆
  • 结果回写时，worker-scheduler 不自己实现结果处理逻辑 —— 直接复用 app-gateway/action 包代码（Go 包引用，非 HTTP 调用）

七、dmfr 框架

dmfr（DreamMaker Framework）是内部 Go 框架，提供以下标准化能力：

能力用法不用的后果
HTTP Serverdmfr.HTTPServer()手写 Wrapper 会遗漏 trace/metrics
HTTP Clientdmfr.HTTPClient(serviceName)手写 baseURL 绕过服务发现
日志logging.Info(ctx, "msg", zap.Field...)散落的 logger 无法做 trace 关联
错误码ecode 包业务错误缺乏统一分类
响应包装httpServer.JSON(c, resp, err)响应格式不一致
JSON优先用 Sonic，不用 encoding/json性能损失明显
开发原则：能用 dmfr 解决的不要重复造轮子。新写代码前先确认框架层是否已有现成封装。
