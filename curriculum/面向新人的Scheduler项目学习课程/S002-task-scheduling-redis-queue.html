一、任务状态机

每个任务都有 5 种内部状态：

状态含义触发函数 (action_base.go)Mongo DAO (dao_record.go)
queued已存储 + 已入队，等待消费Base.Add()AddAppRecord()
runningWorker 已取走，执行中Base.Run()RunAppRecord()
success执行成功，结果已写入Base.Success()SuccessAppRecord()
failed执行失败，错误已记录Base.Failed()FailedAppRecord()
stopped用户主动取消Base.Stop()StopAppRecord()
stateDiagram-v2
    [*] --> queued : Add (存储 + 入队)
    queued --> running : Run (被 Worker 消费)
    running --> success : Success
    running --> failed : Failed
    running --> stopped : Stop (用户取消)
    queued --> failed : 异常 (入队后异常)

每次状态流转后，SetCache() 更新 Redis 缓存，使 /status 轮询可以亚秒响应。

注意：外部 API 将 queued 展示为 waiting，但内部只有上述 5 种状态。状态常量定义在 model/constance.go。

二、Action 编排模式

2.1 设计模式：Template Method + Strategy

核心 Action 接口定义在 app/app-gateway/action/interface.go：

type Action interface {
    ActionName() string
    Add(ctx, msg) error           // 入库（Mongo）
    Run(ctx, msg) error           // 标记 running
    Stop(ctx, msg) error          // 用户取消
    Success(ctx, msg) error       // 标记成功
    UpdateOutput(ctx, msg) error  // 中间结果更新
    Failed(ctx, msg, err) error   // 标记失败
    GetAppMsg(ctx, taskID, msg) error    // 读 Mongo 任务记录
    ProduceResult(ctx, msg) error        // 写结果到 Kafka
}

2.2 可选接口（Go 类型断言实现能力检测）

可选接口职责检查方式
RequestMapper参数映射（APP 配置 → 请求参数）action.(RequestMapper)
MsgProducer入队（produce pending task）action.(MsgProducer)
MsgConsumer出队（consume pending task）action.(MsgConsumer)
Generator生成下发给 Worker 的 JobReportDataaction.(Generator)

为什么用类型断言而不是一个大接口：不同 action 类型需要不同能力，全放一个接口会强制空实现。Go 的类型断言是天然的"接口隔离"。

2.3 编排链路

BeforeProduce (参数映射) → Produce (存储+入队) → Consume (出队) → BeforeCall (调用前映射) → GenerateTask (生成 JobData) → AfterCall (结果处理)

三、Redis 队列设计（核心）

3.1 两种队列对比：List vs ZSet

维度旧方案 - List (ComfyUI/SD)新方案 - Sorted Set (commonAction)
数据结构Redis ListRedis Sorted Set (ZSet)
入队LPushZAdd(key, score, member)
出队BRPop（阻塞弹出）ZRange + ZRem（扫描 + 原子删除）
排序FIFO按 score 排序（优先级 + 时间戳）
消息体完整 AppTaskMsg JSON仅 user::taskID；完整数据在 Mongo
优先级不支持不同优先级不同 Redis key
并发控制无member 中 user 前缀可做按用户限制
竞争安全BRPop 原子弹出ZRem 返回值 ≥ 1 表示抢到

3.2 为什么 Redis 只存 ID 不存完整消息

  • AppTaskMsg 可能包含 base64 图片、ComfyUI 工作流 JSON（体积大）
  • ZSet member 越短排序越快
  • 任务参数可能在预处理阶段被修改；双份存储需要同步
  • "Redis 做索引层，Mongo 做数据层"—— 关注点分离

3.3 队列 Key 结构 —— 不是一个大队列，而是多个小队列

格式：apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}

维度含义示例值
priority优先级0, 1, 2
source请求来源dm, sf, mj
taskMode任务模式default, fast
cluster资源集群v2prod, aliyun-hangzhou-1

示例：

apps_pending_task::dm::default::v2prod::prod          ← 普通优先级
apps_pending_task::2::dm::default::v2prod::prod       ← 高优先级 (priority=2)
apps_pending_task::dm::fast::aliyun-hangzhou-1::prod  ← fast 模式，阿里云集群

为什么拆成多个队列：

  • 隔离：不同 cluster 的 Worker 只消费自己集群的任务
  • 独立限流：不同 source/taskMode 可以有不同消费规则
  • 优先级调度：WeightedScheduler 可以在不同优先级 key 间轮转
  • 性能：小队列意味着 ZRange 扫描范围更小

3.4 ZSet 入队

代码在 commonAction.Produce()：

key = priority.BuildPendingKey(pri, msg.Source, msg.TaskMode, msg.Cluster, dmfr.ENV())
member := fmt.Sprintf("%s::%s", msg.GetRealUser(), msg.TaskID)
c.dao.GetRedis().ZAdd(ctx, key, msg.PreprocessTime, member)

关键设计：

  • priority=0：key 省略 priority 段（向后兼容旧任务）
  • score = 毫秒时间戳（msg.PreprocessTime）：同优先级内 FIFO 语义
  • member 包含 user：出队时无需额外查询即可做并发控制

3.5 ZSet 出队 —— 乐观抢占

代码在 commonAction.tryConsume()，核心流程：

  1. ZRange(0, 255) —— 批量扫描前 256 个 member
  2. 逐个解析 member，取出 user 和 taskID
  3. 检查 GetUser() —— 该用户是否已有正在执行的任务？
  4. 如果并发冲突 → 加入 queueJob 列表，跳过
  5. 如果无冲突 → grabJob() 尝试抢占
  6. grabJob：ZRem 返回 ≥ 1？抢到了！从 Mongo 加载 + 注册到 etcd
  7. 第一轮结束后 → 第二轮遍历 queueJob（并发冲突的任务）
func (c *commonAction) tryConsume(ctx context.Context, pri int, msg *model.AppTaskMsg) error {
    pendingTaskKey := priority.BuildPendingKey(pri, ...)
    members, _ := rds.ZRange(ctx, pendingTaskKey, 0, 255)

    queueJob := []string{}  // 有并发冲突的 member，第二轮再试
    for _, member := range members {
        user, taskID := c.splitMember(member)

        // 检查该用户是否已有任务在跑
        if c.concurrentManager.GetUser(source, taskMode, cluster, user) >= 1 {
            queueJob = append(queueJob, member)
            continue  // 先跳过，给其他用户机会
        }
        if err := c.grabJob(ctx, pendingTaskKey, member, msg); err == nil {
            return nil  // 抢到了！
        }
    }
    // 第二轮：消费有并发冲突的任务（所有无冲突的都没抢到时）
    for _, member := range queueJob {
        if err := c.grabJob(ctx, pendingTaskKey, member, msg); err == nil {
            return nil
        }
    }
    return err
}

func (c *commonAction) grabJob(ctx context.Context, key, member string, msg *model.AppTaskMsg) error {
    num, _ := c.dao.GetRedis().ZRem(ctx, key, member)
    if num < 1 {
        return err  // 被别的 scheduler 抢走了
    }
    // 抢到了：从 Mongo 加载完整消息 + 注册到 etcd
    c.dao.GetAppRecord(ctx, taskID, msg)
    c.schedulerDao.AddTask(ctx, msg)
    return nil
}
为什么 ZRem 不需要 Lua 脚本？
  • ZRem 本身是原子的（Redis 单线程模型）
  • 不需要原子的"读取-检查-删除"封装
  • ZRange 只是"peek"；真正的竞争点在 ZRem
  • 多个 scheduler 同时 ZRange 到同一个 member 没关系 —— 谁先 ZRem 谁赢
  • 如果需要"仅当 score < X 才删除"（条件删除），才需要 Lua；这里的条件判断（并发控制）在应用层做

3.6 两轮扫描策略的意义

  • 第一轮：跳过并发冲突用户（GetUser() >= 1），优先分配给没有运行中任务的用户 —— 公平性（防止一个高频用户独占 Worker）
  • 第二轮：如果第一轮没找到，消费冲突任务 —— 吞吐量（不让 Worker 空闲）

这是经典的公平性 vs 吞吐量权衡。

四、优先级调度 —— WeightedScheduler

代码在 pkg/priority/scheduler.go：

func (s *WeightedScheduler) NextPriority(qctx QueueContext, cfg *Config) (int, bool) {
    sortedCfg := cfg.SortedQueues()  // 按优先级降序排
    if pri, found := pickPriority(st, sortedCfg); found {
        st.counters[pri]--  // 消耗一次配额
        return pri, true
    }
    resetCounters(st, sortedCfg)  // 所有配额耗尽 → 重置
    if pri, found := pickPriority(st, sortedCfg); found {
        st.counters[pri]--
        return pri, true
    }
    return 0, false
}

示例配置 [{priority:2, weight:5}, {priority:1, weight:3}, {priority:0, weight:2}]：每 10 次消费中，priority=2 得 5 次，priority=1 得 3 次，priority=0 得 2 次。一轮结束后配额重置。

4.1 Consume 的三层策略

// 1. 无 queues 配置 → 原始行为
if cfg == nil || len(cfg.Queues) == 0 {
    c.tryConsume(ctx, 0, msg)
    return
}
// 2. 加权选择
if cfg.Enabled && c.prioScheduler != nil {
    if pri, ok := c.prioScheduler.NextPriority(qctx, cfg); ok {
        if c.tryConsume(ctx, pri, msg) == nil && msg.TaskID != "" {
            return
        }
    }
}
// 3. 降序兜底
for _, p := range priority.AllPriorities(cfg) {
    if c.tryConsume(ctx, p, msg) == nil && msg.TaskID != "" {
        return
    }
}
防饥饿机制：配额制度保证即使 weight=1 的队列每轮也能至少被消费 1 次。降序兜底意味着如果高优先级队列为空，低优先级任务立即有机会。相比严格优先级（高负载下完全饿死低优先级），加权轮转是经典的公平调度方式。

五、用户并发控制

代码在 app/worker-scheduler/manager/concurrent.go：

type ConcurrentManager struct {
    taskMap *ConcurrentMap[string, *atomic.Int64]  // source::taskMode::cluster → count
    userMap *ConcurrentMap[string, *atomic.Int64]  // source::taskMode::cluster::user → count
}

两个 map 分别跟踪任务维度和用户维度的并发数。

5.1 CAS 原子操作

func (c *ConcurrentManager) addClampNonNegative(v *atomic.Int64, delta int64) int64 {
    for {
        curr := v.Load()
        if delta < 0 && curr == 0 { return 0 }     // 不能减到负数
        next := curr + delta
        if delta < 0 && next < 0 { next = 0 }      // 钳位到 0
        if v.CompareAndSwap(curr, next) {           // CAS：成功则返回，失败则重试
            return next
        }
    }
}

为什么用 CAS 而不是 Mutex：低竞争场景（只在任务开始/结束时更新），CAS（乐观、无阻塞）比 Mutex（悲观、goroutine 调度开销）性能更好。

5.2 etcd Watch 驱动同步

  • 新任务注册到 etcd（/task/{env}/{taskID}） → Watch 事件触发 ConcurrentManager.Add(..., +1)
  • 任务完成或 Worker 死亡（etcd key 过期/删除） → Watch 事件触发 Add(..., -1)
  • ConcurrentManager 是最终一致的 —— etcd 保证有序的 Watch event 递送

5.3 多 Pod 一致性

  • 每个 worker-scheduler Pod 都有自己的内存 ConcurrentManager
  • 所有 Pod Watch 同一个 /task/{env}/ 前缀
  • 任意 Pod 分配任务（写 etcd） → 所有 Pod 收到 Put 事件 → 各自 +1
  • 任务完成（删 etcd） → 所有 Pod 收到 Delete 事件 → 各自 -1
  • 不是严格精确的：etcd Watch 有毫秒级延迟；极端边缘情况下可能短暂超出并发限制，但对实际使用场景可接受

六、Kafka 事件广播

Kafka 的角色：任务完成后通知下游系统。Redis 队列负责任务调度（谁下一个被消费）；Kafka 负责事件广播（告诉所有关心方）。

函数写入时机消息内容下游消费者
WriteResult任务成功/失败后完整 AppTaskMsg（含 output）consumer 服务：数据上报、告警、分析、模型统计
WriteStep每次状态变更AppTaskMsgStep（状态流转事件）monitor 服务：Prometheus 指标（运行时间、排队时间等）
重要区分：Kafka 通知的是内部后端服务（统计、监控、告警），不是用户。用户通过 GET /apps/{app}/status 读 Mongo 获取结果。 
func (d *Dao) WriteResult(ctx context.Context, taskMsg *model.AppTaskMsg) error {
    dataBytes, _ := json.Marshal(taskMsg)
    return d.kafkaResult.WriteMessages(ctx, kafka.Message{
        Key:   []byte(taskMsg.TaskID),   // 同一任务的消息落在同一 partition
        Value: dataBytes,
    })
}

Key = TaskID 保证同一任务的消息在一个 partition 内有序。
