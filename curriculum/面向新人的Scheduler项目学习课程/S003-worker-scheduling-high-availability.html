二、Legacy Leader 选举 — K8s LeaseLock（旧版 scheduler）

历史背景：旧版 app/scheduler 部署 3 副本，但同一时刻只有一个 Leader 做调度。没有选举的话，多副本同时拉 Redis 队列、派发任务，会导致重复调度。当前架构已迁移到 app/worker-scheduler（多 Pod 并行，无 Leader），本节内容仅供了解历史设计。

2.1 核心代码

func electLeader(ctx context.Context) {
    id := uuid.New().String()
    lock := &rl.LeaseLock{
        LeaseMeta: metav1.ObjectMeta{
            Namespace: conf.Config.Election.KubeNamespace,
            Name:      "dreammaker-scheduler-lock-" + conf.Config.ENV,
        },
        LockConfig: rl.ResourceLockConfig{Identity: id},
        Client: kube.NewKubeClient().CoordinationV1(),
    }
    leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
        Lock:          lock,
        LeaseDuration: time.Second * 15,
        RenewDeadline: time.Second * 10,
        RetryPeriod:   time.Second * 2,
        Callbacks: leaderelection.LeaderCallbacks{
            OnStartedLeading: func(ctx context.Context) { run(ctx) },
            OnStoppedLeading: func() { os.Exit(0) },
            OnNewLeader: func(identity string) { ... },
        },
    })
}

2.2 三个时间参数

参数值含义
LeaseDuration15sLease 有效期；Leader 必须在此时间内续约
RenewDeadline10sLeader 完成一次续约 API 调用的截止时间
RetryPeriod2sFollower 重试获取 Lease 的间隔

约束关系：RetryPeriod < RenewDeadline < LeaseDuration

最坏故障切换窗口：LeaseDuration - RenewDeadline + RetryPeriod = 15 - 10 + 2 = 7 秒

2.3 OnStoppedLeading: 为什么直接 os.Exit(0)?

一旦续约失败（失去 Leader），进程直接退出。看起来"很暴力"，但这是 K8s 原生选举的标准做法：

  1. 避免脑裂：如果旧 Leader 不退出，它可能继续拉队列、分派任务，跟新 Leader 产生冲突
  2. K8s 自动重建：退出后 K8s Deployment 控制器自动创建新 Pod，它会以 Follower 身份加入竞选。原理：Deployment 有一个 replicas 字段（比如设为 3），控制器会持续保证"当前运行的 Pod 数量 = replicas"。一旦某个 Pod 退出（不管是崩溃还是主动 os.Exit(0)），控制器发现只剩 2 个了，就自动拉起一个新 Pod 补上
  3. 状态无损：调度器是无状态的——所有状态在 etcd / Redis / Mongo，重启后从存储恢复
为什么用 K8s Lease 而不是 etcd 选举？
  • etcd 选举需要管理 gRPC Session/KeepAlive
  • K8s Lease 是原生资源，通过 K8s API Server（本身已高可用）访问
  • 官方 client-go/tools/leaderelection 库久经考验
  • 关注点分离：etcd 用于 Worker/Task 注册，K8s Lease 用于集群管理

三、etcd Worker/Task 注册

3.1 etcd 基础

etcd 是基于 Raft 的分布式 KV 存储（通常 3 或 5 节点）。

Redisetcd
优化方向速度（10W+ QPS，异步复制）一致性（Raft，~1W QPS，强一致）
DM 中用于任务队列、缓存、锁Worker/Task 运行态注册

etcd 的四个核心能力（DM 都用到了）：

能力含义类比DM 里怎么用
Put / Get / Delete基本的读写删跟 Redis SET / GET / DEL 一样注册 Worker（Put）、查询 Worker（Get）、注销 Worker（Delete）
Watch监听某个 key 或前缀的变化，有变化时实时推送事件像订阅通知——"这个 key 变了告诉我"Scheduler Watch /worker/ 和 /task/ 前缀，实时感知 Worker 上下线和 Task 增减
Lease给 key 绑一个 TTL（过期时间），到期自动删除像租房合同——不续约就自动失效Worker 注册的 key 绑 Lease，进程崩溃后 key 自动过期 → Scheduler 通过 Watch Delete 事件感知
Txn（事务）原子的"如果…则…否则…"操作像数据库的 Compare-And-SwapUpdateWorker 时用 Txn(Compare(ModRevision)) 做乐观锁，防止并发更新覆盖

前缀查询 / 前缀 Watch

etcd 的 key 是有层级的字符串（像文件路径）。可以用前缀一次性查询或监听一批 key：

Get("/worker/prod/", WithPrefix)     → 拿到所有 prod 环境的 Worker
Watch("/task/prod/", WithPrefix)     → 监听所有 prod 环境 Task 的增删改

这就是为什么 DM 的 key 设计成 /worker/{env}/{podName} 格式——{env} 在中间，用前缀就能隔离不同环境。

ModRevision

etcd 里每个 key 有一个 ModRevision（修改版本号），每次写入自动递增。Txn 事务可以用它做乐观锁：

Txn:
  If   key 的 ModRevision == 我上次读到的值
  Then Put(key, newValue)         → 没被别人改过，更新成功
  Else 放弃                       → 被别人改过了，需要重试

跟 S002 里 Redis ZRem 的"原子抢占"思路类似——都是用原子操作解决并发竞争，只是实现层面不同。

Watch + WithPrevKV

Watch 事件默认只推送当前值。加 WithPrevKV 后，Delete 事件会额外携带被删除前的值（PrevKV）。DM 用这个来获取"刚挂掉的 Worker 的信息"——知道是谁挂了、它在跑什么任务，才能做精准的清理和恢复。

3.2 Key 格式

用途Key 格式Value示例

Task 运行注册/task/{env}/{taskID}AppTaskMsg JSON/task/prod/task-uuid-456

都包含 {env} 实现多环境隔离（test/prod 共享同一 etcd 集群）。

3.3 Lease 机制

const defaultTTL = 7200  // 2 小时

func (d *Dao) grantLease(ctx context.Context) (*clientv3.LeaseGrantResponse, error) {
    leaseCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    return d.etcd.Grant(leaseCtx, defaultTTL)
}

func (d *Dao) grantLeaseLoop(ctx context.Context) {
    ticker := time.NewTicker(300 * time.Second)  // 每 300s 重新 Grant
    // ...
}
设计选择：Grant vs KeepAlive

DM 用 Grant（每 300s 重新创建 Lease）而非标准的 KeepAlive（续同一个 Lease）。

后果：未被重写的 key（Task key）挂在旧 Lease 上，最多 7200s 后过期。频繁重写的 key（Worker key 通过 30s 心跳重写）每次绑定到最新 Lease。

3.4 写入操作：AddTask 与 UpdateWorker

AddTask——当 Scheduler 给 Worker 分配了一个任务时调用：

  1. 把 taskID 拼成 etcd key：/task/{env}/{taskID}
  2. 把整个 AppTaskMsg 序列化为 JSON 作为 value
  3. 调 etcd Put(key, value, WithLease(当前 Lease)) 写入，绑定当前 Lease

写入后，这个 task key 就代表"这个任务正在运行"。所有 Pod 的 watchTask 都会收到 Put 事件 → ConcurrentManager +1。

UpdateWorker——心跳、任务完成、shutdown 等场景都会调用，用 Txn 乐观锁更新：

  1. 读当前值：从 etcd Get /worker/{env}/{podName}，拿到当前 JSON 值 + ModRevision（版本号）
  2. 内存中修改字段：如果调用方传了 KV 参数（如 status=terminating），就在 JSON 里改对应字段；心跳不传参数，所以不改任何字段
  3. Txn 写回：提交一个事务——"如果 ModRevision 还等于我读的时候那个值，就 Put 写入新值并绑定最新 Lease；否则放弃（说明别人抢先写了）"
为什么用 Txn 乐观锁？
Worker 状态可能被多个来源更新：心跳上报、任务完成、shutdown 通知。如果不做并发控制，后写的值可能覆盖先写的值（ABA 问题）。

Txn 的 Compare(ModRevision) 保证"我读到的版本 = 当前版本"时才写入，否则放弃。这跟数据库的乐观锁 UPDATE ... WHERE version = ? 是同一个思路。

悲观锁需要分布式 Mutex（复杂/慢）。冲突概率极低（每个 Pod 只更新自己的 key），乐观锁更合适。

3.5 Watch 机制

go s.watchWorker(ctx)
go s.watchTask(ctx)

func (d *Dao) WatchWorker(ctx context.Context) clientv3.WatchChan {
    key := fmt.Sprintf(etcdWorkerPrefix, dmfr.ENV())
    return d.etcd.Watch(ctx, key,
        clientv3.WithPrefix(),
        clientv3.WithPrevKV())  // 关键：Delete 事件时获取旧值
}

WithPrevKV() 的作用：Delete 事件的"当前值"是空的（key 都删了，没有值了），但 Scheduler 需要知道"删掉的是谁"才能做清理。加了 WithPrevKV 后，Delete 事件会额外携带删除前的 value（即之前 Put 进去的 Worker/Task 信息），Scheduler 就能解析出 workerType、cluster、用户等信息，做精准的缓存移除和并发计数恢复。

四、心跳与故障检测

DM 同时使用：主动心跳 + 被动 Lease 过期。

4.1 Sidecar 30s 心跳

func (s *Service) poolLoop(ctx context.Context) {
    for {
        select {
        case <-ctx.Done(): return
        case <-time.Tick(time.Second * 30):
            s.heartbeat(ctx)
            if s.workerPool.Cap() != s.attribute.Load().Concurrency {
                s.workerPool.Tune(s.attribute.Load().Concurrency)

}

心跳做两件事：

  • 上行（Sidecar → Scheduler）："我还活着，podName=xxx"

4.4 Worker Delete 事件处理

代码在 app/worker-scheduler/service/service_event_handler.go：

func (s *Service) handleWorkerDelete(ctx context.Context, ev *clientv3.Event) {
    worker := &model.WorkerPodAttributes{}
    json.Unmarshal(ev.PrevKv.Value, worker)  // ← PrevKV 拿旧值

    s.workerCache.Delete(worker.Name)           // ① 删除缓存
    s.cacheKeyManager.WorkerDelete(worker)      // ② 清理 cache key 索引
    s.workerClusterMap.Decr(                    // ③ 集群计数 -1
        genWorkerClusterKey(worker.Type, worker.Project, worker.GetTaskMode()))
}

4.5 Task Delete 事件 → 并发计数恢复

func (s *Service) handleTaskEvent(ctx context.Context, ev *clientv3.Event) {
    var sub int64
    var v []byte

    switch ev.Type {
    case clientv3.EventTypePut:
        sub = 1; v = ev.Kv.Value         // 新任务 → +1
    case clientv3.EventTypeDelete:
        sub = -1; v = ev.PrevKv.Value    // 任务结束/过期 → -1
    }

    task := &model.AppTaskMsg{}
    json.Unmarshal(v, task)
    s.concurrentManager.Add(task.Source, task.TaskMode,
        task.Cluster, task.GetRealUser(), sub)
}
心跳 30s vs Lease TTL 7200s 为什么差这么多？

心跳的目的是"刷新 Lease + 同步配置"（不是故障检测）。正常关闭用显式上报（shutdown → exit）。只有异常崩溃才依赖 Lease 过期。TTL=7200s 必须远大于 Grant 间隔（300s），避免误删 key。

五、Worker 生命周期状态机

状态含义可接受的上报类型
pendingPod 刚创建，sidecar 尚未注册register
running正常工作中heartbeat, consume, progress, result, shutdown
recoveringWorker 恢复中（如 ComfyUI 重启推理进程）recover（恢复后回到 running）
terminating收到 K8s SIGTERM，优雅关闭中exit
terminated已退出，但 etcd key 仍存在（等 Autoscaler 或 K8s 回收）—
stateDiagram-v2
    [*] --> pending : K8s 创建 Pod
    pending --> running : sidecar register
    running --> running : heartbeat / consume / result
    running --> recovering : recover 上报
    recovering --> running : 恢复完成
    running --> terminating : shutdown 信号
    terminating --> terminated : exit 上报
    terminated --> running : Autoscaler 扩容
    terminated --> [*] : K8s 回收 Pod

处于 terminated 或 terminating（invalidWorkerStatus）的 Worker 不会被加入 cacheKeyManager（排除在任务分配之外）。

六、Sidecar 优雅关闭

收到 K8s SIGTERM 后的完整流程：

  1. K8s 发送 SIGTERM 给 sidecar
  2. Sidecar cancel context → 停止接收新任务
  3. 等待 workerPool 关闭（最长 10 分钟）
  4. 上报 type=shutdown 给 scheduler → scheduler UpdateWorker(status=terminating)
  5. 等待所有任务完成
  6. 上报 type=exit 给 scheduler → scheduler UpdateWorker(status=terminated)
  7. 进程退出
两阶段上报（shutdown → exit）的意义：Scheduler 知道"Worker 正在关闭但还没完全关"→ terminating 状态不分配新任务，但已有任务可以继续执行完毕。

七、Autoscaler（扩缩容机制）

7.1 DM 中的两种自动扩缩容

机制解决的问题触发条件实现方式
K8s HPA（基础设施层）流量波动 —— 自动扩缩 API 服务 PodCPU / Memory 阈值原生 K8s HPA + Knative KPA

7.3 扩容逻辑

注意：扩容不是"创建新 Pod"，而是"唤醒 terminated 状态的 Pod"。

  1. 前置检查：有 terminated 的 Worker 可用？没有则跳过
  2. 决策（shouldScaleUp）： 
    if workerCount == 0 { return true }              // 没有 Worker → 必须扩
if workerCount <= int(queueLength)/2 { return true }  // Worker 数 ≤ 队列长度/2 → 扩
  3. 计算步长： 
    step := ceil(queueLength / 2)
step = min(step, MaxWorker - len(runningWorkers))
  4. 执行：遍历 terminated workers，调用 apiKube.UpdateWorker 重启每个 Pod

7.4 缩容逻辑

条件（必须全部满足）：

  • Running 数量 > MinWorker
  • Worker 当前不忙
  • 空闲时间 > ScaleDownIdleTime

动作：调用 apiKube.DeleteWorker 删除合格的 Worker。

7.5 冷却机制

扩缩容记录存在 Redis ZSet 中（score = 时间戳）。每次操作前检查是否过了 ScaleCooldown 间隔。

keyPrefixAutoscalerRecord = "autoscaler_record::{env}::{workerType}::{taskMode}::{cluster}"

7.6 安全检查（防止雪球式过度扩容）

if pendingWorkers > 0 || terminatingWorkers > 0 {
    return  // 本轮跳过
}

为什么需要这个检查：因为 runningWorkers 只计 running 状态，pending 的 Pod 对 shouldScaleUp 不可见。没有这个检查，Autoscaler 每 30s 都会认为"Worker 不够"继续加。

八、初始化与数据恢复

每个 worker-scheduler 实例启动时（在 service.New() 中）：

  1. 并行加载：sync.WaitGroup 并发从 etcd 拉取所有 Worker（GetAllWorker）和所有 Task（GetAllTask）
  2. 恢复 Worker 缓存：填充 workerCache、cacheKeyManager（type/cluster 索引）、workerClusterMap（集群维度计数）
  3. 恢复并发计数：遍历所有 Task，每个在 concurrentManager 中 +1
  4. 启动 Watch：加载完成后才启动 watchWorker/watchTask 做增量更新
"先加载，再 Watch"模式：加载建立基线，Watch 处理后续变更。即使在加载和 Watch 启动之间发生了变化，Watch 事件会覆盖过期值（最终一致性）。

九、关键设计决策总结

问题选择原因
etcd vs Redis 各自角色etcd 做状态正确性（注册、强一致）；Redis 做吞吐量（队列、锁、扩缩容记录）不同语义用不同存储
Lease TTL 多长合适7200s太短（60s）：Grant 间隔 300s > TTL，导致误删。太长（24h）：崩溃恢复等 24h，用户任务槽"死锁"
etcd 集群宕机怎么办Watch 中断（5s 重试）、心跳 UpdateWorker 失败但 sidecar 不崩、新任务分配暂停、etcd 恢复后自动恢复、重启时 loadInitialData 保证最终一致优雅降级 + 自愈
为什么 Worker 用 Pull 不用 PushWorker 主动上报空闲 → scheduler 才下发天然背压，Worker 不会被打爆
