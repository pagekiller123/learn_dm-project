Scheduler 是什么？

核心使命
把 AI 生成任务（文生图、图生视频、3D 等）从用户提交到 GPU Worker 执行，全流程调度
一句话架构
Scheduler = Go 微服务集群 + Redis 任务队列 + MongoDB 记录中心 + etcd 注册中心 + K8s 服务发现 + dmfr 框架
技术栈速览
Go + dmfr微服务框架，统一 HTTP / 日志 / 错误码
Redis (ZSet)任务队列 + 乐观抢占 + 状态缓存
MongoDB任务记录中心（AppRecord）
etcdWorker/Task 运行态注册
Kafka任务结果通知下游（监控 / 统计）
K8s + Istio服务发现、流量路由、统一鉴权
Hertz / FiberHTTP 框架（新 Hertz / 老 Fiber）

五层架构总览

1外部请求层前端 / Monet 客户端 / 内部工具 → 组装请求、携带鉴权
↓
2业务服务层api-outer / app-gateway / 2d / story-board → 参数校验、鉴权、入队
↓
3基础设施层worker-scheduler → 拉队列、分配任务、回写结果、Autoscaler
↓
4Worker 执行层worker-sidecar + Workers → 执行推理、上报结果
↓
5外部供应商层ComfyUI / SD-WebUI / 火山 / Kling / Runway / Sora → 实际 AI 推理
核心原则：每层只做自己的事，不越界

三大核心组件

app-gateway
任务入口
1 权限校验 CheckAppAccess
2 参数映射 + 组件解析
3 Mongo 写 AppRecord
4 Redis 入队 + 返回 task_id
为什么不能绕过？
安全（唯一鉴权入口）
可观测（必须创建 AppRecord）
一致性（状态机依赖初始状态）
worker-scheduler
调度核心
多 Pod 并行，无 Leader 选举
Redis 拉任务 → Mongo 加载 → etcd 注册 → 下发
Worker Pull 模型
Worker 主动上报"我空闲了"
天然背压，Worker 不被打爆
worker-sidecar
异构适配器
Adapter Pattern
将调度逻辑与推理后端解耦
新增 AI 能力：
scheduler 代码不需要改
只需：
1. sidecar 新增 worker 实现
2. action 层处理参数映射

为什么需要三套存储？

Redis
短生命周期"待消费"队列
ZSet 排序（score = 时间戳）
不同优先级不同 Redis key
亚秒响应 /status 轮询
分布式锁
10W+ QPS · 微秒延迟
MongoDB
长生命周期"任务记录中心"
任务参数、状态、结果全量存储
AppRecord：查询、审计、计费
AppTaskMsg：完整任务消息
持久化 · 灵活查询
etcd
运行态"强一致注册中心"
Lease：TTL 自动过期清理
Watch：实时感知 Worker 上下线
Txn：乐观锁防并发覆盖
Raft 强一致
强一致 · 自动清理
核心原则：不同语义用不同存储，不要强求一套搞定 — 经典分布式系统取舍

Redis ZSet 队列与乐观抢占

ZSet 设计亮点
score = 毫秒时间戳 → 同优先级内 FIFO
member = user::taskID — 完整数据在 Mongo
ZRem 返回 ≥ 1 = 抢到了（原子操作，无需 Lua）
多个 scheduler 同时 ZRange 没关系 — 谁先 ZRem 谁赢
多队列 Key
apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}
priority=0 时省略 priority 段（向后兼容 5 段格式）
隔离不同 cluster · 独立限流 · 支持优先级调度 · 小队列 ZRange 更快
两轮扫描策略
第一轮 — 公平性
ZRange(0, 255) 批量扫描
逐个检查 GetUser() — 该用户有任务在跑？
有冲突 → 跳过，加入 queueJob
无冲突 → grabJob() 尝试 ZRem
第二轮 — 吞吐量
第一轮没抢到 → 遍历 queueJob
消费冲突任务，不让 Worker 空闲
经典的 公平性 vs 吞吐量 权衡

优先级调度与并发控制

WeightedScheduler 加权轮转
pri:2 w:5
pri:1 w:3
pri:0 w:2
每 10 次消费中：高 5 次 / 中 3 次 / 低 2 次
防饥饿机制
配额耗尽 → 重置 → 每轮至少消费 1 次
高优先级队列为空 → 低优先级立即有机会（降序兜底）
用户并发控制
ConcurrentManager
两个维度：taskMap（任务）+ userMap（用户）
CAS 原子操作 — 乐观、无阻塞
低竞争场景比 Mutex 性能更好
etcd Watch 驱动同步
新任务 → Watch Put → 所有 Pod +1
任务完成 → Watch Delete → 所有 Pod -1
最终一致：毫秒级延迟，对实际场景可接受

etcd 注册、心跳与故障检测

Put/Get/Delete基本读写删
Watch监听变化，实时推送
LeaseTTL 自动过期清理
Txn乐观锁事务
Key 格式 & 心跳
/worker/{env}/{podName} — Worker 注册
/task/{env}/{taskID} — Task 运行注册
Sidecar 每 30s 心跳 → Scheduler UpdateWorker（Txn 写回）
Grant 每 300s 重新创建 Lease · TTL = 7200s
故障检测链路
Worker 崩溃 → 心跳停止 → Lease 过期 → Watch Delete → 缓存清理 + 计数恢复

Worker 生命周期与 Autoscaler

Worker 状态机
pending → running → terminating → terminated
recovering — 推理进程重启中
terminated / terminating 不参与任务分配
优雅关闭（两阶段）
1. K8s 发送 SIGTERM
2. 停止接收新任务
3. 上报 shutdown → status=terminating
4. 等待已有任务完成（最长 10 分钟）
5. 上报 exit → status=terminated
自定义 Autoscaler vs HPA
HPA 看 CPU / Memory → 看不到 GPU 任务队列长度
自定义 Autoscaler 直接读 MongoDB 队列长度决策
30s 定时 + Redis 分布式锁
扩容
Worker = 0 → 必须扩
Worker ≤ 队列/2 → 扩
唤醒 terminated Worker
缩容
Running > MinWorker
Worker 当前不忙
空闲 > IdleTime
安全检查：有 pending / terminating Worker 时跳过 → 防雪球

关键设计决策总结

三套存储各司其职Redis 吞吐（队列+缓存） · MongoDB 持久（记录+审计） · etcd 一致性（注册+Watch）
Worker Pull 模型Worker 主动上报空闲 → 天然背压 → Worker 不会被打爆
多 Pod 并行 + 乐观抢占etcd Watch 同步状态 + Redis ZRem 竞争任务 → 无需 Leader 选举
两轮扫描第一轮公平性优先（跳过冲突用户） · 第二轮吞吐量兜底（不让 Worker 空闲）
先加载再 Watch启动时从 etcd 全量加载建立基线 → 然后 Watch 增量更新 → 最终一致性
不同语义用不同存储
不同场景用不同策略
