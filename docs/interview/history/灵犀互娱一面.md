### 硬伤 2：SSE 全链路逻辑漏洞（全场最致命）

**这是整场最值得复盘的一段**。面试官的追问链是这样的：

- 客户端 ↔ 本机服务端：SSE（流式）

- 本机服务端 ↔ 云端：普通 HTTP RESTful（短连接 \+ 轮询）

然后他抛出一个非常尖锐的矛盾：

> "你 PC 上的服务端和服务器端的服务端不是流式协议，那客户端和 PC 上的服务端走流式协议还有什么意义？正常要流式也应该是全链路流式，才能一个 token 一个 token 往外吐。"
> 
> 

你的回答是："印象中会不断轮询……应该是流式结果……这个我没有考虑过。"

**问题出在哪**：轮询是拉模式，拿到的是**一次性响应体**；流式推送是推模式，才能逐 token 吐。"轮询"和"流式结果"这两个词在逻辑上是冲突的，你当时没有察觉这个自相矛盾，等于在面试官面前暴露了对**端到端数据流的理解盲区**——你自己系统里 token 是怎么从 LLM 一路流到用户屏幕的，你并没有真正掌握。

**帮你想清楚正确理解（二面如果被追问，按这个答）**：

这其实有两种自洽的架构，你当时应该先分清是哪一种：

- **方案 A（全链路流式，体验最优）**：本机服务端到云端 LLM 网关也应该走流式（SSE 或 WebSocket 或 HTTP chunked），云端逐 token 吐，本机服务端做**透传 \+ 事件翻译**，这样客户端看到的才是真正的逐 token 流。此时本机服务端不是"轮询"，而是把上游流式响应转发给下游 SSE。

- **方案 B（本机端是事件代理，非 token 级流式）**：如果本机到云端确实是短连接轮询，那客户端 SSE 推送的其实不是"token 流"，而是**任务状态事件流**（任务开始 / 进度 / 完成），和逐 token 输出是两回事。这时要诚实承认：SSE 的语义是"服务端主动推送事件"，而非"LLM 流式输出"，两者要分开说。

**你当时最该做的**：不要答"没考虑过"。哪怕一时想不清，也应该说"这里确实有个设计取舍：如果云端是非流式轮询，客户端 SSE 推送的其实是任务状态事件而非 token 级流式；真正的 token 级流式需要云端到本机也走流式，这部分的链路我可以再核实下"。**主动承认设计边界 \+ 给出分析框架，远比"没考虑过"强。**

同时补一个概念澄清：**"轮询 \+ 一次性响应"和"SSE 逐 token 流"是不可能共存的**。如果你实际实现里云端返回的是 SSE 兼容响应（HTTP 流式），那本机端到云端其实也是"流式 HTTP"，只是你没意识到它和 SSE 同源。去查一下你们云端 LLM 网关的返回格式，把这个链路彻底弄明白，这会是二面你能主动讲的亮点。
