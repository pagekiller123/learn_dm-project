2.1 DreamMaker 平台定位

DreamMaker 是网易互娱内部的 AI 美术平台，目标是把市面上的 AI 模型（文生图、图生视频、3D生成、语音等）统一封装成内部服务，让游戏美术师通过智能体交互完成创作，从"亲手画"转变为"驾驭 AI Agent 操作"。

2.4 各层技术选型 WHY

组件选型为什么
Agent 框架LangGraph原生状态机 + Checkpointer 持久化 + interrupt 人机交互，比 LangChain AgentExecutor 更灵活可控
Agent 服务FastAPI + Asyncio原生 async 支持 SSE 长连接，性能优于 Flask
网关/调度Go + Hertz/Fiber高并发低延迟，适合 IO 密集的任务分发

三、面试易错点

致命错误 1：自我介绍流水账念简历。面试官已经看过简历，重复念一遍浪费时间。应该提炼 2-3 个技术亮点，用一句话概括每个。
致命错误 2：讲五层架构时只讲调度不讲 Agent，或只讲 Agent 不讲调度。必须讲清楚两者如何打通——Agent 的工具调用如何变成调度平台的任务。
致命错误 3：被问"为什么选 Agent 不选算法"时贬低算法岗。正确话术是"两者都有价值，我选择 Agent 是因为我的技能组合和职业兴趣更匹配工程侧"。
致命错误 4：被追问"LangGraph 换掉你还能做吗"时心虚。要展示对底层原理的理解——状态机本质就是 while 循环 + 状态字典 + 条件路由，框架只是封装。

Q4：DreamMaker 五层微服务架构详解

满分逐字稿（核心重点题）

面试标准逐字稿

DreamMaker 采用五层微服务架构，从上到下分别是：外部请求层、业务服务层、基础服务层、Worker 执行层、外部供应商层。我按请求链路从上往下讲。

第一层是外部请求层，包括 Monet 桌面客户端和 DreamMaker 主站 Web 前端。Monet 客户端是 Electron 应用，内嵌了我做的 Agent 服务，用户在画布上对话，Agent 理解意图后调用工具。主站是 Web 端，提供更完整的项目管理和素材管理功能。两个入口都通过 HTTP 请求打到下一层。

第二层是业务服务层，核心组件是 app-gateway。它负责三件事：任务入口接收、参数校验、入队。当 Agent 决定生成一张图片时，它调用 generate_node 工具，这个工具实际上是向 app-gateway 发 HTTP POST 请求。Gateway 校验参数合法性、检查用户配额，然后把任务写入 Redis ZSet 队列，同时在 MongoDB 创建任务记录，返回 task_id。这一层还有其他业务服务处理用户管理、项目管理等非 AI 任务。

第三层是基础服务层，核心是 worker-scheduler。它负责任务消费和分配。当前版本采用多 Pod 并行部署，多个 scheduler 实例同时消费 Redis 队列，通过 ZRange+ZRem 的原子操作天然去重（只有一个实例能 ZRem 成功），无需 Leader 选举。分配时根据 Worker 类型匹配和负载情况，把任务推送给对应的 Worker Sidecar。这一层还依赖 etcd 做服务注册发现和配置管理，Redis 做任务队列，MongoDB 做任务持久化。

第四层是 Worker 执行层，核心是 worker-sidecar。它是一个统一的任务执行进程，内部通过 Worker 接口做策略模式路由——每个 sidecar 实例启动时向 worker-scheduler 注册，拿到自己的 workerType（比如 kling、tripo、openai），然后在接收到任务时实例化对应的 Worker 实现。所有 Worker 实现（图像、视频、3D、腾讯混元、火山引擎、语音、LLM、工具类、工作流、桌面软件，共 10 大类）都编译在 sidecar 同一个二进制里，通过接口多态而非进程间通信来解耦。sidecar 框架统一负责任务拉取、进度上报、结果回写和 panic 恢复，具体的 AI 调用逻辑由各 Worker 实现封装。部署上用 K8s StatefulSet，因为 Worker 需要稳定的网络标识来和 scheduler 的注册信息对应，而且缩容时需要有序地从最大序号开始下掉空闲节点。

第五层是外部供应商层，包括 Stable Diffusion、腾讯混元、火山引擎、OpenAI 等。Worker 通过 HTTP/gRPC 调用这些外部 API。因为供应商接口不稳定，经常返回 429 限流，所以我在这一层设计了指数退避重试+备用供应商切换的容错降级策略。

整个链路打通来看：用户在画布上说"生成一张图"→ Agent 推理选择工具 → 工具调用 app-gateway 入队 → scheduler 消费分配 → Worker 调用供应商 → 结果回传 → Agent 通过 SSE 推送给前端渲染。这是我实际参与的端到端链路，Agent 侧和调度侧我都有代码贡献。

追问防御

追问1：你说 Agent 侧和调度侧都参与了，具体哪些是你写的？

回答：Agent 画布侧我是主要开发者，三层上下文、SSE 协议、HITL 引擎都是我设计和实现的。调度侧我是"参与"角色，主要贡献在优先级队列的加权轮询调度算法和供应商容错降级模块，整体架构是团队 senior 设计的，我在理解架构的基础上负责具体模块的实现和优化。

追问2：这个架构有什么不足？

回答：目前有几个技术债。一是旧版 scheduler 采用 K8s Lease Leader 选举做高可用，当前 worker-scheduler 虽然改成了多 Pod 并行消费，但 Autoscaler（自动扩缩容）模块仍用 Redis 分布式锁做串行化，高峰期锁竞争可能成为瓶颈，后续可以考虑分片或优化锁粒度。二是 Agent 侧的 Checkpointer 用的是本地 SQLite——因为 Monet Agent 是随桌面客户端打包的本地服务，SQLite 在单用户场景下完全够用；但局限是数据绑定在本机，用户换机器或重装后历史对话无法迁移，如果未来要做云端 Agent 服务则需要换成 PostgreSQL 等远程存储。三是 Agent 提交任务后通过 while 循环轮询（submit → poll → fetch_result）获取结果，每次 poll 是非阻塞的 HTTP GET 立即返回，但轮询本身会持续 sleep + 重试直到终态，理想方案是调度侧主动回调或推送通知，减少无效请求。
