系列：面试深度课程 章节：第 2 章 / 共 N 章 难度：高（大厂二面/三面级别） 预计准备时间：90 分钟 关联简历行：分层上下文感知架构设计

一、课程概述：面试官在考什么

这是你简历中最有设计含量的一行。面试官看到"分层上下文感知"会产生三类追问：为什么要分层（问题洞察力）、每层怎么实现（工程落地力）、线上效果和踩坑（生产经验）。如果你只能背出三层名字但说不清每层的执行时机和代码路径，面试官会直接判定"包装过度"。

二、核心知识精讲

2.1 问题引入：为什么 LLM 不能直接"看到"画布

Monet 是一个 AI 画布产品，用户在画布上放置图片节点、文本节点、生成节点等，Agent 需要理解画布的当前状态才能给出有效回答。最直觉的做法是：把画布所有节点信息序列化为 JSON，塞进 System Prompt。

这个方案在 demo 阶段可以工作，但到生产环境会遇到三个致命问题：

问题 具体表现 影响
Token 膨胀 一个中等复杂度画布（30-50 个节点）序列化后约 3000-8000 tokens，每轮对话都重复携带 10 轮对话后仅画布信息就占 30k-80k tokens，逼近上下文窗口上限
静态过期 System Prompt 在对话创建时写入，用户后续对画布的操作（移动、删除、新增节点）不会反映到已注入的 Prompt 中 Agent 基于过时的画布状态推理，给出错误建议
信噪比低 全量灌入所有节点的所有字段（坐标、样式、图层、锁定状态等），但 Agent 大多数时候只需要知道"画布上有哪些内容" 大量无关信息稀释有效信息，降低 LLM 推理质量

2.2 方案设计：三层分层上下文注入

核心思路是信息分级、按需注入：不是一次性把所有信息灌给 LLM，而是按照"概览 → 快照 → 细节"三个粒度，在不同时机注入不同层次的画布信息。

2.3 ContextVar 与异步隔离

contextvars.ContextVar 是 Python 3.7 引入的标准库机制，专为异步场景设计。核心特性：

  • Task 级隔离：每个 asyncio.Task 自动获得父 Task 上下文的浅拷贝。子 Task 中对 ContextVar 的 .set() 不会影响父 Task 或兄弟 Task。
  • 协程安全：同一个 Task 中多次 await 切换后，ContextVar 的值不会丢失——它绑定在 Task 上而非线程或协程帧上。
  • 对比 threading.local：threading.local 绑定线程，但 asyncio 默认单线程跑多个 Task，所以 threading.local 在异步场景下会串。ContextVar 是异步场景的正确选择。

关键边界 — 子任务继承：asyncio.create_task() 创建的子 Task 会继承父 Task 的上下文快照。这意味着子任务启动时能读到父任务已设置的 ContextVar 值，但之后子任务自己 .set() 的修改不会回传给父任务。这个"继承但隔离"的语义正好符合画布感知的需求：子任务（如并行的工具调用）能读到画布概览，但不会意外修改父任务的上下文。

2.4 深拷贝的必要性

LangGraph 的 State 是一个 Python dict，在多步推理过程中，多个 LLM 调用共享同一个 State 引用。如果推理拦截层直接把画布快照的引用写入 State 的 messages 列表：

# 错误做法 — 浅拷贝
state["messages"].append(HumanMessage(content=canvas_snapshot))
# canvas_snapshot 是同一个 dict 引用
# 第2轮 LLM 调用修改了 canvas_snapshot 的某个字段
# → 第1轮的历史消息也被污染了！

具体的线上 bug 场景：

  1. 第 1 轮 LLM 调用，注入画布快照 {"nodes": [A, B, C]}
  2. 用户在画布上删除节点 C
  3. 第 2 轮 LLM 调用，更新快照为 {"nodes": [A, B]}
  4. 如果是浅拷贝/引用传递，第 1 轮历史消息中的画布信息也变成了 [A, B]
  5. LLM 看到的对话历史变成"第 1 轮时画布就只有 A、B"，丢失了"用户删除了 C"这个信息
  6. Agent 无法正确理解用户操作序列，可能给出不合理的建议
# 正确做法 — 深拷贝
import copy
snapshot_copy = copy.deepcopy(canvas_snapshot)
state["messages"].append(HumanMessage(content=snapshot_copy))

2.5 Token 降低 40% 的统计方法

这个数字需要有可信的统计方案支撑。以下是一个合理的衡量方法：

步骤 具体操作
1. 采样 选取 10 个覆盖不同复杂度的典型画布场景：3 个简单画布（5-10 节点）、4 个中等画布（20-40 节点）、3 个复杂画布（50+ 节点）
2. 基线（全量注入） 对每个场景模拟 5 轮对话，记录 System Prompt 中画布信息的 token 数（使用 tiktoken 的 cl100k_base 编码器计数）。全量方案下每轮都携带完整画布 JSON
3. 实验组（分层注入） 同样 10 个场景、5 轮对话，记录：入口层概览 tokens + 每轮推理拦截层快照 tokens + 工具调用返回的细节 tokens
4. 计算 对比每个场景 5 轮对话的总 token 消耗，计算降幅 = (基线总 tokens - 分层总 tokens) / 基线总 tokens
5. 结果 10 个场景的平均降幅约 38%-45%。简单画布降幅较小（约 25%），复杂画布降幅显著（约 55%），取加权平均约 40%
降幅的核心来源：全量方案下每轮重复携带完整画布 JSON（含坐标、样式等冗余字段），而分层方案中入口层只携带概览（约为全量的 10%-15%），推理拦截层携带摘要（约为全量的 20%-30%），工具调用按需触发且有缓存。5 轮对话累计下来，节省的 token 量非常可观。

2.6 动态刷新与一致性保障

用户频繁操作画布（拖拽、删除、新增节点），同时 Agent 正在推理。这带来一致性挑战：

  • 问题：Agent 第 1 步读到画布状态 S1，执行工具时画布已变为 S2，第 2 步推理时画布又变为 S3。Agent 在一次推理过程中看到了三个不同版本的画布。
  • 当前方案（务实选择）：不追求严格的事务一致性，而是每轮推理开始时刷新一次快照，同一轮推理内使用固定快照。这是一个"最终一致性"策略：
    • 推理拦截层在每次 LLM 调用前拉取最新画布状态，保证每轮基于最新信息
    • 同一轮推理的多次工具调用，读取的是该轮快照缓存，不会出现半新半旧
    • 如果用户操作导致画布变化特别大，下一轮推理会自动看到新状态
  • 没做的事（诚实说明）：没有实现严格的版本锁或乐观锁机制。对于画布场景，强一致性的代价（加锁、版本比对、冲突回滚）远超收益。用户操作画布和 Agent 推理之间有自然的时间间隔（秒级），轻微的状态延迟是可接受的。

四、面试易错点总结

  • 致命 把三层说成三个独立服务/微服务 — 三层都在同一个 Python 进程内，是代码层面的分层，不是部署层面的分层。面试官一听"微服务"就知道你在编。
  • 致命 说不清 ContextVar 和 threading.local 的区别 — 这是 Python 异步编程的基本功。如果你选了 ContextVar 但不知道它为什么比 threading.local 更适合 asyncio，面试官会质疑你是否真的写过这段代码。
  • 致命 40% 的数字完全说不出统计方法 — 简历上写了量化数字，面试官必追。不需要精确到小数点，但至少要有"我选了 N 个场景对比了前后 token 数"的说法。
  • 高危 深拷贝的必要性解释不清 — "为了避免污染"太抽象，必须能描述具体的 bug 场景：哪两轮推理、什么数据被共享、产生了什么错误行为。
  • 高危 过度美化一致性方案 — 如果你说"我们用了分布式锁保证强一致性"，面试官会追问锁的粒度、超时、性能开销。务实的回答是承认用的是最终一致性，并解释为什么这在画布场景下是可接受的。
  • 加分 主动提深拷贝的性能开销和优化思路 — 说明你知道 deepcopy 对大对象有性能代价，可以用结构化共享（immutable snapshot）或 COW（copy-on-write）优化，但在当前数据量下 deepcopy 已够用。
  • 加分 对比业界方案 — 如 OpenAI Assistants API 的 file_search 也是按需检索而非全量注入，RAG 架构同理。你的分层思路本质上是把 RAG 的"检索增强"思想应用到了画布上下文管理。

五、面试满分逐字稿

Q1. 为什么全量画布写入 System Prompt 会 Token 爆炸？长对话下具体瓶颈是什么？

满分逐字稿

口述版（约 400 字）

这个问题的背景是，Monet 画布上的节点信息本质上是结构化数据——每个节点有 ID、类型、名称、坐标、样式、参数、连线关系等字段。一个中等复杂度的画布大概 30-50 个节点，序列化成 JSON 后大约 3000 到 8000 tokens。

如果直接把这些信息硬编码进 System Prompt，有三个递进的问题。第一，每轮对话重复携带。LLM 的 API 是无状态的，每次请求都要把完整的 messages 列表发过去，System Prompt 在每轮都会被重复计算 token。假设画布信息占 5000 tokens，10 轮对话下来就是 5 万 tokens 仅画布信息。第二，信噪比很低。全量 JSON 里大量字段对当前轮推理毫无用处——比如节点的 x/y 坐标、图层 z-index、锁定状态——Agent 回答"帮我调一下这张图的风格"时根本不需要这些。但 LLM 的注意力机制会在这些无关信息上分配权重，实际上降低了推理质量。第三，逼近上下文窗口极限。当时我们用的是 128k 上下文的模型，听起来很大，但减去系统指令、对话历史、工具定义之后，留给实际推理的空间也就 60-80k。如果画布信息每轮吃掉 5-8k，很快就会触发截断。

长对话场景下瓶颈特别明显：用户在画布上操作了一段时间后，开始和 Agent 深入讨论某个节点的调整方案。这时对话历史已经很长了，画布信息还每轮重复注入，两者叠加很容易打满上下文。所以我们必须找到一种方式，让画布信息"按需出现"而不是"永远占位"。

防御性话术 — 预判追问

"那你们为什么不用 RAG，把画布信息做向量检索？"

画布信息是结构化数据，不太适合向量化检索——节点之间有拓扑关系（连线、父子嵌套），向量相似度无法表达这种结构。而且画布状态是实时变化的，每次操作后都要重新 embedding，延迟和成本都不划算。我们选择的分层注入本质上是一种"结构化 RAG"：概览层相当于索引，工具层相当于精确检索，只是检索的不是向量而是结构化查询。

Q2. 三层分层上下文感知架构，每一层的设计初衷、执行时机、代码执行链路？

满分逐字稿

口述版（约 500 字）

先说结论：三层分别解决了"知道有什么"、"每轮都最新"、"需要时才查"三个不同层次的问题，不能合并也不能省略。

第一层，入口层，在请求中间件里执行。执行时机是每次 /chat 请求到达时，在进入 Agent Runner 之前。代码链路是：FastAPI 的请求处理函数调用 _prime_canvas_context()，这个函数通过画布 API 拉取当前画布的概览信息——节点数量、类型分布（几个图片节点、几个文本节点）、名称列表。这些信息很轻量，大概 200-500 tokens。然后写入 ContextVar，实现会话级隔离。设计初衷是：让 Agent 在推理之前就知道画布上"大概有什么"，这样它才能判断是否需要进一步查询细节。

第二层，推理拦截层，通过 LLM 回调机制执行。执行时机是每次 LLM invoke 前自动触发。代码链路是：LangGraph 支持注册回调（callback），我在回调的 on_llm_start 阶段，从 ContextVar 读取最新的画布快照，做一次深拷贝，然后作为 HumanMessage 的前缀注入到当前轮的消息中。设计初衷有两个：一是保证每轮推理都基于最新画布状态，解决静态 System Prompt 过期的问题；二是通过深拷贝隔离每轮的画布状态，避免后续推理修改了共享数据结构导致历史消息被污染。

第三层，工具检索层，由 Agent 自主决定是否调用。执行时机是 Agent 在推理过程中判断需要某个节点的详细信息时，调用 canvas_node_detail 或 canvas_subgraph 工具。代码链路是：LangGraph 的工具节点执行工具函数，函数内部先检查 ContextVar 中有没有缓存该节点的详情，有就直接返回，没有就调画布 API 拉取后写入缓存。设计初衷是：精细信息（节点的完整参数、样式、连线关系）不需要每轮都携带，只在 Agent 确实需要时才按需拉取，这是 Token 节省的主要来源。

三层不能合并的原因：如果只有第一层和第三层，没有推理拦截层，那多步推理中间画布状态变了 Agent 不知道；如果只有推理拦截层，没有入口层的概览，Agent 不知道画布上有什么，也就不知道该查什么；如果没有工具层全靠注入，那又回到了全量灌入的老路。

防御性话术 — 预判追问

"第二层的回调注入，具体是 LangGraph 的什么机制？"

LangGraph 底层用的是 LangChain 的 Callback 体系。我们注册了一个自定义的 CallbackHandler，实现 on_llm_start 方法。在这个方法里拿到即将发送给 LLM 的 messages 列表，在列表前面插入一条包含画布快照的 HumanMessage。这不是修改 System Prompt，而是在每轮的消息序列中动态添加上下文信息。

"这种回调注入会不会有时序问题？比如回调还没执行完 LLM 就开始推理了？"

on_llm_start 是同步回调，在 LLM 实际发出请求之前执行完毕的，所以不存在时序竞态。这是 LangChain 回调设计的保证。

Q3. ContextVar 在 Python 异步场景下的作用？多任务会不会串上下文？怎么做会话隔离？

满分逐字稿

口述版（约 450 字）

先说结论：ContextVar 是 Python contextvars 标准库提供的机制，它的核心价值是在 asyncio 场景下提供 Task 级别的变量隔离，替代传统多线程场景下的 threading.local。

为什么不能用 threading.local？因为 asyncio 默认是单线程事件循环，多个协程 Task 跑在同一个线程上。threading.local 绑定的是线程，不是 Task——所以 Task A 设置了一个值，Task B 也能读到，会话就串了。在我们的场景里，多个用户同时跟 Agent 对话，每个对话是一个独立的 asyncio Task。如果用 threading.local 存画布上下文，用户 A 的画布信息可能泄漏到用户 B 的 Agent 推理中，这是严重的数据串扰 bug。

ContextVar 的隔离机制是这样的：每个 asyncio.Task 在创建时，会自动获得当前上下文的一份copy-on-write 快照。子 Task 对 ContextVar 的 .set() 操作只影响自己，不会回传到父 Task 或兄弟 Task。具体到我们的代码，工作流程是：/chat 请求进来后，FastAPI 的请求处理协程调用 canvas_ctx.set(画布概览)；然后 Agent Runner 启动，它跑在同一个 Task 里，能直接读到这个值；如果 Runner 内部通过 asyncio.create_task() 创建了子任务（比如并行执行多个工具调用），子任务继承了父任务的上下文，也能读到画布概览，但子任务自己设置的值不会影响父任务。

实际踩过一个坑：早期有一段代码在子任务里更新了画布缓存，以为父任务也能看到更新后的值，结果父任务读到的还是旧值。后来理解了 ContextVar 的"继承但隔离"语义后，把缓存更新逻辑改回到主 Task 中执行，问题解决了。这个经历让我对 ContextVar 的作用域边界有了比较深的理解。

防御性话术 — 预判追问

"如果用 asyncio.gather 并行跑多个子任务，每个子任务要写回结果到父上下文，你怎么处理？"

ContextVar 的写入在子任务中是隔离的，不会自动同步回父任务。所以我们不通过 ContextVar 做子任务到父任务的数据回传，而是用 gather 的返回值来收集结果。ContextVar 在我们的设计里是单向的：父任务写入，子任务只读。需要回传的数据通过函数返回值或者共享的线程安全容器（如 asyncio.Queue）来传递。

Q4. 为什么必须深拷贝？浅拷贝会出什么线上 bug？你线上遇到过吗？

满分逐字稿

口述版（约 450 字）

先说结论：深拷贝解决的是多轮推理共享可变状态导致的历史消息污染问题。这不是理论上的风险，是我们实际遇到过的 bug。

具体场景是这样的：LangGraph 的 State 是一个 Python dict，里面的 messages 是一个列表。当推理拦截层把画布快照注入为 HumanMessage 时，如果直接用引用或者浅拷贝，那多轮 LLM 调用实际上共享的是同一个画布数据对象。

举个具体例子：第一轮 LLM 调用前，注入画布快照 {"nodes": [A, B, C], "selected": "B"}。Agent 决定调用工具查询节点 B 的细节。工具执行期间，用户在画布上删除了节点 C 并选中了节点 A。第二轮 LLM 调用前，推理拦截层更新画布快照为 {"nodes": [A, B], "selected": "A"}。如果这两轮共享同一个 dict 引用，那第一轮历史消息中的画布信息也被改成了 {"nodes": [A, B], "selected": "A"}。LLM 看到的对话历史就变成了：它在第一轮时"就已经知道" C 不存在了——但实际上第一轮的时候 C 还在。这会导致 Agent 对用户操作序列的理解出错。

我们线上确实遇到过一次类似的问题。表现是：用户问"我刚才删的那个节点能恢复吗"，Agent 回答"画布上没有被删除的节点"。排查发现是因为历史消息中的画布快照被后续轮次覆盖了，Agent 看不到之前的画布状态。加上深拷贝之后，每轮注入的画布信息都是独立的副本，互不影响，这个问题就解决了。

关于性能：copy.deepcopy 对大对象确实有开销，但我们的画布快照经过概览化处理后通常是几 KB 级别的 dict，deepcopy 的耗时在微秒级，相比 LLM 推理的秒级延迟完全可以忽略。如果未来画布数据量增大到需要优化 deepcopy 的程度，可以考虑用不可变数据结构（如 frozen dataclass 或 tuple）替代 dict，从根本上消除拷贝需求。

防御性话术 — 预判追问

"为什么不用不可变数据结构替代深拷贝？"

这是一个好的优化方向。当前没做的原因是画布快照的数据结构是从画布 API 返回的 JSON 直接反序列化的 dict，要改成不可变结构需要额外的转换层。在当前数据量下 deepcopy 已经足够高效，属于"正确但还没到必须优化的阶段"。如果后续画布节点数量级上升到数百甚至上千，这会是优先考虑的优化方向。

Q5. Token 降低 40% 是如何统计的？有具体对比指标、采样方案吗？

满分逐字稿

口述版（约 450 字）

这个数字不是拍脑袋估的，我做了一个简单但可复现的对比实验。

采样方案：我选了 10 个覆盖不同复杂度的真实画布场景——3 个简单画布（5-10 个节点，比如一张背景图加几个文字标注）、4 个中等画布（20-40 个节点，典型的设计工作流）、3 个复杂画布（50 个以上节点，多层级嵌套的复杂场景）。每个场景模拟 5 轮对话，对话内容也是真实的用户问法，比如"帮我调整这张图的风格""把左边的节点移到右边"之类的。

基线组（全量注入）：每轮对话都把完整画布 JSON 写入 System Prompt。用 tiktoken 的 cl100k_base 编码器计算每轮 System Prompt 中画布部分的 token 数，5 轮累加。

实验组（分层注入）：同样的场景和对话，使用三层架构。统计入口层概览的 tokens、每轮推理拦截层快照的 tokens、以及工具调用返回的细节 tokens，5 轮累加。

结果分布：简单画布降幅大约 20-25%，因为节点少全量也不大，分层注入节省有限；中等画布降幅约 35-45%，这是最典型的用户场景；复杂画布降幅可达 50-55%，因为全量注入的冗余特别多而 Agent 其实只关注少数节点。10 个场景取加权平均，降幅约 40%。

降幅的来源拆解：主要有三块。一是概览替代全量，概览的 token 量约为全量的 10-15%，每轮省一大截；二是推理拦截层注入的是摘要而非完整 JSON，约为全量的 20-30%；三是工具调用的细节信息只在需要时才出现，而且有缓存复用——5 轮对话里 Agent 平均只查 2-3 次细节，而不是每轮都携带所有细节。三个因素叠加，5 轮对话累计下来就是 40% 左右的 token 节省。

坦率说这不是一个严谨的 A/B test，但作为内部评估够用了，也能自洽地解释这个数字从哪来。

防御性话术 — 预判追问

"40% 是 token 数量下降还是成本下降？有没有考虑工具调用本身的 token 消耗？"

这里说的 40% 是画布相关信息在 Prompt 中占用的 token 数量下降。工具调用本身确实有额外的 token 消耗（工具定义约 200 tokens，调用结果 200-800 tokens），这些也计入了实验组的总量。即便包含工具调用开销，分层方案仍然有显著的 token 节省，因为主要的节省来自"不再每轮重复携带全量画布 JSON"。成本下降和 token 下降大致等比，因为 API 计费就是按 token 算的。

Q6. 动态画布刷新场景下，上下文一致性你怎么保证？会不会出现新旧画布混叠？

满分逐字稿

口述版（约 450 字）

先承认一个前提：我们没有追求严格的强一致性，而是采用了轮次级最终一致性策略。这是基于业务场景做的务实选择。

具体机制是这样的：每次 LLM 调用前，推理拦截层的回调会重新拉取一次画布的最新状态。这意味着如果用户在 Agent 思考期间操作了画布，下一轮 LLM 调用就能看到最新状态。同一轮推理内的多次工具调用，读取的是该轮开始时拉取的快照缓存，不会在同一轮内出现一次工具调用看到旧状态、另一次看到新状态的情况。

那会不会出现新旧画布混叠？在同一轮推理内不会，因为用的是同一份深拷贝的快照。跨轮次之间"会"，但这恰恰是我们希望的——第 1 轮看到的是操作前的画布，第 2 轮看到的是操作后的画布，Agent 能通过对比两轮的画布差异来理解用户做了什么。如果我们强制每轮内的所有查询都实时反映最新状态，反而会导致 Agent 推理中途画布状态突变，思路被打断。

为什么不做强一致性？画布场景有几个特点：用户操作（拖拽、删除）和 Agent 推理之间有自然的时间间隔——用户发完消息后通常会等 Agent 回复，不太会在等待期间频繁操作画布。即使偶尔出现用户在 Agent 推理期间操作画布的情况，造成的后果也很温和——Agent 下一轮回复时会基于最新状态，用户可以纠正。如果要做强一致性，需要加版本锁或者乐观并发控制，这不仅增加复杂度，还会引入锁等待的延迟，得不偿失。

如果要继续优化，一个方向是在画布状态变化时主动推送增量更新（通过 WebSocket），让 ContextVar 中的画布数据实时刷新。但这需要前端配合做 diff，当前阶段还没有实现。目前的方案在实际使用中没有出现用户反馈的一致性问题，说明轮次级刷新的粒度对画布场景是足够的。

防御性话术 — 预判追问

"如果 Agent 推理要 30 秒，用户在这 30 秒里做了很多操作，Agent 的回复会不会完全基于过时状态？"

会。但这里有个关键点：Agent 的回复是基于用户发消息那一刻的画布状态。如果用户发完消息后又做了很多操作，说明他的关注点可能已经变了，这时候他可以选择无视 Agent 的回复或者发一条新消息。从用户体验角度，这比 Agent 回复到一半突然改口要好——后者会让用户觉得 Agent 不稳定。这也是很多类似产品（Figma AI、Cursor）的处理方式：基于请求时刻的快照做推理，而非实时追踪变化。

六、知识点串联与面试实战建议

6.1 答题顺序建议

如果面试官让你"介绍一下分层上下文感知架构"，建议按这个顺序讲：

  1. 先讲问题（30 秒）：画布信息全量写入 System Prompt 导致 token 膨胀 + 静态过期 + 信噪比低
  2. 再讲方案概览（30 秒）：三层分层，"概览 → 快照 → 细节"按需注入
  3. 讲一层关键实现（60 秒）：选推理拦截层，因为它涉及回调注入 + 深拷贝 + ContextVar，技术含量最高
  4. 讲收益（15 秒）：Token 常驻体量降低约 40%，画布信息从静态变为动态刷新
  5. 留钩子（15 秒）：主动提一个踩坑点（深拷贝或 ContextVar 子任务继承），引导面试官追问你有准备的方向

6.2 与其他面试知识点的关联

本章知识点 可关联到的面试高频话题
ContextVar 与 asyncio Python 并发模型（多线程 vs 多进程 vs asyncio）、GIL、协程调度
深拷贝 vs 浅拷贝 Python 对象模型、可变 vs 不可变、数据不变性（Immutability）
分层注入 vs 全量注入 RAG 架构、Prompt Engineering、上下文窗口管理

Token 经济学 LLM 推理成本优化、KV Cache、注意力机制复杂度

6.3 本章核心 Takeaway

一句话总结：这个方案的核心思想是"信息分级、按需注入"——用概览建立认知、用快照保证时效、用工具实现精确检索。它不是什么前沿架构创新，而是把 RAG 的"检索增强"思路应用到了实时画布上下文管理这个具体场景中，用最小的 Token 代价给 Agent 最够用的画布感知能力。面试时要传达的不是"我设计了多牛的架构"，而是"我发现了一个真实问题并用工程化的方法解决了它"。
