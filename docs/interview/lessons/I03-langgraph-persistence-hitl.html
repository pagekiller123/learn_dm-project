二、核心知识精讲

2.1 LangGraph 执行机制与状态机原理

2.1.1 StateGraph 核心模型

LangGraph 的核心是 StateGraph：用 TypedDict 或 Pydantic Model 定义 State 结构，节点(Node)是普通函数或协程，边(Edge)定义路由逻辑。整个执行本质是一个 while 循环驱动的有限状态机。

# LangGraph 伪代码：核心执行循环
def stream(graph, input, config):
    state = input                       # 初始化 State
    current_node = START                 # 从 START 节点开始
    while current_node != END:          # while 循环驱动
        node_fn = graph.nodes[current_node]
        try:
            update = node_fn(state)     # 执行节点函数
            state = merge(state, update) # 合并状态更新
            checkpointer.put(state)     # 持久化 checkpoint
        except GraphInterrupt:
            checkpointer.put(state)     # interrupt 也要保存
            return                      # 中断循环，等待 resume
        current_node = router(state)    # 路由到下一节点
    return state

关键设计决策：

  • State 是不可变传递的：每个节点接收当前 State 的副本，返回 partial update，由框架负责 merge。这避免了节点之间直接修改共享状态导致的竞态。
  • Reducer 机制：State 字段可以指定 reducer（如 Annotated[list, add_messages]），控制同一字段多次更新的合并策略（追加 vs 覆盖）。
  • 条件路由：add_conditional_edges 根据当前 State 动态决定下一个节点，实现分支逻辑。

2.2 Checkpointer 持久化机制

2.2.1 Checkpointer 工作原理

Checkpointer 是 LangGraph 的持久化抽象层。每次节点执行完成后，框架自动调用 checkpointer.put() 将当前 State 序列化并写入存储。恢复时通过 thread_id 查询最近的 checkpoint 加载 State，从断点继续执行。

# Checkpointer 核心接口
class BaseCheckpointSaver:
    def put(self, config, checkpoint, metadata, new_versions):
        """每个节点执行后自动调用，写入序列化的 State"""
        ...
    def get_tuple(self, config):
        """按 thread_id 查询最近的 checkpoint"""
        ...
    def list(self, config, *, before, limit):
        """列出历史 checkpoint，支持回溯"""
        ...

存储层可选实现：

实现适用场景优势劣势
SqliteSaver本地开发/单机桌面零依赖、嵌入式单进程锁、不支持多实例
PostgresSaver生产服务端ACID、多实例并发需运维数据库

MemorySaver测试/演示最简单进程退出即丢失

2.2.2 我的实现：SQLite 本地持久化

在 Monet 桌面客户端场景中，Agent 和客户端打包在一起运行在用户本机。我选择 SQLite 作为 Checkpointer 后端，原因是：

  • 零部署依赖：桌面客户端不能要求用户装 PostgreSQL/Redis；
  • 嵌入式运行：SQLite 库随 Python 一起分发，无需额外进程；
  • 单用户场景：Monet 是单用户桌面应用，不存在多实例并发写入。
必须主动承认的局限性：

SQLite Checkpointer 是原型方案，适合桌面单机场景。如果要把这套 Agent 搬到线上多实例部署（如 K8s Pod），SQLite 的单进程写锁和文件级并发会成为硬伤。生产改造路径是替换为 PostgresSaver（ACID + 连接池）或 RedisSaver（低延迟 + TTL 自动过期），Checkpointer 接口是抽象的，替换只需改初始化一行代码。

2.3 interrupt 原理与 HITL 机制

2.3.1 interrupt 底层实现

interrupt 不是暂停线程，而是通过异常中断 Graph 的 while 循环迭代。这是面试中最容易答错的点。

# interrupt 底层伪代码
def interrupt(value):
    """在节点函数中调用 interrupt()"""
    raise GraphInterrupt(value)  # 抛出特殊异常

# Graph 执行循环中的处理
while current_node != END:
    try:
        update = node_fn(state)
        state = merge(state, update)
    except GraphInterrupt as e:
        # 不是 crash，而是"有序中断"
        state["__interrupt__"] = e.value  # 保存中断信息
        checkpointer.put(state)           # State 已保存
        return  # 退出 while 循环，但 State 完整保留

# resume 时的处理
def resume(thread_id, resume_value):
    state = checkpointer.get(thread_id)   # 从 checkpoint 恢复
    state["__resume__"] = resume_value     # 注入 resume 值
    # 从被中断的节点重新开始执行
    continue_from(interrupted_node, state)

关键理解：

  • GraphInterrupt 是异常，不是信号。节点执行栈被展开，但 State 在抛异常前已由框架保存。
  • resume 时，框架从 checkpoint 恢复 State，重新进入被中断的节点，此时 interrupt() 调用不再抛异常，而是返回 resume 传入的值。
  • 这意味着被中断节点的代码会重新执行，因此节点中 interrupt() 之前的逻辑必须是幂等的。

2.3.2 我的 HITL 审批引擎设计

基于 LangGraph 的 interrupt 机制，我设计了一套自定义权限分级协议：

# 工具权限分级装饰器
class PermissionLevel(Enum):
    AUTO = "auto"          # 只读操作，自动放行
    CONFIRM = "confirm"    # 写入/高危操作，需人工审批

@tool(permission_level=PermissionLevel.AUTO)
def canvas_node_detail(node_id: str) -> dict:
    """查看画布节点详情 - 只读，自动放行"""
    ...

@tool(permission_level=PermissionLevel.CONFIRM)
def create_node(node_type: str, params: dict) -> dict:
    """创建画布节点 - 写操作，需人工确认"""
    ...

@tool(permission_level=PermissionLevel.CONFIRM)
def delete_node(node_id: str) -> bool:
    """删除画布节点 - 高危操作，强制审批"""
    ...

审批流程在 tools 节点中实现：

# tools 节点中的权限检查逻辑
def tools_node(state: AgentState) -> dict:
    tool_calls = state["messages"][-1].tool_calls
    for call in tool_calls:
        tool = get_tool(call["name"])
        if tool.permission_level == PermissionLevel.CONFIRM:
            # 触发 interrupt，挂起等待审批
            approval = interrupt({
                "type": "tool_approval",
                "tool_name": call["name"],
                "args": call["args"],
                "description": tool.description
            })
            if not approval["approved"]:
                return {"messages": [ToolMessage("用户拒绝了该操作")]}
        # 执行工具
        result = tool.invoke(call["args"])
    return {"messages": [ToolMessage(result)]}

2.4 会话级任务取消机制

2.4.1 问题背景

在对话场景中，用户可能在 Agent 还在处理上一个请求时发送新消息。如果不处理旧任务，会出现两个问题：

  • 资源浪费：旧任务继续占用 LLM 推理资源和工具执行槽位；
  • 状态冲突：新旧任务同时写入同一 thread 的 checkpoint，导致数据不一致。

2.4.2 实现方案

# 会话级任务取消伪代码
class SessionManager:
    def __init__(self):
        self._active_tasks: dict[str, asyncio.Task] = {}

    async def handle_request(self, session_id: str, message: str):
        # 1. 如果该 session 有正在运行的任务，取消它
        if session_id in self._active_tasks:
            old_task = self._active_tasks[session_id]
            old_task.cancel()              # 发送 CancelledError
            try:
                await old_task             # 等待旧任务安全退出
            except asyncio.CancelledError:
                pass                       # 预期的取消异常

        # 2. 创建新任务
        new_task = asyncio.create_task(
            self._run_agent(session_id, message)
        )
        self._active_tasks[session_id] = new_task

    async def _run_agent(self, session_id: str, message: str):
        try:
            async for event in graph.astream(input, config):
                yield event
        except asyncio.CancelledError:
            # 3. 被取消时，确保 checkpoint 写入完成
            await asyncio.shield(
                checkpointer.flush(session_id)  # 保护写入不被取消
            )
            raise  # 重新抛出，让调用方知道已取消
        finally:
            # 4. 清理 session 记录
            self._active_tasks.pop(session_id, None)

关键细节：

  • asyncio.Task.cancel() 向任务发送 CancelledError，该异常会在下一个 await 点抛出；
  • asyncio.shield() 保护 checkpoint 写入操作不被取消中断，确保 State 写入完整；
  • 调用方通过 await old_task 等待旧任务真正退出后才启动新任务，保证同一 session 不存在并发写入。

三、面试易错点

易错点 1：interrupt 是暂停线程

错误回答："interrupt 会暂停当前线程，等审批通过后唤醒线程继续执行。"

正确理解：interrupt 是通过抛出 GraphInterrupt 异常中断 Graph 的 while 循环。没有线程被暂停，执行栈被展开，State 被序列化到 checkpoint。resume 时是从头重新进入被中断的节点，interrupt() 此时返回 resume 值而非抛异常。

易错点 2：觉得 Checkpointer 就是"存档读档"

不够准确的回答："Checkpointer 就是把状态存到数据库，下次启动再读出来。"

更完整的理解：Checkpointer 不只是存档。它记录的是每个节点执行后的完整 State 快照，支持回溯到任意历史节点（time-travel debugging）。每个 checkpoint 包含 State 数据 + 元数据（节点名、时间戳、parent checkpoint ID），形成一棵 checkpoint 树。生产环境中，这些 checkpoint 的存储、清理、并发访问控制都是工程挑战。

易错点 3：认为自己的工作全是 LangGraph 帮做的

面试官的陷阱："所以你就是用了 LangGraph 的 API 而已？"

防御话术：LangGraph 提供了底层机制（状态机循环、Checkpointer 抽象、interrupt/resume 原语），但我在此之上做了三层工程决策：(1) 设计了权限分级协议，将工具按操作类型标注权限等级；(2) 实现了 SSE 推送 + REST 回传的审批通信链路；(3) 设计了会话级任务取消机制，保证 checkpoint 一致性。框架是地基，但业务逻辑和工程质量是自己的工作。

易错点 4：不主动暴露 SQLite 方案的局限

错误做法：只讲 SQLite 的优点，等面试官追问才被动承认缺陷。

正确做法：主动说明"这是桌面客户端场景下的合理选择，但我清楚如果搬到线上多实例环境需要替换为 PostgresSaver 或 RedisSaver"。面试中主动暴露已知缺陷 + 给出改进路径，比被动承认得分高得多。

易错点 5：HITL 缺少超时和清理机制

面试官追问："用户触发审批后关掉电脑走了，任务怎么办？"

诚实回答 + 改进方向：当前实现没有做审批超时（因为桌面客户端场景中用户基本都在线）。但如果要做生产级改造，应该加超时释放（如5分钟未审批自动拒绝）、会话过期清理（定期扫描挂起状态的 checkpoint 并释放资源）。这是我认识到但在当前版本未实现的改进点。

四、满分逐字稿

Q1 满分逐字稿

详细讲 LangGraph 的执行机制、状态机原理、State 传递机制

好的，我从整体到细节来讲。LangGraph 的核心是一个 while 循环驱动的有限状态机，它和传统 FSM 的区别在于：传统 FSM 的状态是枚举值，而 LangGraph 的 State 是结构化数据，用 TypedDict 或 Pydantic Model 定义，可以包含消息列表、工具调用结果、中间变量等复杂结构。

执行流程是这样的：首先用 StateGraph 定义图结构，节点是普通函数或协程，边定义路由逻辑。调用 graph.invoke() 或 graph.astream() 时，框架内部启动一个 while 循环：从 START 节点开始，每次循环执行当前节点的函数，函数接收当前 State 的副本作为输入，返回一个 partial update。框架通过 merge 逻辑把 update 合并到 State 中。这里有个关键设计叫 Reducer，比如消息列表字段用 add_messages reducer，意味着新消息是追加到列表而不是覆盖。合并完成后，框架自动调用 Checkpointer 保存当前 State，然后通过路由函数决定下一个节点，如此循环直到到达 END 节点。

State 的传递是单向不可变的：每个节点拿到的是 State 副本，不能直接修改原始 State。这保证了节点之间不会因为共享引用出现竞态条件。在我们 Monet Agent 的实现中，State 包含了对话消息列表、当前画布上下文、工具执行结果等字段，整个 Graph 通常是 chatbot 节点（LLM 推理）和 tools 节点（工具执行）之间的循环，通过条件路由判断 LLM 输出中是否包含 tool_calls 来决定走哪条边。

如果面试官问"不用 LangGraph 怎么手写一个最简 Agent 状态机"，核心就是：一个 while 循环 + 一个 dict 当 State + if-else 做路由 + JSON 序列化做持久化。LangGraph 本质上是把这套模式做了抽象和工程化封装，加上了 Checkpointer、interrupt、流式输出等开箱即用的能力。我用 LangGraph 的价值不是"不会写状态机"，而是它省去了大量样板代码，让我能把精力放在业务逻辑（权限分级、审批协议、取消机制）上。

Q2 满分逐字稿

Checkpointer 持久化：你用的 SQLite 本地持久化，线上生产环境为什么不用 Redis/MySQL？生产级断点恢复你这个方案有什么缺陷？

先说结论：我选 SQLite 是适合场景的合理选择，但我清楚它不是生产级方案，如果做多实例部署必须替换。

Monet 是桌面客户端应用，Agent 服务和客户端打包在一起运行在用户本机。这个场景下有三个约束：第一，不能要求用户安装 PostgreSQL 或 Redis，部署成本必须为零；第二，是单用户单进程模型，不存在多实例并发写入的问题；第三，Agent 的对话状态需要跨客户端重启持久化保存，内存方案不够。SQLite 作为嵌入式数据库，零依赖、随 Python 分发、单文件存储，完全匹配这些约束。

但我必须主动说明它的缺陷。第一，SQLite 使用文件级锁，同一时刻只允许一个写入者，如果部署到 K8s 多 Pod 场景，多个实例无法共享同一个 SQLite 文件。第二，SQLite 文件会持续膨胀，我当前没有做 checkpoint 清理策略，长期运行后文件会越来越大。第三，SQLite 没有网络访问能力，无法跨机器共享 Agent 状态。

生产改造路径非常清晰：LangGraph 的 Checkpointer 是抽象接口，底层存储可以无缝替换。线上部署我会选 PostgresSaver，原因是它支持 ACID 事务保证 checkpoint 原子性写入，支持连接池处理并发，行级锁不会阻塞不同 session 的读写。如果对延迟敏感，还可以选 RedisSaver，利用 TTL 自动过期解决 checkpoint 清理问题。替换代码改动量很小，基本只改一行初始化：从 SqliteSaver.from_conn_string("agent.db") 改成 PostgresSaver.from_conn_string("postgres://...")。

所以总结：我在合适的场景用了合适的方案，同时清楚它的边界在哪里、改进路径是什么。面试中我不会回避这个局限性，因为能识别方案的适用边界本身就是工程能力的体现。

Q3 满分逐字稿

会话级任务取消：新请求进来取消旧任务，具体怎么实现的？task.cancel() 后如何保证 Checkpoint 不脏数据？如何等待安全退出？

这个问题的核心是取消安全性：既要快速取消旧任务释放资源，又不能让取消发生在 checkpoint 写入的中途导致数据不一致。

实现分三层。第一层是取消触发：我用一个 SessionManager 维护每个 session_id 到当前 asyncio.Task 的映射。新请求进来时，先检查该 session 是否有活跃任务，有的话调用 old_task.cancel()。这会向旧任务发送一个 CancelledError 异常，该异常会在旧任务下一个 await 点被抛出。

第二层是安全退出保证：旧任务的 Agent 执行逻辑被包在 try/except CancelledError 中。捕获到取消异常后，在 finally 块里执行清理，最关键的一步是用 asyncio.shield() 包裹 checkpoint 的 flush 操作。shield() 的作用是保护被包裹的协程不受外层 cancel 影响，即使 Task 已经被取消，checkpoint 写入操作也会完整执行完毕。写入完成后才重新抛出 CancelledError，让任务真正退出。

第三层是等待确认：触发取消后，新任务不会立即启动，而是通过 await old_task 等待旧任务真正退出。这保证了同一 session 在任何时刻只有一个任务在运行，不会出现新旧任务同时写 checkpoint 的竞态。如果旧任务的清理过程异常缓慢（比如某个工具调用阻塞），await 可能会等很久，但这比数据不一致更可接受。在实践中，由于 CancelledError 会在最近的 await 点抛出，通常几十毫秒内就能完成退出。

总结一下，取消安全性靠三个机制保证：cancel() 发信号、shield() 保护关键写入、await 等待确认退出。这套模式在 asyncio 中是标准做法，但在 Agent 场景下需要特别注意 checkpoint 写入的保护，这是我踩过坑后总结出来的。

Q4 满分逐字稿

LangGraph interrupt 底层原理是什么？是暂停线程还是暂停 Graph 迭代？

结论先行：interrupt 不是暂停线程，而是通过抛异常中断 Graph 的 while 循环迭代。这是理解 LangGraph HITL 机制的关键。

具体来讲，当节点函数内部调用 interrupt(value) 时，它做的事情是抛出一个 GraphInterrupt 异常。这个异常会被 Graph 的执行循环捕获。捕获后框架做两件事：第一，把当前 State（包括 interrupt 携带的 value）序列化写入 Checkpointer；第二，退出 while 循环，返回给调用方一个包含 interrupt 信息的响应。注意此时没有任何线程被挂起，执行栈已经完全展开，Python 协程正常退出。

恢复执行时，外部通过 graph.invoke(Command(resume=value), config) 触发。框架从 Checkpointer 加载之前保存的 State，找到被中断的节点，重新执行该节点的函数。关键在于：这次执行到 interrupt() 调用时，框架检测到有 resume value，不再抛异常，而是把 resume value 作为 interrupt() 的返回值交给节点函数。节点函数继续往下执行，处理 resume 值（比如判断用户是否批准了操作）。

这个设计带来一个重要工程约束：被中断节点中 interrupt() 之前的代码会被重新执行。所以这部分代码必须是幂等的，不能有不可重复的副作用。比如如果在 interrupt() 之前就调用了一个写操作的工具，resume 时这个工具会被再次调用，导致重复写入。在我的实现中，我把权限检查和 interrupt 放在工具实际执行之前，确保 interrupt 前的逻辑只有参数校验和权限判断，没有副作用。

为什么不是暂停线程？因为暂停线程意味着要维持整个执行上下文（调用栈、局部变量），在跨进程恢复时几乎不可能做到。而异常 + checkpoint 的方式，把"执行位置"抽象成了"Graph 中的节点位置 + State 数据"，可以跨进程、跨机器恢复，这才是生产级 HITL 需要的能力。

Q5 满分逐字稿

你做的 HITL 人机审批：自定义权限分级协议，具体分级标准是什么？只读/高危操作如何做工具自动分类？

我的分级协议核心思路是按工具的副作用程度划分权限等级，目前分两级：AUTO（自动放行）和 CONFIRM（需人工审批）。

分级标准是这样的：AUTO 级别对应只读操作，这类工具不会修改画布状态，只做信息查询。比如 canvas_node_detail（查看节点详情）、list_nodes（列出画布节点）、get_generation_status（查询生成任务状态）。即使 Agent 误判调用了这些工具，也不会造成任何损害，所以自动放行。CONFIRM 级别对应写入或命令操作，会修改画布状态或触发不可逆的操作。比如 create_node（创建节点）、delete_node（删除节点）、modify_params（修改节点参数）、run_generation（触发 AI 生成，消耗算力）。这些操作一旦执行就有实际影响，必须让用户确认。

工具分类不是运行时自动推断的，而是在工具定义时通过装饰器静态标注的。每个工具在定义时就用 @tool(permission_level=PermissionLevel.CONFIRM) 这样的装饰器明确标注权限等级。这是一个显式的设计决策：自动分类（比如通过分析函数签名或 docstring 推断）看起来更"智能"，但不可靠。工具的副作用程度是业务知识，不是代码静态分析能准确判断的。比如 run_generation 从函数签名看就是调了个 API，但它会消耗算力资源，这个判断必须由开发者来做。

在 tools 节点的执行逻辑中，每次执行工具前会检查其 permission_level 属性。如果是 CONFIRM 级别，就调用 interrupt() 挂起，通过 SSE 推送一个标准化的审批事件到前端，事件中包含工具名称、参数、描述等信息，让用户看到 Agent 想做什么。用户在前端做出 approve 或 reject 决定后，通过 REST 接口回传，驱动 Graph resume。

协议上还预留了扩展性。目前审批交互类型是简单的确认框（approve/reject），但协议抽象支持多选项（比如"用方案A还是方案B"）、参数修改（用户可以调整工具参数后再执行）等更丰富的交互类型。这个扩展性在设计时就考虑了，interrupt 携带的 value 是一个结构化对象，可以包含任意交互类型信息。

Q6 满分逐字稿

HITL 挂起后，集群大量阻塞任务会不会堆积？你有没有做超时释放、会话过期清理？

先说清楚场景差异，再诚实回答不足。

Monet Agent 当前是桌面客户端单机场景，不存在集群级别的任务堆积问题。每个用户的 Agent 运行在自己的机器上，interrupt 挂起时只占用本机一个 session 的内存，不影响其他用户。而且桌面场景下用户基本都在电脑前操作，从触发审批到用户响应通常是几秒钟的事。所以当前版本确实没有做审批超时和会话过期清理。

但我清楚这个缺陷在生产环境下会成为问题。如果把 Agent 部署为线上服务（比如 Web 版画布 + 云端 Agent），场景就完全不同了：多用户并发、用户可能触发审批后离开页面、网络断连后审批回调丢失。这种情况下如果不做清理，挂起状态的任务会无限堆积，占用服务端资源。

如果要做生产级改造，我会设计三层保护机制。第一层是审批超时：每个 interrupt 挂起时记录时间戳，设置一个超时阈值（比如 5 分钟），后台定时任务扫描超时的 interrupt，自动以 reject 状态 resume，释放资源。第二层是会话过期清理：对于超过一定时间没有活动的 session（比如 30 分钟无新消息），清理其 checkpoint 数据和内存状态。如果用 RedisSaver，可以直接利用 Redis 的 TTL 机制自动过期。第三层是资源上限：限制同一用户同时挂起的审批任务数量，超过阈值的新审批请求直接拒绝并返回提示。

这些改进我在设计阶段就考虑过，但因为桌面客户端场景不迫切需要，在 MVP 版本中做了取舍没有实现。如果面试官进一步追问，我认为这恰恰体现了工程中的适度设计原则：不在不需要的场景中过度工程化，但要确保自己清楚扩展路径。

Q7 满分逐字稿

多用户并发审批、同一画布多操作，会不会出现状态冲突？你如何保证幂等？

分两个层面回答：当前单机场景如何处理，以及多实例场景下的方案。

当前单机场景下，我通过会话级串行化避免状态冲突。每个 session_id 在任意时刻只有一个活跃的 asyncio Task 在运行（就是前面 Q3 讲的取消机制保证的）。同一 session 内，新请求会取消旧任务并等其安全退出后才启动，所以同一 session 的 checkpoint 不会被并发写入。不同 session 之间天然隔离（不同 thread_id），互不干扰。在桌面客户端中，一个用户一个画布一个 session，这套串行化机制足够了。

关于幂等性，需要关注 interrupt/resume 带来的重新执行问题。前面讲过，resume 时被中断的节点会重新执行，interrupt() 之前的代码会再跑一遍。我确保这段代码是幂等的：只做参数校验和权限判断，不执行任何有副作用的操作。工具的实际执行在 interrupt() 返回 approve 之后才进行，保证只执行一次。

如果要扩展到多用户并发场景（比如多人协作同一画布），会面临两个新问题。第一是多用户同时对同一画布发起操作，比如 A 在创建节点的同时 B 在删除节点。这需要在画布操作层面引入乐观锁：每次操作带上画布的版本号，提交时检查版本号是否匹配，不匹配则冲突拒绝或合并。第二是多个 Agent 实例同时写同一 thread 的 checkpoint，这需要把 SQLite 替换为支持行级锁的 PostgreSQL，通过数据库事务保证 checkpoint 写入的原子性。

再补充一点关于审批操作本身的幂等性：前端的 approve/reject 请求可能因为网络重试被发送多次。我在 resume 处理时会检查当前 Graph 是否处于 interrupted 状态，如果已经被 resume 过了（状态不是 interrupted），重复的 resume 请求会被忽略而不是二次执行。这保证了审批操作的幂等。

总结：当前通过 session 级串行化 + 工具执行前置幂等保证 + 审批操作幂等检查三层机制处理状态冲突。多用户协作场景需要额外引入画布版本号乐观锁和数据库级并发控制，这是已知的扩展方向。

五、附录：手写最小 Agent 状态机

面试官可能问："不用 LangGraph，你能手写一个最简单的带持久化的 Agent 状态机吗？" 以下是核心骨架代码，证明你理解本质而非只会调库。
import json
from pathlib import Path

def run_agent(state: dict, tools: dict, llm) -> dict:
    """最小 Agent 状态机：while 循环 + dict state + JSON 持久化"""
    checkpoint_file = Path(f"checkpoint_{state['session_id']}.json")

    # 恢复 checkpoint
    if checkpoint_file.exists():
        state = json.loads(checkpoint_file.read_text())

    while True:
        # 1. LLM 推理
        response = llm.chat(state["messages"])
        state["messages"].append(response)

        # 2. 持久化 checkpoint
        checkpoint_file.write_text(json.dumps(state, ensure_ascii=False))

        # 3. 路由判断
        if not response.get("tool_calls"):
            break  # 无工具调用，退出循环

        # 4. 执行工具
        for call in response["tool_calls"]:
            tool_fn = tools[call["name"]]
            result = tool_fn(**call["args"])
            state["messages"].append({
                "role": "tool", "name": call["name"], "content": result
            })

        # 5. 再次持久化
        checkpoint_file.write_text(json.dumps(state, ensure_ascii=False))

    return state

这 30 行代码就是 LangGraph StateGraph 的最小本质：while 循环（执行引擎）+ dict（State）+ if-else（路由）+ JSON 文件（Checkpointer）。LangGraph 在此基础上加了：类型安全的 State 定义、Reducer 合并策略、流式输出、interrupt/resume、多种 Checkpointer 后端 -- 但核心模型没变。
