前置背景知识（先读这里）

后面的面试题和逐字稿大量引用以下概念。如果你对 SSE 协议细节、Nginx 长连接配置、asyncio 协程管理或 LangGraph 事件体系不熟悉，先把这一节吃透再往下看，否则后面的回答你只是在背，不是在理解。

B1. SSE 协议（重中之重）

一句话定义：SSE（Server-Sent Events）是基于 HTTP 长连接的服务端单向推流协议，MIME 类型为 Content-Type: text/event-stream。

SSE 帧格式

一条完整的 SSE 消息由若干字段行 + 一个空行（双换行 \n\n）构成。双换行是协议硬性规定，少了前端收不到完整消息。

id: 1
event: error
data: {"error_code":500}
                          ← 这里是空行，即 \n\n，代表一条消息结束
字段作用关键细节
id: 事件编号，自增，发给前端 断线重连时浏览器自动把最后收到的 id 放进请求头 Last-Event-ID 带回后端
event: 自定义事件类型 有 event 字段时，前端不能用 onmessage，必须用 addEventListener("error", ...) 等对应名称监听
data: 业务数据 一般放 JSON 字符串。可以有多行 data:，前端会把它们用 \n 拼起来
\n\n 消息结束标记 协议硬性规定：双换行分隔消息，少一个换行前端不会把这条消息视为完整

Comment 注释帧（心跳的基础）

: heartbeat\n\n

冒号开头的行是注释。协议规定：前端直接忽略，不触发任何 JS 回调（onmessage、addEventListener 都不触发），但数据确实在 TCP 连接上传输了 → 用来做心跳，维持连接存活。

onmessage 与 addEventListener

EventSource.onmessage 是 JS 的默认回调，只有不带 event: 字段的普通消息才触发它。一旦消息携带了自定义 event: 字段（如 event: delta），就必须用 addEventListener("delta", handler) 来监听。

Last-Event-ID：断线重连的关键

注意区分协议职责和业务职责：SSE 协议只负责浏览器在重连时把最后收到的 id 通过 Last-Event-ID 请求头带回来。根据这个 ID 从断点补发历史消息，协议不会帮你做，必须自己写业务代码（维护事件缓冲区、查找断点位置、重发后续事件）。适配器基类只负责输出 id 字段，不做补发逻辑。

B2. Nginx（读法：“engine‑x”） 网关背景

Monet 的 SSE 流量要经过 Nginx 反向代理才到达前端。Nginx 对长连接有两个关键行为你必须知道：

配置项含义对 SSE 的影响
proxy_read_timeout 60s Nginx 如果 60 秒内没有收到后端任何数据，就主动把长连接断开 Agent 思考时间很久（几十秒没输出任何 token）时，连接会被 Nginx 掐断
proxy_buffering off 关闭 Nginx 的响应缓冲，收到数据立即转发 SSE 必须关闭，否则 Nginx 缓存数据攒够才发，没有实时流式效果
心跳存在的根本原因：后端每 15 秒发一次心跳 comment 帧，骗过 Nginx 的 proxy_read_timeout，让 Nginx 以为"后端还在传数据"，不断开连接。15s < 60s，留了足够的安全余量。心跳不是发给浏览器看的，是发给 Nginx 看的。

B3. Python asyncio 异步知识（必须懂这 3 点）

流式适配器的心跳机制依赖 asyncio 的协程并发。以下三个概念是理解心跳实现的前提：

1. asyncio.create_task() — 启动后台独立协程

调用 asyncio.create_task(coro) 会在同一个线程、同一个事件循环中启动一个独立协程任务，和主流程并行跑。

# 主协程在处理 Agent 流；心跳是另一个协程，每 15 秒输出一个心跳帧
heartbeat_task = asyncio.create_task(self._heartbeat_loop())
# 此时主流程继续 async for event in raw_stream: ...
# 心跳协程独立运行，隔 15 秒发一次心跳
通俗理解：主流程是"主工人"在搬 Agent 输出的砖，心跳是"兼职工人"每 15 秒喊一声"还活着"。两个人在同一间屋子里（同一线程），但各干各的。

2. task.cancel() — 取消协程

流结束或用户断开连接时，必须把心跳 task cancel 掉。不 cancel 的后果：后台协程继续在事件循环里无限跑 → 协程泄漏，吃内存、占调度资源。

# adapt_stream 的 finally 块：
finally:
    heartbeat_task.cancel()  # 活干完了，把兼职辞退

3. CancelledError — cancel 后协程内部抛出的异常

调用 cancel() 后，目标协程内部会在下一个 await 点抛出 asyncio.CancelledError。必须捕获它，否则会在日志里打一堆错误堆栈：

async def _heartbeat_loop(self):
    try:
        while True:
            await asyncio.sleep(15)
            yield ": heartbeat\n\n"
    except asyncio.CancelledError:
        pass  # 正常取消，不需要报错
通俗理解：你对兼职说"你被辞退了"（cancel），兼职收到通知会抛出"我被辞退了"（CancelledError）。你得接住这个通知说"知道了"（except），不然他会到处喊"我被辞退了"搞得日志很难看。

B4. LangGraph 事件体系

astream_events — 流式事件接口

LangGraph 提供的 astream_events() 返回一个 async generator，源源不断地吐出事件对象。不是一次性返回最终结果，而是 Agent 执行过程中每产生一个动作（输出一个 token、调用一个工具、工具执行完毕）就抛出一个事件。

关键事件类型

事件类型含义携带数据
on_chat_model_stream 大模型正在输出 token 增量文本（delta），比如"你"、"好"、"，我"
on_tool_start Agent 准备调用工具 工具名称、参数
on_tool_end 工具调用执行完毕 工具返回结果

_map_event — 翻译函数

LangGraph 的原始事件格式前端不认识。_map_event 的职责就是把 LangGraph 内部格式翻译成我们前端约定好的 Block 格式：

# LangGraph 原始事件                           翻译后
# on_chat_model_stream  ──_map_event──>  TextBlock Delta（增量文本帧）
# on_tool_start         ──_map_event──>  ToolCallBlock（工具调用帧）
# on_tool_end           ──_map_event──>  ToolResultBlock（工具结果帧）
类比：LangGraph 说法语，前端说中文，适配器是翻译官。翻译官不改变说话内容，只转换语言格式。

2.1 SSE vs WebSocket vs 轮询 — 三种方案对比

AI Agent 场景为什么选 SSE？ Agent 生成过程天然是服务端单向推送，客户端不需要在流式输出过程中向服务端发数据。SSE 基于标准 HTTP，与现有反向代理（Nginx）、负载均衡、CDN 无缝兼容；浏览器 EventSource API 原生支持断线重连和 Last-Event-ID；部署运维成本远低于 WebSocket。唯一的代价是不支持二进制帧和双向通信，但 AI Agent 场景不需要这两个能力。

2.2 适配器模式设计

核心设计思路：将 SSE 协议的通用能力（事件 ID 自增、心跳、异常帧）下沉到基类，将框架特定的事件映射交给子类。这样当底层 Agent 框架从 LangGraph 切换到其他框架时，只需要新增一个适配器子类，协议层和前端完全不用改。

# 基类：BaseStreamAdapter
class BaseStreamAdapter(ABC):
    """SSE 流式适配器基类，封装协议层通用能力"""

    def __init__(self):
        self._event_id: int = 0           # 事件 ID 自增计数器
        self._heartbeat_interval: int = 15 # 心跳间隔（秒）

    def _next_event_id(self) -> int:
        """生成递增事件 ID，用于前端断线重连"""
        self._event_id += 1
        return self._event_id

    async def send_event(self, event_type: str, data: dict) -> str:
        """发送标准 SSE 事件帧"""
        event_id = self._next_event_id()
        return f"id: {event_id}\nevent: {event_type}\ndata: {json.dumps(data)}\n\n"

    async def send_heartbeat(self) -> str:
        """发送心跳帧（SSE comment，不触发前端事件）"""
        return ": heartbeat\n\n"

    async def send_error(self, error_code: str, message: str) -> str:
        """发送异常帧，前端据此决定重试还是终止"""
        return await self.send_event("error", {
            "code": error_code, "message": message
        })

    @abstractmethod
    async def adapt_stream(self, raw_stream) -> AsyncGenerator[str, None]:
        """子类实现：将框架原始事件流映射为统一 SSE 帧"""
        ...

# 子类：LangGraph 适配器
class LangGraphStreamAdapter(BaseStreamAdapter):
    """将 LangGraph astream_events 映射为 Message/Block SSE 帧"""

    async def adapt_stream(self, raw_stream) -> AsyncGenerator[str, None]:
        heartbeat_task = asyncio.create_task(self._heartbeat_loop())
        try:
            async for event in raw_stream:
                sse_frame = self._map_event(event)
                if sse_frame:
                    yield sse_frame
            yield await self.send_event("done", {})
        except Exception as e:
            yield await self.send_error("STREAM_ERROR", str(e))
        finally:
            heartbeat_task.cancel()

    def _map_event(self, event: dict) -> Optional[str]:
        """将 LangGraph 内部事件类型映射为 Block 类型"""
        # on_chat_model_stream -> TextBlock delta
        # on_tool_start -> ToolCallBlock
        # on_tool_end -> ToolResultBlock
        ...

2.3 Message / Block / Delta 三层数据模型

这是整个流式协议的数据架构核心。设计原则：一个 Message 代表 Agent 的一轮完整回复，一个 Block 代表一个内容片段，Delta 是 Block 的增量更新。

层级概念生命周期典型字段
Message Agent 一轮完整回复的容器 从 Agent 开始输出到结束 message_id, role, blocks[], status
Block Message 中的一个内容片段 从创建到完成（可被多次 Delta 更新） block_id, block_type, content
Delta Block 的一次增量更新 瞬时（每个 Token/片段产生一个） block_id, delta_type, text_delta

Block 类型枚举：

  • TextBlock — 文本内容，LLM 逐 token 输出，通过 Delta 增量推送
  • ToolCallBlock — 工具调用，包含 tool_name 和 arguments
  • ToolResultBlock — 工具返回结果
  • ImageBlock — 图片内容（URL 或 base64）
  • ErrorBlock — 执行过程中的错误信息

为什么要 Delta 增量推送而不是每次发完整 Block？

  • LLM 逐 token 生成文本，一个 TextBlock 的完整内容可能有几千字；如果每次都发完整内容，带宽浪费严重。
  • Delta 只发新增的文本片段（比如 3-5 个字），前端拼接即可，带宽效率接近最优。
  • 这和 OpenAI Streaming API 的设计一致：choices[0].delta.content 也是增量。

2.4 心跳保活与断线重连

SSE 长连接在生产环境面临三个杀手：

  1. 中间代理超时：Nginx 默认 proxy_read_timeout 60s，如果 60 秒内没有数据传输，Nginx 会断开连接。Agent 思考时间可能超过 60 秒。
  2. 客户端网络切换：用户从 WiFi 切到 4G，TCP 连接静默断开。
  3. 服务端崩溃：进程被 OOM Kill 或未捕获异常导致连接中断。

心跳机制实现：

async def _heartbeat_loop(self):
    """每 15 秒发送心跳帧，防止中间代理因超时断开连接"""
    try:
        while True:
            await asyncio.sleep(15)
            yield ": heartbeat\n\n"
    except asyncio.CancelledError:
        pass  # 流正常结束时取消心跳任务

心跳帧使用 SSE 的 comment 格式（以冒号开头），不会触发前端的 onmessage 事件，但能保持 TCP 连接活跃。15 秒的间隔小于 Nginx 默认的 60 秒超时，留出足够安全余量。

断线重连机制：

  • 每个 SSE 事件帧都带有递增的 id 字段。
  • 浏览器 EventSource 断线后自动重连，并在请求头带上 Last-Event-ID。
  • 服务端收到 Last-Event-ID 后，从该 ID 之后的位置重新推送（需要服务端维护事件缓冲区）。

2.5 asyncio 异步工程实践

坑 1：同步调用阻塞事件循环

# 错误：直接调用同步 HTTP 库，阻塞整个事件循环
response = requests.get("https://api.example.com/data")

# 正确：使用异步 HTTP 库
async with aiohttp.ClientSession() as session:
    response = await session.get("https://api.example.com/data")

# 或者：用 run_in_executor 包装同步调用
loop = asyncio.get_event_loop()
response = await loop.run_in_executor(None, requests.get, url)

坑 2：ContextVar vs 全局变量

import contextvars

# 全局变量：所有协程共享，并发不安全
global_request_id = None  # 危险！

# ContextVar：每个协程/任务有独立副本，并发安全
request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar('request_id')

async def handle_request(req_id: str):
    request_id_var.set(req_id)
    # asyncio.create_task 会自动复制父任务的 Context
    task = asyncio.create_task(do_work())
    await task

async def do_work():
    # 能正确读取到父任务设置的 request_id
    print(f"Processing request: {request_id_var.get()}")

坑 3：长会话内存膨胀

LangGraph 的 State 对象会存储完整的对话历史。在长会话场景下（用户连续对话 50 轮以上），State 中的 messages 列表不断增长，单个会话的内存占用可能达到数十 MB。

# 解决方案：定期清理历史消息，保留最近 N 轮
def trim_messages(state: AgentState, max_messages: int = 20) -> AgentState:
    """保留系统消息 + 最近 N 轮对话"""
    messages = state["messages"]
    system_msgs = [m for m in messages if m.type == "system"]
    recent_msgs = messages[-max_messages * 2:]  # 每轮包含 user + assistant
    state["messages"] = system_msgs + recent_msgs
    return state

四、面试易错点

易错点 1：把 SSE 和 WebSocket 的能力搞混

SSE 是单向的（服务端推送到客户端），不支持客户端主动发消息给服务端。面试中说"SSE 是双向通信"会直接扣分。正确表述：用户的新请求通过普通 HTTP POST 发送，SSE 只负责服务端推送流式结果。

易错点 2：说"心跳是给客户端看的"

心跳帧的主要目的不是让客户端知道连接还活着（浏览器 EventSource 有自己的连接检测机制），而是防止中间代理（Nginx/网关）因读超时断开连接。如果面试官追问"心跳给谁看的"，回答 Nginx 而不是浏览器。

易错点 3：认为 asyncio.create_task 是"开新线程"

asyncio.create_task 是在同一个线程、同一个事件循环中创建一个新的协程任务。它与多线程无关。如果面试官问"create_task 和 Thread 的区别"，核心答案是：协程切换是协作式的（在 await 点让出控制权），线程切换是抢占式的（OS 调度器控制）。

易错点 4：ContextVar 和 threading.local 混淆

threading.local 是线程级隔离；contextvars.ContextVar 是任务级隔离。在 asyncio 中，多个协程运行在同一个线程上，threading.local 无法区分不同协程，但 ContextVar 可以。而且 asyncio.create_task 会自动复制父任务的 Context 快照。

易错点 5：Delta 增量推送说不清前端怎么拼接

前端收到 block_start 事件时创建空 Block 容器，每收到一个 delta 事件就把 text_delta append 到对应 Block 的 content 末尾，收到 block_end 时标记该 Block 完成。这个拼接逻辑和 OpenAI ChatCompletion Streaming 完全一致，要讲得出来。

Q1. 对比 WebSocket、SSE、轮询，你为什么选择 SSE 做 Agent 流式输出？

满分逐字稿

Q1 参考回答（约 450 字）

我们在 Monet 画布做 AI Agent 流式输出时，技术选型上对比了三种方案：短轮询、WebSocket 和 SSE。

短轮询首先排除了。Agent 一次推理可能持续 5 到 30 秒，如果用轮询，客户端要反复发请求问"好了没"，既浪费带宽也增加延迟，用户体验很差。

WebSocket 的能力其实是过剩的。WebSocket 是全双工的，支持客户端和服务端双向发消息，但 Agent 流式输出场景其实是单向的——服务端不断往客户端推 Token，客户端在流式输出过程中不需要往回发数据。用户的新问题是通过普通 HTTP POST 提交的，不走 WebSocket 通道。如果用 WebSocket，首先是增加了协议复杂度，需要管理连接状态、处理升级握手；其次是运维代价高，WebSocket 连接是有状态的，不走标准 HTTP，对 Nginx 反向代理和负载均衡不够友好，弹性伸缩时需要处理连接迁移；再者我们整个服务是 FastAPI + Uvicorn，WebSocket 需要额外的连接管理逻辑。

最终选择 SSE，原因有几点。第一，SSE 完全基于标准 HTTP，使用MIME类型Content-Type: text/event-stream，对Nginx、负载均衡具备良好的兼容性；并且Nginx关闭 proxy_buffering 禁用代理缓冲（因为SSE要求每一段数据立即透传给前端，不能在缓存里攒着），CDN（Content Delivery Network）调整长连接相关参数即可使用。第二，浏览器原生提供 EventSource API，自带断线自动重连，并且支持 Last-Event-ID请求头；重连时浏览器会携带该ID，由服务端根据事件ID实现断点续推。第三，SSE 的实现代价极低， FastAPI 中通过 StreamingResponse 配合 async generator即可完成流式输出，业务代码简洁。

SSE 的缺点也很明显：不支持二进制帧（只能传文本），不支持客户端主动推送。但这两个限制在我们场景里完全不是问题。如果未来需要双向通信（比如用户中途修改生成参数），我会考虑把 SSE 和 POST 组合使用，而不是换成 WebSocket。

Q2. 你封装的流式适配器基类具体抽象了哪些能力？代码结构怎么设计的？

满分逐字稿

Q2 参考回答（约 480 字）

我设计流式适配器时用的是经典的适配器模式，核心思路是把"SSE 协议的通用能力"和"具体 Agent 框架的事件映射"分离开来。

基类叫 BaseStreamAdapter，它封装了三个维度的通用能力：

第一是事件帧编码。SSE 协议有固定格式：id: xxx\nevent: xxx\ndata: xxx\n\n。基类的 send_event 方法负责把业务数据序列化成标准 SSE 帧，包括 JSON 序列化、换行符处理、事件 ID 自增。事件 ID 用一个简单的自增计数器实现，每发一帧加一，这个 ID 前端会在断线重连时通过 Last-Event-ID 头传回来。

第二是心跳保活。基类提供 send_heartbeat 方法，发送 SSE 的 comment 帧（ : \n\n冒号开头的行），不会触发前端的 onmessage 事件，但能保持 TCP 连接活跃。间隔设定为 15 秒，因为我们 Nginx 配置的 proxy_read_timeout 是 60 秒，15 秒间隔留了足够的安全余量。心跳通过 asyncio.create_task 启动一个独立的后台协程，在流结束时通过 cancel() 清理。

第三是异常帧发送。send_error 方法发送结构化的错误事件，包含 error_code 和 message。前端收到 error 事件后可以根据 error_code 决定是重试还是提示用户。这个设计保证了即使后端出错，前端也能优雅降级，而不是连接突然断开用户一脸懵。

子类是 LangGraphStreamAdapter，它实现基类的抽象方法 adapt_stream。这个方法接收 LangGraph 的 astream_events 产生的原始事件流，然后用一个 _map_event 方法做类型映射：on_chat_model_stream 事件映射为 TextBlock 的 Delta 帧，on_tool_start 映射为 ToolCallBlock 的 block_start 帧，on_tool_end 映射为 ToolResultBlock 的 block_end 帧。

这个结构的好处是：如果未来要换成 AutoGen 或者 CrewAI，我只需要新写一个 AutoGenStreamAdapter，实现它自己的 _map_event 逻辑就行，基类的心跳、ID 递增、异常帧全部复用，前端代码完全不用动。

Q3. Message/Block 双层模型为什么这么设计？Delta 增量推送的具体逻辑是什么？

满分逐字稿

Q3 参考回答（约 500 字）

这个双层模型的设计动机来自 Agent 输出的异构性。Agent 一次回复里可能同时包含文本、工具调用、工具返回结果、甚至图片。如果只用一个扁平的 message 字符串来承载，前端解析和渲染会非常痛苦，也没法做到不同类型内容的差异化展示。

所以我设计了 Message 和 Block 两层结构。Message 是 Agent 一轮回复的容器，拥有 message_id、role、status 等元数据，以及一个 blocks 数组。Block 是 Message 中的一个内容片段，每个 Block 有独立的 block_id 和 block_type。目前支持五种类型：TextBlock（文本）、ToolCallBlock（工具调用）、ToolResultBlock（工具返回）、ImageBlock（图片）、ErrorBlock（错误）。

这样设计的好处是前端可以按 Block 类型做差异化渲染：TextBlock 用 Markdown 渲染器，ToolCallBlock 显示为"正在调用 xx 工具"的加载态，ToolResultBlock 展示结构化结果，ImageBlock 渲染为图片卡片。每种 Block 的渲染组件是独立的，互不干扰。

Delta 增量推送主要用在 TextBlock 上。LLM 逐 Token 生成文本，一个 TextBlock 的完整内容可能有几千字。如果每次都把完整内容发过去，假设一个字 3 字节，3000 字就是 9KB，乘以 Token 数量（可能 500 次），产生大量重复带宽流量、前端重复渲染压力大。所以我用 Delta 模式：每个 SSE 帧只传新增的几个字（text_delta 字段），前端把它 append 到对应 Block 的 content 末尾。

具体的 SSE 事件序列是这样的：首先发一个 block_start 事件，携带 block_id 和 block_type，前端据此创建一个空的 Block 容器。然后连续发 N 个 delta 事件，每个携带对应 block_id 和 text_delta。最后发一个 block_end 事件，标记该 Block 完成。一个 Message 中可能有多个 Block 交替推送（比如先是一段文本，然后调用工具，工具返回后又是一段文本）。

这个设计和 OpenAI 的 Streaming API 思路一致——choices[0].delta.content 也是增量模式。但我们在上面加了 Block 层，让它能承载比纯文本更丰富的内容类型。前端只需要实现一个 Block 状态管理器，监听三种事件（start/delta/end），就能渲染任意复杂的 Agent 输出。

Q4. SSE 长连接心跳保活怎么做的？前端断连、后端异常崩溃，如何保证消息不丢、不重复？

满分逐字稿

Q4 参考回答（约 500 字）

心跳保活和断线容错是 SSE 投入生产后必须解决的问题，我们踩过坑之后建立了一套完整的方案。

心跳保活的实现：我在 BaseStreamAdapter 里用 asyncio.create_task 启动一个后台协程，每 15 秒发送一个 SSE comment 帧，格式是 : heartbeat\n\n。这个帧以冒号开头，按 SSE 规范是注释行，前端 EventSource 不会触发 onmessage 事件，但数据确实在 TCP 连接上传输了，这就能防止中间的 Nginx 反向代理因为 proxy_read_timeout 超时而断开连接。我们 Nginx 配的是 60 秒超时，心跳 15 秒一次，安全余量足够。流正常结束时，通过 heartbeat_task.cancel() 清理这个后台任务，避免资源泄漏。

前端断连的处理：浏览器 EventSource API 有原生的自动重连机制，连接断开后会按默认 3 秒间隔尝试重连。关键是重连时会携带 Last-Event-ID 请求头，值是最后一次收到的事件 ID。我们每个 SSE 事件帧都带了递增 ID，所以服务端收到重连请求后，可以根据 Last-Event-ID 判断客户端已经收到了哪些事件，从断点之后继续推送。不过，这要求服务端维护一个事件缓冲区来暂存最近的事件。我们用一个有界队列（保留最近 200 条事件）来实现，超出容量的老事件会被丢弃——如果断线时间太长导致缓冲区被覆盖，就发一个特殊的 resync 事件通知前端做全量刷新。

后端异常崩溃的处理：这分两种情况。第一种是可捕获的异常，比如 LangGraph 内部抛出异常，这个在 adapt_stream 的 try-except 中捕获，通过 send_error 发送一个结构化的错误帧给前端，前端据此展示错误提示。第二种是进程级崩溃（比如 OOM Kill），这时 TCP 连接会直接中断，前端 EventSource 检测到连接关闭会自动重连，重连后如果服务端已经不知道这个会话的上下文了，就返回一个 session_expired 错误帧，前端提示用户重新发起请求。

关于消息不重复：事件 ID 自增保证了幂等性。前端维护一个已处理的最大事件 ID，收到的事件 ID 如果小于等于已处理 ID，就直接丢弃。这在重连后重发事件的场景下能避免重复渲染。

Q5. 底层框架无感切换，你具体解耦了哪些依赖？如果换成 AutoGen，能直接无缝迁移吗？

满分逐字稿

Q5 参考回答（约 450 字）

我说的"底层框架无感切换"指的是前端和 SSE 协议层不需要任何修改，只需要新增一个适配器子类。具体解耦了三个层次的依赖：

第一是事件格式依赖。LangGraph 的 astream_events 输出的事件格式是 LangGraph 特有的，比如事件类型叫 on_chat_model_stream、on_tool_start 等，事件 payload 的字段也是 LangGraph 定义的。这些细节全部封装在 LangGraphStreamAdapter._map_event 里面，对外输出的是我们自己定义的 block_start、delta、block_end 标准事件。前端只关心我们定义的标准事件，不知道底层用的是什么框架。

第二是流式 API 依赖。不同框架提供流式输出的 API 差异很大。LangGraph 是 astream_events()，返回一个 async generator；AutoGen 可能是回调模式或者自己的事件总线。这个差异被隔离在 adapt_stream 方法中，基类只定义了"输入一个原始流，输出一个 SSE 帧的 async generator"这个契约，具体怎么消费原始流，由子类实现。

第三是状态管理依赖。LangGraph 用 State 对象管理对话历史，AutoGen 用不同的会话管理机制。适配器层不直接操作 Agent 的状态，它只负责"读取事件流、映射格式、输出 SSE 帧"，状态管理是 Agent 层自己的事情。

如果要换成 AutoGen，能不能无缝迁移？诚实说，不是完全无缝的。适配器层确实只需要写一个 AutoGenStreamAdapter 就够了，前端和协议层不用动。但 Agent 层（构建 Agent、定义工具、管理会话）肯定要重写，因为 LangGraph 和 AutoGen 的 Agent 编排 API 完全不同。我的适配器模式解决的是"流式输出协议的解耦"，不是"整个 Agent 框架的解耦"。这个边界面试时要讲清楚，不能过度宣称。

Q6. 线上 SSE 大流量场景下，有没有遇到过消息积压、粘连、乱序问题？怎么解决？

满分逐字稿

Q6 参考回答（约 480 字）

在 Monet 画布的实际使用中，我们确实遇到过与流式推送相关的问题，最典型的有两个。

第一个是消息粘连。现象是前端偶尔收到的 SSE 数据会把两个事件帧粘在一起，导致 JSON 解析失败。排查下来原因出在 Nginx 的 proxy_buffering。Nginx 默认开启响应缓冲，会攒够一定量的数据再转发给客户端，这就导致多个 SSE 帧被合并成一个 TCP 包。解决方案是在 Nginx 配置中加上 proxy_buffering off 和 X-Accel-Buffering: no 响应头，让 Nginx 收到数据立即转发。同时在 FastAPI 的 StreamingResponse 里设置 headers={"X-Accel-Buffering": "no", "Cache-Control": "no-cache"}。

第二个是消息积压。当 LLM 输出速度很快（比如 GPT-4o 的流式输出速度相当快），而前端渲染跟不上时，服务端的 SSE 帧会在发送缓冲区里堆积。这个问题的本质是生产者-消费者速度不匹配。我们的应对方式是在适配器中做了合并优化：如果短时间内（比如 50ms 内）产生了多个 TextBlock 的 Delta，就把它们合并成一个更大的 Delta 帧再发送，减少帧数量。这样既降低了 TCP 包的数量，也减轻了前端的事件处理压力。

关于乱序，SSE 基于 HTTP 长连接，底层是 TCP，TCP 本身保证有序交付，所以正常情况下不会乱序。但如果客户端断线重连，重连后的事件和缓冲区中的旧事件可能存在边界问题。我们通过事件 ID 递增来保证顺序，前端维护一个 lastProcessedId，收到的事件如果 ID 不是 lastProcessedId + 1，说明有遗漏，触发一次全量同步。

还有一个运维层面的问题：单个 Uvicorn worker 的并发 SSE 连接数是有上限的。每个 SSE 连接占用一个协程，虽然协程很轻量，但到了几百个并发长连接时，事件循环的调度延迟会明显增加。我们通过多 worker 部署和连接数监控来应对。

Q7. FastAPI + Asyncio 异步架构，你在项目中遇到过哪些异步坑？

满分逐字稿

Q7 参考回答（约 480 字）

在 Monet Agent 项目中，我们踩过三个比较典型的异步坑。

第一个坑是同步调用阻塞事件循环。这个坑几乎每个用 asyncio 的团队都会踩。我们的 Agent 需要调用一些内部 HTTP 服务，一开始有些代码用的是 requests 库，它是同步的。在 asyncio 事件循环中直接调用 requests.get()，整个事件循环会被阻塞，所有其他协程都得等着——包括 SSE 心跳的发送。结果就是 Agent 调外部接口时，客户端的 SSE 连接因为收不到心跳而被 Nginx 断开。解决方案是统一使用 aiohttp 做 HTTP 请求；对于确实没有异步版本的第三方库，用 asyncio.get_event_loop().run_in_executor(None, sync_func) 包装，把同步调用放到线程池里执行，不阻塞事件循环。

第二个坑是异常吞没。asyncio.create_task() 创建的任务如果抛出异常，默认不会传播到创建它的协程中——异常只是被记录到 Task 对象里，如果没人 await 这个 Task，异常就被静默吞掉了。我们早期的心跳任务就出过这个问题，心跳协程因为某个 bug 抛了异常，但主流程完全不知道心跳已经停了，直到连接被 Nginx 断开才发现。后来的做法是给关键的后台任务加上 task.add_done_callback()，在回调中检查有没有异常，有的话记录日志并做告警。

第三个坑是 async generator 的清理。FastAPI 的 StreamingResponse 接收一个 async generator，如果客户端中途断开连接，generator 需要正确清理资源。但 Python 的 async generator 在被 GC 回收时不保证执行 finally 块。我们的解决方式是在 FastAPI 的中间件层检测客户端断开事件（通过 request.is_disconnected()），主动调用 generator 的 aclose() 方法触发 finally 中的清理逻辑，比如取消心跳任务、释放 LangGraph 的资源。

Q8. 异步缓存、上下文传递，ContextVar 和全局变量的区别？并发安全问题？

满分逐字稿

Q8 参考回答（约 450 字）

这个问题的核心是理解 asyncio 中的并发模型和上下文隔离。

在 asyncio 中，所有协程运行在同一个线程上。这意味着 threading.local() 在这里是无效的——所有协程共享同一个线程局部存储。同样，全局变量也是所有协程共享的。这在并发场景下会导致严重的问题：比如用全局变量存 request_id，协程 A 把它设为 "req-001"，还没用完，事件循环切到协程 B，B 又把它设为 "req-002"，等切回 A 时 request_id 已经被污染了。

Python 3.7 引入的 contextvars.ContextVar 就是为了解决这个问题。ContextVar 提供任务级别的隔离：每个 asyncio Task 有自己独立的 Context 副本。当你调用 asyncio.create_task() 时，新任务会自动复制父任务当前 Context 的一个浅拷贝（copy-on-write 语义）。子任务修改 ContextVar 不影响父任务，父任务后续的修改也不影响已经创建的子任务。

在我们的 Monet Agent 项目中，ContextVar 主要用在两个场景。第一是请求追踪：每个请求进来时生成一个 trace_id，存到 ContextVar 中，后续所有的日志输出都从 ContextVar 中读取 trace_id 来关联。因为一个 SSE 请求的生命周期中可能会 create_task 出去做心跳、做工具调用等，ContextVar 能保证这些子任务都能拿到正确的 trace_id。第二是用户上下文：当前请求对应的用户信息、权限信息存在 ContextVar 中，Agent 执行工具调用时需要用到用户身份来鉴权。

并发安全方面需要注意一点：ContextVar 的隔离是Task 级别的，不是 await 级别的。同一个 Task 内部的多次 await 之间共享同一个 Context。如果一个 Task 内部先 set 了某个 ContextVar，然后 await 了一段时间再 get，中间不会被其他 Task 篡改。但如果你在 Task 内部修改了一个 ContextVar 指向的可变对象（比如 list 或 dict），那它依然不是线程安全的——不过在 asyncio 单线程模型下，这通常不是问题，因为不会有真正的并行执行。

Q9. 大量 Agent 长会话并发，你的服务内存、连接数瓶颈在哪里？做过哪些优化？

满分逐字稿

Q9 参考回答（约 500 字）

Agent 长会话并发是我们上线后面临的一个核心性能挑战。瓶颈主要在三个方面：

第一是内存。每个活跃的 Agent 会话在内存中维护一个 LangGraph State 对象，里面存了完整的对话历史（所有 Message 和 Block）。一轮对话大概占 50-200KB，如果用户连续对话 30 轮以上，单个会话的 State 可能膨胀到几十 MB。100 个并发长会话就是几 GB 内存。我们的优化方案是对话历史裁剪：在每轮对话开始前，检查 State 中的 messages 数量，超过阈值（比如 20 轮）就只保留 system prompt 加最近 N 轮对话。被裁剪的历史可以存到 Redis 中做持久化，需要时再加载回来。另外，LangGraph 的每次调用会生成大量中间 event 对象，这些对象在 astream_events 消费完后应该被 GC 及时回收。我们确认了 async generator 正确使用 async for 消费，不会把整个事件流 buffer 在内存里。

第二是连接数。每个 SSE 长连接占用一个协程，虽然 asyncio 的协程很轻量（大约 1-2KB 栈空间），但每个连接背后还有 TCP socket 资源和 Uvicorn 的连接管理开销。操作系统层面的 file descriptor 限制（默认 1024）也可能成为瓶颈。我们的应对方式是：调整 ulimit -n 到 65535；设置 Uvicorn 的 --limit-max-requests 让 worker 定期重启释放可能的泄漏资源；通过 Prometheus 监控每个 worker 的活跃连接数，超过阈值触发告警。

第三是事件循环调度延迟。当并发协程数量增加时，事件循环的 select/poll 调用需要检查更多的 file descriptor，调度延迟会增加。在高并发场景下，SSE 心跳帧的发送间隔可能从 15 秒漂移到 20 秒甚至更多。我们通过多 worker 部署来分散压力，每个 worker 进程有独立的事件循环。同时在心跳间隔上留足余量——15 秒间隔对应 60 秒的 Nginx 超时，即使漂移 50% 也不会触发超时断开。

整体来说，Agent 长会话的性能优化思路是：控制单会话内存占用（历史裁剪）、控制并发连接数（多 worker + 监控告警）、保证关键路径的延迟（心跳余量设计）。

六、追问链路与防御要点

高频追问 1：你说的 Delta 增量推送，如果某个 Delta 丢了怎么办？前端渲染会不会出问题？

防御要点：正常情况下 SSE 基于 TCP 不会丢包。如果因为断线导致事件丢失，前端通过 Last-Event-ID 重连后会收到重发的事件。如果缓冲区已经过期无法重发，服务端发送 resync 事件，前端做全量刷新。关键是承认这个场景存在，并说明兜底方案，而不是说"不可能丢"。

高频追问 2：为什么不用 gRPC streaming？

防御要点：gRPC streaming 性能更好（二进制序列化 + HTTP/2 多路复用），但我们的场景是浏览器直连，浏览器对 gRPC 的支持需要 gRPC-Web 代理，增加了部署复杂度。SSE 天然被浏览器支持，不需要额外组件。如果是微服务间的流式通信，gRPC 是更好的选择。

高频追问 3：asyncio 协程泄漏怎么排查？

防御要点：用 asyncio.all_tasks() 查看当前事件循环中的所有活跃 Task。如果 Task 数量持续增长不释放，说明有协程泄漏。常见原因：create_task 后没有 await 或 cancel，或者 async generator 没有被正确关闭。可以用 Python 的 tracemalloc 模块追踪内存分配源头。

高频追问 4：SSE 和 HTTP/2 Server Push 有什么区别？

防御要点：HTTP/2 Server Push 是让服务端在客户端请求之前主动推送资源（比如推 CSS/JS 文件），目的是减少 RTT。SSE 是一个持续的事件流，目的是实时推送数据。两者解决的问题完全不同，不要混为一谈。
