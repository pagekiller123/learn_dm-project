二、核心知识精讲

2.1 Redis ZSet 做优先级队列的原理

Redis Sorted Set（ZSet）底层由 ziplist（元素少时）或 skiplist + hashtable（元素多时）实现。每个成员关联一个 score（float64），集合按 score 自动排序。核心特性：

  • ZADD 插入/更新：O(log N)
  • ZRANGEBYSCORE 按分数范围取成员：O(log N + M)
  • ZREM 删除指定成员：O(log N)，且为原子操作——这是无锁抢占的基础

Score 编码设计

我们将 score 设计为 优先级权重 * 10^13 + 时间戳（毫秒级）。这样：

  • 优先级高的 score 更小（高优先级权重值更低），排在 ZSet 前面，优先被消费
  • 同优先级内，时间戳更小的任务排前面，实现 FIFO
// score 编码示例
score = priority_weight * 1e13 + timestamp_ms

// priority=1 (高优先级), 提交时间 1700000000000
score = 1 * 1e13 + 1700000000000 = 11700000000000

// priority=5 (低优先级), 提交时间 1699999999000
score = 5 * 1e13 + 1699999999000 = 51699999999000

// 高优先级 score 更小，排在前面，即使提交时间更晚

2.2 ZRange + ZRem 无锁乐观抢占

"无锁"不是说完全没有同步机制，而是不需要显式的分布式锁（如 RedLock）。核心思路是利用 Redis 单线程执行模型和 ZREM 的原子性：

  1. 多个消费者同时执行 ZRANGEBYSCORE queue -inf +inf LIMIT 0 1 获取候选任务 ID
  2. 多个消费者可能拿到同一个任务 ID
  3. 所有消费者对该任务 ID 执行 ZREM queue taskId
  4. 由于 Redis 单线程，只有一个 ZREM 返回 1（删除成功），其他返回 0
  5. 返回 1 的消费者获得任务所有权，返回 0 的消费者跳过，重新拉取

Lua 脚本封装：更安全的原子操作

上述两步（ZRANGE + ZREM）虽然在逻辑上是安全的，但存在一个效率问题：多个消费者可能反复拉到同一个任务然后 ZREM 失败。用 Lua 脚本将两步合并为一个原子操作可以进一步优化：

-- Lua 脚本：原子地取出并删除一个最高优先级任务
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', '+inf', 'LIMIT', 0, 1)
if #tasks == 0 then
    return nil
end
local task = tasks[1]
local removed = redis.call('ZREM', KEYS[1], task)
if removed == 1 then
    return task    -- 抢占成功
else
    return nil     -- 被其他消费者抢走
end

Lua 脚本在 Redis 中以原子方式执行（单线程，脚本执行期间不会被其他命令打断），因此 ZRANGE 和 ZREM 之间不会有其他消费者插入。

为什么不用分布式锁？分布式锁（如 RedLock）引入额外的锁竞争、超时、续租等复杂性。而 ZREM 天然具有"谁删成功谁拥有"的语义，本质上是一种乐观并发控制——先做操作，通过返回值判断是否成功，失败则重试。这比悲观锁的性能更好，实现更简单。

2.3 加权轮询 + 降序兜底防饥饿

纯优先级调度的致命问题：高优先级任务持续涌入时，低优先级任务永远轮不到执行——即任务饥饿。解决方案是加权轮询（Weighted Round-Robin）。

算法模型

  1. 配额分配：每轮调度周期分配固定的调度槽位，高优先级占 70%，低优先级占 30%
  2. 配额内消费：先从高优先级队列消费，每消费一个任务扣减一个配额
  3. 配额耗尽切换：高优先级配额用完后，切换到低优先级队列消费
  4. 降序兜底：当某一级配额耗尽且该级队列为空时，剩余配额可被其他级别借用
// 加权轮询调度伪代码
func (s *Scheduler) weightedRoundRobin() {
    totalSlots := 10                     // 每轮 10 个调度槽位
    highQuota  := totalSlots * 70 / 100  // 高优先级 7 个
    lowQuota   := totalSlots - highQuota // 低优先级 3 个

    consumed := 0

    // 阶段一：消费高优先级队列
    for consumed < highQuota {
        task := popFromQueue("high_priority")
        if task == nil { break }
        dispatch(task)
        consumed++
    }

    // 阶段二：消费低优先级队列（保底 + 借用剩余配额）
    remaining := totalSlots - consumed
    for i := 0; i < remaining; i++ {
        task := popFromQueue("low_priority")
        if task == nil { break }
        dispatch(task)
    }

    // 降序兜底：如果低优先级也空了，高优先级可继续消费剩余槽位
    // （反之亦然）
}

25% 吞吐量提升的来源

提升并非来自单个环节，而是多个优化的叠加效果：

  • 减少空轮询：原先无配额机制时，调度器在高优先级队列反复轮询，低优先级队列几乎不被触及。加权轮询使两个队列都被有效利用，减少了空转
  • 降低重试开销：饥饿导致用户重复提交低优先级任务，产生大量重复入队和去重开销。饥饿问题解决后，重复提交率下降
  • 资源利用率提升：Worker 因为只收到高优先级任务导致负载不均（某些特定类型的 Worker 空闲），配额机制让任务分布更均匀

数据流

  1. 配置存储：运维人员在 etcd 写入 /config/concurrency/{userId}，值为该用户允许的最大并行任务数
  2. Watch 监听：每个 Scheduler 实例启动时 Watch 该前缀，收到 PUT/DELETE 事件后更新内存中的配置缓存
  3. 任务准入：任务入队时，用 atomic.LoadInt32 读取当前计数，与配置上限比较；未超限则 atomic.AddInt32(&counter, 1) 递增，超限则拒绝
  4. 任务完成：任务结束回调中 atomic.AddInt32(&counter, -1) 递减

Go sync/atomic 为什么线程安全

sync/atomic 包提供的操作（如 LoadInt32, AddInt32, CompareAndSwapInt32）在 CPU 指令层面是原子的，直接映射为 CPU 的 CAS（Compare-And-Swap）指令。在多 goroutine 并发场景下：

  • 不需要 sync.Mutex，避免锁竞争和上下文切换开销
  • AddInt32 返回新值，可用于即时判断是否超限
  • 底层由 Go runtime 保证内存可见性（happens-before 语义）

etcd Watch 断连重试

func watchConcurrencyConfig(cli *clientv3.Client, prefix string) {
    for {
        // Watch 返回一个 channel，阻塞读取事件
        watchChan := cli.Watch(context.Background(), prefix,
            clientv3.WithPrefix(),
            clientv3.WithPrevKV(),
        )

        for resp := range watchChan {
            if resp.Err() != nil {
                // Watch channel 关闭或出错，跳出内层循环触发重建
                log.Warnf("watch error: %v, reconnecting...", resp.Err())
                break
            }
            for _, ev := range resp.Events {
                updateConcurrencyLimit(ev) // 更新内存缓存
            }
        }

        // 到这里说明 Watch 断开，短暂等待后重建
        // etcd client-go 内部有自动重试，但外层兜底更安全
        time.Sleep(time.Second)
        reloadFullConfig(cli, prefix) // 重连后全量拉取一次，防止漏掉事件
    }
}
关键设计：全量拉取 + 增量 Watch。Watch 断连期间可能错过事件，重连后必须先做一次全量 GET，再开始 Watch。这是 etcd Watch 的标准模式，面试中提到这一点会加分。

Redis 批量操作的原子性

Redis 的 MGET、MSET 等批量命令本身是原子的，但 Pipeline 不是——Pipeline 只是批量发送命令减少 RTT，各命令之间可能被其他客户端的命令穿插。如果需要多步骤的原子操作，必须使用 Lua 脚本或 MULTI/EXEC 事务。

MongoDB 选型逻辑

AI 任务的参数字段高度异构：图像生成任务有 width, height, prompt, negative_prompt, steps；视频生成任务有 fps, duration, motion_strength；3D 任务有 mesh_format, texture_resolution。如果用 MySQL：

  • 要么建一张"大宽表"，100+ 列大多数为 NULL，查询效率低
  • 要么每种任务一张表，表数量爆炸，新增任务类型就要 DDL
  • 要么用 JSON 字段，但失去 MySQL 的强 schema 优势

MongoDB 的 Schema-free 特性天然适合这种场景：每个任务文档自描述字段，新增任务类型无需改表结构。加上 MongoDB 的水平扩展（sharding）能力，在任务量增长时更容易扩容。

三、面试易错点

易错点 1：把"无锁"理解为"完全没有同步机制"

正解：无锁指的是不使用显式的分布式锁（如 RedLock），但 ZREM 本身的原子性就是一种同步机制——它利用 Redis 单线程模型实现了"乐观并发控制"。面试时说"无锁"要紧跟解释用什么替代了锁。

易错点 2：把 Redis Pipeline 说成"原子操作"

正解：Pipeline 只减少了网络 RTT（客户端批量发送命令，服务端批量返回），但命令之间不保证原子性。真正的原子性要用 Lua 脚本（单线程执行，不被打断）或 MULTI/EXEC 事务（但事务内不能依赖中间结果做分支判断）。

易错点 3：etcd Watch 断连后直接重新 Watch 而不做全量拉取

正解：断连期间可能错过事件（PUT / DELETE），如果直接续 Watch，内存状态会与 etcd 不一致。正确做法是先全量 GET 重建状态，再 Watch 增量更新。这是 etcd Watch 的标准模式。

易错点 4：把 atomic.AddInt32 和 "先读后写"混淆

正解：if atomic.LoadInt32(&c) < limit { atomic.AddInt32(&c, 1) } 这段代码在高并发下不安全——Load 和 Add 之间可能被其他 goroutine 插入。正确做法是用 CompareAndSwapInt32 做 CAS 循环，或用 AddInt32 后检查返回值是否超限，超限则回退（AddInt32(&c, -1)）。

易错点 5：说 MongoDB 比 MySQL "性能更好"

正解：MongoDB 的优势不在于绝对性能，而在于 Schema 灵活性和水平扩展能力。在固定 schema、复杂事务的场景下，MySQL 反而更合适。面试时要强调"场景适配"而非"绝对优劣"。

四、满分逐字稿

Q1 满分逐字稿

为什么选用 Redis ZSet 做优先级队列？不用 RabbitMQ、Kafka？

我们选 Redis ZSet 做优先级队列，核心原因有三个。

第一，优先级表达能力。我们的 AI 任务有多个优先级等级，需要在同一个队列里按优先级连续排序。ZSet 的 score 是浮点数，可以编码为"优先级权重乘以 10 的 13 次方加上毫秒级时间戳"，这样既保证高优先级排前面，同优先级内又按 FIFO 排序。RabbitMQ 虽然支持优先级队列，但它是离散的，最多 255 级，而且需要在创建队列时预先声明，灵活性不够。Kafka 本身没有原生优先级概念，要么用多 topic 模拟，要么在消费端排序，都比较 hack。

第二，消费模型匹配。我们的调度器是主动拉取模型——worker-scheduler 按轮次主动去队列取任务、分配给 worker。ZSet 的 ZRANGEBYSCORE 加 ZREM 天然支持这种"拉取-竞争-确认"的消费模式，而且 ZREM 的原子性让多个消费者竞争时不需要额外的分布式锁。RabbitMQ 是推模式，需要 consumer 注册回调和 ACK 机制，跟我们的调度模型不太匹配。

第三，基础设施复用。平台本身已经有 Redis 集群用于缓存和会话管理，新增一个 ZSet 几乎零运维成本。如果上 RabbitMQ 或 Kafka，需要额外部署和维护一套消息中间件集群，对我们这个中等吞吐量的场景来说投入产出比不划算。我们的任务量级大概是每秒几十到几百个任务入队，远达不到需要 Kafka 百万级吞吐的程度。

当然 ZSet 也有局限性——它没有消息持久化保证（虽然 Redis 有 AOF/RDB，但不如 Kafka 的副本机制强）、没有死信队列、没有消费组的 offset 管理。这些我们通过 MongoDB 记录任务状态来补偿：任务入队同时写 MongoDB 做持久化，任务超时未完成由定时任务扫描 MongoDB 做补偿重投。

Q2 满分逐字稿

ZRange + ZRem 无锁乐观抢占的执行流程？为什么不需要分布式锁？如何保证并发消费不重复？

我来详细讲一下整个消费流程。

第一步，候选拉取。消费者调用 ZRANGEBYSCORE queue -inf +inf LIMIT 0 1，从 ZSet 中取出 score 最小的一个任务 ID——也就是当前最高优先级的任务。这一步是只读操作，多个消费者可以同时执行，可能拿到同一个任务 ID。

第二步，竞争删除。拿到任务 ID 后，消费者立即执行 ZREM queue taskId。这是关键：ZREM 是 Redis 的原子操作，在 Redis 单线程模型下，多个 ZREM 命令是串行执行的。第一个执行的 ZREM 返回 1 表示删除成功，后续对同一个 taskId 的 ZREM 返回 0 表示元素已不存在。

第三步，所有权确认。消费者检查 ZREM 的返回值：返回 1 则获得该任务的所有权，开始执行；返回 0 则说明被其他消费者抢走了，回到第一步重新拉取。

为什么不需要分布式锁？传统方案是先加分布式锁、再读取任务、再删除任务、最后释放锁。锁带来几个问题：一是锁本身的获取有竞争开销，在高并发下会成为瓶颈；二是锁超时和续租的复杂性，如果持锁的消费者挂了，需要等锁过期才能释放；三是 RedLock 实现本身有争议——Martin Kleppmann 和 Salvatore Sanfilippo 的那场著名辩论说的就是这个问题。而 ZREM 天然具有"谁删成功谁拥有"的语义，本质上是乐观并发控制，不存在锁超时和续租的问题。

在实际工程中，我们进一步用 Lua 脚本把 ZRANGEBYSCORE 和 ZREM 封装为一个原子操作。这样的好处是减少了"多个消费者拉到同一个任务后竞争失败"的概率——Lua 脚本在 Redis 中原子执行，取出和删除之间不会被其他命令穿插，第一个执行 Lua 脚本的消费者必然抢到任务。这让空转率从大约 30% 降到了接近 0。

至于"会不会漏消费"——不会。如果 ZREM 失败，消费者会立刻重新拉取下一个任务，ZSet 中其他任务不受影响。如果消费者在 ZREM 成功后崩溃了，这个任务确实会丢失在 ZSet 层面，但我们在 MongoDB 里有任务状态记录，定时任务会扫描状态为"已分配但超时未完成"的任务进行补偿重投。

Q3 满分逐字稿

低优先级任务饥饿问题怎么解决？加权轮询 + 降序兜底的具体算法逻辑？

任务饥饿是纯优先级调度的经典问题。在我们上线初期确实遇到过：高优先级任务持续涌入，低优先级任务在队列里积压了几个小时都没有被消费。用户投诉说"普通任务提交了半天没结果"。

我们的解决方案是加权轮询调度加降序兜底。

具体算法是这样的：每轮调度周期，我们按配置分配调度槽位。比如总共 10 个槽位，高优先级配额 70% 即 7 个，低优先级配额 30% 即 3 个。调度器先从高优先级队列消费，每消费一个任务，高优先级配额减 1，直到配额耗尽或者队列为空。然后切换到低优先级队列，用剩余的槽位消费低优先级任务。

降序兜底机制是对配额制的补充：当高优先级配额用完后，如果高优先级队列还有剩余任务，它们不会占用低优先级的配额——低优先级的 3 个槽位是"保底的"。反过来，如果高优先级队列为空，它的剩余配额可以借给低优先级使用，这样不浪费算力。再反过来说，如果低优先级队列也空了，剩余槽位还可以回流给高优先级。这个"空了就让"的逻辑保证了算力不会因为某一级队列为空而闲置。

70/30 这个比例是根据业务实际调优的。我们统计了一段时间的任务分布：高优先级任务大约占总量的 60-70%，低优先级占 30-40%。70/30 的配额保证了在典型负载下两边都不会饥饿，同时给了高优先级任务合理的优先权。这个比例写在配置中心，可以根据业务变化动态调整，不需要改代码重新部署。

效果方面，上线加权轮询后，低优先级任务的平均等待时间从原来的几十分钟降到了几分钟内，调度吞吐量整体提升了大约 25%。这个提升来自三个方面：一是减少了空轮询——原来调度器反复扫高优先级队列，现在按配额分配更均匀；二是减少了用户因饥饿而重复提交造成的重复入队开销；三是 Worker 的负载更均衡了，某些只处理低优先级任务类型的 Worker 从闲置变成了有活干。

Q4 满分逐字稿

etcd Watch + 内存原子计数器做用户并发管控：原子计数器为什么线程安全？etcd Watch 断连重试怎么处理？

我先讲架构，再分别讲原子计数器和 Watch 断连。

整体架构：我们用 etcd 存储每个用户的最大并发任务数配置，key 是 /config/concurrency/{userId}，value 是数字。每个 Scheduler 实例启动时 Watch 这个前缀，收到变更事件后更新内存中的配置缓存。任务准入判断时，用 Go 的 sync/atomic 包维护每个用户当前正在运行的任务计数。

为什么 atomic 计数器是线程安全的？sync/atomic 包的操作直接映射为 CPU 的原子指令，比如 x86 上的 LOCK XADD。这个 LOCK 前缀保证指令执行期间独占缓存行，其他 CPU 核心不能同时修改同一个内存地址。具体使用上，我们在任务准入时调用 atomic.AddInt32(&counter, 1)，它返回新值，如果新值超过配置上限就立刻 atomic.AddInt32(&counter, -1) 回退并拒绝任务。在任务完成回调中调用 atomic.AddInt32(&counter, -1) 递减。这比用 Mutex 性能好很多，因为 atomic 操作没有锁竞争、没有 goroutine 挂起和唤醒的开销。

这里有个细节：为什么不用 if Load < limit then Add？因为 Load 和 Add 之间存在竞态——两个 goroutine 同时 Load 都看到 4，都小于 limit 5，都 Add，结果变成 6 超限了。正确做法是先 Add 再检查，超了就回退，这样的 CAS 语义才是安全的。

etcd Watch 断连重试怎么处理？这是 etcd Watch 的标准问题。我们的做法是三层保障：第一层，etcd 的 Go client（clientv3）内部有自动重连和重试机制，大多数短暂的网络抖动它自己就处理了。第二层，我们在外层套了 for 循环，如果 Watch channel 关闭或返回错误，等待 1 秒后重建 Watch。第三层也是最关键的：重连后不直接续 Watch，而是先做一次全量 GET——用 clientv3.Get 加 WithPrefix 拉取所有配置，重建内存缓存，然后再开始 Watch。因为断连期间可能错过了配置变更事件，如果直接续 Watch，内存状态和 etcd 会不一致。

这个"全量拉取加增量 Watch"的模式其实是 Kubernetes Informer 的核心设计思路，我们只是在小规模场景下用了同样的方法。

Q5 满分逐字稿

单用户并行任务限制，如果瞬间大量请求打进来，是限流、排队还是直接丢弃？策略是什么？

我们采用的策略是排队为主，限流兜底，不会直接丢弃。

具体来说，并发管控发生在两个层面。第一层是准入限制：当用户当前正在运行的任务数达到上限（比如 5 个），新提交的任务不会被丢弃，而是正常入 Redis ZSet 队列排队，但不会被调度器分配给 Worker 执行。调度器在分配任务时会检查该用户的原子计数器，如果已满就跳过这个任务，去消费其他用户的任务。等该用户有任务完成、计数器递减后，下一轮调度就会取到这个排队中的任务。

第二层是入队限流：如果用户瞬间提交了大量任务（比如脚本跑批），入队阶段有速率限制，防止短时间内把 Redis ZSet 撑满。这一层用的是标准的令牌桶限流——每个用户每秒最多入队 N 个任务，超过的请求返回 429 Too Many Requests，由客户端做退避重试。

为什么不直接丢弃？因为 AI 生成任务通常是用户主动发起的，每个任务对用户来说都有价值。直接丢弃用户体验很差——用户不知道任务丢了还是在排队。排队可以给用户一个明确的预期："你的任务在第 X 位，预计等待 Y 分钟"。只有在极端情况下（队列积压超过系统容量阈值），我们才会触发熔断拒绝新任务，但这属于系统级保护而非用户级管控。

从效果看，上线并发管控后，单用户独占算力的问题基本消除了。之前最严重的时候一个自动化脚本用户占了集群 40% 的算力，其他用户排队时间翻倍。限制后每个用户最多占用固定的并行槽位，整体的任务平均等待时间下降了明显。

Q6 满分逐字稿

你 Go 开发过程中，分布式队列并发安全怎么保证？

我从三个层面来讲我们的并发安全保障。

第一层是 Redis 层面的跨进程并发安全。多个 Scheduler 实例同时消费同一个 Redis ZSet 队列，并发安全靠两个机制：一是 ZREM 的原子性——Redis 单线程模型保证同一时刻只有一个 ZREM 执行成功；二是 Lua 脚本封装——把 ZRANGEBYSCORE 和 ZREM 组合成一个原子脚本，消除两步之间的竞态窗口。实际上就是前面讲的无锁乐观抢占方案。

第二层是进程内的 goroutine 并发安全。在单个 Scheduler 实例内，多个 goroutine 共享内存数据结构。我们按场景选择不同的同步原语：对于用户并发计数器这种简单的整数操作，用 sync/atomic，性能最好；对于任务状态 map 这种复杂数据结构的读写，用 sync.RWMutex，允许多读单写；对于 goroutine 间的任务分发，用 buffered channel 做解耦，生产者往 channel 写、消费者从 channel 读，channel 自身保证并发安全。

第三层是业务层面的幂等保障。分布式环境下，网络抖动可能导致任务被重复投递或重复完成回调。我们在 MongoDB 中用任务 ID 做幂等键：任务状态更新用 findOneAndUpdate 加条件 status: "running"，只有当前状态匹配才更新。如果任务已经被标记为"完成"或"失败"，重复的完成回调不会产生副作用。

一个踩过的坑是：早期我们用 sync.Map 存任务状态缓存，以为它并发安全就万事大吉了。后来发现在"读取-判断-更新"这种复合操作上，sync.Map 的单次操作虽然安全，但多步组合依然有竞态。改成 sync.RWMutex 保护整个复合操作后问题才解决。这也让我深刻理解了"原子操作安全"和"业务逻辑安全"是两个层次的问题。

Q7 满分逐字稿

Redis 批量操作有没有原子性问题？如何避免超卖、重复消费？

这个问题很好，Redis 批量操作的原子性是一个容易踩坑的地方。

首先要区分三种"批量"：第一种是 MGET、MSET 这样的多键命令，它们在 Redis 中是单条命令，原子执行；第二种是 Pipeline，它只是把多条命令打包发送减少网络 RTT，但服务端仍然是逐条执行的，不保证原子性——中间可能被其他客户端的命令穿插；第三种是 MULTI/EXEC 事务，它保证事务内的命令要么全部执行要么全不执行，但有个关键限制——事务内不能根据中间结果做分支判断，因为所有命令在 EXEC 时才一起执行。

在我们的场景中避免超卖和重复消费的做法：任务从 ZSet 中取出并删除这个操作，我们用 Lua 脚本保证原子性。Lua 脚本在 Redis 中以单线程方式执行，脚本执行期间不会被其他命令打断，所以 ZRANGEBYSCORE 和 ZREM 之间不存在竞态。ZREM 返回 1 就是获得了所有权，返回 0 就是别人先抢到了，不存在超卖。

重复消费的防线有两道：第一道是 ZREM 的原子性——任务从 ZSet 中被删除后就不可能被第二个消费者取到；第二道是 MongoDB 中的任务状态机——任务从 "pending" 到 "running" 的状态转换用 findOneAndUpdate 加前置条件，只有状态为 "pending" 才能更新为 "running"。即使极端情况下 Redis 那层出问题（比如主从切换导致数据短暂不一致），MongoDB 这层也能兜住，不会重复执行。

还有一个实践经验：我们早期用 Pipeline 批量获取多个任务的信息，发现偶尔会有数据不一致的问题——A 命令读到了 B 命令还没来得及写的旧值。后来改成 Lua 脚本后问题消失了。所以我们的经验是：如果多个操作之间有逻辑依赖，必须用 Lua 脚本，Pipeline 不够用。

Q8 满分逐字稿

MongoDB 存储任务信息，为什么选 Mongo 不选 MySQL？任务字段频繁变更的场景优势是什么？

我们选 MongoDB 存储任务信息，核心原因是 AI 任务的参数字段高度异构。

具体来说，我们平台支持十几种不同类型的 AI 任务——图像生成、视频生成、3D 模型生成、语音合成等等。每种任务的参数完全不同：图像任务有 width、height、prompt、negative_prompt、steps、cfg_scale 这些字段；视频任务有 fps、duration、motion_strength、camera_motion；3D 任务有 mesh_format、texture_resolution、poly_count。而且随着我们接入新的 AI 供应商和新的模型能力，参数字段在频繁变化——平均每两周就会新增一种任务类型或者给现有类型加新参数。

如果用 MySQL，有三个方案，都不理想。第一是"大宽表"方案，把所有可能的字段都建成列，一张表一百多列，大多数记录 90% 的列是 NULL，查询效率低，而且每次新增字段要做 ALTER TABLE，线上大表改结构风险很高。第二是"多表"方案，每种任务类型一张表，表的数量随任务类型增长，JOIN 查询复杂度高，新增任务类型要建新表还要改代码。第三是用 MySQL 的 JSON 字段来存可变参数，这其实是个折中，但失去了 MySQL 强 schema 的类型检查优势，而且 MySQL 的 JSON 查询性能不如 MongoDB 的 BSON。

MongoDB 的 Schema-free 特性天然适合这个场景。每个任务文档自描述字段结构，图像任务的文档和视频任务的文档可以有完全不同的字段，存在同一个 collection 里。新增任务类型只需要在代码里定义新的参数结构体，直接写入 MongoDB，不需要任何 DDL 操作。而且 MongoDB 对嵌套文档和数组有很好的查询支持，任务参数可以自然地用嵌套结构表达。

另外一个考量是水平扩展。随着平台用户增长，任务量级从初期的日均几万增长到日均几十万。MongoDB 的 sharding 机制支持按 userId 或 taskType 做分片，水平扩展比较自然。MySQL 做分库分表需要中间件（比如 ShardingSphere），引入额外的复杂性。

当然 MongoDB 也有取舍——它不支持跨文档事务（4.0 以后支持但性能有损），所以我们的任务状态更新都是单文档操作，用 findOneAndUpdate 加条件保证原子性。涉及跨任务的统计查询，我们用聚合管道或者离线同步到分析数据库来做，不依赖 MongoDB 的事务。
