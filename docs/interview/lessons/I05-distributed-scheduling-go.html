二、核心知识精讲

2.1 Redis ZSet 做优先级队列的原理

Redis Sorted Set（ZSet）底层由 ziplist（元素少时）或 skiplist + hashtable（元素多时）实现。每个成员关联一个 score（float64），集合按 score 自动排序。核心特性：

  • ZADD 插入/更新：O(log N)
  • ZRANGEBYSCORE 按分数范围取成员：O(log N + M)
  • ZREM 删除指定成员：O(log N)，且为原子操作——这是无锁抢占的基础

多队列隔离 + 时间戳排序

DM 的优先级调度不是在一个 ZSet 里用 score 编码优先级，而是不同优先级对应不同的 Redis key（不同的 ZSet 队列），每个队列内 score = 纯毫秒时间戳，实现同优先级内先来先服务（FIFO）。

// key 格式：apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}
// priority=0 时省略 priority 段（向后兼容旧格式）

// 普通优先级队列
apps_pending_task::dm::default::v2prod::prod

// 高优先级队列（priority=2）
apps_pending_task::2::dm::default::v2prod::prod

// score = 毫秒时间戳（PreprocessTime），纯 FIFO
ZAdd("apps_pending_task::2::dm::default::v2prod::prod", 1700000000000, "user1::task-A")
ZAdd("apps_pending_task::dm::default::v2prod::prod",    1700000001000, "user2::task-B")

优先级调度靠 WeightedScheduler 在多个队列之间做加权轮询（比如高优 70% / 低优 30% 的配额分配），而不是靠 score 在单个 ZSet 内排序。详见 2.3 节。

面试易错点：不要说"score 编码了优先级"或"所有任务在同一个 ZSet 里按优先级排序"。实际设计是多 key 隔离 + 加权轮询，这才是真实的工程方案。多 key 隔离的好处：每个队列的 ZRange 扫描量小、不同优先级可以独立限流、Worker 按 cluster 精确消费。

2.2 ZRange + ZRem 无锁乐观抢占

"无锁"不是说完全没有同步机制，而是不需要显式的分布式锁（如 RedLock）。核心思路是利用 Redis 单线程执行模型和 ZREM 的原子性。

实际执行流程（tryConsume + grabJob）

  1. 批量候选拉取：消费者调用 ZRange(key, 0, 255)，一次取出该优先级队列中最多 256 个候选（按 score 即时间戳排序，最早的在前）
  2. 遍历 + 用户并发检查：对每个 member（格式 user::taskID），检查该 user 是否已有任务在运行。有并发冲突的暂存到 queueJob 列表跳过
  3. 竞争删除（grabJob）：对无冲突的 member 执行 ZREM key member
  4. 由于 Redis 单线程，只有一个 ZREM 返回 ≥ 1（删除成功），其他返回 0
  5. 返回 ≥ 1 的消费者获得任务所有权 → 从 MongoDB 加载完整数据 → 注册 etcd → 执行
  6. 返回 0 的消费者继续遍历列表中下一个候选（不需要重新 ZRange）
  7. 二轮兜底：第一轮遍历完后，对 queueJob 中跳过的 member 再做一轮 grabJob

为什么没有用 Lua 脚本合并 ZRange + ZRem？

有人可能会想：把 ZRange 和 ZRem 封装成一个 Lua 脚本原子执行，不就消除了竞态窗口吗？确实可以，但我们实际代码没有这样做，原因是：

  • 中间需要业务判断：ZRange 拿到候选后，还要检查用户并发（查 concurrentManager）、检查 member 格式是否合法等逻辑。这些判断涉及 Go 进程内存中的状态，无法在 Redis Lua 脚本里完成
  • 批量拉取 + 逐个尝试的模式足够高效：一次拉 256 个候选，即使前几个被抢了，后面还有大量候选可以尝试，不需要反复网络往返
  • 实际竞争压力不大：DM 的任务量级是每秒几十到几百，多 Scheduler 实例并发扫同一队列的频率不高，空竞争率实测很低
为什么不用分布式锁？分布式锁（如 RedLock）引入额外的锁竞争、超时、续租等复杂性。而 ZREM 天然具有"谁删成功谁拥有"的语义，本质上是一种乐观并发控制——先做操作，通过返回值判断是否成功，失败则继续下一个候选。这比悲观锁的性能更好，实现更简单。

2.3 加权轮询 + 降序兜底防饥饿

纯优先级调度的致命问题：高优先级任务持续涌入时，低优先级任务永远轮不到执行——即任务饥饿。解决方案是加权轮询（Weighted Round-Robin）。

算法模型

  1. 配额分配：每轮调度周期分配固定的调度槽位，高优先级占 70%，低优先级占 30%
  2. 配额内消费：先从高优先级队列消费，每消费一个任务扣减一个配额
  3. 配额耗尽切换：高优先级配额用完后，切换到低优先级队列消费
  4. 降序兜底：当某一级配额耗尽且该级队列为空时，剩余配额可被其他级别借用
// 加权轮询调度伪代码
func (s *Scheduler) weightedRoundRobin() {
    totalSlots := 10                     // 每轮 10 个调度槽位
    highQuota  := totalSlots * 70 / 100  // 高优先级 7 个
    lowQuota   := totalSlots - highQuota // 低优先级 3 个

    consumed := 0

    // 阶段一：消费高优先级队列
    for consumed < highQuota {
        task := popFromQueue("high_priority")
        if task == nil { break }
        dispatch(task)
        consumed++
    }

    // 阶段二：消费低优先级队列（保底 + 借用剩余配额）
    remaining := totalSlots - consumed
    for i := 0; i < remaining; i++ {
        task := popFromQueue("low_priority")
        if task == nil { break }
        dispatch(task)
    }

    // 降序兜底：如果低优先级也空了，高优先级可继续消费剩余槽位
    // （反之亦然）
}

25% 吞吐量提升的来源

提升并非来自单个环节，而是多个优化的叠加效果：

  • 减少空轮询：原先无配额机制时，调度器在高优先级队列反复轮询，低优先级队列几乎不被触及。加权轮询使两个队列都被有效利用，减少了空转
  • 降低重试开销：饥饿导致用户重复提交低优先级任务，产生大量重复入队和去重开销。饥饿问题解决后，重复提交率下降
  • 资源利用率提升：Worker 因为只收到高优先级任务导致负载不均（某些特定类型的 Worker 空闲），配额机制让任务分布更均匀

2.4 etcd Watch + 内存原子计数器做用户并发管控

数据流

  1. 配置存储：运维人员在 etcd 写入 /config/concurrency/{userId}，值为该用户允许的最大并行任务数
  2. Watch 监听：每个 Scheduler 实例启动时 Watch 该前缀，收到 PUT/DELETE 事件后更新内存中的配置缓存
  3. 任务准入：任务入队时，用 atomic.LoadInt32 读取当前计数，与配置上限比较；未超限则 atomic.AddInt32(&counter, 1) 递增，超限则拒绝
  4. 任务完成：任务结束回调中 atomic.AddInt32(&counter, -1) 递减

Go sync/atomic 为什么线程安全

sync/atomic 包提供的操作（如 LoadInt32, AddInt32, CompareAndSwapInt32）在 CPU 指令层面是原子的，直接映射为 CPU 的 CAS（Compare-And-Swap）指令。在多 goroutine 并发场景下：

  • 不需要 sync.Mutex，避免锁竞争和上下文切换开销
  • AddInt32 返回新值，可用于即时判断是否超限
  • 底层由 Go runtime 保证内存可见性（happens-before 语义）

etcd Watch 断连重试

func watchConcurrencyConfig(cli *clientv3.Client, prefix string) {
    for {
        // Watch 返回一个 channel，阻塞读取事件
        watchChan := cli.Watch(context.Background(), prefix,
            clientv3.WithPrefix(),
            clientv3.WithPrevKV(),
        )

        for resp := range watchChan {
            if resp.Err() != nil {
                // Watch channel 关闭或出错，跳出内层循环触发重建
                log.Warnf("watch error: %v, reconnecting...", resp.Err())
                break
            }
            for _, ev := range resp.Events {
                updateConcurrencyLimit(ev) // 更新内存缓存
            }
        }

        // 到这里说明 Watch 断开，短暂等待后重建
        // etcd client-go 内部有自动重试，但外层兜底更安全
        time.Sleep(time.Second)
        reloadFullConfig(cli, prefix) // 重连后全量拉取一次，防止漏掉事件
    }
}
关键设计：全量拉取 + 增量 Watch。Watch 断连期间可能错过事件，重连后必须先做一次全量 GET，再开始 Watch。这是 etcd Watch 的标准模式，面试中提到这一点会加分。

2.5 Go 工程实践要点

并发安全层次

层级机制适用场景
Redis 层ZRem 原子性（单线程串行执行）跨进程的任务抢占

Redis 批量操作的原子性

Redis 的 MGET、MSET 等批量命令本身是原子的，但 Pipeline 不是——Pipeline 只是批量发送命令减少 RTT，各命令之间可能被其他客户端的命令穿插。如果需要多步骤的原子操作，必须使用 Lua 脚本或 MULTI/EXEC 事务。

MongoDB 选型逻辑

AI 任务的参数字段高度异构：图像生成任务有 width, height, prompt, negative_prompt, steps；视频生成任务有 fps, duration, motion_strength；3D 任务有 mesh_format, texture_resolution。如果用 MySQL：

  • 要么建一张"大宽表"，100+ 列大多数为 NULL，查询效率低
  • 要么每种任务一张表，表数量爆炸，新增任务类型就要 DDL
  • 要么用 JSON 字段，但失去 MySQL 的强 schema 优势

MongoDB 的 Schema-free 特性天然适合这种场景：每个任务文档自描述字段，新增任务类型无需改表结构。加上 MongoDB 的水平扩展（sharding）能力，在任务量增长时更容易扩容。

三、面试易错点

易错点 1：把"无锁"理解为"完全没有同步机制"

正解：无锁指的是不使用显式的分布式锁（如 RedLock），但 ZREM 本身的原子性就是一种同步机制——它利用 Redis 单线程模型实现了"乐观并发控制"。面试时说"无锁"要紧跟解释用什么替代了锁。

易错点 2：把 Redis Pipeline 说成"原子操作"

正解：Pipeline 只减少了网络 RTT（客户端批量发送命令，服务端批量返回），但命令之间不保证原子性。真正的原子性要用 Lua 脚本（单线程执行，不被打断）或 MULTI/EXEC 事务（但事务内不能依赖中间结果做分支判断）。

易错点 3：etcd Watch 断连后直接重新 Watch 而不做全量拉取

正解：断连期间可能错过事件（PUT / DELETE），如果直接续 Watch，内存状态会与 etcd 不一致。正确做法是先全量 GET 重建状态，再 Watch 增量更新。这是 etcd Watch 的标准模式。

易错点 4：把 atomic.AddInt32 和 "先读后写"混淆

正解：if atomic.LoadInt32(&c) < limit { atomic.AddInt32(&c, 1) } 这段代码在高并发下不安全——Load 和 Add 之间可能被其他 goroutine 插入。正确做法是用 CompareAndSwapInt32 做 CAS 循环，或用 AddInt32 后检查返回值是否超限，超限则回退（AddInt32(&c, -1)）。

易错点 5：说 MongoDB 比 MySQL "性能更好"

正解：MongoDB 的优势不在于绝对性能，而在于 Schema 灵活性和水平扩展能力。在固定 schema、复杂事务的场景下，MySQL 反而更合适。面试时要强调"场景适配"而非"绝对优劣"。

四、满分逐字稿

Q1 满分逐字稿

为什么选用 Redis ZSet 做优先级队列？不用 RabbitMQ、Kafka？

我们选 Redis ZSet 做优先级队列，核心原因有三个。

第一，优先级表达能力和调度灵活性。我们的 AI 任务有多个优先级等级，我们按优先级把任务分到不同的 Redis key——每个 key 就是一个独立的 ZSet 队列。key 格式大致是 apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}，不同优先级直接在 key 层隔离。每个队列内部的 score 是纯毫秒时间戳，保证同优先级内先来先服务。优先级之间的调度靠加权轮询——调度器按配额比例（比如高优 70%、低优 30%）分别从不同优先级队列消费，避免低优先级饥饿。RabbitMQ 虽然也支持优先级队列，但它是离散的，最多 255 级，需要创建队列时预声明，灵活性不够。Kafka 本身没有原生优先级概念，要么用多 topic 模拟，要么在消费端排序，都比较 hack。

第二，消费模型匹配。我们的调度器是主动拉取模型——worker-scheduler 按轮次主动去队列取任务、分配给 worker。ZSet 的 ZRANGEBYSCORE 加 ZREM 天然支持这种"拉取-竞争-确认"的消费模式，而且 ZREM 的原子性让多个消费者竞争时不需要额外的分布式锁。RabbitMQ 是推模式，需要 consumer 注册回调和 ACK 机制，跟我们的调度模型不太匹配。

第三，基础设施复用。平台本身已经有 Redis 集群用于缓存和会话管理，新增一个 ZSet 几乎零运维成本。如果上 RabbitMQ 或 Kafka，需要额外部署和维护一套消息中间件集群，对我们这个中等吞吐量的场景来说投入产出比不划算。我们的任务量级大概是每秒几十到几百个任务入队，远达不到需要 Kafka 百万级吞吐的程度。

当然 ZSet 也有局限性——它没有消息持久化保证（虽然 Redis 有 AOF/RDB，但不如 Kafka 的副本机制强）、没有死信队列、没有消费组的 offset 管理。这些我们通过 MongoDB 记录任务状态来补偿：任务入队同时写 MongoDB 做持久化，任务超时未完成由定时任务扫描 MongoDB 做补偿重投。

Q2 满分逐字稿

ZRange + ZRem 无锁乐观抢占的执行流程？为什么不需要分布式锁？如何保证并发消费不重复？

我来详细讲一下整个消费流程。我们的实现是 tryConsume 和 grabJob 两个函数配合完成的。

第一步，批量候选拉取。消费者调用 ZRange(key, 0, 255)，一次性从指定优先级队列的 ZSet 中取出最多 256 个候选成员（按 score 即提交时间从小到大排列，最早提交的排前面）。这一步是只读操作，多个消费者可以同时执行，可能拿到相同的候选列表。批量拉取而非逐个拉取是为了减少 Redis 网络往返。

第二步，遍历筛选 + 并发检查。遍历候选列表，对每个 member（格式是 user::taskID）做两件事：第一，检查这个 user 当前是否已经有任务在运行（通过 concurrentManager.GetUser() 查询）。如果该用户已有并发任务，就先把这个 member 放进一个 queueJob 列表跳过，留到第二轮再尝试。如果无并发冲突，进入第三步。

第三步，竞争删除（grabJob）。对选中的 member 执行 ZREM key member。这是关键：ZREM 是 Redis 的原子操作，在 Redis 单线程模型下，多个 ZREM 命令是串行执行的。第一个执行的 ZREM 返回值 ≥ 1 表示删除成功（抢到了），后续对同一个 member 的 ZREM 返回 0 表示元素已不存在（被别人抢走了）。

第四步，所有权确认。检查 ZREM 的返回值：返回值 ≥ 1 则获得该任务的所有权，接着从 MongoDB 加载完整任务数据、注册到 etcd，开始执行；返回 0 则说明被其他消费者抢走了，继续遍历列表中的下一个候选（不需要重新 ZRange）。

第五步，二轮兜底。第一轮遍历完后，如果还没抢到任务，会对 queueJob 中暂时跳过的 member 再做一轮 grabJob 尝试。这是公平性和吞吐量的权衡——第一轮优先跳过已有并发任务的用户（公平优先，不让一个用户独占资源），第二轮再回头消费这些被跳过的任务（吞吐兜底，不让算力空转）。

为什么不需要分布式锁？传统方案是先加分布式锁、再读取任务、再删除任务、最后释放锁。锁带来几个问题：一是锁本身的获取有竞争开销，在高并发下会成为瓶颈；二是锁超时和续租的复杂性，如果持锁的消费者挂了，需要等锁过期才能释放；三是 RedLock 实现本身有争议——Martin Kleppmann 和 Salvatore Sanfilippo 的那场著名辩论说的就是这个问题。而 ZREM 天然具有"谁删成功谁拥有"的语义，本质上是乐观并发控制（类似 CAS），不存在锁超时和续租的问题。

关于 ZRange 和 ZRem 分离的竞态问题。有人可能会问：ZRange 和 ZRem 是两条独立的 Redis 命令，中间有时间窗口，多个消费者 ZRange 看到同一个 member，然后都去 ZRem 竞争，这不是浪费吗？确实存在一定的"空竞争"概率。但在我们的场景下，这个代价可以接受：第一，批量拉 256 个候选意味着即使前几个被抢了，后面还有大量候选可以尝试，不需要重新拉取；第二，Redis 单线程模型下 ZRem 执行极快（微秒级），竞争窗口很短；第三，在 DM 的实际任务量级下（每秒几十到几百个入队），多 Scheduler 实例同时扫同一个队列的并发度不高，实际空竞争率很低。

至于"会不会漏消费"——不会。如果 ZREM 竞争失败，消费者继续遍历列表中的下一个候选。如果消费者在 ZREM 成功后崩溃了，这个任务确实会丢失在 ZSet 层面，但我们在 MongoDB 里有任务状态记录，定时任务会扫描状态为"已分配但超时未完成"的任务进行补偿重投。

Q3 满分逐字稿

低优先级任务饥饿问题怎么解决？加权轮询 + 降序兜底的具体算法逻辑？

任务饥饿是纯优先级调度的经典问题。如果用严格优先级策略——"高优先级队列非空就不看低优先级"——那高负载时低优先级任务会完全饿死。在我们上线初期确实遇到过：高优先级任务持续涌入，低优先级任务在队列里积压了几个小时都没有被消费。用户投诉说"普通任务提交了半天没结果"。

我们的解决方案是 WeightedScheduler 加权轮询 + 降序兜底，三层消费策略。

加权轮询的核心机制是 WeightedScheduler，代码在 pkg/priority/scheduler.go。它为每个优先级维护一个配额计数器（counter），初始值等于配置的 weight。每次调 NextPriority() 时，按 priority 降序找到第一个 counter > 0 的优先级，返回它并把 counter 减 1。当所有 counter 都归零时，全部重置回初始 weight，开始新一轮。

举个例子：配置 [{priority:5, weight:5}, {priority:0, weight:3}]。一轮 8 次消费中，priority=5 被选 5 次，priority=0 被选 3 次。因为 pickPriority 按降序遍历，所以前 5 次都选 priority=5（高优先级先消耗配额），后 3 次选 priority=0。然后配额全部重置，新一轮开始。

三层消费策略在 commonAction.Consume() 里实现：

  • 第一层（无配置兼容）：如果没有配置 queues，等价于旧行为，只消费 priority=0 的队列
  • 第二层（加权选择）：调 WeightedScheduler.NextPriority() 选出一个优先级，尝试 tryConsume 从对应队列消费。如果成功拿到任务就返回
  • 第三层（降序兜底）：如果加权选的队列是空的（没有任务可消费），不浪费这次消费机会——按 priority 降序逐个尝试所有声明的队列，谁有任务就消费谁

降序兜底的作用：假设这一轮 WeightedScheduler 选了 priority=5，但 priority=5 的队列恰好空了。如果没有兜底，这次 Consume 调用就白跑了。有了降序兜底，它会继续尝试 priority=3、priority=0 等其他队列，只要有任务就消费。这保证了算力不会因为某一级队列为空而闲置。

为什么叫"降序"兜底：兜底遍历时仍然按 priority 从高到低的顺序尝试（AllPriorities 返回降序列表），所以在兜底阶段依然优先消费高优先级任务。这是一个保底机制，不是打破优先级的机制。

防饥饿的关键是配额制保底：即使低优先级的 weight 只有 3（占比 3/8），每 8 次 NextPriority 调用也至少会选它 3 次。只要它的队列里有任务，这 3 次消费就会给低优先级任务机会。对比严格优先级策略（高优先级队列非空就永远不看低优先级），加权轮询从算法层面保证了低优先级不会永远饿死。

weight 比例写在配置中心（Config.Queues），可以根据业务变化动态调整，不需要改代码重新部署。配置变更时 WeightedScheduler 会自动检测到 Queues 列表变化并重置计数器。

Q4 满分逐字稿

etcd Watch + 内存原子计数器做用户并发管控：原子计数器为什么线程安全？etcd Watch 断连重试怎么处理？

我先讲架构，再分别讲原子计数器和 Watch 断连。

整体架构：每个用户同时能跑的任务数需要限制（防止一个用户占满整个集群算力）。实现方式是 ConcurrentManager——一个纯内存的原子计数器，代码在 app/worker-scheduler/manager/concurrent.go。它维护两个 map：taskMap（按 source::taskMode::cluster 维度计数）和 userMap（再加上 user 维度）。计数器由 etcd Watch 驱动：当一个任务被注册到 etcd（key 是 /task/{env}/{taskID}），Watch 收到 PUT 事件就 +1；当任务完成或 Worker 挂掉导致 etcd key 被删除，Watch 收到 DELETE 事件就 -1。

消费时的并发检查：在 tryConsume 遍历候选任务时，对每个 member 调用 concurrentManager.GetUser(source, taskMode, cluster, user)，如果返回值 ≥ 1（该用户已有任务在运行），就暂时跳过这个 member，放入 queueJob 列表。注意：这里不是"先抢占再检查再回退"，而是先检查再决定要不要抢——检查通过才去 grabJob。

原子计数器为什么线程安全？ConcurrentManager 使用 go.uber.org/atomic 的 Int64，底层是 Go sync/atomic 包。关键的增减操作是一个 CAS 循环（addClampNonNegative）：

  • 先 Load 当前值 curr
  • 计算 next = curr + delta（如果 delta 为负且结果 < 0，钳位到 0）
  • 调用 CompareAndSwap(curr, next)——如果当前值仍是 curr 就原子地设为 next
  • CAS 失败说明有其他 goroutine 修改了值，重新循环

这个模式的线程安全性来自 CPU 的原子指令（x86 上是 CMPXCHG 配合 LOCK 前缀）：在 CAS 执行期间，独占缓存行，其他核心不能修改同一地址。相比 Mutex，CAS 循环没有 goroutine 挂起/唤醒的调度开销，在竞争不激烈时（任务开始/结束频率不高）性能更好。

为什么用 CAS 而不是简单的 atomic.Add？因为需要"钳位到 0"的语义——任务完成时 -1，但计数器不能减到负数（防止 Watch 事件乱序或重复导致计数器跑负）。简单的 atomic.Add 无法做条件判断，CAS 循环才能实现"如果当前值已经是 0 就不减"的逻辑。

etcd Watch 断连重试怎么处理？代码在 worker-scheduler/service/service.go 的 watchTask 方法：

  • 正常流程：for 循环 select 等待 watchChan，收到事件就遍历 watchResp.Events，调用 handleTaskEvent 更新计数器
  • Channel 关闭或报错：调用 waitWithRetry（等待一段时间后重新调用 dao.WatchTask 重建 Watch）
  • 启动时全量初始化：loadInitialData 会从 etcd 全量拉取当前所有注册的 task，初始化 ConcurrentManager 的计数器

这个"启动时全量 List + 运行时增量 Watch"的模式，和 Kubernetes Informer 的 List-Watch 思路一致。但需要注意：当前代码在 Watch 断连重连时只是重新开 Watch，没有重做全量 List。这意味着如果断连期间有任务的 PUT/DELETE 事件丢失，计数器可能和 etcd 真实状态产生偏差。不过在实际运行中：etcd clientv3 内部有修订号（revision）追踪，短暂断连后重连通常能从上次的 revision 继续推送事件；只有 etcd compaction 删掉了历史 revision 时才会真正丢事件——这种情况很少发生。

多 Pod 如何保持一致？每个 worker-scheduler Pod 都有自己独立的 ConcurrentManager，存在内存里。多 Pod 之间靠 etcd Watch 同步：所有 Pod 都 Watch 同一个 /task/{env}/ 前缀，一个 Pod 注册了任务（写 etcd），其他 Pod 都收到 PUT 事件各自 +1。最终每个 Pod 的计数器基本一致——etcd Watch 有毫秒级延迟，极端情况下可能短暂超过并发限制，但对"限制并发"场景够用。

Q5 满分逐字稿

单用户并行任务限制，如果瞬间大量请求打进来，是限流、排队还是直接丢弃？策略是什么？

我们采用的策略是排队为主，限流兜底，不会直接丢弃。

具体来说，并发管控发生在两个层面。第一层是准入限制：当用户当前正在运行的任务数达到上限（比如 5 个），新提交的任务不会被丢弃，而是正常入 Redis ZSet 队列排队，但不会被调度器分配给 Worker 执行。调度器在分配任务时会检查该用户的原子计数器，如果已满就跳过这个任务，去消费其他用户的任务。等该用户有任务完成、计数器递减后，下一轮调度就会取到这个排队中的任务。

第二层是入队限流：如果用户瞬间提交了大量任务（比如脚本跑批），入队阶段有速率限制，防止短时间内把 Redis ZSet 撑满。这一层用的是标准的令牌桶限流——每个用户每秒最多入队 N 个任务，超过的请求返回 429 Too Many Requests，由客户端做退避重试。

为什么不直接丢弃？因为 AI 生成任务通常是用户主动发起的，每个任务对用户来说都有价值。直接丢弃用户体验很差——用户不知道任务丢了还是在排队。排队可以给用户一个明确的预期："你的任务在第 X 位，预计等待 Y 分钟"。只有在极端情况下（队列积压超过系统容量阈值），我们才会触发熔断拒绝新任务，但这属于系统级保护而非用户级管控。

从效果看，上线并发管控后，单用户独占算力的问题基本消除了。之前最严重的时候一个自动化脚本用户占了集群 40% 的算力，其他用户排队时间翻倍。限制后每个用户最多占用固定的并行槽位，整体的任务平均等待时间下降了明显。

Q6 满分逐字稿

你 Go 开发过程中，分布式队列并发安全怎么保证？

我从三个层面来讲我们的并发安全保障。

第一层是 Redis 层面的跨进程并发安全。多个 Scheduler 实例同时消费同一个 Redis ZSet 队列，并发安全靠 ZREM 的原子性——Redis 单线程模型保证同一时刻只有一个 ZREM 执行成功，返回值 ≥ 1 表示"我抢到了"，其他消费者返回 0 表示"被别人抢了"。具体流程是：先 ZRange 批量拉取一批候选（最多 256 个），逐个检查用户并发后尝试 ZRem 抢占。ZRange 和 ZRem 是两条独立命令（中间有业务逻辑判断，无法合并为 Lua 脚本），但因为一次拉了一批候选，前几个被抢了还有后续的可以继续尝试，整体效率足够高。实际上就是前面讲的无锁乐观抢占方案。

第二层是进程内的 goroutine 并发安全。在单个 Scheduler 实例内，多个 goroutine 共享内存数据结构。我们按场景选择不同的同步原语：对于用户并发计数器这种简单的整数操作，用 sync/atomic，性能最好；对于任务状态 map 这种复杂数据结构的读写，用 sync.RWMutex，允许多读单写；对于 goroutine 间的任务分发，用 buffered channel 做解耦，生产者往 channel 写、消费者从 channel 读，channel 自身保证并发安全。

第三层是业务层面的幂等保障。分布式环境下，网络抖动可能导致任务被重复投递或重复完成回调。我们在 MongoDB 中用任务 ID 做幂等键：任务状态更新用 findOneAndUpdate 加条件 status: "running"，只有当前状态匹配才更新。如果任务已经被标记为"完成"或"失败"，重复的完成回调不会产生副作用。

一个踩过的坑是：早期我们用 sync.Map 存任务状态缓存，以为它并发安全就万事大吉了。后来发现在"读取-判断-更新"这种复合操作上，sync.Map 的单次操作虽然安全，但多步组合依然有竞态。改成 sync.RWMutex 保护整个复合操作后问题才解决。这也让我深刻理解了"原子操作安全"和"业务逻辑安全"是两个层次的问题。

Q7 满分逐字稿

Redis 批量操作有没有原子性问题？如何避免超卖、重复消费？

这个问题很好，Redis 批量操作的原子性是一个容易踩坑的地方。

首先要区分三种"批量"：第一种是 MGET、MSET 这样的多键命令，它们在 Redis 中是单条命令，原子执行；第二种是 Pipeline，它只是把多条命令打包发送减少网络 RTT，但服务端仍然是逐条执行的，不保证原子性——中间可能被其他客户端的命令穿插；第三种是 MULTI/EXEC 事务，它保证事务内的命令要么全部执行要么全不执行，但有个关键限制——事务内不能根据中间结果做分支判断，因为所有命令在 EXEC 时才一起执行。

在我们的场景中避免超卖和重复消费的做法：核心靠 ZREM 的原子性。我们的消费流程是 ZRange 批量拉取候选 + 逐个 ZRem 抢占。ZRange 和 ZRem 是两条独立命令（没有用 Lua 脚本合并，因为中间需要做用户并发检查等业务判断），但 ZREM 本身是原子的——Redis 单线程保证同一个 member 只有一个 ZREM 返回 ≥ 1。返回 1 就是获得了所有权，返回 0 就是别人先抢到了，不存在超卖。批量拉 256 个候选的设计保证了即使前几个被抢走，后面还有候选可以继续尝试，空竞争的代价很低。

重复消费的防线有两道：第一道是 ZREM 的原子性——任务从 ZSet 中被删除后就不可能被第二个消费者取到；第二道是 MongoDB 中的任务状态机——任务从 "pending" 到 "running" 的状态转换用 findOneAndUpdate 加前置条件，只有状态为 "pending" 才能更新为 "running"。即使极端情况下 Redis 那层出问题（比如主从切换导致数据短暂不一致），MongoDB 这层也能兜住，不会重复执行。

关于是否需要 Lua 脚本的补充说明：面试中常被追问"为什么不用 Lua 脚本把 ZRange 和 ZRem 合并成原子操作"。答案是：我们在 ZRange 拿到候选之后、ZRem 之前，需要做用户并发检查（查询 Go 进程内存中的 concurrentManager 状态），这个业务判断逻辑在 Go 进程里，Redis Lua 脚本做不了。所以设计上接受了 ZRange 和 ZRem 之间的竞态窗口，通过批量拉取 + ZRem 返回值判定来保证正确性。如果场景更简单（不需要中间业务判断），Lua 脚本确实是更优的选择。

Q8 满分逐字稿

MongoDB 存储任务信息，为什么选 Mongo 不选 MySQL？任务字段频繁变更的场景优势是什么？

我们选 MongoDB 存储任务信息，核心原因是 AI 任务的参数字段高度异构。

具体来说，我们平台支持十几种不同类型的 AI 任务——图像生成、视频生成、3D 模型生成、语音合成等等。每种任务的参数完全不同：图像任务有 width、height、prompt、negative_prompt、steps、cfg_scale 这些字段；视频任务有 fps、duration、motion_strength、camera_motion；3D 任务有 mesh_format、texture_resolution、poly_count。而且随着我们接入新的 AI 供应商和新的模型能力，参数字段在频繁变化——平均每两周就会新增一种任务类型或者给现有类型加新参数。

如果用 MySQL，有三个方案，都不理想。第一是"大宽表"方案，把所有可能的字段都建成列，一张表一百多列，大多数记录 90% 的列是 NULL，查询效率低，而且每次新增字段要做 ALTER TABLE，线上大表改结构风险很高。第二是"多表"方案，每种任务类型一张表，表的数量随任务类型增长，JOIN 查询复杂度高，新增任务类型要建新表还要改代码。第三是用 MySQL 的 JSON 字段来存可变参数，这其实是个折中，但失去了 MySQL 强 schema 的类型检查优势，而且 MySQL 的 JSON 查询性能不如 MongoDB 的 BSON。

MongoDB 的 Schema-free 特性天然适合这个场景。每个任务文档自描述字段结构，图像任务的文档和视频任务的文档可以有完全不同的字段，存在同一个 collection 里。新增任务类型只需要在代码里定义新的参数结构体，直接写入 MongoDB，不需要任何 DDL 操作。而且 MongoDB 对嵌套文档和数组有很好的查询支持，任务参数可以自然地用嵌套结构表达。

另外一个考量是水平扩展。随着平台用户增长，任务量级从初期的日均几万增长到日均几十万。MongoDB 的 sharding 机制支持按 userId 或 taskType 做分片，水平扩展比较自然。MySQL 做分库分表需要中间件（比如 ShardingSphere），引入额外的复杂性。

当然 MongoDB 也有取舍——它不支持跨文档事务（4.0 以后支持但性能有损），所以我们的任务状态更新都是单文档操作，用 findOneAndUpdate 加条件保证原子性。涉及跨任务的统计查询，我们用聚合管道或者离线同步到分析数据库来做，不依赖 MongoDB 的事务。
