二、核心知识精讲

2.1 etcd Lease 租约机制

etcd Lease 是服务注册发现的核心存储层。在 DreamMaker 中，Worker 不直接操作 etcd，而是通过三层架构实现注册发现：Worker-sidecar 每 30s 通过 HTTP 心跳上报给 worker-scheduler，worker-scheduler 负责管理 etcd 中的注册 key（/worker/{env}/{name}）。worker-scheduler 维护一个 TTL=7200s 的 Lease，每 5 分钟重新 Grant 刷新。如果 worker-scheduler 宕机，2 小时后 Lease 过期，所有 Worker key 自动删除。

sequenceDiagram
    participant WS as Worker-Sidecar
    participant S as Worker-Scheduler
    participant E as etcd 集群

    Note over S: 启动时 Grant Lease（TTL=7200s）
    WS->>S: HTTP Report（type=register）
    S->>E: Put /worker/{env}/{name}（绑定 Lease）
    E-->>S: Watch 事件：PUT

    loop 每 30s
        WS->>S: HTTP Report（type=heartbeat）
        S->>E: re-PUT /worker/{env}/{name}
    end

    loop 每 5 分钟
        S->>E: 重新 Grant Lease，刷新 TTL
    end

    Note over WS: Worker 宕机，心跳停止
    Note over S: 不再为该 Worker re-PUT
    Note over E: Lease 过期后自动删除 key
    E-->>S: Watch 事件：DELETE
    S->>S: 从调度缓存移除该 Worker
    S->>S: 清理任务路由 + 递减集群计数器

30s 心跳间隔的设计考量：这是应用层 HTTP 心跳的频率，用于让 worker-scheduler 及时感知 Worker 健康状态。调小到 10s → 心跳请求量增 3 倍，worker-scheduler 处理压力增大。调大到 60s → Worker 宕机后感知延迟更长，可能持续向不可用节点分配任务。30s 保证 1-2 个周期内感知异常，及时停止分配。

2.2 Worker 故障转移策略

2.3 K8s 扩缩容：HPA + 自定义 Autoscaler

DM 用了两套扩缩容机制：CPU Worker（调供应商 API）用 K8s HPA 按 CPU/内存水位扩缩；GPU Worker（本地部署模型推理）用自定义 Autoscaler 按 Redis 队列积压深度扩缩。GPU 资源贵且 HPA 的 CPU 指标无法反映 GPU 负载，所以需要自定义逻辑。

为什么 GPU Worker 不能用 HPA：HPA 基于 CPU/内存指标，但 GPU Worker 的 GPU 可能满载而 CPU 很闲，HPA 看 CPU 5% 会误判为"资源充足"。自定义 Autoscaler 直接读 Redis 队列长度来决定扩缩容。两者不冲突——HPA 管基础设施弹性（CPU Worker），Autoscaler 管业务弹性（GPU Worker）。

StatefulSet vs Deployment：Worker 用 StatefulSet 部署有两个原因：(1) 稳定的网络标识（worker-0, worker-1...），与 etcd 注册的 key 对应，scheduler 能精确知道哪个 Worker 是哪个；(2) 有序缩容，缩容时从最大序号开始下掉，可以确保先下掉最近扩容的（通常是空闲的）节点。

2.4 指数退避重试

退避阶梯：1s → 2s → 4s → 8s → 16s → 32s
最大重试次数：6次
总等待上限：63s（1+2+4+8+16+32）

触发条件：HTTP 429（限流）/ 503（服务不可用）/ 连接超时 / 网络错误
不重试条件：HTTP 400（参数错误）/ 401（认证失败）/ 403（权限不足）/ 模型不存在

白名单管控：容错降级通过配置白名单控制生效范围。配置存储在 MongoDB，按 app_code（能力标识）粒度管控——只有白名单内的能力才启用备用供应商切换，其他能力直接返回失败。测试环境和生产环境通过不同的配置集区分，部署时通过环境变量加载对应配置。

2.6 量化指标的统计方法

35% 空闲算力降低：对比扩缩容上线前后各两周的监控数据。扩缩容前，集群固定 20 个 Worker 节点，低峰期（如凌晨）大部分节点空闲，平均空闲率约 55%。上线后动态扩缩容根据队列积压调整节点数，低峰期缩容到 8-10 个节点，平均空闲率降至约 20%。(55%-20%)/55% ≈ 降低 35%。
50% 任务失败率降低：取容错降级上线前后各一个月的任务状态统计。上线前第三方供应商 429 导致的任务失败率约 8%（高峰期可达 15%）。上线后通过退避重试+备用链路切换，同类失败率降至约 4%（高峰期约 7%）。(8%-4%)/8% = 降低 50%。统计维度是"因供应商限流/不可用导致的最终失败"，不包括参数错误等不可重试类型。

三、面试易错点

错误 1：说"心跳间隔越小越好"。错！心跳过频会增加 etcd 负载，在大规模集群下（100+ Worker）可能影响 etcd 的 Raft 一致性性能。要讲清楚 tradeoff。
错误 2：混淆"重试"和"重新调度"。重试是同一个 Worker 对同一个供应商请求重试（指数退避），重新调度是把任务分配给另一个 Worker 执行。两者层级不同。
错误 3：说"GPU Worker 也可以用 HPA"。HPA 基于 CPU/内存指标，GPU 满载时 CPU 可能很闲，HPA 会误判。必须讲清楚 DM 用了两套：CPU Worker 用 HPA，GPU Worker 用自定义 Autoscaler 按队列积压深度扩缩。
错误 4：量化数字说不出统计口径。面试官问"35% 怎么统计的"你答不出来，这个数字就等于没说。必须能讲出"对比哪个时间段、什么维度、计算公式是什么"。

四、满分逐字稿

Q1：etcd Lease 租约机制原理？心跳 30s 依据？

满分逐字稿

面试标准逐字稿

etcd Lease 本质上是一个带 TTL 的"租约对象"，所有绑定到这个 Lease 的 key 会在 Lease 过期时一起删除。

在我们的调度平台里，Worker 的注册发现不是 Worker 直连 etcd，而是Worker-sidecar 通过 HTTP 心跳上报给 worker-scheduler，worker-scheduler 负责维护 etcd 中的注册信息。具体流程是：worker-scheduler 启动时调用 etcd Grant 创建一个 TTL=7200s（2小时）的 Lease，然后每 5 分钟重新 Grant 一次刷新 Lease；Worker-sidecar 启动时通过 HTTP 调用 worker-scheduler 的 Report 接口注册自己，worker-scheduler 收到后将 Worker 信息 Put 到 etcd（如 /worker/{env}/{name}），绑定当前 Lease；之后 sidecar 每 30s 发一次 HTTP 心跳，worker-scheduler 收到后 re-PUT 该 Worker 的 key，保持信息新鲜。

如果 Worker 宕机或网络断连，心跳停止。worker-scheduler 侧通过心跳超时判断 Worker 不可用，不再为其 re-PUT key。当 Lease 最终过期时，etcd 自动删除绑定在该 Lease 上的所有 Worker key。worker-scheduler 自身通过 Watch 机制监听 /worker/ 前缀，收到 DELETE 事件后将该 Worker 从内存调度缓存中移除、从任务路由表中清理，并递减对应集群的 Worker 计数器——这样后续任务就不会再分配给已下线的节点。

30s 心跳间隔的设计考量：这个 30s 是应用层 HTTP 心跳的频率，目的不是续约 etcd Lease（那是 worker-scheduler 每 5 分钟做的），而是让 worker-scheduler 及时感知 Worker 的健康状态和负载情况。30s 间隔在故障感知速度和网络开销之间取平衡——调小到 10s，心跳请求量增加 3 倍，对 worker-scheduler 有额外压力；调大到 60s，Worker 宕机后要等更久才能被发现不可用。30s 保证在 1-2 个心跳周期内就能感知异常，及时停止向该 Worker 分配新任务。

Q2：Worker 故障时任务如何处理？

满分逐字稿

面试标准逐字稿

我们采用"检测→标记→重试→兜底"四步策略。

首先是检测：Scheduler 通过 etcd Watch 实时监听 Worker 注册 key 的变化，DELETE 事件触发故障处理流程。

其次是标记：将该 Worker 状态设为 DOWN，同时扫描 MongoDB 中该 Worker 名下所有 status=RUNNING 的任务，全部标记为 FAILED_RETRYABLE。

然后是重试：这些任务进入重试队列，由 Scheduler 重新分配给其他健康 Worker。这里有一个关键点——AI 生成任务通常是幂等的，相同参数提交两次会得到不同结果（因为随机种子不同），但不会产生"重复消费"的副作用，所以重试是安全的。但有一个例外：如果任务已经提交到外部供应商并且供应商已经开始计算，重新提交会导致重复计费。所以在重试前，我们会先查询供应商侧的任务状态——如果已经在执行中，就等待其完成而不是重新提交。

最后是兜底：每个任务有最大重试次数限制（默认 3 次），超过后标记为 FAILED_FINAL 并触发告警。防止某些因为参数问题永远无法成功的任务无限重试占用队列资源。

Q3：自定义 K8s 扩缩容 vs HPA？

满分逐字稿

面试标准逐字稿

我们实际上用了两套扩缩容机制，解决不同层面的问题。

DM 的任务分两类：调供应商 API 的任务（如 Kling、Runway）只需要 HTTP 调外部接口，跑在 CPU Worker 上；开源部署的任务（如 ComfyUI、SD）需要本地 GPU 推理，跑在 GPU Worker 上。CPU Worker 相对廉价，用 K8s HPA 按 CPU/内存水位扩缩就够了。但 GPU Worker 不行——GPU 满载推理时 CPU 可能很闲，HPA 看 CPU 5% 会觉得"资源充足"甚至触发缩容，这完全是误判。所以我们针对 GPU Worker 自定义了 Autoscaler。

自定义 Autoscaler 的核心指标是 Redis 任务队列积压深度。每 30 秒检查一次，扩容条件是 Worker 数 ≤ 队列长度的一半；缩容条件是 Worker 不在忙且空闲时间超过配置的阈值，同时 Running Worker 数要大于最小副本数下限。扩容的方式比较特别——不是创建新 Pod，而是唤醒已 terminated 的 Pod，调 api-kube 的 UpdateWorker 接口重新激活它；缩容则是调 DeleteWorker 删除空闲 Pod。

有几个细节：第一，扩缩容有冷却期，通过 Redis ZSet 记录操作历史，冷却期内跳过本轮，防止指标抖动导致频繁扩缩（thrashing）。第二，缩容时会检查 Worker 是否在忙，只对空闲且超过阈值的 Worker 缩容，实现优雅下线。第三，设置了最小副本数下限（MinWorker），即使完全空闲也不会缩到零。第四，有安全检查——如果有 Worker 处于 pending 或 terminating 状态，本轮直接跳过，防止"还没启动完就又触发扩容"的雪崩式超扩。第五，因为多个 worker-scheduler 实例同时运行，用 Redis 分布式锁保证同一时刻只有一个实例执行扩缩容。

上线后对比固定节点部署，动态扩缩容把平均空闲算力占用降低了约 35%——主要收益在低峰时段。

Q4：StatefulSet 部署 Worker 的原因？

满分逐字稿

面试标准逐字稿

用 StatefulSet 而不是 Deployment 主要是两个原因：稳定网络标识和有序扩缩容。

第一，稳定网络标识。StatefulSet 的 Pod 名称是 worker-0、worker-1 这种固定命名，而 Deployment 的 Pod 名称是随机后缀（如 worker-7f8b9c）。Worker 启动时在 etcd 注册的 key 是 /workers/worker-0，Scheduler 根据这个 key 来分配任务和追踪状态。如果用 Deployment，Pod 重启后名称变了，etcd 里的旧 key 就成了僵尸数据，需要额外的清理逻辑。StatefulSet 保证重启后名称不变，注册 key 自然对得上。

第二，有序扩缩容。StatefulSet 缩容时默认从最大序号开始删除（worker-19 先于 worker-18）。这意味着我们可以在扩容时新增的节点优先被缩容掉，而初始的稳定节点保持在线。结合优雅下线机制，缩容过程是可预测、可控制的。Deployment 的缩容是随机的，可能下掉一个正在执行任务的 Pod，处理起来更复杂。

Q5：35% 空闲算力降低的统计维度？

满分逐字稿

面试标准逐字稿

这个 35% 的统计方法是对比扩缩容上线前后各两周的 Worker 空闲率均值。

空闲率的定义是：在每个 5 分钟采样窗口内，"空闲 Worker 数 / 总 Worker 数"。空闲 Worker 的判定标准是"当前没有执行中的任务"。上线前集群固定 20 个节点，日间高峰空闲率约 20%，凌晨低谷空闲率高达 80%，加权平均约 55%。上线后动态扩缩容，日间根据队列积压扩到 15-25 个节点，凌晨缩到 8-10 个，加权平均空闲率降到约 20%。(55%-20%) / 55% ≈ 降低 36%，四舍五入为 35%。

说实话这个数字的主要贡献是低峰时段的缩容收益——高峰期反而可能比固定部署多扩了几个节点。但从整体资源利用率看，动态扩缩容确实显著减少了"付了钱但没在用"的算力浪费。

Q6：指数退避重试的阶梯设计？

满分逐字稿

面试标准逐字稿

我们的指数退避阶梯是 1s→2s→4s→8s→16s→32s，最多 6 次重试，最长总等待 63 秒。

为什么是这个参数？首先，基数 1s 是因为 429 限流通常是秒级恢复——供应商的限流窗口一般是 1 分钟内 N 次请求，等 1 秒后重试大概率能过。底数 2 的指数增长确保在供应商持续限流时不会疯狂重试加剧拥塞。上限 32s 是因为 AI 生成任务本身耗时较长（图像生成通常 10-30 秒），用户对"多等 30 秒"的感知没那么敏感，但超过 1 分钟体验就很差了。6 次重试、总等待 63 秒，是在"尽量等供应商恢复"和"不让用户等太久"之间的平衡点。

实现上还加了一个抖动因子（jitter）：实际等待时间 = 基础退避 × (0.5 + random(0, 0.5))。这是为了避免多个任务同时触发 429 后在相同时刻重试，造成"惊群效应"再次打满供应商限流。

Q7：可重试 vs 不可重试异常分类？

满分逐字稿

面试标准逐字稿

核心判断标准是：这个错误是否有可能通过重试自行恢复。

可重试异常包括：HTTP 429（限流，等一会就恢复）、503（服务暂时不可用）、连接超时（网络抖动）、DNS 解析失败（临时性网络问题）。这类错误的共同特点是"现在不行，过一会可能就行了"。

不可重试异常包括：HTTP 400（参数错误，重试 100 次参数还是错的）、401（认证失败）、403（权限不足）、404（模型或接口不存在）、422（参数校验不通过）。这类错误是确定性的，重试没有意义，应该立即返回失败并告知用户具体原因。

在代码实现上，我们定义了一个 RetryableError 接口，供应商适配层在捕获 HTTP 错误时根据状态码决定抛出 RetryableError 还是普通 Error。重试逻辑只对 RetryableError 生效。还有一种特殊情况：供应商返回 200 但 body 里的 code 表示"模型正在加载中"，这也归类为可重试——因为冷启动加载通常 10-30 秒就完成。

Q8：多供应商兜底切换策略？

满分逐字稿

面试标准逐字稿

我们的策略是"故障切换"而不是"负载均衡切换"。区别在于：负载均衡是所有供应商同时接流量按权重分配，故障切换是每个请求总是先走主供应商，主供应商失败后才切到备用。

选择故障切换的原因是：不同供应商的模型效果有差异，我们希望优先使用效果最好的那个，备用供应商是"能用但效果可能略差"的兜底。如果做负载均衡，用户会发现"同样的提示词，生成结果质量时好时差"，体验不一致。

具体实现是一个无状态的 per-request fallback chain。每个请求独立走一遍"主→备"链路：先调主供应商，内部有 3 次指数退避重试（1s→2s→4s），如果 3 次都失败且错误类型是可重试的（429 限流、503 不可用、网络超时等），就立即切到 fallback 链路中的下一个供应商。备用供应商同样有自己的重试，如果也失败则继续往后切，直到链路耗尽或遇到不可重试错误为止。

这个设计是无状态的——系统不记录"哪个供应商当前不可用"，不维护熔断器状态。每个新请求都从主供应商开始尝试。这意味着主供应商恢复后，下一个请求自然就能成功，不需要额外的"恢复探测"机制。代价是：在主供应商持续故障期间，每个请求都会先打一次主供应商、等它超时后才切备用，增加了延迟。但对 AI 生成任务来说（本身耗时 10-30s），多等几秒重试的感知不强，这个 tradeoff 是可接受的。

另外，fallback 规则是按模型粒度配置在 MongoDB 中的，不是所有任务都有备用链路——只有配了 fallback rule 且 enabled=true 的模型才会触发切换，其他直接返回失败。规则里还可以配 skip_on（某些错误不切换，比如内容审核不通过）和 retry_on（只在匹配特定错误时才切换），实现精细化控制。

Q9：白名单管控实现？测试/生产环境区分？

满分逐字稿

面试标准逐字稿

白名单配置存储在 MongoDB，按 app_code 粒度管控。

每个 AI 能力（如文生图、图生视频）在系统中有唯一的 app_code 标识。白名单配置记录哪些 app_code 启用容错降级、对应的主备供应商是什么、退避参数是什么。只有白名单内的能力才会触发备用供应商切换，白名单外的能力在主供应商失败后直接返回错误。

这样设计的原因是：不是所有供应商都有备用链路。有些 AI 能力只有一个供应商能提供（比如某些私有化部署的模型），对这些能力做供应商切换没有意义。白名单机制让运维可以精细化控制哪些能力启用降级，避免全局生效带来的不确定性。

测试和生产环境通过部署时的环境变量区分——DM_ENV=test 或 DM_ENV=prod，服务启动时加载对应的配置集。测试环境的白名单通常覆盖所有能力（方便测试降级链路），生产环境只覆盖已验证过备用链路效果的能力。

Q10：50% 失败率降低的压测数据？

满分逐字稿

面试标准逐字稿

50% 的统计口径是：因供应商限流/不可用导致的最终任务失败率，对比容错降级上线前后各一个月的数据。

上线前，第三方供应商返回 429 或 503 时任务直接标记为 FAILED，没有任何重试。统计显示这类失败占总任务量的约 8%，高峰期（如大型活动期间全公司美术师集中使用）可达 15%。

上线后，指数退避重试消化了大部分 429 场景（大约 70% 的 429 在前 2 次重试内恢复），剩余的通过备用供应商切换兜底，同类失败率降至约 4%。(8%-4%)/8% = 降低 50%。

关于线上峰值 QPS，说实话我没有做过专门的压测，这个数据我需要查监控才能给出准确数字。但从日常观察看，高峰期平台整体的任务提交 QPS 大约在每秒几十到一两百这个量级——AI 生成任务本身是重型任务（单任务执行时间 10s-几分钟），不是传统互联网那种上万 QPS 的场景，瓶颈不在吞吐量而在并发执行容量和供应商限流。
