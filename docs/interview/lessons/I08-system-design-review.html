I08 — 现场架构设计与压力复盘

定位 终面压轴 + 技术深度 覆盖题数 10 题 难度 ★★★★★ 时长 ~60 分钟

一、课程概述

本章分为两部分：现场架构设计题（考系统设计能力）和压力复盘题（考技术深度和反思能力）。这两部分通常出现在终面或高压追问环节，面试官通过这些题判断候选人是否有"架构师思维"和"工程自省能力"。

题型考察维度权重面试官意图
架构设计系统全局设计能力40%能否从零搭建完整系统，技术选型有 reasoning
压力复盘技术深度 + 自省能力30%遇到过什么坑、怎么排查、有没有反思改进
技术债认知工程成熟度30%能否主动发现不足而不是被动辩解
核心策略：架构设计题用你的真实项目经验作答——不是"我设想一个系统"，而是"我做过一个系统，它是这样设计的"。复盘题展示自省能力——主动暴露不足比被动挖出来强 10 倍。

2.3 复盘回答方法论

复盘题用 PDCA 结构回答：

  1. Problem（问题描述）：简洁描述现象，不超过 2 句话
  2. Debug（排查过程）：详细讲排查思路和工具，展示系统性思维
  3. Cause（根因分析）：找到技术根因，不停留在表面
  4. Action（修复 + 改进）：修复方案 + 防止再犯的系统性改进

三、面试易错点

错误 1：架构设计题"从零开始设计"，不复用项目经验。面试官其实就是在问你的项目，你应该用项目经验作答，展示 reasoning 而不是想象力。
错误 2：复盘题讲不出具体排查过程。只说"我修了一个 bug"不够，要讲"怎么发现的→怎么定位的→用了什么工具→为什么是这个根因→怎么修的→怎么防再犯"。
错误 3：被问技术债时防御性回答"我觉得做得都挺好的"。面试官问技术债是在考你的工程成熟度——能主动识别不足说明你有架构思考能力。

四、满分逐字稿

Q1：从零设计 AI 美术创作 Agent 平台（核心重点）

满分逐字稿（500-800字）

面试标准逐字稿

这道题我可以直接用我在网易做的 DreamMaker 平台来回答，因为它就是一个完整的 AI 美术创作 Agent 平台。我按 4S 法拆解。

Scenario（场景）：目标是让游戏美术师通过自然语言对话驱动 AI 完成创作——"帮我生成一张赛博朋克风格的角色原画"。核心功能包括：画布交互（Agent 感知画布状态并操作）、多模态生成（图像/视频/3D）、任务排队（AI 生成耗时长需要队列化）、断点续跑（对话中断后恢复）、流式输出（实时看到 Agent 思考和生成过程）。用户规模是公司内部几百到上千美术师，不是 C 端百万级。

Service（服务拆分）：我会拆成五层。第一层是客户端层——桌面端嵌入 Agent 服务，Web 端直接请求网关。第二层是 Agent 服务层——Python + FastAPI，核心是 LangGraph 状态机驱动的 Agent，负责自然语言理解、工具选择、画布感知。我在这一层设计了三层上下文注入（入口层/推理层/工具层）解决 LLM 感知动态画布的问题，SSE 流式推送让前端实时看到 Agent 思考过程，HITL 审批引擎确保高危操作必须人工确认。第三层是业务网关——Go 实现的 app-gateway，做参数校验、权限检查、任务入队。第四层是调度层——worker-scheduler 基于 Redis ZSet 做优先级队列消费，etcd 做 Worker 服务发现和心跳检测，支持加权轮询防止低优先级饥饿。第五层是 Worker 执行层——sidecar + 10 类 Worker 调用各家 AI 供应商 API。

Storage（存储）：Redis 存任务队列（ZSet 天然有序支持优先级），MongoDB 存任务详情（AI 任务参数高度异构，Schema-free 适配），etcd 存 Worker 注册信息和配置，SQLite 存 Agent 对话 Checkpoint（本地持久化，生产环境应换 PostgreSQL）。

Scale（扩展）：Agent 服务层水平扩展——FastAPI 无状态（状态在 Checkpointer），多实例负载均衡。调度层通过 etcd Leader 选举保证单点消费一致性。Worker 层基于队列积压动态扩缩容 K8s StatefulSet。供应商层设计了指数退避重试 + 备用链路切换的容错降级。

这套架构在网易内部稳定运行了几个月，支撑了图像/视频/3D 等 10 类 AI 能力的调度和执行。

Q2：长对话上下文膨胀与 UI 状态同步

满分逐字稿

面试标准逐字稿

这两个问题我在项目中都遇到过，核心解法是"分层 + 按需"。

上下文膨胀的问题：LLM 有 Token 窗口限制，长对话下消息列表越来越长，加上画布状态信息，很容易超限。我的方案是三层分层上下文注入——入口层只注入 200 Token 的画布概览，推理层每次 LLM 调用前动态注入（而不是写死在 System Prompt），工具层让 Agent 按需查询细节。常驻 Token 降低约 40%。对于消息列表膨胀，超过 20 轮后对早期消息做摘要压缩——用一次 LLM 调用把前 15 轮总结为 2-3 句话，替代原文。

UI 状态同步的问题：用户操作画布的同时 Agent 在推理，画布状态可能变化。我的方案是"请求级快照"策略——每次 /chat 请求开始时拍一次画布快照，整个 Agent 执行过程中使用这个快照。不做实时同步，因为 Agent 一次推理通常几十秒，这期间画布变化的概率低，而且即使变了，Agent 基于略旧的快照做操作也不会出错（最多生成的节点位置不是最新的，用户可以手动调整）。这是一个"最终一致性"的设计选择——简单可靠优先于强一致。

Q3：高可用 AI 任务调度系统设计

满分逐字稿

面试标准逐字稿

我在 DreamMaker 里实际做了这个系统，核心是"四层防御"：

第一层，队列隔离：不同类型的任务走不同的 Redis ZSet 队列，图像生成队列和视频生成队列隔离，一类供应商宕机不影响其他类型任务的执行。

第二层，心跳检测 + 故障转移：etcd Lease+Watch 实现 Worker 心跳检测，30s 间隔、90s TTL。Worker 宕机后自动将其任务标记为失败并放入重试队列，由 scheduler 重新分配到健康 Worker。

第三层，弹性扩缩容：自定义扩缩容模块监控队列积压深度，超阈值时调用 K8s API 扩容 StatefulSet，空闲时缩容。比 HPA 更适合 AI 场景（CPU 指标不反映真实负载）。

第四层，供应商容错降级：第三方 API 返回 429/503 时指数退避重试（1s→2s→...→32s，最多 6 次），超时未恢复切换备用供应商。可重试和不可重试异常严格分类，400/401 直接返回错误不重试。白名单按 app_code 粒度管控哪些能力启用降级。

这套方案上线后，集群空闲算力降低约 35%，因供应商限流导致的任务失败率降低约 50%。

Q4：Agent 工具调用权限体系设计

满分逐字稿

面试标准逐字稿

我在 Monet 画布中实现了基于 LangGraph interrupt 的 HITL 审批引擎，核心是"工具分级 + 自动路由"。

具体来说，每个工具通过装饰器标注权限等级：auto（自动放行，如查询画布节点详情）、confirm（需要用户确认，如创建节点、删除节点）、deny（禁止执行，如系统级操作）。Agent 在 tools 节点执行工具时，检查权限等级：auto 直接执行；confirm 调用 LangGraph 的 interrupt() 挂起执行，通过 SSE 向前端推送审批事件（包含操作描述、参数预览、确认/拒绝按钮）；用户确认后通过 REST 接口回传 approve/reject，驱动 Graph resume 继续或终止。

如果要设计一套更完整的权限体系，我会在此基础上扩展三个方向：第一，输出校验层——Agent 的文本回复也做内容审核，拦截有害、错误或不合规的输出。第二，调用频率限制——单次对话内限制工具调用总次数和单工具调用次数，防止 Agent 失控。第三，审计日志——所有工具调用记录到审计表，包括谁触发的、什么参数、审批结果、执行结果，支持事后追溯。

Q5：上万 Agent 会话并发的性能优化

满分逐字稿

面试标准逐字稿

上万并发是 C 端场景的量级，我们平台目前是 B 端（几百美术师），但我可以讲架构上的扩展思路。

首先是服务拆分和无状态化。Agent 服务本身应该是无状态的——对话状态通过 Checkpointer 持久化到外部存储（PostgreSQL/Redis），任何一个 Agent 实例都能恢复任意会话。这样水平扩展只需要加实例，前面挂负载均衡器。

其次是连接管理。SSE 长连接是资源大户——每个会话占一个 HTTP 连接。单实例通常能支撑几千个 SSE 连接（受文件描述符和内存限制）。上万需要多实例 + 连接层分离——用独立的 SSE 网关（如 Nginx 的 SSE 代理）做连接管理，Agent 服务只负责计算。

第三是LLM 调用并发控制。LLM API 是最贵的资源，需要用 Semaphore 限制总并发数，超出的排队等待。可以按优先级排队——VIP 用户的请求优先获取 LLM 调用槽位。

第四是内存管理。LangGraph State 随对话轮次增长，长会话的 State 可能很大。需要定期做消息压缩（早期消息摘要化），以及会话超时回收——15 分钟无活动的会话释放内存中的 State，下次请求时从 Checkpointer 恢复。

Q6：最难的技术难点及排查过程

满分逐字稿

面试标准逐字稿

最难的问题是一个画布上下文"幽灵污染"bug——Agent 在多轮对话中偶尔会"看到"不属于当前画布的节点信息。

现象：用户反馈 Agent 描述画布时提到了一些不存在的节点，好像看到了"别人的画布"。

排查过程：首先怀疑是 ContextVar 泄漏——检查了 ContextVar 的定义和使用，确认每次请求开始时都正确 set 了新值，排除了跨请求泄漏。然后检查日志，发现问题只在多轮对话中出现，单轮不会。打断点发现 LangGraph State 中的画布快照数据在第 N 轮出现了第 N-1 轮的画布信息残留。

根因：画布快照注入时使用了浅拷贝。LangGraph State 是一个可变字典，注入画布信息时直接把快照字典赋值给 State 的一个字段。第 N 轮 LLM 处理过程中修改了这个字典（比如添加了一些中间标记），由于浅拷贝，这些修改同时影响了缓存中的原始数据。第 N+1 轮注入时，缓存中的数据已经被污染了。

修复：在注入画布快照时使用 copy.deepcopy()，确保每轮拿到的是完全独立的数据副本。同时在 State 更新的 Reducer 中也加了深拷贝保护。

反思：这个 bug 教会我一个原则——在有状态的系统中，所有跨边界传递的可变数据都应该深拷贝，除非你能证明不会被修改。另外，这类"偶发"bug 通常意味着并发或状态管理问题，排查时应该优先检查数据的共享和隔离边界。

Q7：线上严重 bug 及复盘

满分逐字稿

面试标准逐字稿

最严重的一次是 SSE 连接泄漏导致服务 OOM。

现象：Agent 服务运行几天后内存持续增长，最终 OOM 被 K8s kill。重启后运行几天又出现。

排查：先看监控，内存是缓慢线性增长，不是突然暴涨，说明是某种资源泄漏。用 Python 的 tracemalloc 做内存快照对比，发现大量 asyncio 的 StreamWriter 对象没有被回收。追踪到 SSE 推送的生成器——当前端异常断连（不是正常关闭）时，服务端的 SSE 生成器没有被正确清理，asyncio 的 async generator 如果不显式调用 aclose() 就不会释放资源。

修复：给 SSE 流式推送加了 try/finally 块，在 finally 中显式调用 generator.aclose()。同时加了超时机制——如果 30 秒内没有数据推送（不算心跳），主动关闭连接。还加了连接数监控告警，超过阈值提前预警。

反思：Python async generator 的生命周期管理是一个容易忽略的坑——它不像同步 generator 那样在 GC 时自动调用 close()，必须显式管理。这次事故后，所有 async generator 的使用都加了 async with 或 try/finally 保护。

Q8：重构 Agent 画布项目的优化方向

满分逐字稿

面试标准逐字稿

如果重构，我会优化四个方面：

第一，Checkpointer 从 SQLite 换成 PostgreSQL。SQLite 是文件级存储，单机限制，多实例部署时 Agent 会话无法跨实例恢复。换成 LangGraph 官方的 PostgresSaver 或 RedisSaver，所有实例共享同一个 checkpoint 存储，真正支持水平扩展。

第二，增加 Agent 记忆系统。目前只有短时记忆（会话内消息）和工作记忆（画布上下文），缺少跨会话的长时记忆。我会增加：对话结束后 LLM 生成摘要 → Embedding → 存入向量数据库。下次新会话时检索相关历史摘要注入 Prompt，让 Agent 能记住"上次用户喜欢什么风格"。

第三，增加输出校验层。目前 HITL 只做了工具调用侧的审批，Agent 的文本输出没有校验。如果 Agent 给出了错误的操作建议但没调用工具，无法拦截。改进方案是对关键输出做语义校验——比如检查 Agent 是否声称画布上存在某个不存在的节点。

第四，HITL 增加超时机制。目前审批挂起后没有超时释放，如果用户不回应，Agent 会一直阻塞。应该设置 5 分钟超时，超时后自动取消操作，释放资源，通知用户"操作已超时取消"。

Q9：分布式调度系统的技术债

满分逐字稿

面试标准逐字稿

目前有三个比较明确的技术债。

第一，单 Leader 调度瓶颈。虽然 scheduler 做了 etcd Leader 选举保证高可用（Leader 挂了会自动选新 Leader），但同一时刻只有一个 Leader 在消费 Redis 队列和分配任务。高峰期如果任务量很大，单 Leader 的消费速度可能成为瓶颈。改进方向是分片消费——按任务类型将队列分片到不同的 scheduler 实例，每个实例只负责自己分片的队列。

第二，缺乏灰度发布机制。目前 Worker 更新是全量滚动更新——所有 Worker 同时更新到新版本。如果新版本有 bug，会影响所有任务。改进方向是按 Worker 分组灰度：先更新 10% 的 Worker 观察错误率，没问题再全量推。

第三，监控和可观测性不足。目前主要靠日志排查问题，缺少全链路 Tracing。一个任务从 Agent 提交到最终完成，中间经过 gateway、scheduler、Worker、供应商，如果失败了很难快速定位是哪个环节出了问题。改进方向是接入 OpenTelemetry，每个任务携带 trace_id 贯穿全链路。

Q10：Agent 项目的性能瓶颈上限

满分逐字稿

面试标准逐字稿

Agent 服务的终极瓶颈不在我们自己的代码，而在 LLM API 调用。

分析一下各层的上限：SSE 连接——单实例 FastAPI 支撑几千个 SSE 长连接没问题（asyncio 非阻塞 IO）。画布感知——ContextVar + 内存缓存，开销可忽略。Agent 状态机——LangGraph 的 while 循环本身很快，瓶颈不在这。Checkpointer——SQLite 写入延迟微秒级，PostgreSQL 也是毫秒级，不是瓶颈。

真正的瓶颈是 LLM API 调用——每次推理 1-10 秒，一个 Agent 对话可能需要 3-5 次 LLM 调用，总耗时 10-30 秒。这意味着单个会话的端到端延迟就是 10-30 秒，这不是系统优化能解决的，是 LLM 本身的速度限制。

并发上限取决于 LLM API 的 QPS 限制。如果供应商给 100 QPS，每个会话平均 4 次 LLM 调用，那理论上同时能处理 25 个并发会话。要提高并发，要么谈更高的 QPS 配额，要么用更快的模型（更小的模型推理更快），要么优化 Token 用量（我的分层上下文方案就是在减少每次 LLM 调用的 Token 量，间接提高吞吐）。

调度平台侧的瓶颈是 Worker 数量和供应商并发限制。当前 20 个 Worker 节点，每个 Worker 支持 3-5 个并发任务，理论上限是 60-100 个并发 AI 生成任务。扩容可以增加 Worker 数量，但最终瓶颈还是供应商的 API 并发限制。
