一、课程概述

1.1 为什么需要这节课

在灵犀互娱（阿里游戏）的面试中，暴露了两个致命问题：

  1. 三层部署拓扑讲不清楚：面试官始终无法理解系统的物理部署结构，分不清"本地 Python 服务"和"云端 Go 微服务"各自负责什么、为什么需要这种拆分。
  2. SSE 全链路一致性矛盾：面试官追问"如果本地到云端不是流式，那客户端到本地做 SSE 有什么意义？"——候选人没有给出清晰的回答，导致面试官认为架构理解存在自相矛盾。

这两个问题的根源是同一个：没有建立"三个物理位置、两种数据流"的清晰心智模型。一旦面试官的心智模型和你讲的对不上，后面所有技术细节都是噪音。

1.2 面试官在考什么

当面试官问"讲讲你的系统架构"时，他不是在考你能不能画框图，而是在考：

考察维度权重面试官真正想听到什么
部署拓扑认知30%你知道代码跑在哪台机器上吗？进程边界在哪？
通信协议选型25%不同链路为什么选不同的协议？你能说清楚理由吗？
数据流分层25%哪些数据走流式、哪些走轮询？这不矛盾吗？
工程取舍意识20%你做过 trade-off 吗？为什么不全链路流式？
核心策略：回答架构问题时，永远从物理部署位置开始讲，而不是从"模块"或"层"开始讲。先让面试官建立空间感（三台机器/三个进程），再往里填每个位置的职责和它们之间的通信方式。

2.1.1 本地服务的两条出站链路

本地 Python 服务向"云端"发起的请求不是一条链路，而是两条，协议完全不同：

链路目标服务协议用途
本地 → AIGW（LLM 网关） LLM 推理 SSE 流式（OpenAI 兼容，stream: true） Agent 对话、思考、工具决策
本地 → DM Scheduler 任务执行 HTTP REST + 轮询 生图/生视频/3D 等生成任务

面试时切忌笼统说"本地到云端是 HTTP"——LLM 链路是全链路流式的，生成任务链路才是轮询。

2.2 模块一：Electron 客户端前端

UI 形态

前端是一个 Electron 桌面应用（React + TypeScript），核心界面由两部分组成：

  • 画布区域（基于 React Flow）：用户在画布上创建各类节点（图像、视频、3D、音频、文本等），节点之间可以连线表示引用关系——比如一个 3D 生成节点连出一条线到格式转换节点，表示"用前一个节点的输出作为输入"。
  • Agent 聊天面板（侧边栏）：用户在这里和 AI Agent 对话，Agent 可以理解画布上下文、调用工具、在画布上创建或修改节点。

用户操作流程

用户有两种操作方式：

  1. 直接操作画布：手动创建节点、填写生成参数（如提示词、模型选择）、点击"生成"按钮。这条路径不经过 Agent，前端直接调后端 API 提交生成任务。
  2. 通过 Agent 对话：在聊天面板输入自然语言指令（如"帮我生成一张赛博朋克风格的图"），Agent 理解意图后自动调用工具、创建节点、提交生成任务。这条路径走 SSE 流式协议。

画布数据存储在哪里

一个容易误解的点：画布数据（节点、连线、历史版本）不存在用户本地，而是存在云端的画布后端服务（dm-tapnow-backend，部署在网易内网）。前端操作画布（增删改节点）直接调画布后端 API 写入云端数据库；本地 Agent 需要感知画布时，也通过 HTTP GET 向同一个画布后端拉取数据。

本地 Agent 服务上不存任何画布数据。它是纯计算节点——跑 Agent 逻辑、调 LLM、推 SSE 事件。本地唯一持久化的数据是 SQLite 里的 LangGraph checkpoint（对话历史状态）。这也是为什么模块二中 Agent 读画布要用 ContextVar 做请求内缓存——每次都要走网络到云端拉取，缓存起来避免同一个 /chat 内重复 HTTP。

另一个推论：Agent 在画布上创建节点后，会推 canvas.render 事件让前端全量刷新——因为 Agent 是通过 HTTP 调画布后端 API 创建节点的（写到云端数据库），前端需要重新从云端拉最新数据才能看到 Agent 的操作结果。

前端与后端的通信（后端开发者需要知道的）

前端有两套独立的 API 客户端，分别对应本地 Agent 和云端服务：

客户端目标典型请求协议

apiClient云端服务/api/canvases、/api/canvas/{id}/actionsHTTP REST

Agent 对话的 SSE 流程（这是后端最需要理解的部分）：

  1. 用户输入消息 → 前端用 fetch()（不是浏览器原生 EventSource）发起 POST /chat，请求体包含 session_id、canvas_id、消息内容。
  2. 后端返回 text/event-stream 响应，前端通过 ReadableStream 逐帧解析 SSE 事件。
  3. 事件类型与前端行为的对应关系：
    • block.created（type=text）→ 在聊天面板创建新的文本气泡
    • block.delta → 增量追加文本到气泡（打字机效果），或追加工具调用的参数
    • block.updated → 更新工具调用状态（生成中→已完成），或推送生成任务的进度/结果
    • interaction.request → 弹出 HITL 审批卡片（确认/批量确认/选择），用户决策后前端调 POST /chat/{sessionId}/resume，原始 SSE 流继续推送后续事件
    • canvas.render → 触发画布刷新（Agent 在画布上创建了新节点）
    • stream.done / stream.error / stream.cancelled → 流结束，前端做收尾处理

通信方向：SSE 是单向的

SSE 是半双工协议——服务端推、客户端收。前端想给后端发消息，走的是独立的 HTTP 请求，不是通过 SSE 回传：

方向方式例子
后端 → 前端SSE 事件流block.delta（token 增量）、interaction.request（审批请求）、canvas.render（画布刷新）
前端 → 后端独立 HTTP 请求POST /chat（发消息）、POST /chat/{id}/resume（审批决策）、POST /sessions/{id}/cancel（取消）

整个对话的通信模型是：前端发一个 POST /chat，后端返回一条 SSE 长连接持续推事件；中间如果需要 HITL 审批，前端通过另一个 POST /chat/{id}/resume 告诉后端用户的决策，原来那条 SSE 流不会断，后端继续在上面推后续事件。

面试要点：面试官可能会问"前端怎么消费 SSE"。关键要说清楚：用 fetch + ReadableStream 而不是 EventSource（因为需要 POST 方法和自定义 header），前端有自定义的 SSE 帧解析器，支持断线指数退避重连（最多 5 次），重连时通过 Last-Event-ID header 实现续传。

过渡：前端发出的 POST /chat 请求到达本地 Python 服务后，由 dm-monet-agent 的 Agent 引擎接管——下面介绍这个引擎的内部结构。

2.3 模块二：dm-monet-agent 本地服务

这是整个系统最核心的模块——它是 Agent 的大脑，负责理解用户意图、编排工具调用、管理上下文、推送流式事件。前端发来的 POST /chat 请求，就由这个模块全权处理。

2.3.1 Agent 引擎：DeepAgents + LangGraph

Agent 的核心循环基于 ReAct 模式（Reasoning + Acting）：LLM 推理 → 决定是否调工具 → 执行工具 → 观察结果 → 继续推理。这个循环由 DeepAgents 框架（内部封装，基于 LangGraph 构建）驱动，底层是 LangGraph 的 StateGraph 状态机——LLM 节点和 Tool 节点是两个状态，条件路由根据 LLM 输出决定走哪条边。

flowchart LR

（调 AIGW 流式接口）"]
    LLM --> Decision{"需要工具？"}
    Decision -->|"是"| Tool["执行工具
（生图/查画布/操作节点）"]
    Tool --> Observe["观察结果"]
    Observe --> LLM
    Decision -->|"否"| Response["输出回答
（SSE 推送给前端）"]

几个关键设计决策：

  • LLM 调用：通过 ChatAIGW（继承自 LangChain 的 ChatOpenAI）调 AIGW 网关，默认 streaming=True，token 逐个流回（详见 I04）。
  • 状态持久化：用 LangGraph 的 SqliteSaver 做 Checkpointer，对话状态存本地 SQLite。选 SQLite 是因为 Agent 跑在用户本机、单用户场景，不需要分布式存储（详见 I03）。
  • 递归限制：recursion_limit=15，防止 Agent 陷入工具调用死循环。

2.3.2 事件循环、协程与 ContextVar

理解 dm-monet-agent 的运行模型，需要先搞清楚三件事：事件循环怎么调度、为什么不能阻塞、画布数据怎么在深层调用链中传递。

事件循环与协程

服务用 FastAPI + uvicorn 运行，底层是一个 asyncio 单线程事件循环。整个服务只有一个线程、一个事件循环，所有请求都是这个循环里的协程。

虽然是单用户本地服务，但用户可以在同一个画布下开多个聊天会话。如果会话 A 的 Agent 还在流式回复中，用户切到会话 B 又发了一条消息——事件循环里就同时跑着两个 /chat 协程。不过同一个 session 不会并发，代码入口第一步就是 await _cancel_existing_chat(session_id)，先取消同 session 未完成的 chat。

一次 /chat 请求的协程调用链：

chat()                                          ← 整个请求是一个协程
  ├─ await _cancel_existing_chat(session_id)    ← 取消同 session 旧请求
  ├─ await _prime_canvas_context(canvas_id)     ← 异步 HTTP 拉画布详情
  │     └─ await canvas_client.get_canvas_detail()  ← httpx.AsyncClient 发 HTTP GET
  ├─ create_model / create_agent                ← 同步，创建 Python 对象，不涉及 I/O
  └─ return StreamingResponse(inner_stream)     ← 返回后 uvicorn 驱动 inner_stream
       └─ async for event in agent.astream_events():  ← Agent 主循环
            ├─ await ChatAIGW._astream()              ← 等 AIGW 返回下一个 token
            ├─ await tool.invoke()                     ← 执行工具（可能包含 HTTP 调用）
            └─ yield SSE frame                         ← 产出一帧给前端

每个 await 是一个协程挂起点——当前协程暂停，把控制权还给事件循环。事件循环检查有没有其他协程的 I/O 就绪了，有就切过去执行。比如会话 A 在 await ChatAIGW._astream() 等 AIGW 返回下一个 token 时，事件循环发现会话 B 的画布 HTTP 响应到了，就切去跑 B 的后续逻辑。等 A 的 token 到了再切回来。这不是并行（同一时刻只有一个协程在跑），但因为大部分时间花在等 I/O，协程切换让 CPU 不闲着，宏观上看起来像并发。

为什么不能阻塞

单线程事件循环的致命问题：任何同步阻塞调用都会冻住整个服务。

# ❌ 阻塞写法 — 事件循环停转，所有请求卡住，SSE 流中断
import time, requests
time.sleep(5)
resp = requests.get("https://api.example.com")

# ✅ 异步写法 — 只挂起当前协程，事件循环继续调度其他协程
import asyncio, httpx
await asyncio.sleep(5)
async with httpx.AsyncClient() as client:
    resp = await client.get("https://api.example.com")

所以 dm-monet-agent 的所有 I/O 都用异步版本：HTTP 请求用 httpx.AsyncClient（不用 requests）、等待延迟用 asyncio.sleep（不用 time.sleep）、LLM 调用用 _astream / ainvoke（async 方法）。

ContextVar：协程局部变量

ContextVar 是 Python 标准库 contextvars 提供的协程局部变量。变量定义在模块级（看起来像全局变量），但值的存储是 per-Task 的——每个 asyncio Task 有自己独立的一份，互不干扰。类比 threading.local() 是线程局部变量（per-thread），ContextVar 是协程局部变量（per-Task）。

底层机制：每个 asyncio Task 内部挂着一个 Context 对象（类似一个字典）。set() 写入当前 Task 的 Context，get() 从当前 Task 的 Context 读取。Task 创建时从父级拷贝一份 Context 快照，之后各写各的。

# 全局变量 — 所有协程共享，await 切走后可能被别的协程覆盖  ❌
canvas_text = None

# ContextVar — 每个协程 Task 各有一份，await 切走也不会被覆盖  ✅
_canvas_text: ContextVar[str | None] = ContextVar("canvas_text", default=None)

dm-monet-agent 定义了两个画布相关的 ContextVar（canvas/context.py）：

  • _canvas_overview_text：渲染好的画布概览 Markdown 文本，供每次 LLM 调用时注入
  • _canvas_detail：画布详情原始 dict，供 canvas_subgraph 工具复用

为什么需要 ContextVar？ /chat 的调用链很深：routes.py → DeepAgentStreamAdapter → agent.astream_events() → LangGraph 状态机 → CanvasAwareChatAIGW._astream() → inject_canvas_overview()。画布数据需要在最深层的 inject_canvas_overview() 使用，但中间隔着 LangGraph 框架代码——改不了框架的函数签名，没法把画布数据当参数传下去。

ContextVar 的做法：入口写入，深层直接读取，不改中间任何一层的函数签名：

/chat 入口（routes.py:289）
    │
    ├─ await _prime_canvas_context(canvas_id)
    │     ├─ await canvas_client.get_canvas_detail()    ← HTTP GET 拉画布，只拉一次
    │     ├─ set_canvas_detail(detail)                   ← 写入 ContextVar
    │     └─ set_canvas_overview_text(overview)           ← 写入 ContextVar
    │
    └─ Agent 运行（多轮 LLM + 工具调用）
          │
          ├─ 第 1 次 LLM 调用
          │     └─ inject_canvas_overview()
          │           └─ get_canvas_overview_text()       ← 从 ContextVar 读，不发 HTTP
          │
          ├─ 工具调用: canvas_subgraph
          │     └─ get_canvas_detail()                    ← 从 ContextVar 读，复用入口数据
          │
          └─ 第 2 次 LLM 调用
                └─ inject_canvas_overview()
                      └─ get_canvas_overview_text()       ← 同一请求内始终读同一份缓存

ContextVar 在这里的核心价值：免传参（深层代码直接 get()，不用改 LangGraph 框架的函数签名）和请求内缓存（入口拉一次画布数据，同一个 /chat 请求内多次 LLM 调用和工具调用复用，避免重复 HTTP）。

LangGraph 内部产生的事件（on_chat_model_stream、on_tool_start、on_tool_end 等）是框架私有的，前端无法直接消费。要理解这些事件从何而来，需要先看清 token 从 AIGW 到前端的完整流式调用链：

关键理解：astream_events() 不是凭空产生事件的——它是一个观察者，包裹住状态机的整个执行过程。当 LLM 节点在流式 yield token 时，它拦截到每个 yield，包装成 on_chat_model_stream 事件；当状态机路由到工具节点、工具开始/结束执行时，同样拦截并包装成 on_tool_start / on_tool_end。token 的真正源头是 AIGW 返回的 SSE 流，经过上面的每一层一路 yield 下来——每层都是 async iterator，没有任何地方攒批或阻塞，这就是 LLM 链路能做到全链路流式的根本原因。

DeepAgentStreamAdapter 的职责就是把这些内部事件翻译成前端约定的 SSE 协议：

LangGraph 内部事件翻译后的 SSE 事件含义
on_chat_model_stream（纯文本）block.created（type=text）+ block.deltaLLM 正在逐 token 输出文本
on_chat_model_stream（含 tool_call_chunks）block.created（type=tool_use）+ block.deltaLLM 决定调用工具，参数正在流式生成（还没开始执行）
on_tool_startblock.updated（status=running）工具开始执行（参数已确定）
on_tool_endblock.updated（status=completed，result 内嵌）工具执行完毕，返回结果。tool_use block 内嵌 result，没有独立的 tool_result block
interrupt() 触发interaction.requestAgent 需要用户审批（HITL）
on_custom_event（canvas.render）canvas.renderAgent 修改了画布，通知前端刷新

这层翻译的价值在于框架解耦：如果未来换掉 LangGraph（比如换成 AutoGen 或 CrewAI），只需要写一个新的 StreamAdapter 实现事件映射，前端协议不用改（详见 I04）。

2.3.4 分层上下文感知

Agent 不是一个"纯聊天机器人"——它需要知道画布上现在有什么。上下文注入分三层（详见 I02）：

  1. 画布概览（入口层）：每次 /chat 请求进来时，调 _prime_canvas_context(canvas_id) 向画布后端拉取画布详情，渲染成 Markdown 摘要（节点数、类型分布、名称列表），通过 ContextVar 缓存在请求作用域内。后续每次 LLM 调用前，通过 inject_canvas_overview() 注入到最新一条 HumanMessage 前面——这样 LLM 能"看到"画布全貌，但不会把全量节点信息塞满上下文。
  2. 按需查询（工具检索层）：Agent 可以通过 canvas_node_detail 和 canvas_subgraph 两个工具按需查询某个节点的详细信息或子图拓扑——只有 Agent 判断需要时才调用，避免无关信息占用 token。
  3. Token 预算管理（三道防线）：随着对话轮次增加，上下文总量会逼近模型窗口限制（128k）。第一道防线是 token 预检（用 tiktoken 编码器计算即将发送的 message 列表 token 数）；第二道是渐进式裁剪（从最早的历史开始裁，优先裁工具调用结果，保留系统提示词和最近 4 轮）；第三道是 LLM 摘要压缩（把被裁掉的部分用轻量模型压缩成 200-500 token 的摘要拼到保留内容前面）。

2.3.5 HITL 人机审批

Agent 调用工具时，需要判断这个操作是否需要用户确认。权限配置分两层：

第一层：工具级静态配置。在 Agent 工厂（factory.py）中，通过一个静态字典定义哪些操作需要 interrupt 审批：

PERMISSION_INTERRUPT_ON_TOOLS = {
    "execute": True,      # 执行 shell 命令
    "write_file": True,   # 写文件
    "edit_file": True,     # 编辑文件
}

不在字典里的工具（如 query_models、canvas_node_detail、generate_and_create_node）默认不需要审批，直接执行。这个字典在创建 Agent 时传给 DeepAgents 框架的 interrupt_on 参数。

第二层：请求级权限模式。前端发 /chat 时带 permission_mode 参数：

  • ASK 模式 → 使用上面的字典，写操作需要审批。
  • FULL_ACCESS 模式 → 传 None，所有操作都自动放行，不触发任何 interrupt。

当工具命中 interrupt_on 配置时，完整的中断-恢复流程如下：

第一步：中断（interrupt）

DeepAgents 框架在工具节点执行前调用 interrupt()，LangGraph 抛出 GraphInterrupt 异常中断状态机循环——注意这不是线程挂起，而是异常驱动的控制流。中断时 LangGraph 自动把当前 state（对话历史、工具调用参数、节点执行位置等）通过 Checkpointer 持久化到 SQLite。

第二步：推送审批事件

中断后，DeepAgentStreamAdapter 进入一个 while True 循环：先调 aget_state(config) 从 Checkpointer 读取 state snapshot，检查是否有 pending interrupts。有则调 _build_interaction_frame(interrupt) 构造 interaction.request SSE 事件推给前端，事件内容包括：

  • 操作名称（如 write_file）
  • 操作参数（如文件路径、内容）
  • 操作描述
  • 可选项：["approve", "reject"]
  • 如果是批量操作（多个工具调用），会合并成一个 batch 审批

第三步：等待用户决策

推完审批事件后，代码调 register_interrupt(session_id) 创建一个 asyncio.Event，然后 await asyncio.wait_for(event.wait(), timeout=300) 挂起当前协程等待——SSE 连接不断开，前端仍然保持着这条长连接。超时 300 秒未决策则自动失败。

第四步：恢复（resume）

用户在前端审批卡片上选择 approve 或 reject → 前端调 POST /chat/{sessionId}/resume → 后端 resolve_interrupt() 把 decision 存入内存并 event.set() 唤醒等待中的协程 → 代码用 Command(resume=matched_decision) 调 astream_events() 恢复状态机。

恢复时 LangGraph 框架从 Checkpointer 读取之前持久化的 state，找到中断时的节点位置，重新执行该节点函数。此时 interrupt() 不再抛异常（因为已经有了 resume value），节点继续往下执行工具逻辑。这要求 interrupt() 之前的代码必须是幂等的——因为重新执行时会再跑一遍。

如果用户 approve → 工具正常执行，结果通过 SSE 推给前端。如果 reject → 工具跳过，Agent 收到拒绝信息后可能换一种方式继续对话。恢复后可能又触发新的 interrupt（比如 Agent 接着又要调另一个写操作），所以外层是 while True 循环，直到 graph 正常完成（无 pending interrupt）才退出。

2.3.6 任务提交与轮询（连接模块三）

当 Agent 决定执行一个 AI 生成任务（比如调用 generate_image 工具），本地服务通过 DmProvider 向云端提交任务：

  1. 提交：POST /api/v1/apps/{app}/run，携带生成参数（提示词、模型选择等），云端返回 task_id。
  2. 轮询：InvocationRuntime._poll_until_complete() 以固定间隔（图像 5s、3D 10s、视频 30s）循环调 GET /api/v1/apps/{app}/status，每次返回一次性 JSON 快照（status、progress、error）。轮询在后台默默进行，中间进度不会推送给前端——前端在此期间看到的是工具调用卡片的"执行中"状态。
  3. 获取结果：任务成功后调 fetch() 拿最终结果（图片 URL、视频 URL 等）。结果作为工具返回值，被 LangGraph 捕获为 on_tool_end 事件，DeepAgentStreamAdapter 翻译成 block.updated（status=completed）推给前端——前端此时才看到生成完成的结果。

注意：这里的轮询对象是云端 DM Scheduler（模块三），不是 AIGW。AIGW 只负责 LLM 推理的流式调用，不负责生成任务。

2.3.7 反向代理：Nginx vs Electron 自定义协议

前端访问本地 Python 服务和云端 API 的路由方式，在浏览器版和 Electron 桌面版是不同的：

部署形态Agent 请求（/chat 等）云端 API 请求（/api/*）
Web 浏览器版 Nginx 反向代理到远程 Agent 服务 前端将 /api/ 改写为 /proxyApi/，Nginx 反代到云端后端
Electron 桌面版 自定义 agent://local 协议，Electron 主进程拦截后用 net.fetch 转发到本地 Python 服务（http://127.0.0.1:{port}） apiClient 通过 /proxyApi/ 前缀走同样的路径改写

为什么 Electron 要用自定义协议而不直接 localhost？因为 Electron 加载的页面可能是 HTTPS 协议，直接请求 http://127.0.0.1 会触发浏览器的混合内容限制和 CORS 预检。自定义 agent:// 协议绕过了这个问题——主进程拦截请求后自动注入认证 header（X-Access-Token、X-Auth-User 等）再转发。

Nginx 的 SSE 关键配置：Web 版的 Nginx 全局配置了 proxy_buffering off 和 proxy_cache off，确保 SSE 事件不会被 Nginx 缓冲。如果不关闭缓冲，Nginx 会攒满一个 buffer 再转发，前端收到的 token 就变成一批一批的，打字效果完全丧失。本地 Python 服务也通过响应头 X-Accel-Buffering: no 做了双保险——即使 Nginx 没全局关闭缓冲，这个 header 也能让 Nginx 对该响应单独禁用。

过渡：本地服务提交的任务到达云端后，由 DM Scheduler 微服务集群接管——下面介绍云端的任务调度和执行链路。

2.4.3 优先级队列调度（详见 I05）

队列隔离：不同优先级对应不同的 Redis key，队列按 key 隔离。key 格式为 apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}，score 是毫秒时间戳（同优先级内先进先出）。

加权轮询解决饥饿问题：纯优先级调度有经典问题——"高优先级队列非空就不看低优先级"，高负载时低优先级任务会完全饿死。我们的做法是加权轮询：为每个优先级维护一个配额计数器（counter），初始值等于配置的 weight。每次调度时 pickPriority 按 priority 降序遍历，找到第一个 counter > 0 的优先级，返回它并把 counter 减 1。当所有 counter 都归零时全部重置回初始 weight，开始新一轮。举例：配置 [{priority:5, weight:5}, {priority:0, weight:3}]，一轮 8 次调度中前 5 次选 priority=5、后 3 次选 priority=0——高优先级在同一轮内优先被消费，但低优先级按配额比例保证不会饿死。

降序兜底：加权轮询选出的优先级队列可能恰好为空（没有该优先级的任务）或候选全被其他 Pod 抢走了。此时 Consume 函数会 fallback 到降序遍历所有优先级队列——从最高优先级到最低逐个 tryConsume，哪个队列先拿到任务就返回，确保这次消费循环不会空跑。所以完整的消费流程是：加权选队列 → 尝试消费 → 失败则降序扫全部队列兜底。

无锁乐观抢占（tryConsume + grabJob）：

  1. 批量候选拉取：消费者调用 ZRange(key, 0, 255)，一次取出该优先级队列中最多 256 个候选（按 score 排序，最早的在前）。
  2. 遍历 + 用户并发检查：对每个 member（格式 user::taskID），检查该 user 是否已有任务在运行。有并发冲突的暂存到 queueJob 列表跳过。
  3. 竞争删除（grabJob）：对无冲突的 member 执行 ZREM key member。由于 Redis 单线程，只有一个 ZREM 返回 ≥ 1（删除成功），其他返回 0。返回 ≥ 1 的消费者获得任务所有权 → 从 MongoDB 加载完整数据 → 注册 etcd → 执行。返回 0 的消费者继续遍历列表中下一个候选（不需要重新 ZRange）。
  4. 二轮兜底：第一轮遍历完后，对 queueJob 中跳过的 member 再做一轮 grabJob。
为什么没有用 Lua 脚本合并 ZRange + ZREM？
确实可以把 ZRange 和 ZREM 封装成 Lua 脚本原子执行来消除竞态窗口，但实际没这样做，原因有三：① ZRange 拿到候选后还要检查用户并发（查 Go 进程内存中的 concurrentManager），这些业务判断无法在 Redis Lua 里完成；② 批量拉 256 个候选 + 逐个尝试的模式足够高效，前几个被抢了后面还有大量候选，不需要反复网络往返；③ DM 的任务量级是每秒几十到几百，多 Scheduler 实例并发扫同一队列的频率不高，空竞争率实测很低。

为什么不用分布式锁？
分布式锁（如 RedLock）引入额外的锁竞争、超时、续租等复杂性。而 ZREM 天然具有"谁删成功谁拥有"的语义，本质上是一种乐观并发控制——先做操作，通过返回值判断是否成功，失败则继续下一个候选。比悲观锁性能更好、实现更简单。

etcd Watch + 内存原子计数器做用户并发管控：

每个用户同时能跑的任务数需要限制，防止一个用户占满集群算力。实现方式是 ConcurrentManager——一个纯内存的原子计数器，维护两个 map：taskMap（按 source::taskMode::cluster 维度计数）和 userMap（再加上 user 维度）。计数器由 etcd Watch 驱动：任务注册到 etcd（key /task/{env}/{taskID}）时 Watch 收到 PUT 事件 +1；任务完成或 Worker 崩溃导致 key 删除时 Watch 收到 DELETE 事件 -1。消费时的并发检查：在 tryConsume 遍历候选任务时，对每个 member 调 concurrentManager.GetUser()，如果返回值 ≥ 1（该用户已有任务在运行），就暂时跳过放入 queueJob 列表。

原子计数器的线程安全：ConcurrentManager 使用 go.uber.org/atomic 的 Int64，底层是 Go sync/atomic 包。关键的增减操作是一个 CAS 循环——先 Load 当前值，计算 next = curr + delta（负数结果钳位到 0），调 CompareAndSwap(curr, next)，CAS 失败说明有其他 goroutine 修改了值，重新循环。

多 Pod 一致性：每个 worker-scheduler Pod 都有自己独立的 ConcurrentManager。多 Pod 之间靠 etcd Watch 同步——所有 Pod 都 Watch 同一个 /task/{env}/ 前缀，一个 Pod 注册了任务（写 etcd），其他 Pod 都收到 PUT 事件各自 +1。最终每个 Pod 的计数器基本一致——etcd Watch 有毫秒级延迟，极端情况下可能短暂超过并发限制，但对"限制并发"场景够用。

2.4.4 Worker 注册发现与心跳（详见 I06 Q1）

在我们的调度平台里，worker-scheduler 启动时调用 etcd Grant 创建一个 TTL=7200s（2小时）的 Lease，然后每 5 分钟重新 Grant 一次刷新 Lease；Worker-sidecar 启动时通过 HTTP 调用 worker-scheduler 的 Report 接口注册自己，worker-scheduler 收到后将 Worker 信息 Put 到 etcd（如 /worker/{env}/{name}），绑定当前 Lease；之后 sidecar 每 30s 发一次 HTTP 心跳，worker-scheduler 收到后 re-PUT 该 Worker 的 key，保持信息新鲜。

如果 Worker 宕机或网络断连，心跳停止。worker-scheduler 侧通过心跳超时判断 Worker 不可用，不再为其 re-PUT key。当 Lease 最终过期时，etcd 自动删除绑定在该 Lease 上的所有 Worker key。worker-scheduler 自身通过 Watch 机制监听 /worker/ 前缀，收到 DELETE 事件后执行三个清理动作：将该 Worker 从内存调度缓存中移除（workerCache.Delete）、从任务路由表中清理（cacheKeyManager.WorkerDelete，按类型/集群的索引）、递减对应集群的 Worker 计数器（workerClusterMap.Decr）——这样后续任务就不会再分配给已下线的节点。

2.4.5 弹性扩缩容（详见 I06 Q3）

DM 的任务分两类：调供应商 API 的任务（如 Kling、Runway）只需要 HTTP 调外部接口，跑在 CPU Worker 上；开源部署的任务（如 ComfyUI、SD）需要本地 GPU 推理，跑在 GPU Worker 上。CPU Worker 相对廉价，用 K8s HPA 按 CPU/内存水位扩缩就够了。但 GPU Worker 不行——GPU 满载推理时 CPU 可能很闲，HPA 看 CPU 5% 会觉得"资源充足"甚至触发缩容，这完全是误判。所以我们针对 GPU Worker 自定义了 Autoscaler。

自定义 Autoscaler 的核心指标是任务队列积压深度（GPU Worker 类型如 ComfyUI、SD 从 MongoDB 查 status=queued 的记录数）。每 30 秒检查一次，扩容条件是 Worker 数 ≤ 队列长度的一半；缩容条件是 Worker 不在忙且空闲时间超过配置的阈值，同时 Running Worker 数要大于最小副本数下限。扩容的方式比较特别——不是创建新 Pod，而是唤醒已 terminated 的 Pod，调 api-kube 的 UpdateWorker 接口重新激活它；缩容则是调 DeleteWorker 删除空闲 Pod。

有几个细节：第一，扩缩容有冷却期，通过 Redis ZSet 记录操作历史，冷却期内跳过本轮，防止指标抖动导致频繁扩缩（thrashing）。第二，缩容时会检查 Worker 是否在忙，只对空闲且超过阈值的 Worker 缩容，实现优雅下线。第三，设置了最小副本数下限（MinWorker），即使完全空闲也不会缩到零。第四，有安全检查——如果有 Worker 处于 pending 或 terminating 状态，本轮直接跳过，防止"还没启动完就又触发扩容"的雪崩式超扩。第五，因为多个 worker-scheduler 实例同时运行，用 Redis 分布式锁保证同一时刻只有一个实例执行扩缩容。

2.4.6 容错降级：重试与供应商切换（详见 I06 Q6-Q8）

worker-sidecar 调用供应商时的容错分三层，从内到外依次是：

第一层：executeWithRetry——同一供应商内的快速重试

代码在 api/external/aigw/openai.go，是一个同步的 for 循环，最多 3 次重试，指数退避 1s→2s→4s。匹配的错误类型是网络超时、连接拒绝、TCP 读写错误、网关错误（HTTP 502+）等暂时性故障。HTTP 429 限流不在这里处理。最后一次失败不再 sleep，直接返回错误。

第二层：queue-retry——针对 429 限流的长退避轮询

专门针对 PT 模型（art1/art3）等白名单内的模型。当供应商返回 429 时，不是立即失败，而是进入一个更长的退避轮询循环。参数从配置文件读取，默认值为：初始退避 3s、最大退避 60s、倍数 2.0、抖动因子 ±20%、最大等待时间可达数小时。退避阶梯是 3s→6s→12s→24s→48s→60s（cap）。抖动的计算方式是 基础退避 ± (基础退避 × jitter)，即双向随机偏移，避免多个任务在同一时刻重试造成惊群效应。如果 queue-retry 最终超时仍未恢复，错误会被标记为可重试类型，从而触发外层的 Fallback chain。

第三层：Fallback chain——供应商之间的切换

代码在 worker-sidecar/pkg/fallback/executor.go。当主供应商的内层重试全部耗尽后，如果错误是可重试类型，fallback.Run 会切到 fallback 链路中的下一个供应商。每个备用供应商内部又有自己的 executeWithRetry（独立的 3 次重试）。链路是线性的：主供应商 → 备用 1 → 备用 2 → ...，直到某一个成功或全部耗尽。

整个过程是无状态的 per-request fallback——不维护熔断器状态，不记录哪个供应商"当前不可用"，每个新请求都从主供应商开始尝试。这意味着主供应商恢复后，下一个请求自然就能成功，不需要额外的"恢复探测"机制。代价是：主供应商持续故障时，每个请求都要先打一次主供应商、等它重试耗尽后才切备用，增加了延迟——但对 AI 生成任务（本身耗时 10s-几分钟）来说，多等几秒重试的感知不强。

Fallback 规则按模型粒度配置在 MongoDB 的 dreamworker_fallback_rule 集合中，每条规则包含主模型、备用模型列表、最大 fallback 深度、以及 skip_on（某些错误不切换，如内容审核不通过）和 retry_on（只在匹配特定错误时才切换）的精细化控制。

可优化点：引入熔断器（Circuit Breaker）
当前的无状态 per-request fallback 有一个代价：主供应商持续故障时，每个请求都要先打一次主供应商、等 3 次重试耗尽后才切备用，白白浪费几秒延迟。如果引入熔断器模式，可以记住"这个供应商最近挂了"：失败次数超过阈值后进入 Open 状态，短期内直接跳过主供应商、立即走备用；一段时间后放一个探测请求试试是否恢复（Half-Open），成功则恢复正常流量（Closed）。这能显著减少故障期间的用户等待时间。当前没做的原因是实现简单优先，且 AI 任务本身耗时长（10s-几分钟），多等几秒重试的感知不强——但如果供应商故障频率上升，熔断器会是下一步的优化方向。

2.4.7 结果如何回到本地 Agent

worker-sidecar 执行完任务后，将结果（图片 URL、视频 URL 等）和状态（success/failed）回写 MongoDB。没有回调、没有推送——本地 Agent 通过轮询 GET /api/v1/apps/{app}/status 查到 status: success 后，从响应的 data 字段取出结果。

这意味着从任务完成到本地 Agent 感知到结果，有一个轮询间隔的延迟（图像 5s、3D 10s、视频 30s）。但相对于任务本身几秒到几分钟的执行时间，这个延迟可以忽略不计。

2.6 为什么生成任务链路不做全链路流式

面试官一定会追问：既然 LLM 链路已经是全链路 SSE，生成任务为什么不也做成全链路流式？答案涉及工程取舍：

方案优点缺点适用场景
全链路 SSE/WebSocket 端到端延迟最低；实时性最好 云端需要维护大量长连接；跨网络（用户PC到云端）长连接不稳定；Worker 执行本身就是批处理，不产生流式输出 纯 LLM 对话产品（如 ChatGPT Web）
LLM 流式 + 任务轮询（当前方案） LLM 链路全链路流式、体验好；任务链路 HTTP 无状态、高可靠；轮询可控制频率 任务结果有轮询间隔的延迟（按任务类型不同，3-30 秒） AI Agent + 异步生成任务的混合场景
全链路轮询 最简单 LLM Token 流式输出做不了，用户体验差 纯后台任务系统

核心论点：LLM 推理链路必须流式——token 是逐个生成的，不流式用户就要等 5-30 秒看完整回复，体验不可接受。但生成任务不同——Worker 调用外部 AI 供应商本身就是"提交→等→拿结果"的批处理模式，供应商 API 不产生中间流式输出，所以全链路流式没有意义。轮询间隔（图像 5 秒、视频 30 秒）相对于任务本身 10 秒-几分钟的执行时间，延迟可忽略不计。

2.8 SSE 长连接的工程细节

本地 Python 服务在返回 SSE 响应时的关键设置：

  • 使用 FastAPI 的 StreamingResponse，media_type="text/event-stream"。
  • 响应头设置 X-Accel-Buffering: no——这是告诉上游代理（如 Nginx）禁用缓冲，保证 SSE 事件能实时推送。这意味着部署架构中可能存在反向代理层。
  • 内置心跳机制（stream.heartbeat 事件），防止长连接被代理或防火墙因空闲而断开。
  • 流结束时发送 stream.done，异常时发送 stream.error，取消时发送 stream.cancelled，前端据此做不同的 UI 收尾处理。

三、面试易错点

3.1 把部署拓扑讲成逻辑分层

错误表述："我们的系统分为 Agent 层、网关层、调度层、执行层..."
问题：面试官听不出来这些"层"分别跑在哪台机器上。他会以为所有东西都在云端，然后你说"Agent 跑在本地"，他就困惑了——"等等，你说的本地是什么意思？"
正确方式：先说三个物理位置（用户桌面上的 Electron、用户桌面上的 Python 后端进程、网易机房的云端 Go 服务），再分别说每个位置里有什么。

3.2 SSE "全链路"表述矛盾

错误表述："我们用 SSE 实现全链路流式通信"
问题：面试官问"那本地服务到云端也是 SSE 吗？"你答不上来，因为实际是 HTTP 轮询。整个叙述自相矛盾。
正确方式：明确区分两种数据流。说"客户端和本地服务之间用 SSE 做实时事件推送，本地服务和云端之间用 HTTP 轮询拉取任务结果，轮询到结果后再通过 SSE 推给客户端"。

3.3 解释不清为什么需要本地 Python 服务

错误表述："本地跑一个 Python 后端是历史原因..."
问题：面试官会认为你不理解架构设计意图。
正确方式：本地服务存在有三个合理理由——(1) Agent 需要实时感知本地画布状态，云端做不到；(2) LLM Token 流式输出需要低延迟 SSE，本地到前端是 localhost 没有网络延迟；(3) 用户可能在断网时也需要部分 Agent 功能。

3.4 忽略轮询的工程细节

错误表述："我们轮询云端接口获取结果"（然后就没了）
问题：面试官会追问轮询间隔、超时、退避策略、错误处理。
正确方式：准备好细节——轮询间隔按任务类型不同（图像 5 秒、3D 模型 10 秒、视频 30 秒）、错误重试时使用指数退避、任务级别有不同超时上限、异常状态处理（任务失败/超时/被取消）。

3.5 不敢承认架构不完美

错误表述：面试官质疑时拼命辩解"我们的架构是最优的"
问题：没有架构是完美的。拼命辩解暴露两个问题——不理解 trade-off，或者不够自信。
正确方式：主动说出当前方案的代价（轮询有延迟、长连接有连接管理成本），以及为什么在当前业务场景下这些代价是可接受的。

四、满分逐字稿

Q0：介绍一下你们的前端画布是什么形态？用户怎么使用？

满分逐字稿

面试标准逐字稿

我们的前端是一个 Electron 桌面应用，界面分两块：画布区域和 Agent 聊天面板。

画布区域类似一个无限白板，用户在上面创建各种类型的节点——图像生成、视频生成、3D 模型、音频、文本等等。节点之间可以连线，表示引用关系。比如用户先生成一张图，然后从这个图像节点拉一条线到视频生成节点，意思是"用这张图作为输入去生成视频"。每种节点有自己的参数面板，用户填好提示词、选好模型，点生成就会提交到云端执行。

右侧是 Agent 聊天面板，用户可以用自然语言和 AI Agent 对话。Agent 能感知画布上当前有什么节点、选中了什么，然后自动调用工具来操作画布——比如用户说"帮我生成一张赛博朋克风格的图"，Agent 会自己创建图像生成节点、填好参数、提交任务，用户在聊天面板里能实时看到 Agent 的思考过程和工具调用结果。

所以用户有两种操作路径：手动操作画布（直接创建节点、填参数、点生成）和通过 Agent 对话（自然语言驱动，Agent 自动操作画布）。后者走的就是 SSE 流式协议。

Q0.1：前端是怎么消费后端的 SSE 流的？

满分逐字稿

面试标准逐字稿

前端用 fetch + ReadableStream 来消费 SSE，没有用浏览器原生的 EventSource。

原因是 EventSource 只支持 GET 请求，但我们的 /chat 接口是 POST（要带 session_id、canvas_id、消息内容等 body），而且需要自定义 header（认证 token、用户信息）。所以前端自己实现了一个 SSE 帧解析器，用 fetch 发 POST 请求，拿到 response body 的 ReadableStream 后逐帧解析 id:、event:、data: 行。

后端推过来的事件类型和前端行为是一一对应的：block.created 创建一个新的文本气泡或工具调用卡片；block.delta 往气泡里增量追加文本，形成打字机效果；block.updated 更新工具调用的状态（比如从"生成中"变成"已完成"并带上结果）；interaction.request 弹出 HITL 审批卡片，用户点确认后前端调 POST /chat/{sessionId}/resume，原始 SSE 流不会断，继续推送后续事件。

还有一个细节是断线重连。前端实现了指数退避重连（最多 5 次），重连时通过 Last-Event-ID header 告诉后端上次收到的事件编号，后端可以据此续传。另外 Agent 在画布上创建了新节点时，会推一个 canvas.render 事件，前端收到后触发画布全量刷新，把 Agent 的操作结果渲染出来。

Q1：请介绍一下你做的系统的整体架构

满分逐字稿

面试标准逐字稿

我先从部署拓扑讲起，因为这个系统比较特殊——它运行在三个不同的物理位置上。

第一个位置是用户桌面上的 Electron 客户端，这是前端 UI，用户在这上面操作画布、输入对话。

第二个位置也在用户的电脑上，但它是一个独立的后端进程——Python 写的 dm-monet-agent 服务。它和 Electron 客户端打包在一起，启动 Electron 时自动拉起。这个服务负责运行 AI Agent 的核心逻辑：DeepAgents 框架（基于 LangGraph 构建的状态机）、LLM 调用编排、上下文管理，以及通过 SSE 向 Electron 推送实时事件。

第三个位置是网易内网的云端服务器，跑的是 Go 写的 dreammaker-scheduler 微服务集群——app-gateway 做任务入口和参数校验，worker-scheduler 做 Leader 选举和任务分配，Worker 集群负责实际调用外部 AI 供应商（比如 Stable Diffusion、DALL-E、混元等）完成图片、视频、3D 模型的生成。

这三者之间的通信方式不一样。Electron 和本地 Python 服务之间通过SSE 长连接做实时推送——因为 LLM 是逐 Token 输出的，需要流式通道。本地 Python 服务向"云端"发起的请求其实分两条链路：一条是调 AIGW（LLM 网关）做 Agent 推理，用的是 OpenAI 兼容的流式接口（stream: true），AIGW 返回的也是 SSE token 流，所以 LLM 链路是全链路流式的——token 从 AIGW 流到本地服务、再流到前端；另一条是调 DM Scheduler 做图片/视频/3D 的生成任务，用的是标准 HTTP REST——POST 提交任务、GET 轮询状态——因为生成任务本身是异步批处理，耗时几秒到几分钟，供应商 API 不产生中间流式输出，轮询是最稳定的方式。

Q2：为什么要在用户的电脑上跑一个本地后端服务？直接调云端不行吗？

满分逐字稿

面试标准逐字稿

放在本地有三个核心原因。

第一，Agent 需要实时感知本地画布状态。我们的 Agent 不是一个纯聊天机器人，它能看到用户画布上当前有什么图层、选中了什么、光标在什么位置。这些信息在本地内存里，如果 Agent 跑在云端，每次推理都要把画布状态序列化传到云端，延迟和带宽代价都很大。放在本地的话，Agent 可以直接从内存读取画布快照，做到毫秒级的上下文感知。

第二，LLM Token 流式输出需要低延迟通道。LLM 每个 Token 的生成间隔大概 10-50 毫秒，如果从云端推到用户桌面，经过公网或内网延迟，Token 流会变得断断续续。本地服务和 Electron 之间是 localhost 通信，网络延迟可以忽略不计，用户看到的打字效果是流畅的。

第三，关注点分离。本地服务专注于 Agent 逻辑和用户交互体验，云端专注于 GPU 密集型的 AI 生成任务。这样两边可以独立迭代——我改 Agent 的推理链路不需要动云端的调度系统，云端加新的 AI 供应商也不影响本地 Agent 逻辑。

Q3：客户端到本地是 SSE，本地到云端不是流式——这不矛盾吗？

满分逐字稿

面试标准逐字稿

不矛盾，因为这是两种完全不同的数据流，时间尺度和特性差了几个数量级。

客户端到本地的 SSE 承载的是Agent 的实时事件流——LLM 逐 Token 输出（每个 Token 间隔 10-50ms）、工具调用通知（Agent 决定调什么工具了）、状态变化（Agent 正在思考 / 正在执行 / 已完成）。这些事件是毫秒级粒度的，用户需要实时看到，所以 SSE 这种服务端推送协议是最合适的。

本地到云端的通信承载的是异步 AI 生成任务——一个生图任务从提交到完成可能需要 10 秒到 2 分钟。这种任务的特点是：(1) 任务提交是一次性的 POST 请求；(2) 执行过程中 Worker 不产生有意义的中间流式输出（不像 LLM 有 Token 流）；(3) 结果就是最终的图片 URL。对这种场景，HTTP 轮询是最简单、最可靠的方式——无状态、不需要维护长连接、网络抖动时自动恢复。

这两种数据流最终汇聚在本地 Python 服务里。当 Agent 发起一个生图任务，它把任务 POST 到云端后，会在后台起一个轮询协程去查任务状态。这时候 SSE 连接对前端推送的内容会是"任务已提交，正在生成..."。等轮询到结果了，再通过同一条 SSE 连接推送"生成完成，这是结果"。所以前端只需要监听一个 SSE 端点，它不需要知道数据是从 LLM 流式来的还是从云端轮询来的——这个复杂性被本地 Python 服务屏蔽了。

Q4：既然轮询有延迟，为什么不用 WebSocket 做本地到云端的通信？

满分逐字稿

面试标准逐字稿

这是一个 trade-off 问题，要看具体场景。

用 WebSocket 做本地到云端的通信，技术上当然可以——云端任务状态变化时主动推给本地，延迟更低。但在我们的场景里，有几个原因让我们选择了轮询。

第一，长连接跨网络不稳定。本地服务到云端走的是公网或者内网 VPN，网络质量不可控。WebSocket 长连接一旦断了就需要重连逻辑，重连期间如果有任务完成了就可能丢消息，还需要引入消息确认和补偿机制。HTTP 轮询天然是无状态的，请求失败了下次再请求就行，不需要额外的可靠性保障。

第二，云端的连接管理成本。如果每个用户的本地服务都和云端维持一个 WebSocket 连接，云端需要管理大量长连接的状态。而我们的云端是标准的 HTTP 微服务架构，Worker 执行完任务把结果写到 MongoDB 就完事了，不需要关心谁在等这个结果。轮询的模式下云端完全无状态，扩容缩容更简单。

第三，延迟容忍度不同。LLM Token 流式输出，每 50ms 一个 Token，多 100ms 的延迟用户就能感觉到卡顿——所以这里必须用 SSE。但是一个生图任务本身要跑 10-60 秒，轮询间隔（图像 5 秒、视频 30 秒）带来的额外延迟，用户几乎感知不到。在体验不敏感的环节省掉长连接的工程复杂度，是合理的 trade-off。

当然，如果未来业务需要云端实时推送（比如 Worker 执行过程中的进度百分比），可以在云端增加一个轻量的消息通道（比如用 Redis Pub/Sub 或 SSE），让本地服务订阅而不是轮询。架构是可以演进的，但当前业务场景下轮询已经够用了。

Q5：具体讲讲 SSE 连接上跑的是什么数据？事件类型怎么设计的？

满分逐字稿

面试标准逐字稿

SSE 连接上跑的事件大致分为四类。

第一类是LLM Token 流。Agent 调用 LLM API 时，模型的输出是逐 Token 返回的。本地服务用 DeepAgents 的 StreamAdapter 将 LangGraph 的内部事件翻译成前端协议：每个 Token 增量通过 event: block.delta 推送，前端收到后拼接到对话气泡里，用户看到的就是 AI 在"打字"的效果。对应的 Block 类型是 text，data 里是这次的文本增量。

第二类是工具调用通知。当 Agent 决定调用一个工具（比如生图、搜索素材、调整画布），会推一个 event: block.created 事件告诉前端"我正在调用 xxx 工具"，Block 类型是 tool_use。前端可以渲染一个加载态或者工具调用卡片。工具执行完成后，结果直接内嵌在同一个 tool_use block 里，通过 event: block.updated 推送——不需要单独的"工具结果"Block。

第三类是任务状态更新。这就是数据流 B 的最后一跳——本地服务轮询到云端任务状态变化后，通过 SSE 推给前端。比如"任务排队中"、"正在生成"、"生成完成，图片 URL 是..."。这类更新通过 event: block.updated 或自定义事件推送。

第四类是Agent 状态机事件。DeepAgents 的状态转移（Agent 从"思考"进入"执行"，或者进入"等待用户确认"状态）也会作为事件推送，如 event: interaction.request（HITL 人机审批）。前端据此更新 UI 状态，比如弹出确认对话框。

这些事件共用同一条 SSE 连接，通过 event: 字段区分类型。前端用 EventSource 监听，对不同 event type 注册不同的处理函数。这样前端的代码结构很清晰——它只需要关心"收到什么类型的事件就做什么"，不需要关心事件背后的数据是从 LLM 流式来的还是从云端轮询来的。

Q6：轮询任务状态的具体策略是什么？怎么处理超时和异常？

满分逐字稿

面试标准逐字稿

轮询策略需要平衡实时性和服务器压力。

基本策略是固定间隔轮询，间隔按任务类型区分——图像生成 5 秒、3D 模型 10 秒、视频生成 30 秒。为什么不用指数退避？因为用户在等结果，我们不希望间隔越来越长。保持固定间隔可以在任务完成后尽快通知用户。只有在遇到临时性错误（网络抖动、服务暂时不可用）时才会用指数退避重试。

超时处理分两层。任务级超时：不同类型的任务有不同的超时时间——生图可能 2 分钟，生视频可能 5 分钟。超过这个时间还没完成，本地服务会停止轮询，给前端推一个超时错误事件，让用户决定是否重试。请求级超时：单次 HTTP 请求如果 10 秒没返回（比如网络问题），直接跳过这次轮询，下次继续。不会因为一次网络抖动就报错。

异常状态处理：云端任务有几种终态——completed（成功）、failed（执行失败，比如供应商返回错误）、cancelled（被取消）。轮询到任何终态都停止轮询。对于 failed，本地服务会把错误信息通过 SSE 推给前端，前端展示具体的错误原因。

有一个细节是轮询的生命周期管理——当用户关闭了对话或者切换了 Agent 会话，轮询协程需要被正确取消，否则会造成资源泄漏。Python 的做法是用 asyncio.Task 管理轮询，取消会话时 cancel 掉对应的 Task。

Q7：如果让你重新设计这个架构，你会改什么？

满分逐字稿

面试标准逐字稿

如果重新设计，我会在三个方面做调整。

第一，云端结果通知改用消息推送。当前的轮询方式在任务量少的时候问题不大，但如果一个用户同时提交了多个生成任务，本地服务要同时轮询多个任务状态，对云端的请求量会随任务数线性增长。更优的方案是云端用 Redis Pub/Sub 或者轻量的消息队列，Worker 完成任务后发一个完成事件，本地服务订阅对应的 channel。这样从"轮询拉"变成"推送"，云端压力更小，结果通知也更及时。

第二，加一个本地事件总线。当前 LLM Token 流、工具调用事件、任务状态更新都是各自独立地往 SSE 连接里写，如果未来事件类型更多，管理起来会混乱。可以在本地 Python 服务里加一个内存事件总线（类似 EventEmitter），所有事件源都往总线里发事件，SSE handler 统一从总线消费，这样扩展新事件类型的时候只需要注册新的 producer，不需要改 SSE 的推送逻辑。

第三，增加全链路 Trace ID。当前从用户输入到最终结果展示，中间经过 Electron、本地 Python、云端 gateway、scheduler、Worker、外部供应商，如果某个环节出了问题，排查起来要翻多个系统的日志。如果每个请求在 Electron 端就生成一个 trace_id，一路透传到云端，排查效率会大大提高。

不过我要说明，这些是"如果重新设计"的理想方案。在当时的业务阶段和团队资源下，用最简单的轮询方案快速落地是对的——先让系统跑起来，再在遇到瓶颈时演进。

Q8：这种本地+云端的混合部署架构，在其他场景中你还见过吗？有什么共性？

满分逐字稿

面试标准逐字稿

这种"本地智能+云端算力"的混合部署是 AI 应用落地的一个常见模式。

一个典型的例子是Copilot 类产品——VS Code 的 GitHub Copilot。本地的 VS Code 插件负责代码上下文感知和 UI 交互（这类似我们的本地 Agent 服务），真正的代码生成跑在 GitHub 的云端 GPU 上（这类似我们的云端 Worker）。本地和云端之间也是 API 调用，不是全链路流式。

另一个例子是端侧 AI 推理，比如 Apple Intelligence。设备端跑小模型处理简单任务（文本润色、快捷指令），复杂任务（图片生成、深度理解）交给云端的 Private Cloud Compute。这也是把"轻量推理放本地、重量推理放云端"的思路。

这类架构的共性有三个：(1) 延迟敏感的交互在本地——打字效果、UI 响应、上下文感知，这些对延迟要求高的放在本地，localhost 没有网络延迟；(2) 算力密集的任务在云端——GPU 推理、大模型调用、数据处理，这些需要专用硬件的放在云端，用户本地的电脑通常没有高性能 GPU；(3) 两者之间用简单协议通信——通常就是 HTTP REST，不追求全链路流式，因为两端的时间尺度差异太大。

理解这个模式有助于在面试中用已有经验类比新场景。比如面试官问"你怎么设计一个 AI 辅助设计工具"，我可以直接套用这个模式：本地跑 Agent 做意图理解和交互，云端跑 AI 模型做实际生成，中间用 HTTP 通信。这不是背答案，是从真实项目中提炼出来的架构直觉。
