二、核心知识精讲

2.1 Token 与中文字符的换算

Token 是大语言模型处理文本的最小单位。模型不直接处理"字"或"词"，而是将输入文本切分成 token 序列，再将每个 token 映射为一个整数 ID 送入模型。不同模型使用不同的 tokenizer，切分方式和词表大小都不同。

核心换算关系

文本类型换算比例说明
中文1 个汉字 ≈ 1.5 - 2 个 token常用字偏低，生僻字偏高
反过来1 个 token ≈ 0.5 - 0.7 个汉字用于估算输出长度
英文1 个单词 ≈ 1 - 1.5 个 token常见单词通常 1 个 token，长单词会被拆分
代码变化大变量名、运算符、缩进都会消耗 token

为什么中文消耗更多 token

这和 tokenizer 的训练数据分布有关。以 OpenAI 的 tiktoken cl100k_base（GPT-4 使用的 tokenizer）为例，它基于 BPE（Byte Pair Encoding）算法在大规模文本上训练词表。因为训练数据中英文占比更高，英文的常见子词组合被充分合并成较长的 token，而中文每个字的 UTF-8 编码本身就是 3 个字节，加上在训练数据中出现频率相对较低，很多汉字无法被合并成更长的 token，所以平均下来每个汉字需要更多 token 来表示。

主流 Tokenizer

Tokenizer使用模型算法词表大小
tiktoken (cl100k_base)GPT-4, GPT-3.5BPE~100K
tiktoken (o200k_base)GPT-4oBPE~200K
SentencePieceLLaMA, GemmaBPE / Unigram32K - 128K
Anthropic tokenizerClaudeBPE~100K

面试中如果被问到，先说换算比例，再解释"为什么"（BPE 训练数据分布），最后补一句"实际使用中可以用 tiktoken 库精确计算"。三层递进，从记忆到理解到实践。

2.2 K8s HPA vs VPA 与 DM 的自定义扩缩容

Kubernetes 提供两种原生的自动扩缩容机制，分别解决不同维度的资源弹性问题。

HPA（Horizontal Pod Autoscaler）— 水平扩缩

做什么：根据指标（CPU 利用率、内存使用率、自定义 metrics）自动调整 Pod 副本数。比如 CPU 利用率超过 70% 就加 Pod，低于 30% 就减 Pod。

适用场景：无状态服务（Web 服务器、API 网关），流量增大时多起几个 Pod 分担压力。

VPA（Vertical Pod Autoscaler）— 垂直扩缩

做什么：自动调整单个 Pod 的 resources.requests 和 resources.limits（CPU、内存的申请值和上限值），让每个 Pod 获得更合适的资源配额。

适用场景：有状态服务或不适合水平扩展的场景（数据库、单实例任务处理器），通过给单个 Pod 更多资源来提升处理能力。

局限：调整 resource 通常需要重启 Pod（K8s 1.27+ 才支持 In-Place Resource Resize），对延迟敏感的服务有影响。

DM 为什么不直接用 HPA

DreamMaker 的 GPU Worker 执行的是 AI 推理/生成任务（文生图、图生视频等），这类任务的特点是：

  • CPU/内存指标与负载不相关：GPU Worker 的瓶颈在 GPU 显存和算力，CPU 利用率可能始终很低，用 CPU 指标触发 HPA 完全没有意义。
  • 任务通过队列分发：负载的真实信号是队列深度（等待执行的任务数），而不是 Pod 本身的资源利用率。
  • GPU 实例启动成本高：GPU 节点价格贵、启动慢，需要更精细的扩缩策略（不能像 CPU Pod 那样随意增减）。

因此 DM 采用自定义 Autoscaler：监控任务队列深度，当排队任务超过阈值时扩容 GPU Worker Pod，空闲时缩容。CPU 类 Worker（如调供应商 API 的任务）则仍然使用标准 HPA。

Worker 类型扩缩策略监控指标原因
CPU Worker标准 HPACPU/内存利用率负载与 CPU 正相关
GPU Worker自定义 Autoscaler任务队列深度GPU 负载与 CPU 指标无关

2.3 Sidecar 模式 — 标准定义 vs DM 中的命名

这是一个容易混淆的点，因为 DM 内部的 worker-sidecar 组件名字里带了"sidecar"，但它并不是 K8s 意义上的 Sidecar 容器。面试时必须先把标准定义讲清楚，再解释 DM 的命名。

K8s 标准 Sidecar 模式

在 Kubernetes 中，Sidecar 指的是在同一个 Pod 内与主容器（main container）并行运行的辅助容器，它们共享网络命名空间（localhost 互通）和存储卷。Sidecar 不承担核心业务逻辑，而是提供横切关注点（cross-cutting concerns）的能力。

典型用途：

  • 日志收集：Filebeat/Fluentd sidecar 读取主容器写到共享 volume 的日志文件，转发到 ELK。
  • 服务网格代理：Istio 的 Envoy sidecar 拦截主容器的所有出入流量，实现 mTLS、限流、熔断。
  • 配置热加载：一个 sidecar 轮询配置中心，把最新配置写入共享 volume，主容器 watch 文件变化自动 reload。

DM 中的 worker-sidecar

DM 的 worker-sidecar 名字虽然带"sidecar"，但它的角色是任务执行框架本身——它是一个独立的 Go 服务，负责：

  1. 从 worker-scheduler 接收任务分配
  2. 调用外部 AI 供应商（通过 Gateway 或直连）执行生成任务
  3. 管理重试逻辑和 fallback 链路
  4. 向 worker-scheduler 上报任务状态和结果

它是 Worker Pod 中的主容器，不是辅助容器。之所以叫"sidecar"，可能是早期命名时相对于实际执行 AI 推理的 GPU 进程来说，Go 服务是一个"伴侧"角色——但从 K8s 架构的角度看，这个命名是不严谨的。

面试策略：被问到"Sidecar 模式"时，先讲 K8s 标准定义（辅助容器、共享 Pod、横切关注点），举 1-2 个经典例子（Envoy、日志收集），然后主动说明 DM 中 worker-sidecar 的命名与标准定义的区别，展示你不是死记概念而是真正理解了。

2.4 重试机制的代码级实现

面试官问"重试怎么实现的"时，不能只停在"指数退避重试"这个概念上。要能说出：在哪个层、什么代码结构、怎么判断可重试、退避参数是什么、重试耗尽后怎么办。

重试逻辑的位置

重试逻辑在 worker-sidecar 层，具体是 api/external/aigw/openai.go 中的 executeWithRetry() 函数。

代码结构

// 伪代码，展示核心逻辑
func executeWithRetry(ctx context.Context, req Request) (Response, error) {
    maxRetries := 3
    baseDelay := 1 * time.Second

    for attempt := 0; attempt < maxRetries; attempt++ {
        resp, err := callProvider(ctx, req)

        if err == nil {
            return resp, nil  // 成功，直接返回
        }

        if !isRetryable(err) {
            return nil, err   // 不可重试错误，立即失败
        }

        if attempt < maxRetries - 1 {
            // 指数退避：1s → 2s → 4s
            delay := baseDelay * time.Duration(1<<uint(attempt))
            time.Sleep(delay)
        }
    }
    return nil, fmt.Errorf("retries exhausted after %d attempts", maxRetries)
}

关键细节

  • 同步 for 循环：重试在同一个 goroutine 内完成，不会重新入队、不会换 Worker。
  • 可重试错误判断：网络超时、连接拒绝、TCP 读写错误——这些是暂时性故障，等一下可能恢复。注意 HTTP 429 限流不是在 executeWithRetry 中处理的，而是由单独的 queue-retry 机制用更长的退避策略（3s→60s，最长可达 12 小时）来处理。
  • 不可重试错误：HTTP 400（参数错误）、401（认证失败）、403（权限不足）、404（接口不存在）——这些是确定性错误，重试无意义。
  • 指数退避：1s → 2s → 4s，避免在供应商限流时持续打满请求。

重试耗尽后的 Fallback

当内部重试全部失败后，不是直接返回错误，而是进入 fallback chain（在 worker-sidecar/pkg/fallback/executor.go）：

flowchart LR
    A["请求到达"] --> B["主供应商
3次指数退避重试"]
    B -->|全部失败 且 可重试| C["Fallback 供应商 1
3次指数退避重试"]
    B -->|成功| Z["返回结果"]
    B -->|不可重试错误| X["立即失败"]
    C -->|全部失败| D["Fallback 供应商 2
..."]
    C -->|成功| Z
    D -->|链路耗尽| X
    D -->|成功| Z

Fallback 也是同步的，在同一个请求上下文中完成，不重新入队。每个 fallback 供应商各自有独立的重试逻辑。整个 retry + fallback 链路对调用方透明——调用方只知道"成功了"或"最终失败了"，不知道中间切了几个供应商。

2.5 产品思维：从用户视角出发

面试官问"游戏 Agent"时特意强调"从玩家角度"，这不是在考 AI 技术实现，而是在考产品思维——你能不能站在用户的位置想问题。这个能力在游戏公司面试中尤其重要，因为游戏行业的核心是"玩家体验"。

"从用户角度"答题的通用框架

  1. 锁定用户是谁：玩家、开发者、运营、美术师？不同角色的痛点完全不同。
  2. 列举痛点场景：这个用户在使用过程中最难受的 3-5 个场景是什么？
  3. 每个痛点对应一个 Agent 方案：Agent 不是技术 demo，是解决特定痛点的产品功能。
  4. 说清楚体验提升：用了 Agent 之后，用户的操作流程哪里变短了、哪里变爽了。

三、面试易错点

易错点 1：Token 换算只记数字不懂原理
面试官问"1 个中文字对应多少 token"时，只说"大约 2 个"是及格线。加分项是解释为什么（BPE 算法 + 训练数据英文为主 + UTF-8 编码），以及不同 tokenizer 的换算比例略有不同。如果能补一句"实际开发中我会用 tiktoken 库精确计算来做 prompt 的 token 预算管理"，就从背知识变成了有实践经验。
易错点 2：HPA 和 VPA 搞混方向
Horizontal = 横向 = 加减 Pod 数量；Vertical = 纵向 = 加减单 Pod 资源。最容易犯的错是把"VPA"说成"给集群加节点"——那不是 VPA，那是 Cluster Autoscaler（CA），是第三种扩缩容机制。记忆口诀：H = 数量变，V = 配额变，C = 节点变。
易错点 3：把 DM 的 worker-sidecar 当成 K8s Sidecar 容器讲
这两个完全不是一回事。K8s Sidecar 是辅助容器（如 Envoy 代理），DM 的 worker-sidecar 是主执行框架。面试时如果把它俩混为一谈，面试官会认为你对 K8s 架构模式的理解有问题。正确做法：先讲标准 Sidecar，再主动说明 DM 的命名差异。
易错点 4：重试只说概念不说代码
"我们用了指数退避重试"是概念层面的正确回答，但面试官追问"具体怎么实现的"时，你需要说出：同步 for 循环、可重试错误判断逻辑（网络超时/连接拒绝/网关错误 vs 400/401/404）、退避参数（1s/2s/4s）、重试耗尽后进入 fallback chain。HTTP 429 由单独的 queue-retry 机制处理，不在 executeWithRetry 里。如果能说出代码在 executeWithRetry() 函数里，用的是 time.Sleep + 倍增计算延迟，说明你真的读过代码。
易错点 5：审题失误——面试官说了两次"从玩家角度"你还在说开发者视角
这不是知识问题，是沟通问题。面试官给提示（"地图太大，要一边开 wiki"）时，你应该顺着这个场景展开，而不是继续按自己准备的答案讲。修正方法：回答前先复述面试官的限定条件（"好的，从玩家的角度来看..."），强制自己进入正确的思路。

四、满分逐字稿

Q1：Token 和中文字符是什么关系？1 个中文字大约对应多少 token？

满分逐字稿

面试标准逐字稿

在大语言模型里，Token 是模型处理文本的最小单位，模型不直接看"字"或"词"，而是先用 Tokenizer 把输入文本切分成 token 序列。

对于中文来说，1 个汉字大约对应 1.5 到 2 个 token，反过来说 1 个 token 大约能表示 0.5 到 0.7 个汉字。英文要好一些，常见英文单词通常 1 个单词就是 1 个 token，长一点的可能 1.5 个。

为什么中文需要更多 token 呢？这跟 Tokenizer 的训练方式有关。以 GPT-4 使用的 tiktoken cl100k_base 为例，它是基于 BPE（Byte Pair Encoding）算法在大规模语料上训练出来的词表。因为训练语料中英文占比远高于中文，英文的常见子词组合会被充分合并成较长的 token，而中文每个字的 UTF-8 编码本身就是 3 个字节，出现频率相对低，没办法被很好地合并，所以平均每个汉字需要更多 token。

不同模型的 Tokenizer 不太一样：OpenAI 系列用 tiktoken，LLaMA 系列用 SentencePiece，但换算比例大致在这个范围内。如果做了中文优化、扩充了中文词表（像 ChatGLM 那样），比例会好一些。在实际开发中如果需要精确计算，可以直接调 tiktoken 库来数，做 prompt 的 token 预算管理时经常要用到。

Q2：K8s 的 HPA 和 VPA 有什么区别？

满分逐字稿

面试标准逐字稿

HPA 是 Horizontal Pod Autoscaler，水平扩缩容，调的是 Pod 的副本数量。比如设一个规则：当 Deployment 里所有 Pod 的平均 CPU 利用率超过 70% 时，就自动增加 Pod 副本数；低于 30% 时缩减。它适合无状态服务，比如 Web API 服务器，流量大的时候多起几个 Pod 分担请求。

VPA 是 Vertical Pod Autoscaler，垂直扩缩容，调的是单个 Pod 的 resource requests 和 limits。比如一个 Pod 原来申请了 256Mi 内存，VPA 发现它实际经常用到 512Mi，就自动把 requests 调高。它适合不方便水平扩展的服务，比如有状态的数据库实例。但 VPA 的局限是调整 resource 通常需要重启 Pod，虽然 K8s 1.27 以后开始支持 In-Place Resource Resize，但还不算完全成熟。

简单记就是：H 是调数量，V 是调配额。另外还有一个 Cluster Autoscaler（CA）是调节点数量的，三者解决的维度不同。

在我实习的 DreamMaker 项目中，CPU 类型的 Worker 用的是标准 HPA，但 GPU Worker 没法用 HPA——因为 GPU 推理任务的瓶颈在 GPU 显存和算力，CPU 利用率可能一直很低，拿 CPU 指标来触发扩缩完全不准。所以我们用了自定义的 Autoscaler，监控的是 Redis 任务队列的深度：排队的任务数超过阈值就扩容 GPU Worker Pod，空闲就缩容。这算是一个根据业务特点选择扩缩策略的例子。

Q3：什么是 Sidecar 模式？你们项目里的 worker-sidecar 是 Sidecar 吗？

满分逐字稿

面试标准逐字稿

Sidecar 模式在 Kubernetes 里指的是在同一个 Pod 内，跟主容器并行运行的辅助容器。它们共享网络命名空间——可以通过 localhost 互通，也共享存储卷。Sidecar 不承担核心业务逻辑，而是提供一些横切关注点的能力。

最典型的例子是 Istio 的 Envoy Sidecar：每个业务 Pod 里都注入一个 Envoy 代理容器，拦截所有进出流量，实现 mTLS 加密、限流、熔断、链路追踪，业务代码完全不用改。另一个常见用途是日志收集——跑一个 Filebeat sidecar，读取主容器写到共享 volume 里的日志文件，转发到 ELK 集群。

Sidecar 模式的核心优势是关注点分离：主容器只关心业务逻辑，通用能力（日志、监控、安全、流量管理）由 sidecar 负责，而且 sidecar 可以独立升级，不影响业务容器。

然后说到我们项目中的 worker-sidecar——说实话，它在 K8s 的定义下并不是一个 Sidecar 容器。它其实是 Worker Pod 中的主容器，是一个 Go 编写的任务执行框架：从 worker-scheduler 接收任务、调用外部 AI 供应商执行生成、管理重试和 fallback 链路、上报状态和结果。它承担的是核心业务逻辑，不是辅助功能。

之所以叫"sidecar"这个名字，我的理解是早期命名的时候，相对于实际执行 AI 推理的 GPU 进程来说，这个 Go 服务被看作是一个"伴侧"的管理角色——但从 K8s 架构模式的角度看，这个命名确实是不严谨的。面试里如果被问到，我觉得主动指出这个差异反而加分，说明不是在死记概念。

Q4：你说的重试机制，代码层面具体怎么实现的？

面试标准逐字稿

重试逻辑写在 worker-sidecar 层，具体是 api/external/aigw/openai.go 里的 executeWithRetry() 函数。

代码结构是一个同步的 for 循环。进入函数后，最多循环 3 次，每次调用供应商接口：如果成功就直接返回结果；如果失败，先判断错误是否可重试——网络超时、连接拒绝、TCP 读写错误、网关错误（502+），这些是暂时性故障，归类为可重试错误；而 400 参数错误、401 认证失败、403 权限不足、404 接口不存在，这些是确定性错误，重试一百次参数还是错的，所以立即返回失败。值得注意的是，HTTP 429 限流不是在这个函数里处理的——它有单独的 queue-retry 机制，用更长的退避策略（初始 3 秒，最大 60 秒，可等待数小时）来应对限流场景。

如果是可重试错误且还有重试次数，就 time.Sleep 一段时间再重试。延迟用指数退避：第一次等 1 秒，第二次等 2 秒，第三次等 4 秒，用位移运算 1 << attempt 来计算。这样做是为了在供应商限流的时候不要持续打满请求，给它喘息恢复的时间。

整个过程是同步的，在同一个 goroutine 内完成，不会把任务重新放回队列、不会换一个 Worker 来执行。这一点很重要——重试是 Worker 内部的事情，对 worker-scheduler 来说任务状态还是"执行中"，scheduler 不感知重试过程。

如果 3 次重试全部耗尽，不是直接返回错误，而是进入 fallback chain。这个逻辑在 worker-sidecar/pkg/fallback/executor.go 里。系统会读取这个模型在 MongoDB 中配置的 fallback 规则，如果有备用供应商，就切到下一个供应商，备用供应商也有自己独立的 3 次重试。如果备用也失败，继续往下切，直到 fallback 链路耗尽才最终返回失败。

整个 retry + fallback 链路也是同步的、在同一个请求上下文中完成的，对上层调用方透明——调用方只看到最终的成功或失败，不知道中间切了几个供应商。这个设计是无状态的：没有维护熔断器、不记录"哪个供应商当前不可用"，每个新请求都从主供应商开始。代价是在主供应商持续故障期间每个请求都要先打一次主供应商等超时，但对于 AI 生成任务（本身就要 10-30 秒）来说，多等几秒重试的感知并不强。

我有两段 AI 相关的实习，一段在科大讯飞，一段在网易互娱，技术栈和工作内容差异挺大的，但形成了一个比较清晰的能力成长弧线。

网易这段是真正进入分布式系统和工程化。DreamMaker 是一个服务网易内部几百个美术师的 AI 平台，技术栈是 Python 写 Agent 客户端 + Go 写后端的分布式调度系统。我从一个只会写 Python 脚本的状态，开始接触 Go 语言、微服务架构、任务调度、K8s 部署、多供应商容错降级这些真正的后端工程问题。

Q6：如果让你给一款开放世界游戏设计 AI Agent，从玩家角度你会怎么做？

满分逐字稿

面试标准逐字稿

好的，我从玩家的角度来想这个问题。我自己玩开放世界和 Roguelike 类型的游戏比较多，像空洞骑士和杀戮尖塔，所以我就从这两个游戏的实际痛点出发来说。

第一个痛点是"迷路 + 不知道去哪"。空洞骑士的地图非常大，而且很多区域需要解锁特定能力才能进入，玩家经常会出现"我知道我要去某个地方，但不记得怎么走了"或者"我刚拿到二段跳，之前哪些路被挡住了来着"的情况。现在玩家的做法是退出游戏去查 Wiki 地图或者看攻略视频。针对这个痛点，可以做一个地图导航 Agent：它记录玩家的探索足迹和已获能力，当玩家长时间在同一区域转圈时主动提示"你之前在遗忘十字路的东边有一条路需要二段跳，现在可以去了"。关键是不剧透——不告诉你那边有什么，只告诉你那条路现在能走了。

第二个痛点是"打 Boss 卡关"。空洞骑士的 Boss 战很难，很多玩家会卡在某个 Boss 上几个小时。现在的做法要么是硬磕，要么退出去看攻略视频学招式。可以做一个战斗策略 Copilot：分析玩家最近几次死亡的模式（比如总是被某个招式打中），给出针对性建议——"这个 Boss 的第三段攻击有一个向下劈砍，你可以往左闪而不是往右跳"。或者根据玩家当前装备的护符组合，建议更适合这个 Boss 的搭配。

第三个痛点是"信息过载"。杀戮尖塔是一个卡牌 Roguelike，每一层选牌、选遗物、选路线都需要决策，高级玩家能记住几百张牌的 Synergy，但新手完全记不住。现在新手的做法是一边打一边开 Wiki 查"这张牌到底好不好"。可以做一个构筑顾问 Agent：基于你当前牌组的构筑方向（比如你已经拿了很多力量牌），在选牌时提示"这张牌跟你的力量流有 Synergy"或者"你缺 AOE，这张可以补"。它不替你做决定，但帮你快速过滤信息。

第四个痛点是"查资料要退出游戏"。这是很多游戏玩家的共同痛点——遇到不懂的机制就要 Alt+Tab 出去搜索。可以做一个游戏内 Wiki RAG Agent：把游戏 Wiki 的内容做成向量检索，玩家在游戏内直接输入问题，Agent 返回相关的知识片段。比如在空洞骑士里问"白色宫殿怎么进"，直接返回解锁条件和位置，不用切出去查。

总结一下，这四个 Agent 的共同设计原则是：减少玩家被迫中断游戏体验的次数。不管是查地图、看攻略还是翻 Wiki，每一次退出游戏都是一次"心流中断"。好的游戏 Agent 应该让这些信息在需要的时候自然出现在游戏内，而不是替玩家做决定。

Q7：你说到 Agent 框架中的 Harness，它解决了什么问题？为什么不能自己写？

满分逐字稿

面试标准逐字稿

Harness 框架主要解决三个自己从头写会非常痛苦的问题。

第一个是动态上下文演进。Agent 不是发一条 prompt 拿一个回答就结束了，它是一个持续运行的过程——用户说一句话、Agent 调一个工具、工具返回结果、再根据结果决定下一步。在这个过程中，上下文是不断增长和变化的。简单的做法是把所有历史消息全塞进 prompt，但这样 token 会爆。Harness 提供了上下文管理的基础设施：哪些信息该保留、哪些可以压缩、什么时候做 summarization、工具调用的结果怎么结构化地注入回上下文。这些不是一次性逻辑，是每一轮对话都要做的，没有框架支撑的话每个 Agent 都要自己重复实现一遍。

第二个是有状态的长时间运行任务。比如 DreamMaker 里用户发起一个图生视频的任务，从提交到完成可能要几分钟甚至更长。这期间 Agent 需要维护一个状态机：任务提交 → 等待调度 → 执行中 → 结果回传 → 后处理。Harness 提供了状态机的抽象和 artifact 管理——中间产物（比如生成的初稿、进度信息）可以被存储和引用，任务如果中断了也能基于状态恢复而不是从头来。如果自己写，光是状态持久化和恢复就是一个不小的工程量。

第三个是工具执行的边界控制。Agent 需要调用外部工具（API 调用、文件操作、代码执行等），但不能让它无限制地调——需要权限控制（哪些工具可以调、哪些参数范围内可以自主决定）和沙箱隔离（代码执行不能影响宿主环境）。Harness 提供了这些执行边界的声明式配置和运行时守卫，不用在业务代码里到处写权限检查。

那为什么不能完全自己写呢？其实不是"不能"，而是框架提供了可复用的基础原语——状态机、核心循环（observe → think → act）、工具注册和调度、上下文窗口管理——这些是所有 Agent 都需要的公共基础设施。自己写的话，每做一个新 Agent 都要重复实现这些。但反过来说，框架解决的是通用问题，业务特定的上下文管理策略还是需要自己实现。比如 DreamMaker 的 Agent 需要根据当前画布状态、用户历史偏好、已有生成结果来动态构建 prompt，这些跟具体业务深度耦合的逻辑是框架管不了的，需要在框架的扩展点上自己写。

所以总结就是：框架管通用、业务管特定。Harness 让你不用重复造状态机和执行引擎的轮子，你把精力花在"对于我的业务场景，上下文应该怎么管理、工具应该怎么编排"上。

Q8：你怎么培养自己从用户角度思考问题的能力？

满分逐字稿

面试标准逐字稿

说实话，这次面试被问到游戏 Agent 的时候，我第一反应确实是从开发者角度去想——NPC 智能化、用户留存分析之类的。被面试官纠正之后我意识到，做 AI 工程的人特别容易掉进"技术方案先行"的思维惯性：先想"我能用什么技术"，而不是"用户遇到了什么问题"。

回顾我在网易的实习经历，DreamMaker 的用户是公司内部的美术师，其实有很多直接接触用户反馈的机会。比如美术师抱怨"生成太慢了"——这个反馈背后的真实痛点不一定是"推理速度慢"，也可能是"我提交了之后不知道要等多久、没有进度反馈、不敢离开页面"。同一个"太慢了"，如果从技术角度理解就是"优化推理性能"，从用户角度理解可能是"加一个进度条和预估时间"。后者的实现成本低得多，但用户体验提升可能更大。

我觉得培养这种能力有三个具体方法。第一是回答任何问题之前先确认"谁是用户"——是玩家、开发者、运营还是美术师？不同角色的痛点完全不同，搞错角色整个回答方向就偏了。第二是用"痛点场景 → 方案"的顺序思考，而不是"技术 → 找应用场景"——前者是产品思维，后者是技术 demo 思维。第三是多当自己产品的用户——我在网易实习的时候会自己去试 DreamMaker 的各种功能，以美术师的身份走一遍完整流程，很多"用着不爽"的地方用开发者视角是发现不了的。

这个教训对我来说挺重要的：技术能力决定你能做什么，但产品思维决定你该做什么。面试里也是一样——面试官的问题限定了角度，先审题、再答题，比答案本身的技术深度更重要。
