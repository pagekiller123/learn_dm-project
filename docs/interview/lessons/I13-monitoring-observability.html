I13 — 监控与可观测性 — 工程稳定性、业务埋点与用户满意度

定位 监控体系梳理 + 面试高频题准备 覆盖题数 2 题 难度 ★★★☆☆ 时长 ~60 分钟

一、课程概述

这节课回答两个面试高频问题：你处理过线上问题吗？和有没有办法主动监控业务层面的用户满意度？

回答这类问题的关键不是堆技术名词，而是展示你的思维框架：先理解监控要解决什么问题，再说 DM 实际做了什么，最后指出哪些还没做、为什么没做、如果做会怎么做。特别是第二个问题，很容易答成"应该加个点赞按钮"——这不够，面试官想听的是你对监控维度的系统性理解。

Mentor 视角

监控的两个维度与业务优先级

监控其实是两种维度：工程上看稳定性，监控维度；产品上看业务数据报表，包括转换和漏斗，想要什么数据会去做埋点上报。这两种都算蛮常规的思路，最主要是看业务上关心的数据重点和稳定性的重点在哪里。

如果再往更深一步看，不同业务的侧重点不同。传统 toC 业务，稳定性反而是最基本的东西，由此延伸出稳定性治理、熔断降级、混沌演练等等。而业务上最重要的是数据，一般都会有专门的 BI 团队做数据报表，因为数据结果就是产品的 KPI，所有功能都是服务于这个报表的结果。

而我们这个业务，坦白说，这两样都不是重点——因为这两个都不是汇报的重心，我们要汇报的是降本。

面试问题考察维度回答要点
你处理过线上问题吗？资源负载较大的情况？工程稳定性认知 + 实操经验DM 的多层监控体系、GPU 自动伸缩、限流策略
有没有办法主动监控用户对任务满意度？产品思维 + 监控维度理解两种维度的区分 + 现有缺失 + 改进思路 + 业务优先级判断

二、行业黑话科普：线上指标与业务数据

在进入 DM 的具体实现之前，先把面试和工作中会反复出现的术语过一遍。分两大块：工程侧的线上指标和产品侧的业务数据概念。

2.1 工程侧：线上指标

流量指标

术语全称含义类比
QPSQueries Per Second每秒查询数。衡量系统当前承受的请求压力高速公路每秒通过的车辆数
TPSTransactions Per Second每秒事务数。侧重于完整的业务事务（一个事务可能包含多个请求）收银台每秒完成的结账数
RPSRequests Per Second每秒请求数。和 QPS 基本同义，只是叫法不同—
RPMRequests Per Minute每分钟请求数。限流场景常用，DM Gateway 的限流就是按 RPM 算的—
吞吐量Throughput单位时间内系统实际处理完成的请求量。QPS 是"进来多少"，吞吐量是"做完多少"工厂每小时的产出量
并发数Concurrency同一时刻正在处理中的请求数。DM Gateway 用 Redis Lua 做并发槽位控制餐厅里同时被服务的桌数

延迟指标

术语含义为什么重要
P5050% 的请求在这个时间内完成（中位数）代表"大多数用户的体验"
P9595% 的请求在这个时间内完成代表"绝大多数用户的体验"，是最常用的 SLO 指标
P9999% 的请求在这个时间内完成代表"最慢的那 1% 用户的体验"，能暴露尾部延迟问题
平均延迟所有请求延迟的算术平均⚠️ 面试陷阱：平均值会被极端值拉高，掩盖真实分布。面试里提延迟建议说 P95/P99，别说"平均"
为什么用百分位数而不是平均值？ 假设 100 个请求中有 99 个 10ms 完成、1 个 5000ms 完成。平均延迟 = 59.9ms，看起来还行；P99 = 5000ms，直接暴露问题。百分位数能告诉你"最差的 N% 用户是什么体验"，这才是用户真正感知到的。

可用性与 SLA 体系

术语全称含义举例
SLAService Level Agreement服务等级协议。写在合同里的，违反要赔钱"保证 99.9% 可用性，否则赔偿月费的 10%"
SLOService Level Objective服务等级目标。团队内部设定的目标，比 SLA 更严格"我们目标 P99 延迟 < 500ms"
SLIService Level Indicator服务等级指标。实际测量值，用来判断 SLO 有没有达标"过去 30 天 P99 延迟实际是 420ms"
可用性Availability系统正常服务的时间占比。常说的"几个 9"99.9% = 每年宕机 8.76 小时

"几个 9"的直观含义：

可用性叫法每年允许宕机时间每月允许宕机时间
99%两个 93.65 天7.3 小时
99.9%三个 98.76 小时43.8 分钟
99.99%四个 952.6 分钟4.38 分钟
99.999%五个 95.26 分钟26.3 秒

Prometheus 指标类型

DM 的 Prometheus 指标用到了三种基本类型，面试里经常被问"你用了什么类型的 metric"：

类型行为适用场景DM 中的例子
Counter只增不减的累加器请求总数、错误总数、已完成任务数dreammaker_apiserver_requests_total
Gauge可增可减的瞬时值当前队列长度、在途请求数、GPU 节点数dreammaker_scheduler_task_queue_length
Histogram把数据分到预定义的桶（bucket）里，统计每个桶的计数延迟分布、任务耗时分布dreammaker_apiserver_http_request_duration_seconds
Histogram 怎么算 P99？ Histogram 不记录每个请求的精确延迟，而是记录"落在 0~5ms 桶里的有 100 个、5~10ms 的有 200 个、10~50ms 的有 50 个……"。Prometheus 的 histogram_quantile(0.99, ...) 函数根据这些桶做插值估算出 P99。桶的边界（bucket）越细，估算越准。DM 的 HTTP 请求延迟设了从 5ms 到 100000ms 的多个桶。

可观测性三大支柱

面试常见问题："可观测性（Observability）包含哪些？" 标准答案是三大支柱：

支柱解决什么问题典型工具DM 的实现
Metrics（指标）"发生了多少？" 数字化的聚合数据，用于告警和趋势分析Prometheus, VictoriaMetrics, Grafana三层 Prometheus 指标 + VictoriaMetrics
Logs（日志）"发生了什么？" 离散的事件记录，用于排查具体问题ELK, Loki, LoghubZap JSON 日志 + Loghub 远程上报
Traces（链路追踪）"在哪条路径上发生的？" 一个请求经过多个服务的完整链路Jaeger, Zipkin, OpenTelemetryJaeger + OpenTelemetry + ntes-trace-id 串联

三者的关系：Metrics 告诉你"有问题了"，Logs 告诉你"具体是什么问题"，Traces 告诉你"问题出在哪个环节"。排障时通常先看 Metrics 发现异常 → 用 Traces 定位到哪个服务 → 用 Logs 查具体错误。

核心概念

术语含义举例
埋点
Event Tracking		在代码里预埋数据采集点，当用户触发某个行为时，上报一条事件数据到数据平台用户点击"生成"按钮 → 上报 {event: "generate_click", model: "flux", user: "xxx"}

漏斗分析详解

漏斗是产品数据分析中最核心的工具，面试里说"业务数据"基本绑定漏斗。以 DM 为例，一个理想的生成任务漏斗是：

漏斗的价值在于定位流失发生在哪一步：

  • "打开页面 → 输入参数"转化率低 → 可能是界面不直观，用户不知道怎么用
  • "点击生成 → 生成成功"转化率低 → 可能是任务失败率高，工程问题
  • "生成成功 → 保存结果"转化率低 → 可能是生成质量不满足预期，这就是用户满意度问题
  • "保存结果 → 二次使用"转化率低 → 可能是用户觉得平台没有持续价值
为什么漏斗和监控有关？ 工程稳定性监控只能告诉你"生成成功率 80%"，但不能告诉你剩下 20% 的成功生成里有多少用户满意。漏斗把工程指标和业务指标串起来了——你不仅知道"系统成功率"，还知道"用户认可率"。这就是前面说的两个维度的区别。

埋点的几种类型

类型做法优点缺点
代码埋点开发者在代码里手动调用 SDK 上报事件精确控制，可以带业务参数开发成本高，容易漏埋
无埋点 / 全埋点SDK 自动采集所有用户交互（点击、滑动、页面停留等）不漏数据，不需要开发介入数据量大、噪音多、缺业务语义
可视化埋点产品/运营在可视化界面上圈选元素，配置要采集的事件不需要改代码只能采集前端交互，不能带复杂参数

DM 目前用的全是代码埋点——Scheduler 的 EventTracking() 和 Agent 的 track_* 函数都是开发者在代码里手动调用的。

A/B 测试

把用户随机分成两组，一组看版本 A（对照组），一组看版本 B（实验组），比较两组在指标上的差异，判断改动是否有效。

举例：想知道在生成结果旁加 👍/👎 按钮会不会提高用户二次使用率 → A 组不加、B 组加 → 跑两周 → 比较二次使用率。如果 B 组显著更高，说明反馈功能有正面效果。

DM 目前没有 A/B 测试框架。

3.1 工程稳定性监控

Prometheus 指标体系（三层）

Scheduler 仓库的 app/metrics/ 目录下定义了三层 Prometheus 指标：

层级关键指标代码位置
API 层HTTP 请求时长直方图（5ms~100s）、请求总数（按状态码/方法/路径）、在途请求数app/metrics/metrics.go
调度层任务排队时间、计算时间、端到端时间、队列长度、GPU 节点状态/数量、模型重载次数app/metrics/scheduler.go
App 层预处理耗时、排队耗时、计算耗时、任务完成数（按成功/失败）、ComfyUI 节点生命周期、大图压缩app/metrics/app.go

P50/P95/P99 延迟：代码里不做显式计算，通过 Histogram bucket 暴露到 VictoriaMetrics，用 histogram_quantile() 在 Grafana 里查。

GPU 资源监控与自动伸缩

GPU 节点状态通过两个 Gauge 指标暴露（app/metrics/scheduler.go）：

dreammaker_scheduler_gpu_backend_node_status  // 按环境/集群/GPU 型号/机器标识打标签
dreammaker_scheduler_gpu_backend_node_count    // 同维度

自动伸缩器（app/worker-scheduler/service/service_autoscaler.go）的工作方式：

  • 每 30 秒检查一次：队列深度 vs Worker 数量
  • 扩容：唤醒已终止的 Pod（不是新建，因为 GPU 节点启动成本高）
  • 缩容：空闲超过可配置的超时时间后释放
  • 有冷却机制、最小/最大 Worker 数约束、Redis 分布式锁防多实例竞争
为什么不用 K8s HPA？ GPU Worker 的 GPU 打满但 CPU 空闲，HPA 看 CPU 利用率会完全误判。所以 DM 对 GPU Worker 用自研的基于队列深度的伸缩器，CPU Worker（调供应商 API）才用标准 HPA。这是 I06 课的重点内容。

限流（QPS 控制）

仓库机制实现方式容错策略
Scheduler滑动窗口限流中间件util/middleware/limiter.go，设 X-RateLimit-* 响应头Redis 挂了放行（fail-open）

所有限流都是 fail-open 策略：Redis 挂了放行请求，保业务连续性。没有熔断器。

健康检查

  • 8 个微服务都暴露了 /ping → "pong" 存活检查端点
  • 心跳接口 /api/v1/user/heartbeat（高频调用，日志里特意排除）
  • Worker Ready() 接口：Sidecar Worker 实现就绪检查
  • K8s 探针：namespace 配置里开启了 katib metrics collector 注入

告警

已实现：积分额度告警（app/app-gateway/service/service_credit_alert.go）

  • 每 30 分钟扫一次用户组积分余额
  • 触达阈值（默认 10000、5000）时通过 POPO 发 P2P 通知给组管理员
  • 去重（跨越更严重级别才通知）、静默窗口（默认 10 分钟防刷屏）、Redis 分布式锁

已设计未完全落地：Gateway 的 PromQL 告警规则（在 observability-metrics-design.md 里规划了错误率 >5%、供应商 5xx、RPM 拒绝率、任务失败率 >20% 等规则，Phase 1 事件管道已实现，告警规则本身还在推进中）

3.2 业务埋点体系

三个仓库用了三种不同的上报方式，但目的相似——记录业务事件的发生和状态：

Scheduler — 两层日志埋点

第一层：业务操作埋点（util/log.go）

  • 关键字 dm_operation_metrics，结构化 JSON 写 stdout，外部日志管线采集
  • 字段：event 名、module、user、group_id、扩展属性
  • 30+ 个打点位置，覆盖：任务创建、蓝图运行/下载、App 运行成功/失败、模型/LoRA/ControlNet 使用、训练事件等

第二层：后端用量埋点 v2（util/event_tracking.go）

  • 关键字 backend_usage_event_tracking_v2
  • 16 种事件类型：app_run、sd_run、3d_run、flux_run、video_run、image_run、blueprint_run、training_task 等
  • 状态：in_progress / success / failed
  • 来源模块通过 X-Tracking-Source-Module HTTP 头传播

Gateway — Kafka 事件管道

Gateway 的监控事件（app/dm-gateway/internal/monitor/event.go）不是日志，而是通过 Kafka 推给独立的 Monitor 服务：

事件类型含义
http_request每个 HTTP 请求
rate_limit_check限流决策
provider_request上游供应商调用
task_created / task_transition / task_terminal任务生命周期
billing_precharged / billing_charged / billing_error计费事件

数据流：Gateway → Kafka（4096 事件缓冲）→ Scheduler 的 Monitor 服务消费 → 转成 11 个 Prometheus 指标。

Monet Agent — HTTP 上报到织女数据服务

  • 4 种事件：monet-agent-run、monet-node-run、monet-tool-run、monet-postprocessor-run
  • 异步队列（最大 1000 条）→ 后台批量（每 0.1s 最多 20 条）→ HTTP POST 到 data-service.vega.nie.netease.com
  • 结果只有 success / failed / canceled，无质量维度

独立 Monitor 服务

Scheduler 仓库里有一个专门的监控微服务（app/monitor/），跑三个协程：

  1. 消费 Kafka App 步骤事件 → 写 Prometheus（任务提交/排队/运行/完成各阶段指标）
  2. 消费 Kafka Gateway 事件 → 写 Prometheus（11 个指标，覆盖 HTTP/限流/供应商/任务/计费）
  3. 轮询 MongoDB → 每 15 秒查一次队列深度（Redis 分布式锁防多实例重复）

3.3 现有体系中缺失的部分

缺失项说明
GPU 显存/利用率实时监控调度层按队列深度管理，不读 nvidia-smi 级别的硬件指标
慢查询检测没有显式的慢查询阈值或告警
连接池监控无
熔断器无，限流是 fail-open 但没有熔断降级
用户满意度信号没有 thumbs up/down、采纳率、重试率分析
业务漏斗/转化率没有"发起任务 → 生成完成 → 用户采纳 → 二次使用"的转化追踪
离线质量评测没有 CLIP score、美学评分等自动化质量评估

四、面试关键题：两种维度的监控

4.1 维度一：工程稳定性监控

这是"系统有没有正常运行"的问题。DM 在这方面做得比较扎实：

  • 指标层：三层 Prometheus 指标（API/调度/App）+ Gateway Kafka 事件管道 → VictoriaMetrics
  • 链路层：Jaeger + OpenTelemetry 跨服务追踪，ntes-trace-id 统一串联
  • 资源层：GPU 节点状态指标 + 自定义自动伸缩器（基于队列深度）
  • 防护层：多层限流（RPM + 并发槽位）、健康检查、积分额度告警

4.2 维度二：业务数据监控

这是"产品有没有解决用户的问题"的问题。DM 在这方面做得比较薄：

  • 已有的：任务成功率（success/failed 二元状态）、App 使用计数、灵感体验点赞（社交互动）
  • 缺失的：生成质量评估、用户满意度信号、转化漏斗、重试率分析

4.3 如果要做业务层面的用户满意度监控，怎么做？

可以从五个层次递进：

层次做什么信号类型实现成本
1. 任务失败原因分类把超时、内容违规、供应商错误、参数校验失败等原因分开统计系统信号低（改埋点字段）
2. 隐式行为信号追踪用户的采纳率（是否保存/导出/下载结果）、重试率（同参数多次生成）行为信号中（加前端埋点）
3. 轻量显式反馈在生成结果旁加 👍/👎，点踩时选原因（质量差/速度慢/不符预期）主观信号中（前后端 + 存储）
4. 核心漏斗转化发起任务 → 生成完成 → 用户采纳 → 二次使用，监控每步转化率波动漏斗信号中高（全链路埋点）
5. 离线质量评测定期用 CLIP 分数、人工抽检等方式衡量模型质量变化趋势客观评估高（评测管线）
关键认知：第 2 层"隐式行为信号"是性价比最高的切入点。用户保存了生成结果 = 隐式认可，用户对同一个 prompt 连续生成 3 次 = 隐式不满。这些行为数据比主观反馈更客观、成本更低、样本量更大。

4.4 但为什么 DM 没优先做这些？

这就是 mentor 讲的重点：不同业务的监控侧重点不同。

  • 传统 toC 产品（比如游戏、社交、电商）：稳定性是基本功，由此延伸出熔断降级、混沌演练；业务上最重要的是数据报表——日活、留存、转化漏斗、LTV——因为数据结果就是产品的 KPI，一般会有专门的 BI 团队做。
  • DM 这类内部工具平台：稳定性和业务数据当然要做，但当前阶段的汇报重心是降本——降低 GPU 调用成本、提高资源利用率、优化供应商选型。监控投入要服务于汇报目标。

所以面试里讲这个话题时，不能只说"应该加什么监控"，还要展示你理解为什么当前没做、什么时候该做——这才是产品思维。

五、面试逐字稿

Q1：你处理过比较麻烦或严重的线上问题吗？比如资源负载较大的情况？

满分逐字稿

面试标准逐字稿

DreamMaker 平台最典型的线上压力场景是GPU 资源负载。因为我们的核心业务是 AI 图像/视频/3D 生成，所有推理任务都跑在 GPU 上，而 GPU 节点价格贵、启动慢，不能像 CPU 服务那样随意扩缩。

在监控层面，我们有一套多层的可观测体系。Scheduler 后端暴露了三层 Prometheus 指标——API 层的请求延迟和在途请求数、调度层的任务排队时间和队列长度、App 层的计算耗时和任务成功率。这些指标被 VictoriaMetrics 抓取，在 Grafana 里做展示和告警。Gateway 那边的做法不一样，它把 HTTP 请求、供应商调用、任务生命周期、计费这些事件通过 Kafka 推给一个独立的 Monitor 服务，Monitor 服务再转成 Prometheus 指标，这样网关本身不用暴露 /metrics 端点，避免了高 QPS 场景下抓取指标对网关性能的影响。

在应对策略上，GPU Worker 的扩缩容是我们自研的自动伸缩器，不用 K8s 原生的 HPA，原因是 GPU Worker 的 CPU 利用率始终很低——瓶颈在 GPU 算力和显存，不在 CPU，所以 HPA 看 CPU 指标完全没意义。我们的自动伸缩器每 30 秒检查一次任务队列深度，队列积压超过阈值就唤醒已终止的 Pod，空闲超时就缩容，用 Redis 分布式锁防止多实例竞争。CPU 类 Worker（比如只调供应商 API 的任务）则继续用标准 HPA。

在防护层面，Gateway 做了多层限流——按 app_code + model 维度的 RPM 滑动窗口限流（Redis ZSET 实现），加上并发槽位限流（Redis Lua 原子 INCR/DECR）。限流策略是 fail-open：Redis 出问题时放行请求，保业务连续性。另外链路追踪上，Scheduler 用 Jaeger、Agent 用 OpenTelemetry，通过网易内部的 ntes-trace-id 头做跨服务 span 串联，排障时可以把一个任务从用户请求到 Agent 执行到 GPU 推理的完整链路拉出来。

追问防守

"GPU 显存/利用率你们有监控吗？" — 说实话，我们在应用层面没有直接读 nvidia-smi 级别的 GPU 硬件指标。GPU 资源管理是在调度层面做的，用队列深度作为负载信号，而不是直接读 GPU 利用率。如果要做更精细的监控，可以在 K8s 集群层面用 DCGM Exporter 采集 GPU 指标到 Prometheus，但这块不在应用层代码里。

"你们有熔断吗？" — 没有。限流做了多层但没有熔断降级。我们的限流是 fail-open 策略，Redis 挂了放行请求。如果要做熔断，传统做法是用 Sentinel 或 Hystrix 之类的方案，在供应商连续报错时快速失败，避免雪崩。但 DM 的场景是内部平台、QPS 不算特别高，相比 toC 业务对熔断的需求没那么迫切。

"慢查询有监控吗？" — 没有显式的慢查询检测。HTTP 请求延迟有 Histogram 直方图，可以在 Grafana 里用 histogram_quantile(0.99, ...) 看 P99 延迟，但没有设阈值自动标记慢查询。如果要做，可以在 middleware 里记录超过阈值的请求到单独的慢查询日志，或者直接在 Prometheus 告警规则里配。

Q2：你说的主动监控更多偏向工程稳定性，有没有办法主动监控业务层面用户对任务表现是否满意，而不是等用户在群里反馈？

满分逐字稿

面试标准逐字稿

这个问题其实涉及两个维度的监控，需要先区分开。

第一个维度是工程稳定性——系统有没有正常运行。这块 DM 已经做了不少：三层 Prometheus 指标、Gateway 的 Kafka 事件管道、GPU 自动伸缩、多层限流、跨服务链路追踪。但这些都是回答"系统有没有坏"，不回答"用户满不满意"。

第二个维度是业务数据——产品有没有解决用户的问题。传统 toC 业务里，这块通常由专门的 BI 团队做数据报表，包括转化漏斗、留存分析、用户行为分析等，因为数据结果就是产品的 KPI。想要什么数据就去做对应的埋点上报。

DM 现在在业务数据这个维度做得比较薄。我看了代码，目前的埋点只覆盖了任务成功/失败的二元状态和使用量统计，没有任何用户满意度信号。现有的"生成反馈"功能只是复制 taskId 给值班同学排障，不是结构化的满意度采集。

如果要做，我觉得有五个递进的层次。

第一层是把任务失败原因分类。现在只记录 success/failed，但失败原因可以细分——超时、内容违规、供应商错误、参数校验失败。这些分开统计后才能定位瓶颈。这个改动成本最低，改埋点字段就行。

第二层是追踪隐式行为信号，这是性价比最高的方向。比如用户生成完之后有没有保存/导出/下载结果——保存了就是隐式采纳；有没有对同一个 prompt 连续生成多次——连续重试就是隐式不满意。这些行为数据比主观反馈更客观，样本量也更大，不依赖用户主动操作。

第三层是轻量的显式反馈。在每个生成结果旁边加 👍/👎，点踩时要求选原因——质量差、速度慢、不符合预期。低成本收集业务信号。

第四层是核心漏斗转化。从发起任务 → 生成完成 → 用户采纳 → 二次使用，监控每一步转化率的波动。转化率突然下降可能意味着某个模型质量退化或者某个供应商出问题。

第五层是离线质量评测。定期用 CLIP 分数、人工抽检等方式衡量模型生成质量的变化趋势，做成 Dashboard，异常波动自动告警。

不过，为什么 DM 目前没优先做这些，有一个业务背景。不同业务的监控侧重点不同——传统 toC 产品的稳定性是基本功，业务数据是 KPI；而 DM 作为内部 AI 平台，当前阶段的核心汇报目标是降本，所以监控投入优先服务于降本相关的指标——GPU 资源利用率、供应商成本、任务单价。这不是说业务数据不重要，而是团队在当前阶段做了优先级选择。如果后续平台进入更成熟的阶段，用户满意度和质量监控一定是要补上的。

追问防守

"你说的隐式行为信号具体怎么落地？" — 前端在"保存"、"导出"、"下载"、"再次生成"这些按钮上加埋点，上报时带上 taskId 和 appName。后端收到后和原始任务关联，就能算出每个 App/模型的采纳率和重试率。重试率高的模型可能质量有问题，采纳率低的 App 可能参数配置不合理。

"CLIP 分数是什么？" — CLIP 是 OpenAI 的多模态对齐模型，它可以给一对（文本, 图像）打一个相似度分数。用生成任务的 prompt 和生成结果算 CLIP score，分数越高说明图像和用户描述越匹配。可以用来做批量质量评测，不需要人工一张张看。但它也有局限——CLIP score 高不一定代表用户喜欢，审美是主观的。

"你真的做过这些吗？" — 这些是我在梳理系统可观测性时识别出的改进方向，不是我实际实现的。DM 现有的监控覆盖了工程稳定性，但业务层面的用户满意度信号确实是一个空白。我做的是理解现有体系、识别缺口、提出改进思路。

回答策略：这道题的核心考察点不是你背了多少监控方案，而是你能不能区分工程监控和业务监控两个维度，并且展示你理解为什么某些东西没做、什么时候该做。最后一段关于"业务优先级"的分析是加分项——它说明你不是只会列技术方案，还能从团队和业务角度理解决策。
