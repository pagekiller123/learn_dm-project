DreamMaker Scheduler 整体架构总览

如果 Monet 是"客户端 Agent"负责理解用户意图，那 DreamMaker Scheduler 就是"云端引擎"负责真正跑 GPU 任务。这一节目标是：能在白板上画出 Scheduler 的核心链路、讲清 app-gateway / worker-scheduler / worker-sidecar 三大组件的边界、并说出为什么这样分层。

跟 Monet 的关键区别：Scheduler 是多服务 + 多用户 + 云端部署的分布式系统，跟 Monet"单机单用户本地服务"完全不同。所以 Scheduler 里的所有讨论——GPU 资源池、Leader 选举、限流、多租户鉴权——都跟 Monet 无关。搞混两边的场景是简历讲解最容易翻车的地方。

一、一句话架构

Scheduler = 多服务 Go 微服务集群 + Redis 任务队列 + Mongo 记录中心 + etcd Worker 注册表 + k8s 服务发现 + dmfr 脚手架。

它没有单一入口——每个服务自带 app/<service>/main.go，通过 tmax istioingress 网关做路径路由，服务间用 dmfr.HTTPClient() 相互调用，任务状态通过 Redis / Mongo / etcd 三层协同管理。

三、五层架构的职责边界

Scheduler 里"五层架构"这个说法来自团队 CLAUDE：外部请求层 → 业务服务层 → 基础服务层 → Worker 执行层 → 外部供应商层。用一张表说清每层的边界：

层级核心组件职责不该做
① 外部请求层 Frontend / Monet / 内部工具 组装 HTTP 请求，携带鉴权 header 打过来 不该直接投递 worker 任务
② 业务服务层 api-outer / app-gateway / 2d / story-board 参数校验、鉴权、参数映射、入库、入队、状态查询 不该直连 Worker、不该做 GPU 调度
③ 基础服务层 worker-scheduler Leader 选举、拉队列、分配任务、结果回写 不该关心具体推理逻辑
④ Worker 执行层 worker-sidecar + 各类 Worker 接收任务、适配后端、执行推理、上报进度和结果 不该反向依赖 app-gateway
⑤ 外部供应商层 ComfyUI / SD-WebUI / 火山 / 混元 / … 真正的 AI 推理 ——

四、三大核心组件（面试必考）

4.1 app-gateway — 任务入口守门员

职责：接住上游 api-outer 转发过来的请求，做四件事：

  1. 权限检查：CheckAppAccess — 判断当前用户能不能调这个 app / sub_app
  2. 组件解析：resolve app component、group、cluster、taskMode、priority
  3. 持久化：AddAppRecord(status=queued) 入 Mongo，同时 Produce pending task 到 Redis 队列
  4. 返回 task_id：立即返回，不等 Worker 执行完

🛡️ 面试防守：为什么必须走 app-gateway，不能绕过？

  1. 安全：api-outer+ app-gateway 是唯一的鉴权和限流入口。绕过等于把 Worker 队列直接暴露给外部
  2. 可观测：所有任务必须留下 AppRecord，方便计费、审计、错误分析
  3. 一致性：任务状态机（queued → running → success/failed）依赖 action.Add 建立初始状态，绕过就没了初态
  4. 扩展性：预处理 / 参数映射 / 优先级都在 app-gateway 层做，绕过等于放弃这些能力

CLAUDE.md 明写："不要绕过 app-gateway 直接从外部投递 worker 任务"。这是团队的硬约束。

4.2 worker-scheduler — 分布式调度大脑

职责：管 Worker 状态 + 分派任务 + 回写结果。整个 Scheduler 里最"分布式"的组件，因为要保证 Worker 池的一致性：

  • Leader 选举：通过 etcd 选出一个 leader，避免多副本抢同一个任务（split-brain）
  • 拉队列：从 Redis 拉 pending task
  • 加载消息：从 Mongo 加载 AppTaskMsg（因为 Redis 里只放 task_id，完整参数在 Mongo）
  • 注册运行：把 task 写到 etcd 的运行注册表，作为"正在跑的任务"的 source of truth
  • 下发给 Worker：Worker 主动上报"我空闲"（report consume），scheduler 才把任务发下去
  • 结果回写：Worker 上报结果 → scheduler 调用 action.AfterCall / MapCallResponse → 写回 Mongo → 删除 etcd 注册

🛡️ 面试防守：为什么 task 状态要同时用 Redis + Mongo + etcd？

  1. Redis：短生命周期"待消费"队列。选它是因为 LPUSH/BRPOP 高吞吐低延迟，适合队列语义。不做长期存储
  2. Mongo：长生命周期"任务记录中心"。所有任务的完整参数、状态、结果都写这里，用于查询、审计、计费
  3. etcd："运行中"状态的强一致 registry。为什么不用 Mongo？因为 etcd 支持 lease + watch，Worker 挂掉时 lease 过期能自动清理；Mongo 做不到这种"心跳自清"

核心思路：用不同的存储服务不同的语义，不用一个存储硬扛所有需求——这是分布式系统的经典权衡。

4.3 worker-sidecar — 异构后端适配器

职责：worker-scheduler 只知道"这个任务要发给某个 Worker"，但 Worker 具体是 ComfyUI / SD-WebUI / 训练 / 外部供应商，用什么协议、参数怎么组织、结果怎么解析——都由 sidecar 适配。

类比：这是适配器模式在生产系统里的规模化应用。sidecar 让 scheduler 的调度逻辑跟具体推理后端解耦，加一种新 Worker 只需要加一种 sidecar，scheduler 侧不改。

    A->>M: 读取 record
    A-->>C: status / output

关键设计点

  • 提交与执行完全异步：提交侧立即返回 task_id，客户端通过 /status 轮询——这是所有 AI 任务系统的标配（推理耗时不可预测）
  • Worker "拉"而非 "推"：Worker 主动 report consume 告诉 scheduler "我可以接活了"，而不是 scheduler 硬塞。这样 Worker 侧永远不会被压垮
  • 状态机通过 action 推进：CLAUDE 明写"队列推进通过 action 完成，不要直接同步调用下一阶段"——这是团队约束，避免耦合和竞态

六、dmfr 脚手架（大量简历技术栈都对应这里）

dmfr = DreamMaker Framework，团队自研 Go 脚手架。你几乎不需要看它的源码，但要能讲清它提供了什么：

能力调用方式不这样做的后果
HTTP Serverdmfr.HTTPServer()手写 wrapper 会漏掉 trace / metrics
HTTP Clientdmfr.HTTPClient(serviceName)手写 base URL 会绕过服务发现
日志logging.Info(ctx, "msg", zap.Field...)散落 logger 会破坏 trace 关联

简历包装点：可以写"基于 dmfr 脚手架开发多个微服务，复用其 HTTP client/server、trace、metrics、ecode、logging 能力，避免重复造轮子"——这既体现你懂微服务基础设施，又体现你有"复用生态"的判断力（面试评论区反复提到的加分点）。

九、检索练习

Q1. 为什么 Scheduler 里任务状态要同时用 Redis + Mongo + etcd？

  • A. Redis 存队列、Mongo 存记录、etcd 存运行时状态并支持心跳自清
  • B. 一个存储不够快，三个存储做冗余备份
  • C. 团队没统一意见，历史遗留
  • D. 分别对应开发 / 测试 / 生产环境
A。三个存储对应三种不同语义：Redis 提供高吞吐的短生命周期队列；Mongo 是"任务记录中心"用于查询和审计；etcd 提供强一致 registry + lease 机制，Worker 挂掉时能自动清理运行注册——这是 Mongo 做不到的。核心思路是"不同存储服务不同语义"。

Q2. 外部工具能不能绕过 app-gateway 直接把任务投递到 Redis 队列？

  • A. 可以，都是内部服务
  • B. 不可以，会绕过鉴权、限流、AppRecord 建立
  • C. 可以但需要额外配置
  • D. 只有超级管理员可以
B。CLAUDE.md 明确禁止。绕过 app-gateway = 没有鉴权、没有 AppRecord 初态、没有限流、没有参数映射，任务状态机会缺失起点。这是团队的硬约束。

Q3. Worker 拉任务采用"pull（Worker 主动 report consume）"而不是"push（scheduler 硬塞）"，主要好处是什么？

  • A. 网络流量更少
  • B. Worker 侧永远不会被压垮，天然反压
  • C. scheduler 侧代码更简单
  • D. B 和 C 都对
B。Push 模式下如果 scheduler 判断错了 Worker 容量，或者 Worker 突然变慢，任务会堆在 Worker 端造成雪崩；Pull 模式下 Worker 完全按自身节奏拉，天然实现反压。这在 GPU 任务这种"处理时长不可预测"的场景下尤其重要。
