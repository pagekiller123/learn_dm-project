Monet 画布感知（Canvas Awareness）

前两节讲了 Agent 的核心循环和工具系统。这一节聚焦一个核心问题：Agent 怎么"看见"画布？

Agent 在画布上操作——生成节点、查询节点、建立连线——但 LLM 本身不知道画布长什么样。Monet 设计了一套三层感知机制，让 Agent 能实时感知画布状态，并根据需要按需查询细节。学完这节你能讲清楚：

  • Agent 怎么在每次 /chat 请求时自动感知画布概览
  • 为什么注入点在模型层而不是 System Prompt
  • 为什么用 contextvar 做请求作用域缓存
  • 按需查询工具怎么复用缓存
  • canvas.render 事件怎么通知前端刷新

一、问题引入

Agent 在画布上操作，但 LLM 本身不知道画布长什么样。如果每次都让 Agent 调工具查画布，token 消耗太大；如果硬编码在 System Prompt 里，画布状态又是动态变化的。

Monet 的解决方案是三层感知机制：

  1. 对话入口预加载：每次 /chat 请求开始时，自动拉取画布概览写入 contextvar
  2. 模型层动态注入：每次 LLM 调用前，把概览注入到 HumanMessage 前缀
  3. 按需查询细节：Agent 需要细节时，调 canvas_node_detail / canvas_subgraph
核心洞察：Agent 的"视觉"不是实时的，而是每次 /chat 请求前刷新一次快照。这跟人眼不一样——人眼是实时流，Agent 是"拍照→看照片→操作→再拍照"。好处是简单可靠，坏处是在一次 /chat 请求的 Agent 工作过程中（可能调用多轮 LLM），如果画布被其他人改了，Agent 不知道。

二、三层感知机制详解

2.1 第一层：对话入口预加载

每次 /chat 请求进来，routes.py 的 _prime_canvas_context 函数会拉取画布详情并写入两个 contextvar：

async def _prime_canvas_context(canvas_id: str) -> None:
    """为本次 /chat 请求拉取画布并写入 contextvar，失败时静默降级。"""
    # 清空上一轮缓存
    set_canvas_detail(None)
    set_canvas_overview_text(None)

    canvas_client = get_canvas_client()
    if canvas_client is None:
        logger.warning("画布客户端未初始化，跳过画布概览注入")
        return

    try:
        # 1. 拉取画布详情（原始 dict）
        detail = await canvas_client.get_canvas_detail(canvas_id)
    except Exception as e:
        logger.warning(f"拉取画布概览失败: canvas_id={canvas_id}, err={e}")
        return

    # 2. 写入 contextvar：原始详情
    set_canvas_detail(detail)

    try:
        # 3. 渲染为 markdown 概览文本
        overview = build_canvas_overview_text(detail)
    except Exception as e:
        logger.warning(f"渲染画布概览失败: canvas_id={canvas_id}, err={e}")
        return

    # 4. 写入 contextvar：渲染后的概览
    set_canvas_overview_text(overview)

两个 contextvar 的定义在 canvas_context.py：

# src/monet/services/canvas_context.py

_canvas_overview_text: ContextVar[str | None] = ContextVar(
    "canvas_overview_text", default=None
)

_canvas_detail: ContextVar[dict[str, Any] | None] = ContextVar(
    "canvas_detail", default=None
)

为什么用 contextvar？

contextvar 是 Python 标准库提供的协程作用域变量，专门解决异步编程中的状态传递问题。

Monet 是并发服务，多个用户同时对话。如果用全局变量存储画布上下文，不同请求会互相污染——用户 A 的画布数据可能被用户 B 的请求覆盖。而 contextvar 是协程作用域的，每个 /chat 请求都有独立的副本，既避免污染，又不需要层层传参。

类比理解：把 contextvar 想象成每个协程的"随身背包"。全局变量是公共储物柜（所有人都能存取，容易拿错），参数传递是手动交接物品（每经过一个函数就要传递一次），而 contextvar 是每个人背自己的包（需要时从自己包里拿，不会拿错）。

🛡️ 面试防守：为什么不在 System Prompt 里硬编码画布状态？

System Prompt 是静态的，画布状态是动态的。如果硬编码，每次画布变化都要重新编译 Agent，成本太高。而且 System Prompt 是所有请求共享的，不同用户看到不同的画布，硬编码会导致串号。

更好的做法是每次 /chat 请求前动态注入，让 LLM 看到当前画布的快照。这样既保证实时性，又避免串号。

2.2 第二层：模型层动态注入

拉取了概览之后，怎么让 LLM 看到？Monet 的做法是在模型层拦截，而不是塞进 System Prompt。

ChatAIGW 继承自 ChatOpenAI，重写了 _astream 和 _agenerate：

# src/monet/model/aigw.py

async def _astream(self, messages, stop=None, run_manager=None, **kwargs):
    """流式推理前注入画布概览和图片 URL 转 base64。"""
    # 1. 注入画布概览到最新 HumanMessage 前缀
    with_canvas = self._inject_canvas_overview(messages)
    # 2. 图片 URL 转 base64
    processed = await self._replace_image_urls(with_canvas, self.aigw_headers)
    # 3. 调用父类流式推理
    async for chunk in super()._astream(processed, stop, run_manager, **kwargs):
        yield chunk

@staticmethod
def _inject_canvas_overview(messages: list[BaseMessage]) -> list[BaseMessage]:
    """把 contextvar 中的画布概览拼到最新 HumanMessage 前缀。"""
    overview = get_canvas_overview_text()
    if not overview:
        return messages  # 没有概览，原样返回

    # 找到最后一条 HumanMessage
    last_human_idx = None
    for i in range(len(messages) - 1, -1, -1):
        if isinstance(messages[i], HumanMessage):
            last_human_idx = i
            break
    if last_human_idx is None:
        return messages  # 没有 HumanMessage，原样返回

    # 深拷贝最后一条 HumanMessage
    original = messages[last_human_idx]
    new_msg = copy.deepcopy(original)

    # 构造注入块
    injected_block = {
        "type": "text",
        "text": CANVAS_CONTEXT_HEADER + overview,
    }

    # 插入到 content 列表最前面
    if isinstance(new_msg.content, list):
        new_msg.content = [injected_block, *new_msg.content]
    elif isinstance(new_msg.content, str):
        new_msg.content = [injected_block, {"type": "text", "text": new_msg.content}]

    # 替换原消息
    messages = list(messages)
    messages[last_human_idx] = new_msg
    return messages

CANVAS_CONTEXT_HEADER 是一个标记，告诉 LLM 这是系统注入的画布上下文：

CANVAS_CONTEXT_HEADER: str = "[CanvasContext 系统注入·仅本轮可见]\n"

为什么注入到 HumanMessage 而不是 SystemMessage？

System Prompt 是静态的，所有请求共享。如果注入到 SystemMessage，需要重新编译 Agent，成本太高。而且 SystemMessage 的权重很高，LLM 会认为这是"永恒真理"，但实际上画布状态是动态变化的。

注入到 HumanMessage 前缀，LLM 会认为这是"用户当前提供的上下文"，权重适中。而且 HumanMessage 是每次请求独立的，不会污染其他请求。

为什么用深拷贝？

LangGraph 的 messages 是状态机的一部分，会被 checkpoint 持久化。如果我们直接修改 messages，会污染 checkpoint，导致后续对话恢复时看到错误的画布状态。

深拷贝确保改写只作用于发给 LLM 的内存副本，原始 messages 不变，checkpoint 不被污染。

🛡️ 面试防守：为什么不直接把概览作为 Tool 的返回值？

Tool 的返回值是给 LLM 看的，但 LLM 需要先调 Tool 才能看到。如果 Agent 不知道画布长什么样，它不知道该调哪个 Tool。这是一个鸡生蛋蛋生鸡的问题。

更好的做法是每次 /chat 请求前自动注入概览，让 LLM 先看到画布的大致形态，再决定要不要调 Tool 查细节。这样既减少 Tool 调用次数，又保证 LLM 有全局视角。

2.3 第三层：按需查询细节

概览只能让 LLM 知道画布的大致形态（节点数量、类型分布、连线关系）。如果 LLM 需要某个节点的详细信息（参数、输出、位置），需要调 Tool 查询。

Monet 提供了两个查询 Tool：

Tool作用返回
canvas_node_detail查询单个节点的完整详情节点的 type、label、位置、参数、输出
canvas_subgraph查询一组节点及其连线子图的节点列表、连线列表

这两个 Tool 的实现都在 canvas_query.py。但它们的缓存策略不同：

canvas_node_detail：直接查后端

这个工具查询单个节点的详情，每次调用都会直接请求后端 API（canvas_client.get_node_detail），不使用 contextvar 缓存。原因是：

  • 单节点查询很轻量（只查一个节点的数据），不值得缓存
  • Agent 可能需要最新数据（比如刚生成的节点），缓存可能过时

canvas_subgraph：复用 contextvar 缓存

这个工具查询一组节点及其连线，需要整张画布的数据。它优先复用 _prime_canvas_context 预加载的 _canvas_detail contextvar：

# src/monet/tools/canvas_query.py

@tool
async def canvas_subgraph(node_ids: list[str]) -> str:
    """查询一组节点及其连线关系。"""
    canvas_id = _resolve_canvas_id()
    if not canvas_id:
        return "错误：无法获取画布 ID，请确认在画布上下文中发起对话。"

    # 优先复用 contextvar 缓存
    detail = get_canvas_detail()
    if detail is None:
        # 缓存不存在，现拉一次
        canvas_client = get_canvas_client()
        detail = await canvas_client.get_canvas_detail(canvas_id)
        # 写回 contextvar，后续工具调用复用
        set_canvas_detail(detail)

    # 从 detail 中筛选目标节点和连线
    nodes = detail.get("nodes", [])
    target_nodes = [n for n in nodes if n.get("id") in node_ids]
    edges = detail.get("edges", [])
    target_edges = [e for e in edges
                    if e.get("source") in node_ids and e.get("target") in node_ids]

    # 格式化为 markdown
    return _format_subgraph(target_nodes, target_edges)
设计哲学：按需查询工具的缓存策略取决于查询粒度。单节点查询轻量，直接查后端保证数据新鲜；子图查询重量，复用预加载的缓存避免重复 HTTP。

🛡️ 面试防守：既然 _prime_canvas_context 已经预加载了缓存，canvas_subgraph 里的 if detail is None 分支什么时候会触发？

正常情况下不会触发——_prime_canvas_context 在 /chat 入口已经预加载了 _canvas_detail，后续所有工具调用都能从 contextvar 读到。

但有一种降级场景会触发：如果 _prime_canvas_context 预加载失败（网络错误、后端 500、超时），异常被捕获后 contextvar 保持 None。此时 canvas_subgraph 被调用，get_canvas_detail() 返回 None，就会触发"现拉一次"分支。

这段代码是防御性编程：让工具在概览注入失败时仍然能工作（只是多一次 HTTP 请求），而不是直接返回错误。如果没有这段代码，预加载失败后 Agent 就没办法查询子图了。

三、画布概览渲染策略

build_canvas_overview_text 函数负责把画布详情渲染为 markdown 文本。它根据节点数量选择不同的渲染策略：

节点数 N策略内容
N = 0empty单行"画布为空"
1–5detailed全部节点 id/type/label/位置/输出 + 全部 edges/groups
6–30medium全部节点 id/type/label + 全部 edges/groups
31–100brief前 60 节点 + 前 60 edges + groups
N > 100summary只列总数 + 类型分布 + groups

示例（detailed 策略）：

## 画布概览
节点：3（gen-image: 2, input-image: 1）
连线：2 条
分组：1 个

### 节点列表
- node-abc | gen-image | 赛博朋克猫咪 | 位置 (100, 200) | 输出 1×completed
- node-def | gen-image | 霓虹灯光效 | 位置 (300, 200) | 输出 1×completed
- node-xyz | input-image | 用户上传参考图 | 位置 (100, 400) | 输出 1×completed

### 连线列表
- node-xyz → node-abc
- node-xyz → node-def

### 分组列表
- group-001 | 猫咪系列 | 2 节点 [node-abc, node-def]

示例（summary 策略，节点数 > 100）：

## 画布概览
节点：150（gen-image: 80, gen-video: 30, input-image: 20, gen-3d: 20）
连线：200 条
分组：5 个

（节点过多，仅显示统计信息。如需查看具体节点，请使用 canvas_node_detail 工具。）

为什么要分级？

LLM 的 context window 是有限的。如果画布有 500 个节点，全列出来会占用大量 token，而且 LLM 也看不过来。分级策略的核心思想是：小画布看细节，大画布看统计。

阈值 5 / 30 / 100 是经验值，可以根据实际使用场景调整。比如如果用户经常操作大画布，可以把阈值调低，让 LLM 更早进入 summary 模式。

🛡️ 面试防守：为什么不直接让 LLM 调 Tool 查画布？

LLM 需要先知道"画布长什么样"才能决定"要不要调 Tool"。如果每次都要调 Tool 查画布，会增加一次 Tool 调用，消耗额外的 token 和时间。

更好的做法是每次 /chat 请求前自动注入概览，让 LLM 先看到画布的大致形态，再决定要不要调 Tool 查细节。这样既减少 Tool 调用次数，又保证 LLM 有全局视角。

这跟人的认知方式类似——你进入一个房间，先扫一眼全局（概览），再决定要不要走过去看某个东西的细节（Tool）。

四、canvas.render 自定义事件

Agent 调 Tool 创建了节点之后，怎么通知前端刷新？Monet 的做法是发一个自定义事件，前端收到后主动拉取最新画布数据。

# 工具内部
await adispatch_custom_event(name="canvas.render", data={})

LangGraph 的 astream_events 会把这个事件 yield 出来，Adapter 透传为 SSE 事件：

# Adapter 内部
elif event_kind == "on_custom_event":
    event_name = event.get("name")
    event_data = event.get("data", {})
    yield SSEFrame(
        event=event_name,
        data={"message_id": message_id, **event_data},
    )

前端收到 canvas.render 事件后，主动调 HTTP 接口拉取最新画布数据，局部刷新渲染。

设计哲学：后端只负责"通知"，前端负责"拉取+渲染"。这样既避免后端推大量数据，又让前端有完全的渲染控制权。这跟 Git 的 webhook 类似——webhook 只告诉你"有 push 了"，具体变了什么你要自己 git fetch。

关于 canvas.render 的详细机制，参见 M003 第六节。

六、面试防守点汇总

问题答案要点
为什么不在 System Prompt 里硬编码画布状态？ System Prompt 是静态的、所有请求共享的；画布状态是动态的、每个用户独立的。硬编码会导致串号，且每次画布变化都要重新编译 Agent。
为什么用 contextvar 做缓存？ contextvar 是协程作用域的，每个请求独立，不会污染其他请求。如果用全局变量，多个请求并发时会互相覆盖；如果用参数传递，需要层层透传，代码臃肿。
为什么注入到 HumanMessage 而不是 SystemMessage？ SystemMessage 权重太高，LLM 会认为这是"永恒真理"；HumanMessage 是每次请求独立的，权重适中，LLM 会认为这是"用户当前提供的上下文"。
为什么用深拷贝？ LangGraph 的 messages 会被 checkpoint 持久化。如果直接修改，会污染 checkpoint，导致后续对话恢复时看到错误的画布状态。深拷贝确保改写只作用于发给 LLM 的内存副本。
为什么不直接让 LLM 调 Tool 查画布？ LLM 需要先知道"画布长什么样"才能决定"要不要调 Tool"。如果每次都要调 Tool 查画布，会增加一次 Tool 调用，消耗额外的 token 和时间。自动注入概览可以减少 Tool 调用次数。
为什么画布概览要分级渲染？ LLM 的 context window 有限。小画布看细节，大画布看统计。分级策略既保证 LLM 有全局视角，又避免占用过多 token。
canvas.render 事件的作用是什么？ Agent 调 Tool 创建了节点后，发一个轻量通知，前端收到后主动拉取最新画布数据，局部刷新渲染。后端只负责"通知"，前端负责"拉取+渲染"。

八、总结

Monet 的画布感知机制是一个典型的"快照+按需查询"设计：

  • 快照：每次 /chat 请求前预加载画布概览，注入到 LLM 的上下文
  • 按需查询：LLM 需要细节时，调 Tool 查询，优先复用缓存
  • 通知刷新：Agent 操作画布后，发 canvas.render 事件通知前端

这个设计的好处是：

  • 简单可靠：每次 /chat 请求前刷新快照，避免状态不一致
  • 性能友好：contextvar 缓存避免重复 HTTP 请求
  • token 节约：分级渲染避免占用过多 context window
  • 职责分离：后端只通知，前端负责渲染

坏处是：

  • 非实时：如果对话中途画布被其他人改了，Agent 不知道
  • 快照过时：Agent 操作画布后，如果不调 Tool 重新查询，看到的还是旧快照

但在 Monet 的场景下，这些坏处可以接受——因为画布操作通常是单用户的，不会有多人并发修改。

简历亮点：设计并实现了 Monet 的画布感知系统，包括 contextvar 请求作用域缓存、模型层动态注入、分级渲染策略，使 Agent 能实时感知画布状态并按需查询细节，同时避免占用过多 context window。
