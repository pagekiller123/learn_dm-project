一、HITL 交互通道（Bullet 1）

一句话：基于 LangGraph interrupt 机制，让 Agent 在执行本地 shell/文件操作前暂停等用户审批，审批通过后 resume 继续。

1.1 业务背景

Monet Agent 运行在用户本机，具备本地 shell 执行和文件读写能力。但不加控制地执行任意命令是危险的（比如 rm -rf /）。需要一个机制让：

  • Agent 想执行写操作时暂停，把操作内容推给前端
  • 用户看到后决定允许/拒绝
  • 决策回传 Agent，Agent 继续或终止

类比：Claude Code 的权限弹窗 — 你输入命令后 CLI 弹窗问你"允许执行吗"，就是同样的 HITL 模式。

sequenceDiagram

🎯 面试防守

  1. Q: interrupt 怎么实现的？
    A: LangGraph 原生支持 interrupt — Agent Loop 执行到需要审批的 tool call 时，graph 进入 interrupted 状态，runner 检测到后通过 asyncio.Event 挂起。前端 resume 回来后 Event.set() 唤醒，graph 从断点继续。
  2. Q: 并发安全问题？同一个 session 多次 resume 怎么办？
    A: Monet 是单机单用户服务（本地客户端），同一 session 同时只有一个 pending interrupt。runtime.py 用 dict 以 session_id 为 key 管理，resolve 时取出 Event 唤醒并清理，重复 resolve 返回 False。
  3. Q: 前端断连了怎么办？interrupt 会永远挂着吗？
    A: 有超时机制。register_interrupt 后如果 Event 在超时时间内没被 set，cleanup_interrupt 自动清理，Agent 中止当前操作并告知用户。
  4. Q: 为什么不用 WebSocket 双工？
    A: Monet 已经有 SSE 长连接用于流式输出。审批是低频操作（一次对话可能 0-2 次），不值得为此额外建立 WebSocket。用户决策通过普通 HTTP POST 回传就够了。

关键词：LangGraph interrupt、Human-in-the-Loop、权限审批、SSE 事件协议
面试强调：这是一个可扩展的协议设计 — 当前只有 Confirmation/Choice 两种交互类型，但协议层是通用的，未来加"从多方案选一个"等新类型无需改 SSE 层。这个设计思路比"只解决当前问题"高一个层次。

Q1. DefaultPermissionEngine 对 "execute" action 返回什么决策？

  • A. ALLOW
  • B. NEEDS_APPROVAL
  • C. DENY
B. NEEDS_APPROVAL — execute 属于 WRITE_ACTIONS，Phase 1 全量审批。

Q2. resolve_interrupt() 返回 False 意味着什么？

  • A. 用户拒绝了操作
  • B. 没有找到对应 session_id 的 pending interrupt
  • C. Event 已经超时
B. _pending_interrupts.get(session_id) 返回 None 时，说明没有 pending interrupt（可能已被清理或从未注册）。

二、MCP 协议接入与运行时管理（Bullet 2）

一句话：让 Monet Agent 能接入任意 MCP server，把外部工具动态注入 Agent 工具列表，支持不重启热加载。

2.1 业务背景

MCP（Model Context Protocol）是 2024-2025 年 AI Agent 领域最热门的标准协议，由 Anthropic 推出。它解决的问题是：让 Agent 以统一方式使用各种外部工具/数据源，不用为每个工具写专属适配代码。

Monet 内置了画布工具（canvas_query、generate 等），但用户可能还想接入自己的 MCP server（比如文件管理、数据库查询、自定义 API）。所以需要：

  • 支持多种传输协议（stdio / HTTP / SSE / WebSocket）
  • 运行时增删改查（不重启 Agent）
  • MCP 工具与内置工具统一调度

🎯 面试防守

  1. Q: MCP 和普通 Function Calling 有什么区别？
    A: Function Calling 是 LLM 层面的（模型输出 tool_call），MCP 是工具发现和连接层面的标准协议。FC 解决"模型怎么调工具"，MCP 解决"工具怎么注册、怎么连接、怎么描述 schema"。两者互补，不冲突。
  2. Q: 热加载怎么做的？重连时 Agent 在跑怎么办？
    A: MCPManager 内部为每个 server 维护 _ServerRuntimeEntry。reload 时先关闭旧 client，再建新连接，更新 raw_tools。如果 Agent 正在用某个 tool，该次调用会正常完成（工具引用还在），下次调用时才用新连接。
  3. Q: 工具名冲突怎么处理？内置工具和 MCP 工具同名？
    A: manager.py 里有 _SAFE_TOOL_NAME_RE 正则对工具名做 sanitize，MCP 工具会带 server name 前缀避免冲突。MCPToolSnapshot 同时保留 name（sanitized）和 original_name。
  4. Q: 某个 MCP server 挂了会影响 Agent 吗？
    A: 不会。每个 server 独立管理，状态变成 "error"，其工具从可用列表移除。Agent 继续用其他工具正常工作。

关键词：MCP（Model Context Protocol）、工具注入、热加载、多传输协议
面试强调：MCP 是 2025 最热的 Agent 标准，能讲清楚协议本身 + 工程落地细节（连接管理、状态模型、故障隔离），是 Agent 岗的核心加分项。

Q1. MCPServerStatus 有哪三种状态？

"connected" / "error" / "disabled" — 对应正常运行、连接失败、用户手动禁用三种情况。

三、声明式后处理调用框架（Bullet 3）

一句话：把后处理系统重构为"注册表 + 执行器协议"模式，新增后处理操作只需写 config + schema，不写执行器代码。

3.1 业务背景

Monet 支持多种后处理操作（AI 扩图、打光、全景图、多角度渲染、裁切等）。每种操作调用不同的后端（DM API 小程序、AIGW 模型、外部 API），但流程高度相似：

  1. 接收参数 → 校验
  2. 提交后端 → 轮询状态
  3. 拿到产物 → 写入画布节点

如果每种操作都手写一个 executor，代码会大量重复。所以设计了声明式框架：通用操作（如 DM 小程序调用）用配置描述参数，框架统一执行。

🎯 面试防守

  1. Q: 为什么不用策略模式 / 工厂模式？
    A: 策略模式需要为每种操作写一个类。我们的设计更进一步 — 大部分操作用同一个 DmAppletExecutor 就能覆盖，只需配置不同参数。只有确实逻辑不同的（如 GPT-Image-2 打光）才写专属 executor。这是"配置优于代码"的思路。
  2. Q: JSON Schema 怎么给前端用的？
    A: OperationDefinition.info() 调用 params_schema.model_json_schema() 生成标准 JSON Schema，前端据此动态渲染参数表单。新增操作不需要前端改代码。
  3. Q: 执行器之间有共享状态吗？
    A: 没有。每次执行创建独立的 OperationRunContext（包含 session、画布客户端、认证信息），executor 通过 ctx 完成所有副作用，无全局状态。
  4. Q: 如果执行器执行到一半失败了怎么办？
    A: Orchestrator 捕获异常，标记操作失败，已创建的中间产物不写入画布。ExecutionResult 只在完全成功时才返回 outputs。

四、批量生成并发轮询与瞬时容错（Bullet 4）

一句话：引入 TaskOutcome 统一终态表达，串行轮询改并发，网络抖动不再误杀任务，批量生成增量回显。

4.1 业务背景

改造前的问题：

  • 串行轮询：批量生成 4 张图，每张轮询到完成才开始下一张，总耗时 = 4 × 单张时间
  • 网络抖动误杀：轮询时一次网络超时就判定任务失败（实际任务可能在后端正常执行）
  • 全量等待：用户必须等所有子任务都完成才能看到结果

核心改动：

# TaskOutcome sum type — 统一终态表达
@dataclass
class Succeeded:
    outputs: list[OutputArtifact]

@dataclass
class Failed:
    error: str
    retryable: bool = False

@dataclass
class Aborted:
    reason: str

TaskOutcome = Succeeded | Failed | Aborted  # Python 3.10+ Union

瞬时容错：轮询时单次网络超时不直接返回 Failed，而是递增 transient_error_count。连续 N 次失败才判定真正失败。

🎯 面试防守

  1. Q: 什么是"瞬时容错"？怎么判断临时故障 vs 真正失败？
    A: 瞬时容错 = 单次轮询失败不算数，连续 N 次（如 3 次）才判定失败。判断依据：HTTP 状态码 5xx 或网络超时是瞬时的，而后端明确返回 failed 状态是确定性的。前者重试，后者直接标 Failed。
  2. Q: asyncio.gather 有任务失败了怎么办？
    A: 用 return_exceptions=True，让每个任务独立完成。失败的标记为 Failed，成功的正常写画布。不会因为一个失败导致全部取消。
  3. Q: 增量回显会不会导致画布状态不一致？
    A: 不会。每个子任务写入独立的画布节点位置（提前占位）。写入是原子操作，失败的位置保留 placeholder 或显示错误状态。
  4. Q: 为什么用 sum type 而不是状态码枚举？
    A: sum type 让每种终态携带不同的数据（Succeeded 有 outputs，Failed 有 error+retryable，Aborted 有 reason）。枚举只能表达"是什么状态"，不能携带上下文信息。这是函数式编程中 Result/Either 的经典模式。

面试强调：这条 bullet 有清晰的"问题→方案→效果"链 — 串行轮询慢（问题）→ 并发+容错+增量（方案）→ 响应速度提升+误判率降低（效果）。效果可以用"批量生成用户等待时间从 N×T 降为 max(T₁...Tₙ)"来量化。

Q1. TaskOutcome 的三个变体分别是？

Succeeded（携带 outputs）、Failed（携带 error + retryable 标记）、Aborted（携带 reason）。

Q2. 改造前批量生成 4 张图的耗时公式是？改造后呢？

改造前：T₁ + T₂ + T₃ + T₄（串行累加）。改造后：max(T₁, T₂, T₃, T₄)（并发取最长）。

五、模拟面试：完整追问链

场景：面试官看完简历后开始追问 Monet 项目。以下模拟真实追问链（从浅到深）。

面试官：介绍一下你在 Monet 项目做了什么？

你：Monet 是网易互娱的 AI 美术智能体平台，运行在用户本地桌面客户端上，通过 SSE 与画布交互。我主要做了四块：Agent 本地执行的权限审批系统、MCP 协议接入、后处理声明式框架、以及批量生成的并发轮询优化。

面试官：你说的 HITL 审批，能具体讲讲怎么实现的吗？

你：Agent 要执行本地命令时，先经过 PermissionEngine 判断 — 读操作直接放行，写操作和执行命令需要审批。需要审批时利用 LangGraph 的 interrupt 机制暂停 Agent，SSE 推一个 interaction.request 事件给前端弹窗，用户点击允许后前端 POST 到 /resume 端点，后端通过 asyncio.Event 唤醒 Agent 继续执行。

面试官：如果用户一直不点审批按钮怎么办？

你：有超时机制。register_interrupt 时设置超时，Event 在限时内没被 set 的话触发 cleanup_interrupt 清理状态，Agent 终止当前操作并给用户返回"审批超时"的提示。

面试官：MCP 那个，热加载是怎么做到的？

你：MCPManager 内部为每个 server 维护一个 _ServerRuntimeEntry，包含 client 连接、状态、工具列表。通过 REST API 增删改时，Manager 关闭旧连接、建立新连接、更新 raw_tools。Agent 每次调用前从 container 获取最新工具列表，所以下一次 tool call 就能用到新加的 MCP 工具。

面试官：四种传输协议为什么都要支持？实际用哪种多？

你：stdio 最常用 — 本地 MCP server 以子进程启动，通过 stdin/stdout 通信，零网络开销。HTTP/SSE 用于远端 server。WebSocket 用于需要双工的场景。协议选择在 MCPServerConfig 里由用户配置，Manager 根据 TransportType 走不同的 connection 路径。

面试官：声明式框架那个，"新增操作只需配置"具体是怎么做到的？

你：核心是 OperationRegistry。每种操作注册一个 OperationDefinition，里面指定 params_schema（Pydantic model）和 executor。大部分操作用同一个 DmAppletExecutor — 它根据 applet_config 里的 app_name 和参数映射调用 DM API 小程序。新增操作只需写一个 Pydantic 参数模型 + 一份 applet_config，在注册表里注册一行就完了。

面试官：那如果新操作的执行逻辑跟 DM 小程序完全不同呢？

你：那就写一个新的 executor 实现 OperationExecutor Protocol（只需实现 execute 方法）。比如打光操作用的是 GptImage2Executor，它直接调 AIGW 模型而不是 DM 小程序。但这种情况少数 — 我们大部分后处理操作都走 DM 平台的小程序通道。

面试官：最后那个并发轮询，asyncio.gather 和 asyncio.TaskGroup 你为什么选前者？

你：gather 更适合我们的场景 — 一个失败不影响其他的。TaskGroup 是 Python 3.11+ 的，遵循"一个失败全部取消"的语义，不符合我们的需求（4 张图里 1 张失败不应该取消其他 3 张）。gather 配合 return_exceptions=True 正好。
