任务调度全链路与 Redis 队列设计

S001 画出了 Scheduler 的整体骨架。这一节我们钻进去——从一个任务被提交到最终返回结果，每一步到底调了什么函数、经过了哪个 Redis 数据结构、状态怎么转换。重点是 Redis 队列设计（ZSet vs List）和优先级调度，这两块是后端面试的高频考点。

本节的面试价值：Redis 数据结构选型、分布式任务队列、乐观抢占（CAS 思想）、加权调度算法——这些是后端校招面试的常客。本节所有内容都来自项目真实代码，面试时可以直接用"我们项目里是这样做的"来回答。

一、任务状态机

所有任务都遵循同一套状态机。5 种内部状态、5 条转换路径（注：对外接口把 queued 展示为 waiting，但内部状态机只认 5 种）：

stateDiagram-v2
    [*] --> queued : Add（入库+入队）
    queued --> running : Run（被 Worker 消费）
    running --> success : Success（执行成功）
    running --> failed : Failed（执行失败/超时）
    running --> stopped : Stop（用户主动取消）
    queued --> failed : Failed（入队后异常）
状态含义触发函数（action_base.go）Mongo 操作（dao_record.go）
queued已入库 + 已入队列，等待消费Base.Add()AddAppRecord()
runningWorker 已拉取，正在执行Base.Run()RunAppRecord()
success执行成功，结果已写入Base.Success()SuccessAppRecord()
failed执行失败，错误已记录Base.Failed()FailedAppRecord()
stopped用户主动取消Base.Stop()StopAppRecord()

每次状态转换后，都会调 SetCache() 更新 Redis 缓存，供前端 /status 轮询秒级返回。状态常量定义在 model/constance.go：

TaskStatusQueued  = "queued"
TaskStatusRunning = "running"
TaskStatusSuccess = "success"
TaskStatusFailed  = "failed"
TaskStatusStopped = "stopped"

二、Action 编排模式

Action 是 Scheduler 里任务状态推进的核心抽象。它定义了一个任务从入库到完成的所有操作。设计模式是模板方法 + 策略的混合。

2.1 Action 接口（8 个核心方法）

定义在 app/app-gateway/action/interface.go：

type Action interface {
    ActionName() string
    Add(ctx, msg) error           // 入库（Mongo）
    Run(ctx, msg) error           // 标记 running
    Stop(ctx, msg) error          // 用户取消
    Success(ctx, msg) error       // 标记成功
    UpdateOutput(ctx, msg) error  // 中间结果更新
    Failed(ctx, msg, err) error   // 标记失败
    GetAppMsg(ctx, taskID, msg) error    // 读 Mongo 任务记录
    ProduceResult(ctx, msg) error        // 写结果到 Kafka
}

2.2 可选接口（Go 类型断言实现策略模式）

除了 Action 核心接口，还有一系列可选接口，action 实现哪个就具备哪种能力：

可选接口职责检查方式
RequestMapper参数映射（APP 配置 → 请求参数）action.(RequestMapper)
MsgProducer入队列（Produce pending task）action.(MsgProducer)
MsgConsumer出队列（Consume pending task）action.(MsgConsumer)
Generator生成 JobReportData 下发 Workeraction.(Generator)
CallResponseMapperWorker 结果映射action.(CallResponseMapper)
Progressor进度读写action.(Progressor)
PreprocessProducer预处理入队action.(PreprocessProducer)
Caller直接调用后端（非 Worker 模式）action.(Caller)
为什么用 Go 类型断言而不是全部放 Action 接口？
因为不同类型的 action 需要的能力不同。比如 ComfyUI 需要 Caller（直连本地后端），而 commonAction 需要 Generator（生成 JobData 下发 Worker）。把所有方法塞进一个接口会产生大量空实现。Go 的类型断言就是天然的"可选接口"机制，等价于其他语言的 interface segregation。

类型断言怎么工作的？

关键点：编排函数的参数类型统一是 Action（核心接口），但通过 action.(XxxInterface) 在运行时探测具体实现是否"额外"实现了某个可选接口。ok == true 就调用该能力，ok == false 就跳过或报错。

以 Produce 编排函数为例（interface.go 第 140 行）：

func Produce(ctx context.Context, appComponent *model.AppComponent,
        action Action, msg *model.AppTaskMsg) error {
    //         ^^^^^^ 参数类型是 Action 核心接口
    //         但运行时的具体值可能是 commonAction、comfyuiAction 等

    // 类型断言 ① —— 问："你实现了 MsgProducer 吗？"
    msgProducer, ok := action.(MsgProducer)
    if !ok {
        // 没实现 → 报错（入队是必须能力）
        return
    }
    action.Add(ctx, msg)                              // 入库
    msgProducer.Produce(ctx, appComponent, msg)        // 入队

    // 类型断言 ② —— 问："你还实现了 PreprocessProducer 吗？"
    preprocessProducer, doPreprocess := action.(PreprocessProducer)
    if appComponent.Preprocess && doPreprocess {
        // 有预处理能力 + 配置启用了预处理 → 走预处理分支
        return preprocessProducer.PreprocessProduce(ctx, msg)
    }
    // 没有预处理 → 走正常入队
    return msgProducer.Produce(ctx, appComponent, msg)
}

同理，AfterCall 里断言 action.(CallResponseMapper)，GenerateTask 里断言 action.(Generator)——整条编排链都是同一个套路。

类比：编排函数 = 流水线工位，Action 核心接口 = 工人的基本资质（人人都有），可选接口 = 工人的额外技能证书。流水线每个工位都会问：

  • "你有 MsgProducer 证吗？" → 有就干入队的活
  • "你有 PreprocessProducer 证吗？" → 有就先走预处理
  • "你有 Caller 证吗？" → 有就直接调外部 API
  • "你有 Generator 证吗？" → 有就生成任务等 Worker 消费

好处：新增一种 AI 能力时，只需要写一个 struct 实现需要的接口组合，编排函数完全不用改。比如新接一个供应商，只要 commonAction 能覆盖（它已经实现了 MsgProducer + MsgConsumer + Generator + CallResponseMapper），连新文件都不用建。

三、Redis 队列设计（重点）

这是本节的核心内容。Scheduler 里同时存在两种 Redis 队列——旧版 List 和新版 Sorted Set。理解两者的区别和选型理由，是后端面试的高频考点。

Redis 基础知识速补（已经熟悉 Redis 的可以跳过）

Redis 是什么？
Redis 是一个内存数据库（所有数据存在内存里，读写极快，单机 10 万+ QPS）。它不像 MySQL/Mongo 主要靠磁盘，所以速度快几个数量级，但代价是容量受内存限制。常用于：缓存、消息队列、分布式锁、计数器、排行榜等。

Redis 的数据结构（面试必知）：
Redis 不是 key-value 那么简单，它的 value 可以是多种数据结构：

数据结构类比核心操作典型场景
String 一个变量 SET key value / GET key 缓存、计数器、分布式锁
List 双端链表（可当队列/栈） LPush（左推入）/ RPop（右弹出）/ BRPop（阻塞弹出） 消息队列（FIFO）、最近 N 条记录
Hash 一个对象 / dict HSet key field value / HGet 存储对象的多个字段（用户信息等）
Set 无序去重集合 SAdd / SMembers / SInter（交集） 标签、共同好友、去重
Sorted Set (ZSet) 有序去重集合（每个元素带一个分数 score） ZAdd key score member / ZRange（按 score 排序取）/ ZRem（删除） 排行榜、优先级队列、延时队列
Stream 日志流（类似 Kafka topic） XAdd / XRead / XAck 消息队列（有消费组、ACK 机制）

本项目用到的两种队列数据结构：

① List 当队列（旧版 ComfyUI 用）：
想象一根管子——左边推入（LPush），右边弹出（BRPop），先进先出（FIFO）。BRPop 的 "B" 是 Block（阻塞），意思是"如果队列空了，就傻等直到有新元素"——不需要轮询，等到就取。

LPush myqueue "task-1"    → 队列: [task-1]
LPush myqueue "task-2"    → 队列: [task-2, task-1]
BRPop myqueue 0           → 弹出 "task-1"（最早的），队列: [task-2]
                            （0 表示无限等待）
优点：简单，BRPop 天然原子（弹出 = 取走，不可能两人取到同一个）。
缺点：纯 FIFO 没法插队（优先级）、没法"先看一眼再决定要不要取"。

② Sorted Set (ZSet) 当优先级队列（新版 commonAction 用）：
想象一个排行榜——每个元素有一个 score（分数），按 score 从小到大排列。

ZAdd myqueue 1000 "user1::task-A"   → 按 score=1000 插入
ZAdd myqueue 900  "user2::task-B"   → 按 score=900 插入
ZAdd myqueue 1100 "user3::task-C"   → 按 score=1100 插入

ZRange myqueue 0 -1                 → 按 score 排序返回:
                                      ["user2::task-B",    score=900
                                       "user1::task-A",    score=1000
                                       "user3::task-C"]    score=1100

ZRem myqueue "user2::task-B"        → 删除该元素，返回 1（成功删了 1 个）
                                      如果另一个消费者也 ZRem 同一个元素 → 返回 0（已经被删了）
优点：可以按 score 排序（实现优先级或时间排序）、可以先 ZRange 看一批再决定取哪个（选择性消费）、ZRem 的返回值天然实现原子抢占。
缺点：不像 BRPop 能阻塞等待，需要轮询（定时去看有没有新的）。

ZSet 的底层实现（面试加分项）：
Redis ZSet 内部用 跳表（Skip List）+ 哈希表 双结构：跳表维护 score 排序（支持范围查询 ZRange），哈希表维护 member → score 映射（支持 O(1) 查找 / 删除 ZRem）。时间复杂度：ZAdd / ZRem = O(log N)，ZRange(0, K) = O(log N + K)。

为什么不用 Redis Stream？
Stream 有消费组和 ACK 机制，看似更适合做消息队列。但 DM 的场景需要"先扫描一批 → 检查每个用户的并发 → 选择性消费"，Stream 的 XReadGroup 是"分配给你就是你的"，不支持这种"看了但不一定要"的模式。ZSet 的 ZRange（看）+ ZRem（选择性取）天然匹配。

3.1 两种队列对比

维度旧版 — List（ComfyUI/SD）新版 — Sorted Set（commonAction）
数据结构Redis ListRedis Sorted Set (ZSet)
入队LPushZAdd(key, score, member)
出队BRPop（阻塞弹出）ZRange + ZRem（轮询扫描 + 原子删除）
排序FIFO（先进先出）按 score 排序（支持优先级 + 时间戳）
消息体完整 AppTaskMsg JSON只存 user::taskID，完整数据在 Mongo
优先级不支持多 key 隔离不同优先级
并发控制无通过 member 里的 user 前缀做用户级限制
竞争安全BRPop 原子弹出，天然安全ZRem 返回值 ≥ 1 才算抢到
为什么新版只在 Redis 存 ID 不存完整消息？
  • 消息体大小：AppTaskMsg 可能包含 base64 图片、ComfyUI workflow JSON 等大字段，存完整消息会占用大量 Redis 内存
  • ZSet member 限制：ZSet 对 member 做排序，member 越短性能越好
  • 一致性：任务参数可能在预处理阶段被修改，如果 Redis 里也存了一份，就要同步两处
  • 面试话术：Redis 做"索引层"、Mongo 做"数据层"，职责分离
重要认知：不是一个大队列，而是很多小队列

你可能以为所有任务都堆在同一个 Redis 队列里——不是的。DM 按 4 个维度 拆成了很多独立的 ZSet 队列，每个 Redis key 就是一个队列：

apps_pending_task::{priority}::{source}::{taskMode}::{cluster}::{env}

维度含义示例值
priority优先级等级0、1、2
source请求来源dm、sf、mj
taskMode任务模式default、fast
cluster资源集群v2prod、aliyun-hangzhou-1

再加上 env（test/prod），每一种组合就是一个独立队列。比如线上可能同时存在：
apps_pending_task::dm::default::v2prod::prod          ← 普通优先级
apps_pending_task::2::dm::default::v2prod::prod       ← 高优先级（priority=2）
apps_pending_task::dm::fast::aliyun-hangzhou-1::prod  ← 快速模式、阿里云集群
apps_pending_task::sf::default::v2prod::prod          ← sf 来源
为什么要拆？
  • 隔离性：不同 cluster 的 Worker 只能消费自己 cluster 的任务，拆开后直接盯对应 key，不用过滤
  • 限流独立：不同 source / taskMode 的消费规则和限流策略不同
  • 优先级调度：拆成多个 key 后，WeightedScheduler 才能在不同 priority 之间按权重轮询
  • 性能：小队列的 ZRange 扫描量小，不用在一个巨大 ZSet 里翻找"哪些是我能消费的"

3.2 ZSet 入队细节

入队代码在 commonAction.Produce()：

// key 格式：apps_pending_task::{priority}::{source}::{task_mode}::{cluster}::{env}
key = priority.BuildPendingKey(pri, msg.Source, msg.TaskMode, msg.Cluster, dmfr.ENV())

// member = "user::taskID"
member := fmt.Sprintf("%s::%s", msg.GetRealUser(), msg.TaskID)

// score = preprocessTime（毫秒时间戳）→ 先提交先消费
c.dao.GetRedis().ZAdd(ctx, key, msg.PreprocessTime, member)

几个关键设计点：

设计点做法为什么
key 格式 apps_pending_task::{priority}::{source}::{task_mode}::{cluster}::{env} 不同优先级用不同 key 隔离队列，消费时按优先级挑 key
priority=0 时 key 少一段 apps_pending_task::{source}::{task_mode}::{cluster}::{env}（无 priority 段） 向后兼容——旧任务没有优先级概念，key 格式不能变
score = 毫秒时间戳 msg.PreprocessTime 同优先级内先来先服务（FIFO 语义）
member 包含 user user::taskID 出队时用 user 前缀做并发控制，不需要额外查询

BuildPendingKey 的实现在 pkg/priority/queue_key.go，只有 18 行：

func BuildPendingKey(priority int, source, taskMode, cluster, env string) string {
    if priority == 0 {
        return fmt.Sprintf("apps_pending_task::%s::%s::%s::%s",
            source, taskMode, cluster, env)
    }
    return fmt.Sprintf("apps_pending_task::%d::%s::%s::%s::%s",
        priority, source, taskMode, cluster, env)
}

3.3 ZSet 出队 — 乐观抢占模式

出队是整个队列设计最精妙的部分。代码在 commonAction.tryConsume()：

%%{init: {'flowchart': {'nodeSpacing': 15, 'rankSpacing': 25}, 'themeVariables': {'fontSize': '12px'}}}%%
flowchart TB
    A["ZRange(0, 255) 批量扫描前 256 个 member"] --> B{遍历每个 member}
    B --> C{"splitMember 解析出 user 和 taskID"}
    C --> D{"user 为空或 taskID 为空？"}
    D -->|是| E["ZRem 清理脏数据"]
    D -->|否| F{"GetUser() 该用户已有任务在跑？"}
    F -->|有并发冲突| G["加入 queueJob 跳过"]
    F -->|无冲突| H["grabJob() 尝试抢占"]
    H --> I{"ZRem 返回值 ≥ 1？"}
    I -->|是，抢到了| J["从 Mongo 加载消息 → 注册 etcd → 成功"]
    I -->|否，被别人抢了| K["继续遍历"]
    G --> L["第一轮结束 → 遍历 queueJob（第二轮）"]
    L --> H

核心代码简化版：

func (c *commonAction) tryConsume(ctx context.Context, pri int, msg *model.AppTaskMsg) error {
    pendingTaskKey := priority.BuildPendingKey(pri, ...)
    members, _ := rds.ZRange(ctx, pendingTaskKey, 0, 255)

    queueJob := []string{}  // 有并发冲突的 member，第二轮再试
    for _, member := range members {
        user, taskID := c.splitMember(member)

        // 检查该用户是否已有任务在跑
        if c.concurrentManager.GetUser(source, taskMode, cluster, user) >= 1 {
            queueJob = append(queueJob, member)
            continue  // 先跳过，给其他用户机会
        }
        if err := c.grabJob(ctx, pendingTaskKey, member, msg); err == nil {
            return nil  // 抢到了！
        }
    }
    // 第二轮：消费有并发冲突的任务（所有无冲突的都没抢到时）
    for _, member := range queueJob {
        if err := c.grabJob(ctx, pendingTaskKey, member, msg); err == nil {
            return nil
        }
    }
    return err
}

func (c *commonAction) grabJob(ctx context.Context, key, member string, msg *model.AppTaskMsg) error {
    num, _ := c.dao.GetRedis().ZRem(ctx, key, member)
    if num < 1 {
        return err  // 被别的 scheduler 抢走了
    }
    // 抢到了：从 Mongo 加载完整消息 + 注册到 etcd
    c.dao.GetAppRecord(ctx, taskID, msg)
    c.schedulerDao.AddTask(ctx, msg)
    return nil
}

🛡️ 面试防守：ZRem 的"乐观抢占"为什么不需要 Lua 脚本？

  1. ZRem 本身是原子操作：Redis 单线程模型下，ZRem 返回的 removed count 天然保证只有一个消费者能抢到同一个 member
  2. 无需 "读-判断-删" 的原子包装：ZRange 只是"看一眼"候选列表，真正的竞争点在 ZRem。多个 scheduler 实例同时 ZRange 到同一个 member 没关系——谁先 ZRem 成功谁赢
  3. 对比 BRPop：List 的 BRPop 也是原子弹出，但它是阻塞式的（没消息时会 block），而且不支持"跳过某些消息"——ZSet + ZRange 可以先扫描、按条件过滤（如并发检查），再决定抢哪个
  4. 什么时候需要 Lua？ 如果需要"读 → 检查条件 → 删"三步原子化（比如"只删 score 小于某个值的 member"），就需要 Lua 脚本。这里不需要，因为条件检查（并发控制）是在应用层做的，Redis 侧只负责原子抢占

3.4 两轮扫描策略

为什么要分两轮？

  1. 第一轮：跳过有并发冲突的用户（GetUser() >= 1），优先消费没有任务在跑的用户——公平性，防止一个高频用户霸占所有 Worker
  2. 第二轮：如果第一轮没抢到任何任务（可能所有无冲突用户的任务都被别的 scheduler 抢了），再回来消费有并发冲突的用户——吞吐量，不让 Worker 空转

这是一个典型的 公平性 vs 吞吐量 的权衡。第一轮保公平，第二轮保吞吐。

3.5 后端面试延伸：Redis 数据结构选型

🛡️ 面试题：Redis List vs ZSet vs Stream 各自适合什么场景？

数据结构适用场景优势劣势
List 简单 FIFO 队列、不需要优先级 BRPop 阻塞等待，零轮询开销；原子弹出天然安全 不支持按条件跳过消息、不支持优先级、不支持消费确认
Sorted Set 需要优先级、需要按条件过滤的任务队列 score 支持排序/优先级；member 可以编码业务信息；ZRem 原子抢占 需要轮询（无阻塞等待语义）；底层 skiplist 内存开销略大于 List
Stream 消息流、需要消费组和 ACK 的场景 原生支持消费组（Consumer Group）、消息确认（ACK）、消息回溯 API 复杂；不适合"按条件跳过某条消息"的场景；消息堆积时内存增长

DM 为什么选 ZSet 不选 Stream？

  • DM 需要"按用户并发数跳过某些任务"——Stream 的 Consumer Group 是顺序消费，做不到跳过
  • DM 的消费确认通过 etcd 注册 + Mongo 状态机实现，不需要 Stream 的 ACK
  • ZSet 的 member 天然支持编码 user::taskID，解析简单
ZSet 底层实现（面试常问）
Redis ZSet 底层有两种编码：
  • ziplist（元素少且小时）：紧凑数组，内存友好但查找 O(n)
  • skiplist + hashtable（元素多时）：skiplist 支持 O(log n) 范围查询（ZRange），hashtable 支持 O(1) 单元素查找（ZScore/ZRem）

DM 的 pending 队列通常有几十到上千个 member，走的是 skiplist + hashtable 编码。ZRange(0, 255) 的时间复杂度是 O(log n + 256)，ZRem 是 O(log n)。

四、优先级调度 — WeightedScheduler

不同的任务可以有不同优先级（由 APP 配置决定）。高优先级任务应该更快被消费——但不能让低优先级永远饿死。解决方案是加权轮询（Weighted Round-Robin）。

4.1 算法原理

代码在 pkg/priority/scheduler.go：

// NextPriority 选出本次应消费的 priority
func (s *WeightedScheduler) NextPriority(qctx QueueContext, cfg *Config) (int, bool) {
    // 1. 按 priority 降序排列所有队列配置
    sortedCfg := cfg.SortedQueues()

    // 2. 找到第一个还有配额的 priority
    if pri, found := pickPriority(st, sortedCfg); found {
        st.counters[pri]--   // 消耗一个配额
        return pri, true
    }

    // 3. 所有配额耗尽 → 重置，重新开始一轮
    resetCounters(st, sortedCfg)
    if pri, found := pickPriority(st, sortedCfg); found {
        st.counters[pri]--
        return pri, true
    }
    return 0, false
}

举个例子：配置 [{priority:2, weight:5}, {priority:1, weight:3}, {priority:0, weight:2}]，那么一轮 10 次消费中，priority=2 被选 5 次，priority=1 被选 3 次，priority=0 被选 2 次。一轮消耗完后，配额重置，开始新一轮。

flowchart LR
    A["NextPriority()"] --> B{"有配额的 priority？"}
    B -->|有| C["选中，配额 -1"]
    B -->|全耗尽| D["resetCounters()
所有配额重置为 weight"]
    D --> E["再选一次"]
    E --> C

4.2 Consume 的三层消费策略

commonAction.Consume() 实际消费时有三层策略（代码在 action_common.go）：

  1. 无 queues 配置 → 等价于旧行为，只消费 priority=0 的队列
  2. 加权选择 → 调 WeightedScheduler.NextPriority() 选一个 priority，尝试 tryConsume
  3. 降序兜底 → 如果加权选的队列空了，按 priority 降序逐个试所有声明的队列
// 1. 无 queues 配置 → 原行为
if cfg == nil || len(cfg.Queues) == 0 {
    c.tryConsume(ctx, 0, msg)
    return
}
// 2. 加权选
if cfg.Enabled && c.prioScheduler != nil {
    if pri, ok := c.prioScheduler.NextPriority(qctx, cfg); ok {
        if c.tryConsume(ctx, pri, msg) == nil && msg.TaskID != "" {
            return
        }
    }
}
// 3. 降序兜底
for _, p := range priority.AllPriorities(cfg) {
    if c.tryConsume(ctx, p, msg) == nil && msg.TaskID != "" {
        return
    }
}

🛡️ 面试防守：加权调度怎么解决低优先级饥饿问题？

  1. 配额制保底：即使 priority=0 的 weight 只有 2，每 10 次消费也至少被选 2 次——不会永远饿死
  2. 降序兜底：加权选空后，会按 priority 降序遍历所有队列。如果高优先级队列恰好空了，低优先级任务就有机会被消费
  3. 对比纯优先级（strict priority）：如果用"高优先级队列非空就不看低优先级"的策略，低优先级在高负载时会完全饿死。加权轮询是经典的公平调度方案

五、用户并发控制

DM 需要限制单个用户在同一类任务上的并发数（防止一个用户的大量请求占满 Worker）。实现方式是内存级计数 + CAS 原子操作。

5.1 ConcurrentManager

代码在 app/worker-scheduler/manager/concurrent.go：

type ConcurrentManager struct {
    taskMap *ConcurrentMap[string, *atomic.Int64]  // source::taskMode::cluster → 计数
    userMap *ConcurrentMap[string, *atomic.Int64]  // source::taskMode::cluster::user → 计数
}

两个 map 分别跟踪任务维度和用户维度的并发数。

5.2 CAS 原子操作

增减计数时使用 CAS（Compare-And-Swap）循环，保证并发安全且不加锁：

func (c *ConcurrentManager) addClampNonNegative(v *atomic.Int64, delta int64) int64 {
    for {
        curr := v.Load()
        if delta < 0 && curr == 0 { return 0 }     // 不能减到负数
        next := curr + delta
        if delta < 0 && next < 0 { next = 0 }      // 钳位到 0
        if v.CompareAndSwap(curr, next) {           // CAS：成功则返回，失败则重试
            return next
        }
    }
}
CAS vs 互斥锁（面试常问）
  • CAS（乐观锁）：不阻塞其他 goroutine，竞争低时性能好；竞争激烈时会空转重试
  • Mutex（悲观锁）：竞争时直接阻塞等待，不空转；但有 goroutine 调度开销
  • 这里用 CAS 合适，因为并发计数的更新频率不高（每个任务开始/结束时各一次），竞争极低

5.3 etcd Watch 驱动

ConcurrentManager 的计数由 worker-scheduler 维护。当一个新任务被注册到 etcd（/task/{env}/{taskID}），Watch 事件会触发 ConcurrentManager.Add(..., +1)；当任务完成或 Worker 挂掉导致 etcd key 过期删除，Watch 事件触发 Add(..., -1)。

这意味着 ConcurrentManager 的计数是最终一致的——etcd 保证 Watch 事件的有序投递，内存计数跟随 etcd 的真实状态。

六、Kafka 事件广播

前面讲的 Redis 队列负责任务调度（谁下一个被消费），但任务完成后，结果怎么通知给下游系统？这就是 Kafka 的角色——事件广播。

Kafka 基础知识速补（已经熟悉 Kafka 的可以跳过）

Kafka 是什么？
Kafka 是一个分布式消息队列（更准确地说是"分布式事件流平台"）。它的核心能力是：生产者把消息写入 Kafka，消费者按自己的节奏读取——生产和消费完全解耦。

跟 Redis 队列最大的区别：Kafka 的消息被消费后不会消失，它会按配置的保留时间（比如 7 天）一直存着，多个消费者可以独立读取同一批消息。而 Redis 的 BRPop / ZRem 是"取走就没了"。

四个核心概念：

概念类比说明
Topic 频道 / 主题 消息的分类。比如"任务结果"一个 topic，"状态变更"一个 topic
Partition 频道里的多条车道 一个 topic 拆成多个 partition，并行写入和消费。同一个 key 的消息总是落在同一个 partition（保序）
Consumer Group 订阅组 同一个 group 内的消费者瓜分 partition（每条消息只被组内一个消费者处理）；不同 group 各自独立消费全量消息
Offset 书签 / 读到第几页 每个 consumer group 在每个 partition 上记录"读到哪了"，下次从这里继续

一句话理解 Kafka 和 Redis 队列的定位差异：
Redis 队列是"抢活干"——多个消费者竞争同一个任务，抢到就是你的（调度）。
Kafka 是"广播通知"——一条消息可以被多个下游系统各自消费一遍（事件分发）。

6.1 DM 里 Kafka 怎么用的

Scheduler 里有两个 Kafka 写入点：

函数写入时机消息内容下游消费者（内部服务）
WriteResult 任务成功 / 失败后 完整的 AppTaskMsg（含 output） consumer 服务：数据上报、告警、埋点、模型统计
WriteStep 任务每一步状态变化时 AppTaskMsgStep（状态转换事件） monitor 服务：Prometheus 指标（运行时间、排队时间等）

注意：Kafka 通知的是内部后台服务（统计、监控、告警），不是用户。用户获取结果走的是 GET /apps/{app}/status 查 Mongo——Kafka 和用户之间没有直接关系。

核心代码非常简单：

func (d *Dao) WriteResult(ctx context.Context, taskMsg *model.AppTaskMsg) error {
    dataBytes, _ := json.Marshal(taskMsg)
    return d.kafkaResult.WriteMessages(ctx, kafka.Message{
        Key:   []byte(taskMsg.TaskID),   // 同一个 task 的消息落在同一个 partition
        Value: dataBytes,
    })
}

注意 Key = TaskID——Kafka 按 key 做 partition 路由，这保证同一个任务的所有消息在同一个 partition 内有序。

6.2 为什么不直接用 Redis 或 Mongo 通知下游？

方案问题
直接查 Mongo 下游要轮询 Mongo"有没有新结果"，延迟高、浪费查询
Redis Pub/Sub 不持久化——消费者没在线时消息就丢了，无法回溯
Redis 再搞一个队列 一个消息只能被一个消费者取走，无法多下游各自消费
Kafka 持久化 + 多 consumer group 独立消费 + 按 key 保序 ✅

6.3 面试对比：Redis 队列 vs Kafka

维度Redis 队列（ZSet / List）Kafka
定位任务调度——"谁下一个被消费"事件广播——"通知所有关心的人"
消费模式竞争消费（取走就没了）每个 consumer group 独立消费全量
持久化内存为主，重启可能丢磁盘持久化，可配置保留天数
吞吐量单机 10万+ QPS，但单线程分布式多 partition 并行，百万级 QPS
顺序性单 key 内有序单 partition 内有序（按 key 路由）
延迟微秒级（内存）毫秒级（要落盘）
回溯不支持（消费了就没了）支持（重置 offset 就能重新消费）
DM 里用在任务排队 + 乐观抢占结果通知 + 状态变更事件

🛡️ 面试防守：为什么 DM 同时用 Redis 和 Kafka，不统一用一个？

场景不同，选型不同。任务调度需要低延迟 + 竞争消费 + 灵活的选择性消费（ZRange 看一批再决定取哪个），Redis 天然适合。结果通知需要持久化 + 多下游独立消费 + 可回溯，Kafka 天然适合。硬要统一反而会牺牲各自的优势——用 Kafka 做调度延迟太高且不支持选择性消费，用 Redis 做事件广播不持久化且不支持多消费组。

八、面试防守合集

🛡️ Q1：Redis ZSet 为什么比 List 更适合任务队列？

List 只支持 FIFO，不能按优先级排序，不能跳过某些消息。ZSet 的 score 天然支持排序（优先级 + 时间戳），member 可以编码业务信息（用户 ID），ZRange 可以批量扫描后按条件过滤再 ZRem 抢占。但 List 的 BRPop 是阻塞式零轮询，延迟比 ZSet 的轮询模式更低——如果不需要优先级和并发控制，List 反而更好（这就是 ComfyUI 还在用 List 的原因）。

🛡️ Q2：ZRange + ZRem 和 BRPop 各自怎么保证竞争安全？

BRPop：Redis 单线程 + 原子弹出，多个消费者同时 BRPop 时只有一个能拿到消息。ZRange + ZRem：ZRange 只是"看"，多个消费者可以同时看到同一个 member；竞争点在 ZRem——Redis 单线程保证只有一个 ZRem 返回 1，其他返回 0。本质都是利用 Redis 单线程的原子性，只是切入点不同。

🛡️ Q3：为什么新版队列只在 Redis 存 ID 不存完整消息？

三个原因：① AppTaskMsg 可能含 base64 图片等大字段，存 Redis 浪费内存且拖慢 ZSet 排序；② 任务参数在预处理阶段可能被修改，如果 Redis 也存了一份就要双写同步；③ Redis 做"索引"、Mongo 做"数据"，职责分离——这是分布式系统常见的"热索引 + 冷存储"模式。

🛡️ Q4：加权优先级调度的饥饿问题怎么解决？

用配额制：每个 priority 有固定 weight，一轮内按 weight 比例分配消费次数，耗尽后重置。即使 weight=1，每轮也至少被选一次。加上"降序兜底"策略——加权选空后会遍历所有队列，如果高优先级队列恰好空了，低优先级立刻有机会。跟 Linux CFS 调度器的 vruntime 思路类似，但实现更简单。

九、检索练习

Q1. commonAction 的 ZSet 入队时，score 用的是什么值？

  • A. 用户 ID 的 hash
  • B. 任务优先级数值
  • C. preprocessTime（毫秒时间戳）
  • D. 随机数
C。score = msg.PreprocessTime，即任务预处理完成的毫秒时间戳。ZSet 按 score 升序排列，所以先提交的任务 score 更小、排在前面——实现同优先级内的 FIFO 语义。优先级通过不同的 Redis key 隔离，不是通过 score。

Q2. tryConsume 的两轮扫描，第一轮跳过、第二轮才消费的是什么任务？

  • A. 优先级低的任务
  • B. 已经超时的任务
  • C. 该用户已有任务在跑的（并发冲突）
  • D. score 太大的任务
C。第一轮通过 ConcurrentManager.GetUser() >= 1 检查，如果该用户已有任务在运行，就先跳过，放入 queueJob 列表。这样优先消费没有任务在跑的用户，保证公平性。第二轮再回来消费有并发冲突的任务，保证吞吐量。

Q3. grabJob() 里用什么操作来实现"乐观抢占"？

  • A. Redis Lua 脚本
  • B. 分布式锁（SETNX）
  • C. ZRem 返回值判断（≥ 1 则抢到）
  • D. 乐观锁（Mongo 版本号）
C。ZRem 在 Redis 单线程下是原子的，返回被删除的元素数量。多个 scheduler 实例同时 ZRem 同一个 member，只有一个返回 1（抢到），其他返回 0。不需要 Lua 脚本，因为竞争点只在这一个操作上。

Q4. WeightedScheduler 的加权轮询，当所有 priority 的配额都耗尽时会怎样？

  • A. 返回错误，等待下一轮
  • B. 随机选一个 priority
  • C. 重置所有配额为初始 weight，重新开始一轮
  • D. 只消费 priority=0 的队列
C。resetCounters() 把所有 priority 的计数器重置为配置的 weight 值，然后再 pickPriority() 选一次。这保证了加权比例在长期运行中保持稳定。如果 reset 后仍然选不到（所有 weight ≤ 0），才返回 false。
