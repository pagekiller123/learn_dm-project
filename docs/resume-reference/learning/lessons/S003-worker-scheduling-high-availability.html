Worker 调度与高可用

S002 讲了任务怎么入队、怎么被消费。但还有一个核心问题没展开：谁来做调度？如果调度器自己挂了怎么办？Worker 挂了怎么检测？队列积压了怎么自动扩容？

这一节覆盖四个高频后端面试话题：Leader 选举、etcd 服务注册、心跳与故障检测、应用层自动扩缩容。每个话题都从代码出发，讲清实现细节和设计权衡。

本节核心价值：这四个话题是分布式系统面试的"必考题型"。不同于教科书讲 Raft / Paxos，DreamMaker 的实现是工程级的取舍——用 K8s Lease 而不是 etcd election、用应用层 Autoscaler 而不是 HPA、用 Lease TTL 而不是心跳超时来检测故障。每个选择背后都有具体原因，这些原因就是你面试时的"回答深度"。

二、Leader 选举 — K8s LeaseLock

worker-scheduler 部署多副本（通常 3 个），但同一时刻只有一个 Leader 在做调度。如果不做 Leader 选举，多个副本会同时拉 Redis 队列、同时分派任务，导致重复调度。

2.1 选举入口代码

代码在 app/scheduler/main.go：

func electLeader(ctx context.Context) {
    id := uuid.New().String()
    lock := &rl.LeaseLock{
        LeaseMeta: metav1.ObjectMeta{
            Namespace: conf.Config.Election.KubeNamespace,
            Name:      "dreammaker-scheduler-lock-" + conf.Config.ENV,
        },
        LockConfig: rl.ResourceLockConfig{
            Identity: id,
        },
        Client: kube.NewKubeClient().CoordinationV1(),
    }
    leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
        Lock:          lock,
        LeaseDuration: time.Second * 15,  // 租约有效期
        RenewDeadline: time.Second * 10,  // 续约截止时间
        RetryPeriod:   time.Second * 2,   // 竞选重试间隔
        Callbacks: leaderelection.LeaderCallbacks{
            OnStartedLeading: func(ctx context.Context) {
                run(ctx)  // 启动调度主循环
            },
            OnStoppedLeading: func() {
                os.Exit(0)  // 失去 Leader 后退出，K8s 重调度
            },
            OnNewLeader: func(identity string) { ... },
        },
    })
}

2.2 三个时间参数

参数值含义面试怎么说
LeaseDuration 15s Lease 有效期——Leader 必须在 15s 内续约，否则 Lease 过期 设太短会因网络抖动频繁切主；设太长 failover 就慢
RenewDeadline 10s Leader 续约的截止时间——必须在 10s 内完成一次续约 API 调用 必须 < LeaseDuration，给续约失败留出检测窗口
RetryPeriod 2s Follower 竞选重试间隔——每 2s 尝试一次获取 Lease 必须 < RenewDeadline，保证切主窗口内至少有几次重试
约束关系：RetryPeriod < RenewDeadline < LeaseDuration。
最坏情况下，Leader 挂掉到新 Leader 上任的时间 = LeaseDuration - RenewDeadline + RetryPeriod = 15 - 10 + 2 = 7 秒。实际通常更快，因为 Follower 每 2s 尝试一次。

2.4 OnStoppedLeading: 为什么直接 os.Exit(0)?

一旦续约失败（失去 Leader），进程直接退出。看起来"很暴力"，但这是 K8s 原生选举的标准做法：

  1. 避免脑裂：如果旧 Leader 不退出，它可能继续拉队列、分派任务，跟新 Leader 产生冲突
  2. K8s 自动重建：退出后 K8s Deployment 控制器自动创建新 Pod，它会以 Follower 身份加入竞选
  3. 状态无损：调度器是无状态的——所有状态在 etcd / Redis / Mongo，重启后从存储恢复

🛡️ 面试防守：为什么用 K8s Lease 不用 etcd election？

  1. etcd election 依赖 etcd Session：需要维护 gRPC 长连接和 Lease KeepAlive，client 断线后 Session 自动过期。这在 K8s 环境下增加了一层 etcd 客户端管理
  2. K8s Lease 是原生资源：不需要额外的 etcd 客户端——直接通过 K8s API Server 操作。K8s API Server 本身已经保证了高可用，且所有 Pod 天然能访问
  3. 生态成熟：k8s.io/client-go/tools/leaderelection 是官方库，controller-manager / scheduler / etcd operator 等核心组件都用它。生产验证充分，不需要自己处理 Session 过期、重连等边界情况
  4. 关注点分离：etcd 在本项目中用于 Worker/Task 注册（业务数据），Leader 选举用 K8s Lease（集群管理），两者职责不混

三、etcd Worker/Task 注册

etcd 在 Scheduler 里承担"运行时注册中心"的角色——记录当前有哪些 Worker 在线、正在跑哪些 Task。S001 说过"etcd 提供 lease + watch，Worker 挂掉时 lease 过期能自动清理"，这一节展开讲它怎么实现的。

3.1 两种 key 格式

用途Key 格式Value示例
Worker 注册 /worker/{env}/{podName} WorkerPodAttributes JSON /worker/prod/comfyui-gpu-abc123
Task 运行注册 /task/{env}/{taskID} AppTaskMsg JSON /task/prod/task-uuid-456

两种 key 都带 {env} 前缀，实现了多环境隔离——测试环境和生产环境共用同一个 etcd 集群但互不干扰。

3.2 Lease 机制

代码在 app/worker-scheduler/dao/dao.go：

const defaultTTL = 7200  // 2 小时

func (d *Dao) grantLease(ctx context.Context) (*clientv3.LeaseGrantResponse, error) {
    leaseCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    return d.etcd.Grant(leaseCtx, defaultTTL)  // 申请一个 7200s 的 Lease
}

func (d *Dao) grantLeaseLoop(ctx context.Context) {
    ticker := time.NewTicker(300 * time.Second)  // 每 300s 重新申请
    for {
        select {
        case <-ticker.C:
            lease, err := d.grantLease(ctx)
            if err != nil { continue }
            d.lease = lease
        case <-ctx.Done():
            return
        }
    }
}
注意：这里是 Grant（重新申请）不是 KeepAlive（续约）
标准 etcd 用法是 KeepAlive 定期续约一个长期 Lease。但 DM 的做法是每 300s 重新 Grant 一个新 Lease，然后后续写入的 key 自动绑到新 Lease。

为什么？KeepAlive 需要维护一个 gRPC 长连接 stream，网络抖动可能导致 KeepAlive stream 断裂，一旦断裂所有绑定的 key 会在 TTL 后全部过期。Grant 重新申请的好处是：即使前一个 Lease 出问题，新 Grant 的 Lease 是独立的，不受影响。代价是前一个 Lease 上的 key 会在 7200s 后过期，但在下次写入时会绑定到新 Lease，所以活跃的 key 不会丢失。

3.3 写入操作：AddTask 与 UpdateWorker

AddTask——简单 Put + 绑 Lease：

func (d *Dao) AddTask(ctx context.Context, msg *model.AppTaskMsg) error {
    key := fmt.Sprintf(etcdTaskKey, dmfr.ENV(), msg.TaskID)
    value, _ := json.Marshal(msg)
    _, err := d.etcd.Put(ctx, key, string(value),
        clientv3.WithLease(d.lease.ID))  // 绑定当前 Lease
    return err
}

UpdateWorker——Txn 乐观锁更新（面试高频）：

func (d *Dao) UpdateWorker(ctx context.Context, podName string,
        kvs ...structure.KV[string, any]) (*model.WorkerPodAttributes, error) {

    key := fmt.Sprintf(etcdWorkerKey, dmfr.ENV(), podName)
    response, _ := d.etcd.Get(ctx, key)           // ① 读当前值
    value := string(response.Kvs[0].Value)

    for _, kv := range kvs {                       // ② 修改字段
        value, _ = sjson.Set(value, kv.Key, kv.Value)
    }

    etcdResp, _ := d.etcd.Txn(ctx).
        If(clientv3.Compare(                       // ③ 比较 ModRevision
            clientv3.ModRevision(key), "=",
            response.Kvs[0].ModRevision)).
        Then(clientv3.OpPut(key, value,            // ④ 一致则写入
            clientv3.WithLease(d.lease.ID))).
        Commit()

    if !etcdResp.Succeeded {
        // ModRevision 不匹配 → 有人抢先写了 → 日志告警
    }
    ...
}
为什么用 Txn 乐观锁？
Worker 状态可能被多个来源更新：心跳上报、任务完成、shutdown 通知。如果不做并发控制，后写的值可能覆盖先写的值（ABA 问题）。

Txn 的 Compare(ModRevision) 保证"我读到的版本 = 当前版本"时才写入，否则放弃。这跟数据库的乐观锁 UPDATE ... WHERE version = ? 是同一个思路。

3.4 Watch 机制

Leader 启动后，会开两个 Watch 协程分别监听 Worker 和 Task 变化：

// service.go → New()
go s.watchWorker(ctx)
go s.watchTask(ctx)

// Watch Worker
func (d *Dao) WatchWorker(ctx context.Context) clientv3.WatchChan {
    key := fmt.Sprintf(etcdWorkerPrefix, dmfr.ENV())
    return d.etcd.Watch(ctx, key,
        clientv3.WithPrefix(),    // 前缀匹配所有 /worker/{env}/*
        clientv3.WithPrevKV())    // 同时拿到变更前的旧值
}

WithPrevKV() 是关键——Delete 事件中，新值为空，只有旧值里才有 Worker/Task 的完整信息（podName、workerType 等），用于清理缓存和恢复并发计数。

四、心跳与故障检测

分布式系统里"检测节点是否活着"有两种经典方式：主动心跳 + 被动 Lease 过期。DM Scheduler 两个都用了。

4.1 Sidecar 30s 心跳

代码在 app/worker-sidecar/service/service.go 的 poolLoop：

func (s *Service) poolLoop(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            return
        case <-time.Tick(time.Second * 30):    // 每 30s
            s.heartbeat(ctx)                    // 上报心跳
            // 动态调整并发池容量
            if s.workerPool.Cap() != s.attribute.Load().Concurrency {
                s.workerPool.Tune(s.attribute.Load().Concurrency)
            }
        }
    }
}

func (s *Service) heartbeat(ctx context.Context) {
    req := &model.ReqWorkerReport{
        Name: s.podName,
        Type: model.WorkerReportTypeHeartbeat,
    }
    msg, err := workerScheduler.Report(ctx, req)  // HTTP 调 worker-scheduler
    if err != nil || msg.Attribute == nil { return }
    s.attribute = atomic.NewPointer(msg.Attribute) // 更新本地配置
}

心跳做两件事：① 告诉 scheduler "我还活着"；② 从 scheduler 拿回最新配置（比如并发数变了，动态调整 worker pool）。

4.2 Scheduler 处理心跳

代码在 app/worker-scheduler/service/service_job.go：

func (s *Service) heartbeat(ctx context.Context, req *model.ReqWorkerReport,
        worker *model.WorkerPodAttributes) (*model.RespWorkerReport, error) {
    worker, err := s.dao.UpdateWorker(ctx, req.Name)
    // 不传 KV → 只做一次 Txn Put，刷新 Lease 绑定
    return &model.RespWorkerReport{Attribute: worker}, err
}

关键点：UpdateWorker(ctx, req.Name) 不传额外 KV 参数——它的作用是把这个 key 重新绑定到当前 Lease。因为每次 Put 都带 WithLease(d.lease.ID)，相当于续约。

4.4 Worker Delete 事件处理

代码在 app/worker-scheduler/service/service_event_handler.go：

func (s *Service) handleWorkerDelete(ctx context.Context, ev *clientv3.Event) {
    worker := &model.WorkerPodAttributes{}
    json.Unmarshal(ev.PrevKv.Value, worker)  // ← PrevKV 拿旧值

    s.workerCache.Delete(worker.Name)           // ① 删除缓存
    s.cacheKeyManager.WorkerDelete(worker)      // ② 清理 cache key 索引
    s.workerClusterMap.Decr(                    // ③ 集群计数 -1
        genWorkerClusterKey(worker.Type, worker.Project, worker.GetTaskMode()))
}

4.5 Task Delete 事件 → 并发计数恢复

func (s *Service) handleTaskEvent(ctx context.Context, ev *clientv3.Event) {
    var sub int64
    var v []byte

    switch ev.Type {
    case clientv3.EventTypePut:
        sub = 1; v = ev.Kv.Value         // 新任务 → +1
    case clientv3.EventTypeDelete:
        sub = -1; v = ev.PrevKv.Value    // 任务结束/过期 → -1
    }

    task := &model.AppTaskMsg{}
    json.Unmarshal(v, task)
    s.concurrentManager.Add(task.Source, task.TaskMode,
        task.Cluster, task.GetRealUser(), sub)
}

🛡️ 面试防守：心跳 30s vs Lease TTL 7200s，为什么差这么大？

  1. 心跳的作用不是故障检测——它主要是"刷新 Lease 绑定 + 同步配置"。30s 间隔保证配置更新足够快（比如并发数调整）
  2. Lease TTL 7200s 才是故障检测的兜底——Worker 正常 shutdown 会主动上报 WorkerReportTypeShutdown → WorkerReportTypeExit，etcd key 通过 UpdateWorker(status=terminated) 标记。只有进程异常崩溃（kill -9、OOM、节点宕机）才依赖 Lease 过期
  3. TTL 设 7200s 而不是几十秒的原因：Grant 重新申请的间隔是 300s。如果 TTL 太短（比如 60s），在 Grant 间隔内 Lease 就过期了，所有 key 会被误删。7200s 留了足够的安全余量。正常工作中 key 每 30s 被心跳续约一次，远在 TTL 到期之前

五、Worker 生命周期状态机

Worker 有 5 种状态：

stateDiagram-v2
    [*] --> pending: K8s 创建 Pod
    pending --> running: sidecar register
    running --> running: heartbeat / consume / result
    running --> recovering: recover 上报
    recovering --> running: recover 完成
    running --> terminating: shutdown 信号
    terminating --> terminated: exit 上报
    terminated --> running: Autoscaler 扩容
    terminated --> [*]: K8s 回收 Pod
状态含义可接受的 Report 类型
pendingPod 刚创建，sidecar 还没注册register
running正常工作中heartbeat, consume, progress, result, shutdown
recoveringWorker 在恢复（如 ComfyUI 重启推理进程）recover（恢复后回到 running）
terminating收到 K8s SIGTERM，正在优雅关闭exit
terminated已退出，但 etcd key 还在（等 Autoscaler 扩容或 K8s 回收）—

invalidWorkerStatus 包含 terminated 和 terminating——处于这两个状态的 Worker 不会被加入 cacheKeyManager（即不参与任务分配）。

六、Sidecar 优雅关闭

sidecar 收到 K8s SIGTERM 后的关闭流程（service.Shutdown）：

sequenceDiagram
    autonumber
    participant K as K8s
    participant S as sidecar
    participant WS as worker-scheduler
    participant E as etcd

    K->>S: SIGTERM
    S->>S: cancel context → 停止接新任务
    S->>S: 等待 workerPool 关闭（最多 10 min）
    S->>WS: report(type=shutdown)
    WS->>E: UpdateWorker(status=terminating)

    S->>S: 等待所有任务完成
    S->>WS: report(type=exit)
    WS->>E: UpdateWorker(status=terminated)
    S->>S: 进程退出

两段式上报（shutdown → exit）的好处：scheduler 知道 Worker "正在关闭但还没完全关闭"，不会在 terminating 阶段给它分新任务，但已有任务可以跑完。

7.2 为什么需要 Redis 分布式锁？

虽然只有 Leader 在调度，但 Autoscaler 跑在 Leader 进程里。在 Leader 切换的瞬间，新旧 Leader 可能短暂并存。加一把 Redis 锁（TTL=180s）确保同一时刻只有一个 Autoscaler 实例在执行。

func (d *Dao) LockAutoscalerRun(ctx context.Context) bool {
    return d.redis.Lock(ctx, fmt.Sprintf(keyLockAutoscalerRun, dmfr.ENV()), 180)
}
func (d *Dao) UnlockAutoscalerRun(ctx context.Context) {
    d.redis.UnLock(ctx, fmt.Sprintf(keyLockAutoscalerRun, dmfr.ENV()))
}

7.3 扩容逻辑

func (s *Service) shouldScaleUp(queueLength int64, workers []*model.WorkerPodAttributes) bool {
    workerCount := len(workers)
    if workerCount == 0 { return true }                    // 没有 Worker → 必须扩
    if workerCount <= int(queueLength)/2 { return true }   // Worker 数 ≤ 队列长度/2 → 扩
    return false
}

扩容步长：step = ceil(queueLength / 2)，上限为 MaxWorker - 现有 Running 数。

扩容方式：找到 terminated 状态的 Worker Pod，调用 apiKube.UpdateWorker 重新激活——相当于"唤醒已关机的机器"。

7.4 缩容逻辑

func (s *Service) scaleDown(ctx context.Context, config *model.WorkerAutoscalerConfig,
        runningWorkers []*model.WorkerPodAttributes) (bool, error) {
    if len(runningWorkers) <= config.MinWorker { return false, nil }

    for _, worker := range runningWorkers {
        realtimeWorker, _ := s.GetWorker(worker.ExpandName())
        // 条件1：不在忙
        if realtimeWorker.Busy { continue }
        // 条件2：空闲超过 ScaleDownIdleTime
        if realtimeWorker.LastFinish + config.ScaleDownIdleTime > time.Now().Unix() {
            continue
        }
        readyToScaleDown = append(readyToScaleDown, worker)
    }
    // 对每个 ready Worker 调 apiKube.DeleteWorker
    ...
}

缩容条件（同时满足）：① Running 数 > MinWorker；② Worker 不在忙；③ 空闲时间超过 ScaleDownIdleTime。

7.5 冷却机制

扩缩容记录存在 Redis ZSet 中（score=时间戳），每次操作前检查 ScaleCooldown 内是否有过操作记录：

// key 格式
keyPrefixAutoscalerRecord = "autoscaler_record::{env}::{workerType}::{taskMode}::{cluster}"

// 保存记录
func (d *Dao) SaveAutoscaleRecord(ctx context.Context, config, history) {
    d.redis.ZAdd(ctx, key, history.Timestamp, jsonBody)
}

// 检查冷却
func (d *Dao) GetAutoscaleRecord(ctx context.Context, config) {
    start := now - config.ScaleCooldown
    d.redis.ZRevRangeWithScore(ctx, key, start, now)
    // 有记录 → 冷却期未过
}

7.6 安全检查

在 scaleUp/scaleDown 之前，还有一个关键的安全检查：如果有 Worker 处于 pending 或 terminating 状态（正在启动或正在关闭），本轮跳过——等状态稳定后再决策。这避免了"扩了一半的 Worker 还没启动完，又扩了一批"的雪崩。

if pendingWorkers > 0 || terminatingWorkers > 0 {
    return  // 跳过本轮
}

🛡️ 面试防守：为什么不用 K8s HPA？

  1. HPA 基于 CPU/Memory 指标，但 GPU Worker 的负载指标不是 CPU——是任务队列长度。GPU 任务可能 CPU 很闲但 GPU 满载，也可能 GPU 在等网络传输 CPU 也不高。HPA 的指标维度不匹配
  2. HPA 无法感知业务语义：它不知道"这个 Worker 空闲了多久"、"队列里有多少任务排着"、"这种 Worker 类型的最大/最小副本数是多少"。这些都是业务逻辑，不适合塞进 HPA 的 Custom Metrics
  3. 扩容对象不同：DM 的扩容是"唤醒 terminated Pod"（apiKube.UpdateWorker），缩容是"删除空闲 Pod"（apiKube.DeleteWorker）。HPA 只能控制 Deployment 的 replicas 数——Worker Pod 不一定由 Deployment 管理（可能是 StatefulSet 或自定义 operator）
  4. 多维配置：不同 WorkerType / TaskMode / Cluster 组合有不同的扩缩容策略（MinWorker、MaxWorker、ScaleDownIdleTime、ScaleCooldown），存在 Mongo 配置表里。HPA 没法做到这种粒度

八、初始化与数据恢复

Leader 启动后，在开 Watch 之前要先加载存量数据。代码在 service.New()：

func (s *Service) loadInitialData(ctx context.Context) {
    wg := sync.WaitGroup{}
    wg.Add(2)
    go func() { defer wg.Done(); s.loadWorkers(ctx) }()
    go func() { defer wg.Done(); s.loadTasks(ctx) }()
    wg.Wait()
}

func (s *Service) loadWorkers(ctx context.Context) {
    workers, _ := s.dao.GetAllWorker(ctx)  // etcd GetAll
    for _, worker := range workers {
        s.workerCache.Set(worker.Name, worker, workerCacheTTL)
        s.cacheKeyManager.WorkerAdd(worker)
        s.workerClusterMap.Incr(genWorkerClusterKey(...))
    }
}

func (s *Service) loadTasks(ctx context.Context) {
    tasks, _ := s.dao.GetAllTask(ctx)  // etcd GetAll
    for _, task := range tasks {
        s.concurrentManager.Add(task.Source, task.TaskMode,
            task.Cluster, task.GetRealUser(), 1)
    }
}

加载完后再开 Watch：go s.watchWorker(ctx) / go s.watchTask(ctx)。这个顺序确保不漏不重：

  1. 先 loadAll：从 etcd 拿到所有当前数据，建立内存状态
  2. 再 Watch：之后的增量变化通过 Watch 实时更新
  3. 不用担心 load 和 Watch 之间的间隙：etcd Watch 可以从指定的 Revision 开始，但 DM 的实现更简单——Watch 的 Put 事件会覆盖 load 的旧值，Delete 事件会清理已加载的数据，最终一致

九、面试防守

🛡️ etcd 和 Redis 在这个系统里各自承担什么角色？

  • etcd：运行时注册中心。存 Worker 在线状态和运行中 Task。选 etcd 因为：① Lease + Watch 提供自动过期和实时通知；② 强一致（linearizable read），不会出现"Worker 已死但还显示在线"
  • Redis：任务队列 + 分布式锁 + 扩缩容记录。选 Redis 因为：① ZSet/List 提供高吞吐队列语义；② 分布式锁（SET NX EX）简单可靠；③ 不需要强一致——锁偶尔失效最多多跑一次 Autoscaler

核心区别：etcd 保证"状态正确"，Redis 保证"吞吐够快"。不用一个存储硬扛所有需求。

🛡️ Lease 过期 TTL 设太短 / 太长分别有什么问题？

  • 太短（如 60s）：Grant 间隔 300s > TTL 60s → 在下次 Grant 之前 Lease 就过期了，所有绑定的 key 被删除。即使 Worker 还在正常工作，也会被误判为"已死"
  • 太长（如 24h）：Worker 异常崩溃后，key 要等 24h 才过期清理。这段时间内并发计数不会恢复（该用户的任务槽被"死锁"），新任务无法分配
  • 7200s（2h）是权衡：远大于 Grant 间隔（300s），不会误删；远小于"不可接受的故障恢复时间"，异常崩溃最多 2h 恢复。正常工作中，心跳每 30s 续约一次，TTL 永远刷新

🛡️ 如果 etcd 集群挂了会怎样？

  • Watch 中断：watchWorker/watchTask 协程检测到 channel 关闭或错误，进入 waitWithRetry 每 5s 重试
  • Worker 注册不受影响：心跳的 UpdateWorker 会失败，但 sidecar 不会因此崩溃——下次心跳重试
  • 新任务分配暂停：因为 AddTask 失败，scheduler 无法注册运行中的 task。但已在运行的 task 不受影响
  • etcd 恢复后自动恢复：Watch 重连后重新收到增量事件。但中间丢失的事件怎么办？loadInitialData 在每次 Leader 切换时会全量加载一次，所以最终一致

十、检索练习

Q1. K8s LeaseLock 的三个时间参数约束关系是什么？

  • A. LeaseDuration < RenewDeadline < RetryPeriod
  • B. RetryPeriod < RenewDeadline < LeaseDuration
  • C. 三者相等即可
  • D. RenewDeadline < RetryPeriod < LeaseDuration
B。RetryPeriod(2s) < RenewDeadline(10s) < LeaseDuration(15s)。RetryPeriod 要足够小保证切主窗口内有多次重试机会；RenewDeadline 要小于 LeaseDuration 给续约失败留出检测窗口。

Q2. UpdateWorker 使用 etcd Txn 的 Compare(ModRevision) 是为了解决什么问题？

  • A. 防止 etcd 写入超时
  • B. 防止多个来源并发更新同一个 Worker 的 ABA 问题
  • C. 加速写入性能
  • D. 实现 Leader 选举
B。Worker 状态可能被心跳上报、任务完成、shutdown 通知等多个来源更新。Txn Compare(ModRevision) 实现乐观锁：只有"我读到的版本 = 当前版本"时才写入。这跟数据库的 WHERE version = ? 是同一个思路。

Q3. 自研 Autoscaler 的扩容条件是什么？

  • A. CPU 使用率超过 80%
  • B. workerCount == 0 或 workerCount <= queueLength / 2
  • C. GPU 显存不足
  • D. 任务失败率超过 5%
B。扩容基于业务指标（队列长度 vs Worker 数量），不是基于硬件指标。workerCount == 0 → 必须扩，否则没人消费；workerCount <= queueLength / 2 → Worker 不够用。扩容步长 = ceil(queueLength / 2)，上限为 MaxWorker。

Q4. Watch 使用 WithPrevKV() 的主要原因是什么？

  • A. 提高 Watch 性能
  • B. Delete 事件的新值为空，需要旧值来获取被删除 Worker/Task 的信息
  • C. 用于实现 Leader 选举
  • D. 减少 etcd 存储空间
B。Delete 事件触发时，key 已经被删了，ev.Kv.Value 为空。只有 ev.PrevKv.Value 里才有被删除的 Worker/Task 的完整信息（podName、workerType 等），用于清理缓存和恢复并发计数。
