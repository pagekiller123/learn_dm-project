一、供应商 429 排队重试（Bullet 1）

一句话：当外部 AI 供应商返回 429 Too Many Requests 时，Worker 进入指数退避重试队列（initial=3s, max=60s, jitter ±20%），最长等待 12h，超时后触发 fallback 切换备用通道。

1.1 业务背景

DreamMaker 对接数十个外部 AI 供应商（OpenAI、Google Gemini、火山引擎等）。这些供应商有严格的 QPS 限制，高峰期频繁返回 HTTP 429。如果 Worker 直接报错给用户，用户体验极差——排了几分钟队，任务到达供应商才被拒，用户不得不手动重试。

业务需求：对用户透明地排队等待，直到供应商恢复容量，同时避免因死等单个供应商导致整体吞吐下降。

什么是指数退避重试？

指数退避 = 每次失败后，等待时间翻倍，而不是固定间隔重试：
第 1 次失败 → 等 3s  → 重试
第 2 次失败 → 等 6s  → 重试
第 3 次失败 → 等 12s → 重试
第 4 次失败 → 等 24s → 重试
第 5 次失败 → 等 48s → 重试
第 6 次失败 → 等 60s → 重试（到上限了，之后都等 60s）
为什么不用固定间隔？
假设供应商限流了，100 个 Worker 同时被 429。如果都固定 3s 后重试 → 3s 后 100 个请求又同时打过去 → 供应商刚喘一口气又被打死 → 无限循环。指数退避让请求越来越稀疏，给供应商恢复的时间。

为什么还要加 jitter（随机抖动）？
即使用了指数退避，100 个 Worker 如果在同一时刻收到 429，它们计算出来的等待时间是一样的（都是 3s → 6s → 12s...），还是会在同一时刻重试。加上 ±20% 随机偏移后，每个 Worker 的重试时间被打散到一个范围内（比如 2.4s~3.6s），不会集中在同一秒涌入。

核心退避算法（Go 伪代码）：

func calcBackoff(attempt int) time.Duration {
    base := initialInterval * math.Pow(multiplier, float64(attempt))
    if base > maxInterval {
        base = maxInterval
    }
    // jitter: ±20% 随机偏移，防止惊群
    jitter := base * 0.2 * (2*rand.Float64() - 1)
    return time.Duration(base + jitter)
}

// initialInterval = 3s, multiplier = 2.0, maxInterval = 60s
// attempt 0: ~3s, 1: ~6s, 2: ~12s, 3: ~24s, 4: ~48s, 5+: ~60s

白名单控制——仅对特定模型启用重试：

func ShouldRetry(model string) bool {
    whitelist := []string{

        if model == m { return true }
    }

}

1.5 Fallback 备用通道切换

指数退避不是无限等的——有一个 maxWait=12h 的总上限。如果 12 小时内供应商一直返回 429，重试循环退出，进入 fallback 流程：

  1. 重试循环退出，返回 retryable error 给上层 executor
  2. executor 查询当前模型的 fallback 通道配置（存在模型配置里），比如 pt-art1 的 fallback 是 pt-art3-openai
  3. 切换到备用供应商，重新发起调用
  4. 如果所有通道都不可用 → 返回用户友好的排队提示（"当前服务繁忙，请稍后重试"），不是直接报 500 错误

设计思路：指数退避解决"短暂限流"（几秒到几分钟），fallback 解决"长时间不可用"（供应商大面积故障）。两层兜底，对用户透明。

面试防守

  1. Q: 为什么不把 429 的任务重新放回 Redis 队列？
    A: 重入队会打乱任务顺序，且 Worker 已经持有执行上下文（模型参数、用户信息）。本地重试避免了序列化/反序列化开销和状态恢复问题。另外重入队后其他 Worker 拉到同样会被 429，不能解决根本问题。
  2. Q: jitter 为什么是 ±20% 而不是更大？
    A: ±20% 在实测中足以打散同一批到达的请求。更大的 jitter 会导致部分请求等待时间过短（失去退避效果）或过长（用户体验下降）。AWS 文档推荐 Full Jitter（0~backoff），我们选 ±20% 是因为供应商恢复窗口相对稳定，不需要太激进的分散。
  3. Q: 12h 最大等待时间怎么确定的？
    A: 根据供应商 SLA（如 OpenAI 声明 99.9% 可用性，最长连续故障约 8.7h/年），加上业务场景（pt-art 是离线出图，用户可容忍较长等待）。在线实时任务不走这条路径。
  4. Q: fallback 切换备用通道具体怎么做的？
    A: 超过 maxWait 后返回 retryable error，上层 executor 根据模型配置查询 fallback 通道列表（如 pt-art1 的 fallback 是 pt-art3-openai），重新发起调用。如果所有通道都 429，最终返回用户友好的排队提示。
  5. Q: 如果 Worker 在重试等待中被杀（OOM / 重启），任务怎么办？
    A: Worker-sidecar 心跳机制保底。Worker 停止上报心跳后，scheduler 会在超时（默认 2min）后将任务重新标记为 pending，另一个 Worker 会重新拉取。任务本身是幂等的（基于 taskId 去重）。

  • B. 24s
  • C. 48s
  • D. 60s
B. 3s * 2^3 = 24s。attempt 从 0 开始计数，attempt=3 是第 4 次重试。
Q2: 为什么选择 Worker 本地重试而不是任务重入队？
1) 重入队打乱顺序；2) Worker 已持有上下文，重入队需要序列化状态；3) 其他 Worker 拉到同样被 429；4) 本地重试避免了调度开销。

二、图片超限自动压缩兜底（Bullet 2）

一句话：在 app-gateway 校验阶段插入图片压缩中间件，超限图片自动压缩到供应商要求范围内，通过 MongoDB 配置驱动实现零代码扩展。

2.1 业务背景

GPT-Image-2 等模型要求输入图片 <4MB。用户上传 8MB 的高清照片，如果直接拒绝，体验极差（"我的图片明明没问题，为什么不能用？"）。产品需求：平台自动处理，用户无感。

第一版（!976）硬编码了压缩逻辑；第二版（!988, 37 files）做了通用化改造：压缩规则从 MongoDB 读取，新模型只需添加一条 DB 记录即可生效。

2.2 技术方案

flowchart LR
    A[用户上传图片] --> B{字节 > MaxSize?}
    B -- No --> E[继续走正常校验]
    B -- Yes --> C[runImageCompress]
    C --> D{压缩后仍超限?}
    D -- No --> E
    D -- Yes --> F[返回错误: 图片过大]

插入时机：在 app-gateway 的校验阶段，DB Rules 校验之后、RegisterValidator 之前。

压缩规则从 MongoDB 读取，每条记录对应一个模型的压缩配置：

配置字段含义示例
app_code哪个模型需要压缩"gpt-image-2"
field_names需要检查压缩的请求参数字段["image", "style_images"]
is_slice字段是否为数组（多张图逐个压缩）true（style_images 是数组）
max_long_side最大长边像素4096
min_short_side最小短边像素256
max_file_size文件大小上限（字节）4194304（4MB）
alpha_mode透明通道处理方式"inherit"

压缩流程（runImageCompress）：

  1. 根据 app_code 从 MongoDB 读取该模型的压缩配置
  2. 遍历 field_names 里的每个字段，取出用户上传的图片
  3. 如果 is_slice=true（字段是数组，如多张参考图），逐张检查和压缩；否则当作单张处理
  4. 对每张图片：先检查文件大小是否超过 max_file_size，超了就按 max_long_side / min_short_side 缩放分辨率，再降低压缩质量（如 quality=85）直到达标
  5. 压缩后仍然超限（比如原图是 200MB 的 RAW 文件）→ 返回错误"图片过大"

零代码扩展：新接一个模型需要图片压缩？在 MongoDB 里加一条配置记录就行，不用改代码、不用发版。

面试防守

  1. Q: AlphaMode inherit vs preserve 有什么区别？
    A: inherit 表示跟随原图的 alpha 通道设置（有透明度则保留，没有则不添加）；preserve 强制保留 alpha 通道（即使压缩后格式变化）。JPEG 不支持 alpha，所以 preserve 模式下必须转 PNG/WebP。
  2. Q: IsSlice 为什么需要单独处理？
    A: 有些模型接受多张参考图（如 style_images 数组），需要对每张图分别检查和压缩。如果把整个数组当一个值处理，无法区分哪张超限。
  3. Q: 压缩会不会影响生成质量？
    A: Options 中的 MaxLongSide/MinShortSide 保证分辨率在供应商推荐范围内。实测 4MB 限制下大部分超限图只需 quality 85 就能达标，肉眼无法区分。如果压缩后仍超限（如 200MB 的 RAW 文件），才返回错误。
  4. Q: 这个中间件的性能开销？
    A: 平均压缩耗时 50-200ms（取决于图片大小），相比 AI 生成的 30s-5min，可忽略不计。配置查询走本地缓存（TTL 5min），不增加 DB 压力。

三、多集群 Worker 发现与任务路由（Bullet 3）

面试价值：多集群调度是后端面试高频题 — 涉及服务发现、负载均衡、集群路由、流量迁移。能讲清楚"为什么要多集群、Pod 怎么发现、流量怎么切"，比讲"接了一个新 API"含金量高一个量级。

一句话：实现 Worker 执行层的多 Kubernetes 集群 Pod 发现与调度，通过域名路由和前置参数校验将任务分发到不同集群，解决单集群 GPU 资源瓶颈。

3.1 业务背景

DreamMaker 的 AI 任务（图像生成、3D 建模、视频渲染）依赖 GPU 资源。随着用户和模型增长，单个 K8s 集群的 GPU 不够用了：

  • 资源瓶颈：高峰期单集群 GPU 全部占满，新任务排队时间长
  • 地域需求：部分供应商 API 在特定机房响应更快
  • 容灾隔离：单集群故障不应影响全部任务

需要让 Worker 可以运行在多个 K8s 集群上，scheduler 能跨集群发现和调度任务。

面试防守

  1. Q: 为什么不用 Service Mesh（如 Istio）做跨集群路由？
    A: 我们的场景不需要 Mesh 那么重的方案。任务是异步入队的（不是同步 RPC），gateway 只需要知道往哪个集群的队列发，域名切换就够了。引入 Istio 增加运维复杂度，收益不大。
  2. Q: 两个集群的 scheduler 怎么协调？会不会出现任务被两边同时消费？
    A: 不会。每个集群有独立的 Redis 队列和独立的 worker-scheduler（各自做 Leader 选举）。gateway 在入队时就决定了任务进哪个集群的队列，不存在跨集群竞争。
  3. Q: 一个集群挂了，任务怎么转移到另一个？
    A: 当前方案是手动切换 — 运维修改域名映射，gateway 后续任务走另一个集群。已入队未执行的任务需要人工迁移。未来可以做自动 failover：监控集群健康 → 自动修改路由。
  4. Q: 怎么决定任务发到哪个集群？
    A: 按模型类型路由。部分 GPU 密集型模型（如 transformer v2）固定走有大显存 GPU 的集群；通用模型走默认集群。路由规则在配置里，修改不需要改代码。

Q1: 多集群方案中，每个集群的 worker-scheduler 是独立还是共享 Leader 选举？
独立。每个集群各自做 K8s LeaseLock Leader 选举，避免跨集群网络延迟影响调度，也实现故障隔离。
Q2: 新集群接入需要改代码吗？
不需要。只需在配置中添加域名映射和集群能力声明（支持哪些模型类型），gateway 根据配置自动路由。

四、统一限流与 API Key 管理（Bullet 4）

一句话：实现 App 级 + Model 级两层滑动窗口限流，配合 API Key 全生命周期管理（创建/轮转/禁用/RBAC 权限），为平台提供细粒度的访问控制。

4.1 业务背景

DreamMaker 开放 API 给内部各工作室使用，需要：

  • 限流：防止单个用户/团队消耗全部供应商配额
  • API Key 管理：支持 Key 轮转（安全合规）、禁用（泄露应急）、权限区分（不同 Key 能调用的 App/Model 不同）
  • 多层级：平台级兜底 + 用户级精细控制

4.2 技术方案 — 限流

两层限流 Key 设计：

层级Redis Key 格式含义示例
App 级app_limit::{user}::{env}::{app}某用户在某个 App 上的请求数app_limit::zhangsan::prod::gpt-image-2
Model 级app_limit::{user}::{env}::{model}某用户在某个模型上的请求数app_limit::zhangsan::prod::gemini-3-pro
Default 兜底app_limit::default::{env}::{app}未配置个性化限额的用户走这条规则app_limit::default::prod::gpt-image-2

滑动窗口限流流程（每次请求到达时，通过 Redis Pipeline 原子执行）：

  1. 清理过期记录：ZRemRangeByScore 删除窗口外的旧请求记录（比如窗口=60s，删掉 60s 之前的）
  2. 统计当前数量：ZCard 数窗口内还有多少条记录
  3. 判断是否超限：如果 count ≥ limit → 返回 429；否则继续
  4. 记录本次请求：ZAdd 把当前时间戳写入 ZSet（score=时间戳, member=时间戳）
  5. 设 Key 过期：Expire 设为窗口时间+1分钟，兜底清理不再活跃的 Key

4.3 技术方案 — API Key 生命周期

API Key 的状态机：

状态含义可转为
active正常使用中disabled / rotated
disabled已禁用（泄露/安全事件）active（确认安全后可重新启用）
rotated已被轮转替代（旧 Key）不可再变更

API Key 的数据结构：

字段含义说明
key_idKey 的唯一标识用于管理操作（禁用/轮转）
key_hashKey 的 Hash 值不存明文，只存 hash，泄露 DB 也不暴露 Key
app_codes可访问的 App 列表RBAC：不同 Key 能调的 App 不同
model_names可访问的 Model 列表更细粒度的权限控制
status当前状态active / disabled / rotated
created_by创建者权限校验：只有创建者或管理员能操作这个 Key

关键操作：

  1. 禁用 Key（PUT /api-keys/:id/status）：
    • 权限校验：必须是用户组管理员 OR Key 创建者
    • 状态流转校验：只有合法的转换才允许（如 active → disabled）
    • 生效方式：Authorization 中间件每次请求都查 Key 状态，disabled 的 Key 下一个请求就会被拦截
  2. 轮转 Key（Rotate）：
    • 生成一个新 Key，旧 Key 标记为 rotated
    • disabled Key 不能 rotate——防止安全事件中误操作产生新的有效 Key

4.5 设计决策

决策点选择原因

Key 存储Hash 存储，不存明文安全合规；泄露 DB 不暴露 Key

面试防守

  1. Q: 滑动窗口 vs 令牌桶 vs 漏桶，怎么选的？
    A: 滑动窗口：实现简单（Redis ZSet 一条命令），精度够用（毫秒级），内存可控（窗口外自动清理）。令牌桶适合需要"突发容忍"的场景（如 API Gateway），但我们的供应商有硬性 QPS 限制，不需要 burst。漏桶适合"匀速输出"，但我们的请求本身不需要匀速。
  2. Q: default 用户兜底是怎么工作的？
    A: 如果某用户没有在限流配置中指定个性化限额，系统会 fallback 到 app_limit::default::{env}::{app} 的规则。这样新用户无需配置就有基本保护，管理员只需为有特殊需求的用户添加规则。
  3. Q: API Key 泄露了怎么处理？
    A: 立即 disable（PUT /api-keys/:id/status body={status:"disabled"}），Authorization 层在下一次请求时就会拦截。然后调查泄露范围、通知用户、必要时 rotate 其他 Key。disabled Key 不能 rotate 是刻意的安全设计。
  4. Q: 限流的原子性怎么保证？并发请求同时到达怎么办？
    A: 使用 Redis Pipeline（MULTI/EXEC）保证 ZRemRangeByScore + ZCard + ZAdd 三个操作的原子性。Redis 单线程特性保证同一 Key 的并发请求串行执行。

简历关联

推荐写法：设计并实现 App 级 + Model 级两层滑动窗口限流（Redis ZSet），配合 API Key 全生命周期管理（创建/轮转/禁用/RBAC 鉴权），支撑平台 N 个工作室的细粒度访问控制。

关键词：Rate Limiting、Sliding Window、API Key Lifecycle、RBAC、Redis Pipeline Atomicity

Q1: 为什么 disabled 的 Key 不允许 rotate？
disabled 通常意味着 Key 可能已泄露或存在安全问题。如果允许 rotate，会生成一个新的有效 Key，相当于在安全事件未调查清楚时重新开放了访问权限。正确流程是：先调查 -> 确认安全 -> 启用 -> 再 rotate。
Q2: 滑动窗口限流为什么用 Redis ZSet 而不是简单的计数器？
简单计数器是固定窗口，有临界点突刺问题（窗口交界处可能放过 2x 的请求）。ZSet 以时间戳为 score，可以精确移除窗口外的记录，实现真正的滑动窗口，限流更平滑。

五、模拟面试：完整追问链

说明：以下模拟一场 15 轮技术面试，面试官会在四个 Bullet 之间跳转追问，考察你对系统的整体理解和细节把握。每个回答控制在 30-60 秒口述长度。

Round 1 — 开场

面试官：你在 DreamMaker 项目中主要负责哪些模块？

参考回答：我主要负责 Scheduler 微服务集群中的三块工作：一是独立完成音频和 3D 新模型的全链路接入（Seed-TTS、Meshy），从 App 注册到 Worker 执行到产物处理；二是供应商限流场景下的重试和降级机制；三是参与了统一限流和 API Key 管理的开发。整体架构是五层的分布式任务调度系统，基于 Go + Redis + MongoDB。

Round 2 — 架构理解

面试官：你说的"五层架构"能画出来讲讲吗？

参考回答：从上到下：1) 外部请求层（api-server 对外、api-outer 对内）；2) 业务服务层（app-gateway 做参数校验和入队）；3) 基础调度层（worker-scheduler 做 Leader 选举和任务分配）；4) Worker 执行层（worker-sidecar + 10 类 Worker）；5) 外部供应商层。数据存储用 Redis ZSet 做任务队列、MongoDB 做记录持久化、etcd 做 Worker 注册和服务发现。

Round 3 — 深入 Bullet 3

面试官：你说独立完成了 Seed-TTS 的接入，具体改了哪些文件？

参考回答：主要是：1) MongoDB 配置脚本——定义 App 元数据和参数 Schema；2) executor 文件——实现音频任务的执行逻辑（构造请求、调用供应商、轮询结果）；3) supplier client——封装 Seed-TTS 的 HTTP API；4) 产物处理——音频文件下载和 CDN 上传。总共约 18 个文件改动，核心创造性工作在 executor 和 supplier 层。

Round 4 — 追问设计

面试官：为什么音频和 3D 不复用图片的 Worker？

参考回答：三个原因：1) 资源隔离——3D 模型生成极耗内存和 CPU，放一起会互相影响；2) 超时策略完全不同——图片 5min、音频 10min、3D 90min；3) 依赖不同——3D Worker 需要特定的格式转换工具链（如 glTF 处理库）。独立 Worker 类型让每类任务可以独立扩缩容。

Round 5 — 踩坑

面试官：接入过程中遇到最难解决的问题是什么？

参考回答：Meshy 3D 模型的超时问题。原有系统默认 60min 超时，但 Meshy 的"AI Texture + Smart Topology"组合任务实测需要 80min。简单加大超时不行——真正卡死的任务会长时间占用 Worker 资源。最终方案是：App 级可配超时 + Worker 轮询时持续上报"polling_supplier"心跳状态，scheduler 只有在心跳断了才判定死亡，而不是靠任务总时长。

Round 6 — 跳到 Bullet 1

面试官：你提到供应商 429 重试，如果供应商连续 12 小时都返回 429 怎么办？

参考回答：超过 12h 最大等待后，重试循环退出，返回 retryable error 给上层。上层 executor 查询 fallback 通道配置——比如 pt-art1 的 fallback 是 pt-art3-openai，尝试切换供应商。如果所有通道都不可用，最终返回用户友好的排队提示（"当前服务繁忙，请稍后重试"），不是直接报错。

Round 7 — 算法细节

面试官：指数退避加 jitter 具体是怎么实现的？为什么需要 jitter？

参考回答：backoff = min(initial * 2^attempt, maxInterval)，然后加上 ±20% 的随机偏移。jitter 的目的是防止惊群效应——如果 100 个 Worker 同时收到 429，不加 jitter 它们会在完全相同的时刻重试，再次打爆供应商。加了 jitter 后请求被分散到一个时间窗内。

Round 8 — 跳到 Bullet 4

面试官：限流你用的什么算法？为什么不用令牌桶？

参考回答：用的 Redis ZSet 实现的滑动窗口。不用令牌桶的原因：我们的供应商有硬性 QPS 上限，不需要"突发容忍"（burst）；滑动窗口实现更简单，Redis ZSet 天然支持按 score 范围删除和计数，一个 Pipeline 搞定；内存也更可控，因为窗口外的记录会被主动清理。

Round 9 — 安全追问

面试官：API Key 泄露了你们怎么处理？

参考回答：第一步 disable（PUT /api-keys/:id/status），Authorization 中间件下一次请求就会拦截这个 Key。第二步调查泄露范围——看日志确认哪些请求用了这个 Key。第三步通知用户，必要时 rotate 其他 Key。注意：disabled Key 不能 rotate，这是刻意的安全设计，防止在安全事件未调查清楚时误操作产生新的有效 Key。

Round 10 — 跳回 Bullet 2

面试官：图片压缩中间件的性能开销你评估过吗？

参考回答：评估过。平均压缩耗时 50-200ms，相比 AI 生成的 30s-5min 可忽略。配置查询走本地缓存（TTL 5min），不增加 MongoDB 压力。压缩只在图片超限时触发（大约 15-20% 的请求），不是所有请求都走。对用户来说感知不到延迟。

Round 11 — 系统设计延伸

面试官：如果让你重新设计这个调度系统，有什么会改的？

参考回答：两个方向：1) 任务优先级——目前 Redis ZSet 按时间排序（FIFO），不支持优先级。可以引入多队列或在 score 中编码优先级权重；2) 自动扩缩容——目前 Worker 数量手动配置，可以结合队列深度做 HPA，3D 队列深了就自动拉起更多 3D Worker。

Round 12 — 工程实践

面试官：你怎么保证接入新模型不影响现有模型的稳定性？

参考回答：三层保证：1) 独立 Worker 类型——新模型的 Worker 和图片 Worker 完全隔离，不竞争资源；2) 灰度发布——新能力先只对内部用户可见，观察 1-2 天再全量开放；3) 配置驱动——新模型的接入不改已有代码，只新增 executor 和 MongoDB 配置，不可能影响已有逻辑。

Round 13 — 数据一致性

面试官：任务状态在 Redis 和 MongoDB 之间怎么保证一致？

参考回答：Redis 是任务队列（热数据），MongoDB 是持久化记录。流程是：任务创建时同时写 Redis 队列和 MongoDB（status=pending）；Worker 完成后更新 MongoDB（status=completed）并从 Redis 移除。如果 Worker 崩溃，Redis 中的任务会被 scheduler 超时重新分配，MongoDB 状态不变（还是 pending）。最终一致性，不追求强一致。

Round 14 — 幂等性

面试官：你提到任务是幂等的，怎么实现的？

参考回答：每个任务有唯一的 taskId（创建时生成）。Worker 执行前先检查 MongoDB 中该 taskId 的状态——如果已经是 completed/failed，直接返回，不重复执行。供应商侧也支持幂等：Seed-TTS 和 Meshy 都是"创建 job → 轮询结果"模式，重复创建同一 job 不会产生副作用（返回已有的 jobId）。

Round 15 — 收尾

面试官：这个项目中你学到最重要的一件事是什么？

参考回答：分布式系统的核心不是"正常路径怎么走"，而是"异常路径怎么处理"。429 重试、超时兜底、Worker 崩溃恢复、Key 泄露应急——这些异常场景的代码量远超正常流程。好的系统设计是让异常处理变成声明式配置（如重试参数、超时配置、fallback 通道列表），而不是散落在业务逻辑里的 if-else。
