## P01 — 封面（~30s）

各位好，今天我来分享一下 DreamMaker 平台的技术架构。

DreamMaker 是我们内部的 AI 美术平台，把市面上的 AI 模型——文生图、图生视频、3D 生成、音频等——统一封装成内部服务，让美术同学在一个桌面应用里就能完成所有 AI 生成工作。

我会从整体部署拓扑开始，然后依次讲前端、本地 Agent 服务、云端调度三个模块。

## P02 — 部署拓扑：三个物理位置（~2min）

我先从部署拓扑讲起，因为这个系统比较特殊——它运行在三个不同的物理位置上。

第一个位置是**用户桌面上的 Electron 客户端**，这是前端 UI，用户在上面操作画布、输入对话。

第二个位置也在用户电脑上，但它是一个独立的后端进程——Python 写的 dm-monet-agent 服务。它和 Electron 客户端打包在一起，启动时自动拉起。这个服务负责运行 AI Agent 的核心逻辑：基于 LangGraph 的状态机、LLM 调用编排、上下文管理，以及通过 SSE 向前端推送实时事件。

第三个位置是**云端服务器**，Go 写的 dreammaker-scheduler 微服务集群——做任务入队、调度、执行，最终调用外部 AI 供应商完成生成。

**[指图]** 这三者之间的通信方式不一样：
- 前端和本地 Python 服务之间是 **SSE 长连接**——因为 LLM 逐 token 输出，需要流式通道。
- 本地服务到云端分**两条链路**：一条调 AIGW 做 LLM 推理，走 OpenAI 兼容的流式接口，token 从 AIGW 一路流到前端，是**全链路流式**的；另一条调 DM Scheduler 做图片/视频/3D 生成，走标准 HTTP REST——POST 提交、GET 轮询——因为生成任务是异步批处理，轮询最稳定。

## P03 — 模块一：Electron 前端 UI 形态（~1.5min）

前端是一个 Electron 桌面应用，React + TypeScript，界面分两块。

**[指图]** 左边是**画布区域**，基于 React Flow，类似一个无限白板。用户在上面创建各种节点——图像生成、视频生成、3D 模型等等。节点之间可以连线表示引用关系，比如从一张图拉线到视频节点，意思是"用这张图作输入去生成视频"。

右边是 **Agent 聊天面板**，用户可以用自然语言和 AI Agent 对话。Agent 能感知画布上有什么节点，然后自动调用工具操作画布。比如用户说"帮我生成一张赛博朋克风格的图"，Agent 会自己创建节点、填参数、提交任务。

所以用户有两条操作路径：**手动操作画布**，直接创建节点填参数点生成；或者**通过 Agent 对话**，自然语言驱动，Agent 自动操作。后者走 SSE 流式协议。

## P04 — 画布数据存储与前后端通信（~1.5min）

一个容易误解的点：**画布数据不在用户本地，而是在云端**。画布后端服务 dm-tapnow-backend 部署在内网，前端操作画布直接调画布后端 API 写到云端数据库。

本地 Agent 服务上**不存任何画布数据**，它是纯计算节点——跑 Agent 逻辑、调 LLM、推 SSE 事件。本地唯一持久化的是 SQLite 里的对话状态 checkpoint。

Agent 在画布上创建节点后，会推一个 `canvas.render` 事件让前端全量刷新——因为 Agent 是通过 HTTP 调画布后端 API 创建节点的，前端需要重新从云端拉最新数据。

**前端通信模型**也很简单：前端发 `POST /chat`，后端返回一条 SSE 长连接持续推事件。中间如果需要审批，前端通过另一个 `POST /chat/{session_id}/resume` 告诉后端用户的决策。SSE 是半双工的——服务端推、客户端收，前端发消息走独立 HTTP 请求。

## P05 — 模块二：Agent 引擎 DeepAgents + LangGraph（~2min）

接下来进入本地 Agent 服务的内部结构。它是 Agent 的大脑，前端发来的 `POST /chat` 由它全权处理。

Agent 核心循环基于 **ReAct 模式**：LLM 推理 → 决定是否调工具 → 执行工具 → 观察结果 → 继续推理。**[指图]** 这个循环由 DeepAgents 框架驱动，底层是 LangGraph 的 StateGraph 状态机——LLM 节点和 Tool 节点是两个状态，条件路由根据 LLM 输出决定走哪条边。

几个关键设计决策：
- LLM 调用通过 `ChatAIGW` 类（继承 LangChain 的 `ChatOpenAI`）调 AIGW 网关，默认流式输出。
- 状态持久化用 `AsyncSqliteSaver`——异步版的 Checkpointer，因为整个服务是 asyncio 单线程事件循环，同步版会阻塞。选 SQLite 是因为单用户本地场景，不需要分布式存储。
- `recursion_limit` 设成 9999，实质不限制，因为 Agent 有 HITL 审批和 token 预算两道安全阀。

## P06 — 事件循环与协程调度（~2min）

理解这个服务的运行模型，要先搞清楚事件循环怎么调度。

服务用 FastAPI + uvicorn 运行，底层是 **asyncio 单线程事件循环**。只有一个线程、一个事件循环，所有请求都是协程。

虽然是单用户服务，但用户可以开多个聊天会话。会话 A 在流式回复时，用户切到会话 B 又发消息——事件循环里就同时跑着两个 `/chat` 协程。不过同一个 session 不会并发，入口第一步就是取消同 session 旧请求。

**[指图]** 这是一次 `/chat` 的协程调用链。每个 `await` 是协程挂起点，当前协程暂停，控制权还给事件循环。比如会话 A 在等 AIGW 返回 token 时，事件循环发现会话 B 的 HTTP 响应到了，就切去跑 B。这不是并行——同一时刻只有一个协程在跑——但因为大部分时间在等 I/O，宏观上看起来像并发。

所以关键原则是：**任何同步阻塞调用都会冻住整个服务**。所有 I/O 都用异步版本——httpx 代替 requests，asyncio.sleep 代替 time.sleep，LLM 调用用 async 方法。

**[翻页]**

## P07 — ContextVar：跨框架传递画布数据（~1.5min）

接下来讲画布数据怎么在深层调用链中传递。

`/chat` 的调用链很深：routes → DeepAgentStreamAdapter → LangGraph 状态机 → CanvasAwareChatAIGW → inject_canvas_overview。画布数据需要在最深层使用，但中间隔着 LangGraph 框架代码——改不了框架的函数签名。

解决方案是 Python 标准库的 **ContextVar**——协程局部变量。变量定义在模块级，看起来像全局变量，但值的存储是 per-Task 的，每个 asyncio Task 有自己独立的一份。

**[指图]** 做法很简洁：入口写入 ContextVar，深层直接读取，不改中间任何一层的签名。这带来两个价值：**免传参**，深层代码直接 get；**请求内缓存**，入口拉一次画布数据，同一请求内多次 LLM 调用和工具调用复用，避免重复 HTTP。

**[翻页]**

## P08 — Message/Block 双层模型与 SSE 事件翻译（~1.5min）

Agent 一次回复里可能同时包含文本、工具调用、图片等多种内容。如果用扁平的 message 字符串承载，前端解析很痛苦。所以设计了 **Message 和 Block 两层结构**：Message 是一轮回复的容器，Block 是其中的内容片段，每个 Block 有独立的 type。目前支持七种 Block：TextBlock、ThinkingBlock、ToolUseBlock、ImageBlock、FileBlock、NodeBlock、SkillBlock。

SSE 事件和 Block 生命周期对应：`block.created` 创建容器，`block.delta` 增量追加（打字机效果），`block.updated` 更新完整状态。一个 Message 里多个 Block 交替推送，整个过程在同一条 SSE 流中交织。

**[指图]** LangGraph 内部事件是框架私有的，前端无法直接消费。**DeepAgentStreamAdapter** 负责翻译——把 `on_chat_model_stream`、`on_tool_start` 等内部事件映射成前端约定的 SSE 协议。这层翻译的价值是**框架解耦**：未来换掉 LangGraph，只需要写新的 StreamAdapter，前端协议不用改。

**[翻页]**

## P09 — 分层上下文感知（~1min）

Agent 不是纯聊天机器人，它需要知道画布上有什么。上下文注入分三层：

第一层，**画布概览**：每次请求进来拉画布详情，按节点规模分 5 级渐进渲染成 Markdown 摘要——节点少的时候输出全量详情，节点多了只输出统计信息。通过 `CanvasAwareChatAIGW` 子类重写注入到每次 LLM 调用前。LLM 能看到画布全貌，但不会塞满上下文。

第二层，**按需查询**：Agent 通过工具按需查询某个节点的详细信息——只在需要时才调，避免无关信息占 token。

第三层，**上下文溢出自动压缩**：当上游 LLM 返回上下文超长错误时，`ChatAIGW` 将其转为 `ContextOverflowError`，DeepAgent 框架内置的 `SummarizationMiddleware` 捕获后自动调 LLM 压缩历史并重试。SSE 层过滤掉压缩过程的输出，用户无感知。整个机制是被动触发的，不是主动 Token 预检。

## P10 — HITL 人机审批流程（~2min）

Agent 调工具时，有些操作需要用户确认。权限配置分两层：工具级静态配置定义哪些操作需要审批，比如执行命令、写文件；请求级权限模式决定是 ASK 还是 FULL_ACCESS。

当工具命中审批配置时，完整流程是：

**第一步**，中断——LangGraph 抛 GraphInterrupt 异常中断状态机，自动把当前 state 持久化到 SQLite。注意这不是线程挂起，是异常驱动的控制流。

**第二步**，推送审批事件——构造 `interaction.request` SSE 事件推给前端，包含操作名、参数、可选项。

**第三步**，等待——创建 asyncio.Event，await 等待，超时 300 秒。**SSE 连接不断开**，前端保持长连接。

**第四步**，恢复——用户选择后前端调 resume 接口，唤醒协程，LangGraph 从 checkpoint 恢复状态机继续执行。这里有个要求：`interrupt()` 之前的代码必须是**幂等的**，因为恢复时会重新执行。

## P11 — 任务提交与轮询（~1min）

Agent 决定执行生成任务时，通过 DmProvider 向云端提交：POST 提交拿 task_id，然后以固定间隔轮询状态——图像 5 秒、3D 10 秒、视频 30 秒。轮询期间前端看到的是工具调用卡片的"执行中"状态。

任务成功后拿结果，结果作为工具返回值被 LangGraph 捕获，翻译成 `block.updated` 推给前端——前端此时才看到完成的结果。

注意轮询对象是云端 DM Scheduler，不是 AIGW。AIGW 只负责 LLM 推理的流式调用。

这就引出了模块三——云端调度服务。

## P12 — 模块三：Scheduler 架构概览与任务全链路（~2min）

生成任务到达云端后，由 Go 写的 dreammaker-scheduler 微服务集群接管。

**[指图]** 四个核心组件：app-gateway 做任务入口和参数校验，worker-scheduler 做任务分配，worker-sidecar 负责执行，AIGW 供应商网关对接外部 AI 供应商。

一个任务的完整链路：本地 Agent POST 提交到 gateway → gateway 参数校验后 ZADD 写入 Redis 优先级队列 + MongoDB 写一条 queued 记录 → worker-scheduler 消费队列、分配给 Worker → sidecar 调供应商执行生成 → 完成后 HTTP Report 回 scheduler → scheduler 写 MongoDB + 推 Kafka → 本地 Agent 轮询拿到结果。

**[翻页]**

## P13 — 优先级队列调度：加权轮询 + 无锁抢占（~2.5min）

调度核心是 Redis ZSet 优先级队列。不同优先级对应不同的 Redis key，队列隔离。score 是毫秒时间戳，同优先级内先进先出。

**加权轮询解决饥饿问题**：纯优先级调度高负载时低优先级会完全饿死。我们为每个优先级维护配额计数器，每次调度找第一个配额大于 0 的优先级，用完后全部重置。比如高优先级 weight=5、低优先级 weight=3，一轮 8 次调度中 5 次给高优先级、3 次给低优先级。降序兜底保证不空跑。

**无锁乐观抢占**的做法：消费者 ZRange 一次取 256 个候选，遍历时检查用户并发，对无冲突的执行 ZREM。Redis 单线程保证只有一个 ZREM 成功，成功者获得任务所有权。这比分布式锁简单高效得多——ZREM 天然具有"谁删成功谁拥有"的语义，是一种乐观并发控制。

为什么不用 Lua 脚本合并 ZRange+ZREM？因为拿到候选后还要检查用户并发，这个业务判断在 Redis Lua 里完成不了。而且批量 256 候选足够高效，空竞争率实测很低。

**[翻页]**

## P14 — 用户并发管控：etcd Watch + 内存原子计数器（~1.5min）

每个用户同时能跑的任务数需要限制。实现方式是 ConcurrentManager——纯内存的原子计数器，用 `go.uber.org/atomic` 的 Int64，关键操作是 CAS 循环保证线程安全。

计数器由 **etcd Watch 驱动**：任务注册到 etcd 时 +1，完成或 Worker 崩溃导致 key 删除时 -1。消费时检查计数器，该用户有任务在跑就暂时跳过。

**多 Pod 一致性**：每个 scheduler Pod 有独立的 ConcurrentManager，靠 etcd Watch 同步——所有 Pod Watch 同一个前缀，一个 Pod 写了 etcd，其他 Pod 都收到事件各自更新。有毫秒级延迟，但对并发限制场景够用。

## P15 — Worker 注册发现与心跳（~1.5min）

Worker 的注册发现也基于 etcd。scheduler 启动时创建 TTL=7200s 的 Lease，每 5 分钟 re-Grant 刷新。Sidecar 启动时 HTTP 注册，scheduler 把 Worker 信息 Put 到 etcd 绑定 Lease。之后 sidecar 每 30 秒心跳，scheduler re-PUT 保持信息新鲜。

Worker 宕机时心跳停止，Lease 过期后 etcd 自动删除 key。scheduler Watch 到 DELETE 事件后做三个清理：从调度缓存移除、从路由表清理、递减集群计数器。后续任务就不会再分配给下线节点。

**[翻页]**

## P16 — GPU Worker 弹性扩缩容（~2min）

DM 的任务分两类：调供应商 API 的跑 CPU Worker，K8s HPA 就够了；开源部署的需要 GPU 推理。GPU 满载时 CPU 可能很闲，HPA 会误判，所以我们自定义了 Autoscaler。

核心指标是**任务队列积压深度**，每 30 秒检查。扩容条件是 Worker 数不超过队列长度的一半，且有已 terminated 的 Pod 可复用——扩容方式是唤醒已终止 Pod，不是创新。缩容条件是空闲超阈值且大于最小副本数。

几个防护机制：冷却机制防频繁扩缩；安全检查跳过 pending/terminating 状态；基于 Redis SetNX 的互斥锁保证多实例只有一个执行扩缩容——这是简化版的锁，不是 Redlock，固定 180 秒 TTL。

**[翻页]**

## P17 — 容错降级：三层重试与供应商切换（~2.5min）

Sidecar 调供应商的容错分三层。

**第一层**，`executeWithRetry`——同一供应商内的快速重试。最多 3 次尝试（含首次调用），指数退避 1 秒、2 秒，最后一次失败不再 sleep 直接返回。匹配网络超时、连接拒绝、TCP 错误，以及 502+ 且 body 含超时特征的网关错误。429 限流不在这里处理。

**第二层**，queue-retry——专门针对 429 限流。白名单 PT 模型返回 429 时进入长退避循环，3 秒起步、上限 60 秒、倍数 2.0、±20% 抖动避免惊群，最长可等 12 小时。超时后触发外层 fallback。

**第三层**，Fallback chain——供应商之间的线性切换。主供应商失败后按链路顺序尝试备用供应商，直到成功或全部耗尽。注意 fallback executor 每步只调一次，底层重试由各供应商的调用实现决定。

整个过程是**无状态 per-request fallback**——不维护熔断器，每个新请求从主供应商开始。好处是恢复自然，不需要探测；代价是故障期间每个请求多等几秒，但对 AI 生成任务感知不强。未来如果故障频率上升，引入熔断器是下一步优化方向。

**[翻页]**

## P18 — 结果回传与总结（~1min）

最后，结果如何回到本地 Agent？Sidecar 执行完后 HTTP Report 给 scheduler，scheduler 写 MongoDB 并推 Kafka。本地 Agent 感知不到这个过程——它通过轮询 gateway 查 MongoDB 状态，拿到 success 和结果。

轮询间隔带来几秒延迟，但相对于任务本身几秒到几分钟的执行时间，可以忽略。

---

回顾一下整条链路：用户在 Electron 画布上操作或和 Agent 对话 → 本地 Python 服务编排 Agent 逻辑、推 SSE 事件 → 生成任务提交到云端 Scheduler → 经过优先级调度、无锁抢占分配给 Worker → Worker 调供应商执行（有三层容错保障）→ 结果回写 MongoDB → 本地 Agent 轮询拿到结果 → 推给前端展示。

这就是 DreamMaker 平台的完整技术架构。谢谢大家，有问题可以交流。
